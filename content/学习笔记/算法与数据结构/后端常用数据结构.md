> 后端面试问数据结构，多数不是要你手搓红黑树，而是问「这个场景为什么选它、代价是什么」。本文按需求反查结构，重点写清适用范围、复杂度与工程上的坑。

## 一、按问题反查结构

| 需求                   | 首选结构             | 典型场景             |
| ---------------------- | -------------------- | -------------------- |
| 按 key 精确查找        | 哈希表               | 缓存、索引、会话     |
| 范围查询、有序遍历     | B+ 树 / 跳表         | 数据库索引、排行榜   |
| 高吞吐写入、顺序追加   | LSM Tree             | 日志型存储、时序数据 |
| 判断「一定不存在」     | 布隆过滤器           | 缓存穿透、去重       |
| 近似去重计数           | HyperLogLog、布隆    | UV、爬虫 URL 去重    |
| 有限容量下的淘汰       | LRU / LFU / TinyLFU  | 本地缓存、页面置换   |
| 节点变化时分摊最少数据 | 一致性哈希           | 分布式缓存分片       |
| 大量定时任务           | 时间轮 / 小顶堆      | 超时关闭、延迟队列   |
| 稠密整数集合与交并运算 | 位图 / RoaringBitmap | 标签人群、签到统计   |
| 前缀匹配               | Trie / FST           | 路由匹配、自动补全   |

## 二、哈希表

哈希表的核心是「哈希函数 + 冲突处理 + 扩容策略」。常见冲突处理有链地址法和开放寻址法：前者对高负载更 tolerant，后者缓存局部性更好但删除麻烦（需墓碑标记）。

工程上最容易出问题的三个点：

1. **负载因子**：超过阈值（常见 0.75）后冲突激增，查询从 `O(1)` 退化。扩容需要迁移全部元素，一次性迁移会造成卡顿，Redis 采用渐进式 rehash，把迁移摊到后续每次读写。
2. **哈希函数质量**：键分布不均会让某些桶变成链表。对外暴露的接口如果允许客户端构造 key，要警惕哈希碰撞攻击。
3. **并发**：并发读写 Go 的 `map` 会直接 panic；用 `sync.RWMutex` 或 `sync.Map`（读多写少、key 集合稳定时更合适）。

## 三、有序结构：B+ 树、LSM 与跳表

| 维度     | B+ 树              | LSM Tree                   | 跳表         |
| -------- | ------------------ | -------------------------- | ------------ |
| 写入     | 原地更新，随机 I/O | 顺序追加，写放大靠合并     | 内存随机插入 |
| 读取     | 稳定 `O(log N)`    | 可能查多层，靠布隆+缓存    | `O(log N)`   |
| 范围扫描 | 叶子链表，很高效   | 需归并多层                 | 天然有序链表 |
| 空间     | 较紧凑             | 有写放大与空间放大         | 指针开销较大 |
| 代表     | InnoDB             | RocksDB、HBase、ClickHouse | Redis ZSet   |

B+ 树适合读多写少、要求稳定延迟的 OLTP；LSM 用「写放大 + 读放大」换极高写入吞吐，后台 Compaction 会带来延迟毛刺；跳表实现比平衡树简单、范围遍历方便，是内存有序集合的常见选择。

一个常被忽略的点：B+ 树的非叶子节点不存数据行，单节点能放更多键，因而树高通常只有 3～4 层，这正是一次点查询只需少量磁盘 I/O 的原因。

## 四、概率型结构

| 结构             | 回答的问题           | 误差方向                       | 空间               |
| ---------------- | -------------------- | ------------------------------ | ------------------ |
| 布隆过滤器       | 元素是否可能存在过   | 可能误判存在，绝不会误判不存在 | 与元素数量线性相关 |
| Counting Bloom   | 支持删除的布隆       | 同上，计数器可能溢出           | 每位变计数器       |
| HyperLogLog      | 基数大约是多少       | 约 1%～2% 相对误差             | 极小，KB 级        |
| Count-Min Sketch | 元素出现频次大约多少 | 只会高估                       | 二维计数器         |

布隆过滤器的两个参数决定误判率：位数组长度 `m`、哈希函数个数 `k`，元素数 `n`。经验上 `m/n ≈ -ln(p) / (ln2)^2`，`k ≈ (m/n) * ln2`。例如期望 1% 误判，约需 9.6 bit/元素、7 个哈希函数。

工程陷阱：

- 标准布隆**不能删除**（一个 bit 可能被多个元素共享），需要 Counting Bloom 或定期重建。
- 元素数量远超预估容量后误判率会急剧上升，必须预留容量或做滚动重建。
- 它只能挡「一定不存在的查询」，不能替代真实存储；缓存穿透场景要配合空值缓存与参数校验。

## 五、缓存淘汰：LRU 与它的改进

经典 LRU 用「哈希表 + 双向链表」实现 `O(1)` 的 get/put：哈希表定位节点，链表维护访问顺序，命中后移到表头，淘汰表尾。

```go
type entry struct {
    key, value int
    prev, next *entry
}

type LRU struct {
    cap     int
    items   map[int]*entry
    head    *entry // 哨兵，head.next 为最近使用
    tail    *entry // 哨兵，tail.prev 为最久未用
}
```

实际问题：

- **偶发批量扫描污染缓存**：一次全表扫描会把热点全部挤出，可用 LRU-K（访问 K 次才进入候选）或 Two Queue 缓解。
- **无法区分频率**：LFU 保留高频项，但对历史热点「记性太好」，需要衰减机制。
- **并发开销**：每次 get 都要移动链表节点并加锁，高并发下争用明显；Redis 用近似 LRU（随机采样）降低精度换吞吐。
- 生产缓存库（如 TinyLFU / W-TinyLFU）通常结合「准入过滤 + 频率 sketch + LRU 淘汰」，命中率明显优于纯 LRU。

## 六、分片与路由：一致性哈希

普通取模 `hash(key) % N` 在节点数变化时几乎要迁移全部数据。一致性哈希把节点和 key 映射到同一个哈希环上，key 顺时针找到第一个节点；增删节点只影响环上相邻区间。

```text
         nodeA
       /       \
  key3           key1
      \         /
       nodeC —— nodeB
```

关键改进是**虚拟节点**：每个物理节点对应环上多个虚拟位置，让数据分布更均匀，也让扩容时新节点能从多个旧节点各分担一部分，而不是只接手一个区间的全部压力。

需要注意：一致性哈希解决的是「迁移量小」，不保证负载均衡，也不负责故障转移；热点 key 仍需单独拆分。Kafka/Redis Cluster 采用固定哈希槽（slot）方案，把「槽 → 节点」的映射作为元数据管理，扩容时按槽迁移，控制力更强。

## 七、时间相关结构

| 结构     | 插入        | 取到期任务    | 适用                   |
| -------- | ----------- | ------------- | ---------------------- |
| 小顶堆   | `O(log N)`  | `O(1)` 看堆顶 | 任务量中等、精度要求高 |
| 时间轮   | 近似 `O(1)` | `O(1)`        | 海量连接超时、定时消息 |
| 有序链表 | `O(N)`      | `O(1)`        | 任务很少               |

时间轮像钟表：把时间切成若干槽，每槽挂一个任务链表，指针按 tick 前进一步就处理当前槽。多级时间轮（类似时分秒针）用少量槽表示很长的时间跨度。代价是精度受 tick 限制，任务取消需要能定位到链表节点。

实践里连接超时管理常用时间轮，业务延迟队列更常用「数据库/Redis ZSet 扫描 + 分桶」，因为需要持久化和可查询，纯内存结构会丢任务。

## 八、位图与前缀树

**位图**用一个 bit 表示一个整数是否存在，40 亿用户只需要约 512MB，且交集/并集是位运算，非常适合标签人群圈选。缺点是稀疏数据浪费空间，RoaringBitmap 通过分段容器（稠密段用位图、稀疏段用数组）解决。

**Trie** 按字符共享前缀，适合路由匹配、敏感词过滤与自动补全；内存开销大，可用双数组 Trie 或 FST 压缩。注意前缀匹配和正则匹配不是一回事，网关路由要另外处理通配符优先级。

## 九、复杂度之外的工程陷阱

| 陷阱                     | 后果                         | 应对                           |
| ------------------------ | ---------------------------- | ------------------------------ |
| 只看理论复杂度           | 忽略常数与缓存局部性         | 用真实数据做基准测试           |
| 忽略内存放大             | 指针、对齐、对象头吃掉内存   | 估算实际占用，必要时用紧凑编码 |
| 忽略并发开销             | 全局锁成为瓶颈               | 分片、读写锁、无锁读           |
| 忽略持久化与恢复         | 重启后结构全丢               | 快照 + 日志，或交给外部存储    |
| 忽略退化输入             | 哈希碰撞、有序插入使树倾斜   | 随机化、限长、监控分布         |
| 结构选型与访问模式不匹配 | 写多场景用 B+ 树导致随机 I/O | 先明确读写比、范围查询需求     |

## 十、实践清单

1. 选结构前先写清：读写比例、是否需要范围查询、数据量级、是否要持久化、能容忍多大误差。
2. 概率型结构必须记录预期容量与当前容量，并设误判率监控。
3. 分片方案要考虑扩容迁移量、热点 key 和元数据管理方式，而不只是哈希函数。
4. 定时任务结构明确精度与持久化需求，别把不可恢复的超时信息只放内存。
5. 用基准测试验证假设，尤其是「这个结构应该更快」的直觉。

## 十一、面试速答

**问：布隆过滤器为什么会有误判，能不能删除？** 多个元素可能共享同一组 bit，未插入的元素也可能所有 bit 都为 1，所以会误判存在；标准版本不能删除，因为清掉某 bit 会影响其他元素，需要计数版或重建。

**问：B+ 树为什么比 B 树适合数据库索引？** 非叶子节点不存数据，扇出更大、树更矮；所有数据落在叶子层且叶子间有链表，范围扫描不需要回溯上层。

**问：一致性哈希解决什么问题？** 把节点增减时的数据迁移量从接近全量降到只影响相邻区间；配合虚拟节点改善分布均匀性，但不负责负载均衡和故障转移。
