## 一、系统设计答题框架

先澄清功能、规模（QPS、读写比、数据量、SLO）、一致性与成本约束；再给出核心数据模型、接口与主链路；最后说明缓存、异步化、存储拆分、容灾、可观测性与演进路径。不要一开始就堆 Redis、Kafka 和分库分表。

```text
入口（鉴权/限流）→ 应用（幂等/编排）→ 缓存 → DB
                         │
                         └→ MQ → 异步消费者/通知/索引
```

## 二、面试题

## 1. 如何设计秒杀系统？

**回答：** 用网关限流和验证码/资格校验挡住无效流量；Redis/Lua 原子预扣库存；消息队列异步创建订单；数据库用条件更新和唯一约束兜底，失败后补偿库存。

**补充：** Redis 扣减不等于最终下单成功。必须处理重复请求、订单写入失败、支付超时和回补；热点商品要按单 SKU 控制并发，不能把所有流量直接打到 MySQL。

## 2. 如何保证接口幂等？

**回答：** 使用业务幂等键，在数据库加唯一索引或通过状态机保证同一请求只产生一次业务效果。

**补充：** Redis 锁只能降低并发重复，最终约束应落在权威存储。支付回调、MQ 消费、网络重试都必须假设至少一次到达。

## 3. 如何设计短链服务？

**回答：** 生成全局唯一 ID，再做 Base62 编码得到短码；短码到长 URL 存在数据库并缓存，跳转请求先查缓存。

**补充：** 需要处理短码碰撞、恶意 URL、热点短链、过期与统计。统计写入宜异步，跳转路径不能同步写分析库。

## 4. 如何估算容量？

**回答：** 由峰值 QPS、平均/峰值请求大小、读写比、保留周期、单机压测能力和冗余系数推算实例与存储。

**补充：** 例如峰值 1 万 QPS、单请求 2KB，则入口带宽约 20MB/s；真实规划还要算协议开销、缓存未命中、复制、突发和至少 N+1 冗余。

## 三、常用原则

1. 缓存解决读压力，不自动提供一致性。
2. 消息队列削峰解耦，不自动提供业务幂等。
3. 分库分表前先解决索引、SQL、归档与读写分离。
4. 限流、降级、超时与背压必须在依赖故障时仍有效。
