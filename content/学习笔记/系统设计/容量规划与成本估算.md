> 「这个系统要几台机器」是架构讨论里最常被随口回答、也最容易翻车的问题。靠谱的答案不是拍脑袋给个数字，而是一条能复算、能被压测校准的换算链：业务指标 → 请求速率 → 峰值并发 → 单机容量 → 实例数 → 账单。这篇把这条链和它背后的假设都摊开。

## 一、先把换算链写下来

```text
DAU / 订单量 / 消息量
   → 平均 QPS（除以一天的秒数，注意业务高峰集中在几小时）
   → 峰值 QPS（乘峰值系数，通常 3~10，活动场景更高）
   → 单请求资源消耗（CPU 毫秒、内存、I/O 次数、出带宽）
   → 单机可承载 QPS（压测得出，再乘目标水位）
   → 实例数（含冗余 N+1 或 N+2）
   → 存储量 / 带宽 / 连接数 / 分片数
   → 月度成本
```

最容易出错的是第一步：「1000 万 DAU」不等于「1000 万 / 86400 ≈ 116 QPS」。用户活跃集中在白天几小时，而且一个页面会派生出十几个 API 请求。

```text
有效秒数   ≈ 8h × 3600 = 28800（而非 86400）
每用户请求 ≈ 20 次 API
平均 QPS   = 1000万 × 20 / 28800 ≈ 6944
峰值 QPS   = 6944 × 3 ≈ 20800
```

这个「派生请求数」和「有效时间窗口」必须和产品/运营确认，或直接从前一年监控数据取，不能自己编。

## 二、Little's Law：把 QPS 换算成并发

\[
L = \lambda \times W
\]

其中 \(L\) 是系统内平均在途请求数，\(\lambda\) 是到达速率，\(W\) 是平均处理时长。

```text
λ = 1000 QPS，平均延迟 W = 50ms = 0.05s
L = 1000 × 0.05 = 50 个并发请求
```

这个数字直接决定连接池、协程数和队列长度：如果 DB 连接池只有 20，而某次慢查询把 \(W\) 从 50ms 拉到 500ms，\(L\) 就变成 500，池子瞬间成为瓶颈并产生排队，延迟进一步上涨——**这就是排队论视角下的雪崩起点**。

推论有三条，比公式本身更有用：

1. **降延迟等于扩容量**，优化慢 SQL 常常比加机器有效。
2. **队列长度必须有上界**，无界队列只是把失败延后，并把延迟变得不可控。
3. **连接池不是越大越好**，过大把压力转嫁给 DB，用 `L` 加上一点余量来设。

## 三、一份可复算的估算示例

假设一个内容站点：日活 100 万，人均 15 次 feed 请求，每次返回 20 条，单条平均 1KB（JSON），数据保留 2 年。

**流量**

```text
日均 feed 请求 = 100万 × 15 = 1500 万
有效窗口 10h = 36000s → 平均 QPS ≈ 417
峰值系数 4 → 峰值 QPS ≈ 1668
单机压测容量（P99 < 100ms）= 400 QPS，目标水位 50%
需实例数 = 1668 / (400 × 0.5) ≈ 8.3 → 9 台，按 N+2 → 11 台
```

**带宽**

```text
单响应 ≈ 20 × 1KB = 20KB
峰值出带宽 = 1668 × 20KB ≈ 33 MB/s ≈ 267 Mbps
开启 gzip/br 后按 0.3 系数 → ≈ 80 Mbps，再加 30% 余量
```

**存储**

```text
每天新内容 5 万条 × 平均 2KB          ≈ 100 MB/天
索引系数 1.5、副本 3、WAL/备份系数 1.3
日增 ≈ 100MB × 1.5 × 3 × 1.3 ≈ 585 MB
两年 ≈ 585MB × 730 ≈ 427 GB
```

注意这里最容易漏的是**索引、副本、binlog/WAL、备份保留、临时空间**，五项叠起来常常让「看着 100G」变成实际 500G。

**内存**

```text
热数据（最近 7 天）= 100MB × 7 × 1.5 ≈ 1GB 原始数据
但缓存对象是反序列化后的结构体，膨胀系数 2~5
Redis 规划 ≈ 4GB，加 30% 碎片余量 ≈ 6GB
```

**连接数**

```text
单实例并发 ≈ 400 × 0.05s = 20
连接池每实例 25 → 11 实例共 275 个 DB 连接
若 DB 上限 300，则几乎没有余量 → 需要 PgBouncer / ProxySQL 做汇聚
```

把这几行写进设计文档，别人就能逐项质疑假设，而不是争论「到底该几台」。

## 四、峰值、水位与冗余

| 概念         | 常见取值              | 说明                                  |
| ------------ | --------------------- | ------------------------------------- |
| 峰值系数     | 3~10                  | 从历史 P99 流量曲线取，大促单独建模   |
| 目标水位     | CPU 30~50%，内存 <70% | 留出 GC、突发、单节点故障接管空间     |
| 冗余         | N+1 / N+2             | 同城多可用区通常按 N+1 或 N+2         |
| 扩容提前量   | 水位 50% 触发         | 资源交付/扩容有分钟到小时级延迟       |
| P99 而非均值 | 必须                  | 均值达标但 P99 超时的容量规划没有意义 |

一个常被忽略的问题：**有状态服务的扩容不是即时的**。加一个数据库分片要迁数据，加 Kafka 分区要 rebalance，Redis 扩分片要 slot 迁移。容量规划里必须为这些操作预留时间和临时空间，否则「弹性扩容」只是 PPT 上的词。

## 五、压测校准：估算只能当起点

压测分四类，目的不同：

| 类型       | 做法                         | 得到什么                              |
| ---------- | ---------------------------- | ------------------------------------- |
| 基准测试   | 单接口固定并发               | 单机理论容量、资源瓶颈定位            |
| 容量测试   | 逐步加压到 SLO 破线          | 满足 P99 目标的最大 QPS               |
| 浸泡测试   | 正常负载跑 12~72h            | 内存泄漏、连接泄漏、GC 退化、日志磁盘 |
| 破坏性测试 | 杀节点、注入延迟、缓存全失效 | 真实冗余度与降级是否生效              |

压测结果失真的常见原因：压测机自身先到瓶颈、数据量和线上差几个数量级（缓存命中率虚高）、只用单一热点 key、没开 TLS/日志/链路追踪、连接池配置与线上不一致、没有预热 JVM/JIT 和缓存。

**结论应以 SLO 为准**：不是「能扛 3000 QPS」，而是「在 P99 ≤ 100ms、错误率 < 0.01% 的前提下能扛 1800 QPS」。

## 六、成本模型：把技术决策翻译成钱

```text
月成本 = 计算 + 存储 + 出带宽 + 中间件/license + 可观测性 + 人力
单位成本 = 月成本 / 月请求数（或每千次请求、每笔订单）
```

| 成本项   | 常见隐藏项                                        |
| -------- | ------------------------------------------------- |
| 计算     | 预留实例折扣、Spot 中断成本、空闲副本、跨 AZ 流量 |
| 存储     | IOPS 计费、快照与备份、跨区域复制、日志留存       |
| 带宽     | 公网出方向、CDN 回源、跨 AZ 数据传输              |
| 中间件   | 托管数据库按 IO 计费、消息队列按分区/Topic 计费   |
| 可观测性 | 日志与 trace 的采集量和留存期，常常比想象中贵     |

用来做取舍的例子：

- **加缓存值不值**：Redis 月成本 ¥2000，DB 读 QPS 从 5000 降到 500，可少 4 个只读副本（¥6000/月），且 P99 从 80ms 降到 12ms → 明显划算。
- **日志全量采 vs 采样**：全量每天 2TB，按 30 天留存 60TB；错误与慢请求全采 + 正常请求 1% 采样，量降两个数量级，排障能力几乎不变。
- **自建 vs 托管**：托管多付的溢价要和「DBA 人力 + 故障恢复时间 + 半夜被叫」一起比，小团队几乎总是托管划算。

**成本也要有 SLO**：定每千次请求成本的目标值，按月看趋势。成本突然上涨往往是架构腐化（N+1 查询、缓存失效、日志误开 debug）的第一信号，比报警更早。

## 七、容量告警与兜底

| 信号                         | 动作                                           |
| ---------------------------- | ---------------------------------------------- |
| CPU / 水位连续 10 分钟 > 60% | 触发扩容评估（不是立即扩容）                   |
| 连接池排队时长上升           | 先查慢查询，再考虑扩池                         |
| 磁盘增长斜率突变             | 查日志级别、binlog 保留、是否有失控的重试      |
| P99 抬升但 QPS 平稳          | 通常是下游变慢，用 Little's Law 看在途请求堆积 |
| 成本环比 +30%                | 逐项归因到带宽/存储/计算                       |

容量兜底始终是**限流、降级、熔断**。任何「按峰值 × 2 买机器」的方案都不如「超限时优雅地少做一点」经济，因为峰值是长尾，而机器是全天计费。参考「限流、熔断与降级」那篇的组合策略。

## 八、模板：一张表填完就能评审

| 项                            | 值  | 依据                                |
| ----------------------------- | --- | ----------------------------------- |
| 业务量                        |     | DAU / 订单量 / 消息量               |
| 派生请求数                    |     | 前端埋点或埋点估算                  |
| 有效时间窗口                  |     | 历史流量曲线                        |
| 平均 / 峰值 QPS               |     | 上式 × 峰值系数                     |
| SLO                           |     | P99 延迟、错误率、可用性            |
| 单机容量                      |     | 容量压测结果                        |
| 目标水位 / 冗余               |     | 30~50% / N+1 或 N+2                 |
| 实例数                        |     | 峰值 QPS ÷ (单机容量 × 水位) + 冗余 |
| 存储（含索引/副本/日志/备份） |     | 行宽 × 行数 × 系数 × 保留期         |
| 峰值带宽                      |     | 响应大小 × 峰值 QPS × 压缩系数      |
| 连接数 / 分片数               |     | Little's Law + 单实例上限           |
| 月成本 / 单位成本             |     | 各项单价 × 用量                     |
| 校准方式                      |     | 压测类型 + 线上复核时间             |

## 九、面试速答

**Q：怎么估算一个短链服务需要多少存储？**
先问量：每天新增多少条、单条多宽、保留多久、几个副本、要不要存点击日志。给公式而不是给数字：`日增 = 条数 × (原始行宽 + 索引宽) × 副本 × 日志系数`，再乘保留天数，并单独算点击日志（通常比短链本身大一两个数量级）。

**Q：1000 QPS、50ms 延迟需要多少连接池？**
由 Little's Law 得在途请求 50 个，连接池设 50 加余量即可；不是「越大越好」。同时要说明如果延迟涨到 500ms，池子会成为排队点，所以限流和超时比扩池更重要。

**Q：压测能扛 3000 QPS，线上为什么 1500 就报警？**
逐项查差异：数据规模与热点分布、缓存命中率、依赖下游的真实延迟、TLS/日志/链路追踪开销、连接池与 GC 配置、流量峰值系数是否低估、压测机是否自身瓶颈。

## 十、一句话收尾

容量规划的价值不在于算得多准，而在于**把每个假设写成可被质疑、可被压测推翻的数字**；这样当流量翻十倍时，你知道该改哪一格，而不是重新拍一次脑袋。
