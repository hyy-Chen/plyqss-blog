> 这三个词经常被当成同义词，其实解决的是不同方向的问题：限流保护自己不被打垮，熔断避免继续调用已经坏掉的下游，降级主动放弃部分功能以保住核心链路。本文按「算法 → 工程实现 → 组合策略」展开。

## 一、先分清职责

| 机制 | 触发条件            | 作用对象 | 典型结果                      |
| ---- | ------------------- | -------- | ----------------------------- |
| 限流 | 请求速率超过阈值    | 入站流量 | 拒绝、排队或降低优先级        |
| 熔断 | 下游错误率/延迟升高 | 出站调用 | 快速失败，不再发起真实调用    |
| 降级 | 系统整体压力或故障  | 业务功能 | 返回兜底数据、关闭非核心功能  |
| 隔离 | 任何时候            | 资源池   | 防止一个依赖耗尽全部线程/连接 |

一句话记忆：限流是「别让太多请求进来」，熔断是「别再往坏掉的地方发请求」，降级是「主动少做一点」。

## 二、限流算法

| 算法     | 核心思想                   | 优点               | 问题                       |
| -------- | -------------------------- | ------------------ | -------------------------- |
| 固定窗口 | 每 N 秒计数，超限拒绝      | 简单、Redis 易实现 | 窗口边界可能出现两倍流量   |
| 滑动窗口 | 统计最近 N 秒内的请求      | 削平边界突刺       | 需要保存时间戳，内存更高   |
| 漏桶     | 请求入桶，恒定速率出桶     | 输出绝对平滑       | 突发流量只能排队，不能借额 |
| 令牌桶   | 按速率生成令牌，取到才放行 | 允许一定突发       | 需要维护令牌与时间         |

生产中最常见的是令牌桶：既能限制长期平均速率，又能容忍短时突发。一个最小的 Go 实现思路：

```go
type TokenBucket struct {
    mu       sync.Mutex
    capacity float64
    rate     float64 // tokens per second
    tokens   float64
    last     time.Time
}

func (b *TokenBucket) Allow(now time.Time) bool {
    b.mu.Lock()
    defer b.mu.Unlock()

    elapsed := now.Sub(b.last).Seconds()
    b.tokens = math.Min(b.capacity, b.tokens+elapsed*b.rate)
    b.last = now
    if b.tokens < 1 {
        return false
    }
    b.tokens--
    return true
}
```

注意用单调时钟（`time.Now()` 自带单调部分）计算时间差，不要依赖可被校正的墙上时钟。

## 三、分布式限流

单机限流只能保护单个实例，全局配额需要共享存储。常见做法是用 Redis + Lua 把「读取计数 → 判断 → 写回 → 设置过期」合成一次原子操作，避免并发下的竞态。

```lua
-- KEYS[1]: 限流键  ARGV[1]: 窗口大小(秒)  ARGV[2]: 阈值
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return current <= tonumber(ARGV[2])
```

工程上的取舍：

- **精度与成本**：每次请求访问 Redis 会增加一次网络往返；高 QPS 场景常用「本地预扣 + 全局批量申请配额」降低调用量。
- **热点键**：按用户/租户限流时，单个大客户可能把某个 Redis 分片打热，需要拆分键或本地聚合。
- **降级策略**：Redis 不可用时，应退回单机限流而不是直接放行，否则限流形同虚设。
- **多维度**：同时按全局、租户、接口、用户限流，取最严格的生效；优先级高的核心接口使用独立配额。

## 四、拒绝也要设计

| 项目         | 建议                                                     |
| ------------ | -------------------------------------------------------- |
| 状态码       | `429 Too Many Requests`；网关排队超时可用 `503`          |
| 响应头       | `Retry-After` 告知重试时间，避免客户端立刻重刷           |
| 响应体       | 给出可读错误码与追踪 ID，便于定位                        |
| 排队 vs 拒绝 | 短时突发可排队，长时过载必须快速拒绝，排队要有上限和超时 |
| 优先级       | 登录、支付等核心链路与报表、导出等后台任务分池，互不挤占 |

客户端侧必须配合：收到 429 后用指数退避加随机抖动重试，并遵守 `Retry-After`；否则服务端限流只会把流量推迟一小会儿再一起打回来。

## 五、熔断器状态机

```text
        ┌──────────── 错误率超阈值 ────────────┐
        │                                      ▼
   Closed（正常放行）                    Open（快速失败）
        ▲                                      │
        │ 探测成功                              │ 冷却时间到
        │                                      ▼
        └──────── HalfOpen（放行少量探测请求）──┘
```

实现要点：

1. 基于**滑动窗口**统计成功/失败，而不是累计总数；窗口太短会抖动，太长会迟钝。
2. 设置**最小请求数**：窗口内只有 2 个请求且全失败，不应触发熔断。
3. 半开状态只放行少量探测请求，成功才恢复，失败则重新进入 Open 并延长冷却。
4. 慢调用也要计入：只有异常才算失败会漏掉「超时但没报错」的下游。
5. 熔断是**按依赖维度**做的：订单服务调库存熔断，不应影响它调用户服务。

## 六、隔离与降级

**隔离（舱壁）**：为每个下游分配独立的连接池、信号量或 goroutine 上限。没有隔离时，一个慢依赖会占满所有连接，导致无关接口一起挂掉。

**降级**：提前定义「关掉什么、保留什么」。例如商品详情页在推荐服务异常时不展示推荐位，在库存服务异常时展示缓存值并标注可能延迟，但下单入口仍然可用。

| 降级手段 | 例子                         | 风险                     |
| -------- | ---------------------------- | ------------------------ |
| 返回兜底 | 静态默认值、上次成功缓存     | 数据陈旧，需标注         |
| 关闭功能 | 隐藏非核心模块、关闭导出     | 需要开关可秒级生效       |
| 异步化   | 写操作转消息队列，先返回受理 | 需处理最终一致与查询状态 |
| 削峰     | 排队、预约、分时段放行       | 用户体验下降             |

降级开关要满足三个条件：配置集中可动态下发、有明确的负责人和回滚方式、生效情况可在监控里看到。写在代码里的 `if` 分支没有开关，等于没有降级能力。

## 七、超时、重试与重试预算

超时必须沿调用链**递减**：入口 3s，下游调用不能也设 3s，否则上游已超时返回，下游还在占用资源。配合 `context` 把取消信号一路传下去。

```text
入口超时 3s
  ├─ 服务 A 本地处理预算 0.5s
  ├─ 调用 B 超时 1.2s（含重试）
  └─ 调用 C 超时 1.0s
```

重试的三条硬约束：

- **只对幂等操作重试**，写操作要有幂等键；读操作天然可重试但仍需限流。
- **退避 + 抖动**：`base * 2^n + random(0, jitter)`，避免故障恢复瞬间所有客户端同时重发。
- **重试预算**：例如重试请求不得超过总请求的 10%，或每层只允许一次重试。多层服务各自重试 3 次，最坏会放大到 `3^N` 次调用。

熔断与重试要配合：熔断打开后直接失败，不再消耗重试次数；否则重试会一直喂给已经过载的下游。

## 八、容量评估与验证

限流阈值不能拍脑袋定，应来自压测得到的拐点：逐步加压，记录 QPS、P99、错误率与资源饱和度，找到「延迟开始急剧上升」的位置，再留出安全余量（常见 30%～50%）设为阈值。

上线前后需要验证：

1. 单实例与集群阈值分别验证，确认配额按实例数正确分配。
2. 演练下游超时、Redis 不可用、依赖返回 5xx，观察熔断与降级是否按预期触发。
3. 监控里能看到被拒绝数、熔断状态、降级开关状态，而不是只知道「接口变慢了」。
4. 限流规则变更可灰度、可回滚，避免一条规则把全站流量挡在门外。

## 九、实践清单

1. 入口、租户、接口三层限流，各自有独立配额和监控。
2. 每个外部依赖设置独立连接池 + 超时 + 熔断，禁止共用无限池。
3. 所有重试带退避抖动和幂等前提，并设置全局重试预算。
4. 降级开关集中管理，定期演练，避免「配了但从没生效过」。
5. 429/503 与熔断事件都计入指标和告警，作为容量不足的信号。
6. 压测确定阈值，大促前按预估流量复核配置。

## 十、面试速答

**问：令牌桶和漏桶的区别？** 漏桶以恒定速率放行、超出部分排队或丢弃，强调平滑输出；令牌桶按速率补充令牌、允许一次性消耗积攒的令牌，能容忍突发。

**问：为什么重试会放大故障？** 下游变慢时上游超时重试，请求总量成倍增加，进一步加重下游负载形成正反馈；需要退避抖动、重试预算和熔断共同约束。

**问：熔断和降级有什么区别？** 熔断是被动保护出站调用，检测到依赖异常后快速失败；降级是主动收缩业务功能，用兜底结果保住核心链路。
