> 「30 分钟后关单」「每天凌晨 2 点对账」「每 5 分钟同步一次配置」，看起来都是「到点执行」，但可靠性要求差得很远。单机 `cron` 和一个进程内 timer 在开发机上从不出问题，上线后却会在重启、多实例、堆积、时区上连续翻车。这篇按「需求分类 → 方案对比 → 可靠性四问 → 落地细节」展开。

## 一、先分清三类任务

| 类型     | 例子                               | 关键要求                       |
| -------- | ---------------------------------- | ------------------------------ |
| 延迟任务 | 30 分钟未支付关单、15 分钟后发提醒 | 时间点精确、量大、允许少量延迟 |
| 周期任务 | 每日对账、每小时聚合               | 不漏跑、不重跑、错过后能补偿   |
| 定时触发 | 定点秒杀开始、定时发布             | 触发时刻集中，瞬时峰值高       |

最容易混淆的是「延迟」和「轮询」：延迟队列是**到点才把任务交给消费者**，轮询是**反复扫描看有没有到点的**。前者精度高、空转少，后者实现简单但扫表压力随数据量线性增长。

## 二、老一辈做法与不合理之处

| 老做法                                  | 当时的合理性               | 上线后的问题                                             |
| --------------------------------------- | -------------------------- | -------------------------------------------------------- |
| 机器 `crontab`                          | 一条配置就能跑             | 单机不 HA；机器下线就漏跑；无执行记录与告警              |
| 进程内 `time.AfterFunc` / `Timer`       | 零依赖、精度好             | 重启全丢；多实例各自触发导致重复执行                     |
| 循环 `SELECT ... WHERE due_at <= now()` | 只用数据库，不引入中间件   | 数据量大后全表扫；多实例抢同一行；无锁会重复执行         |
| Redis 过期回调                          | 以为 key 过期能触发业务    | 过期事件不保证及时、不保证送达，重启即丢，不能当任务队列 |
| 客户端本地定时                          | 前端 setTimeout 到期发请求 | 用户关页面就不执行，且请求可被伪造                       |

**根本问题是把「调度状态」放在了不可靠的地方**：内存、单机、或没有持久化的事件通知里。分布式调度要做的第一件事，是把「谁该在什么时候执行」变成持久化、可领取、可重试的数据。

## 三、五种实现方案对比

| 方案             | 原理                                         | 精度        | 吞吐 | 主要风险                                    |
| ---------------- | -------------------------------------------- | ----------- | ---- | ------------------------------------------- |
| DB 扫表 + 状态机 | 轮询 `due_at`，领取后置为处理中              | 秒级        | 中   | 表大后扫描压力、热点行竞争                  |
| Redis ZSET       | score 为到期时间戳，`ZRANGEBYSCORE` 取到期项 | 秒级        | 高   | 取任务与删除需 Lua 原子化；持久化与故障切换 |
| MQ 延迟消息      | Broker 内部延迟队列按等级投递                | 秒~分钟     | 很高 | 等级固定、长延迟支持有限、堆积影响 lag      |
| 时间轮           | 环形槽 + tick 推进                           | 取决于 tick | 极高 | 内存态需持久化兜底，长跨度要分层            |
| 专用调度器       | XXL-Job / Quartz / K8s CronJob               | 秒级        | 中   | 调度中心自身要 HA，执行器要注册与心跳       |

没有银弹，常见组合是：**短延迟高吞吐用 MQ 或 ZSET，周期任务用调度中心，DB 表作为最终一致性的兜底与对账源**。

## 四、时间轮为什么快

分层时间轮的思想类似钟表：秒针轮 60 槽、分针轮 60 槽、时针轮 12 槽，任务按到期距离放进对应层，越远的层粒度越粗，临近时再降级到更细的轮。

```text
单层轮：slots[0..N-1]，每 tick 前进一格
添加任务 O(1)：slot = (current + delay/tick) % N
到期触发 O(该槽任务数)
长延迟任务 → 记录剩余圈数 remainingRounds，每绕一圈减 1
```

对比 `Timer` 用最小堆：每次插入 \(O(\log n)\)，海量短任务下堆操作成为热点；时间轮插入是 \(O(1)\)。Kafka 的分层时间轮、Go runtime 的 timer 堆（新版按 CPU 分片）都是同一类权衡。

但时间轮是**内存结构**：进程重启后需要重新从持久化存储加载未完成任务，所以它通常是「加速层」而不是「真相源」。

## 五、可靠性四问

```text
不丢：任务持久化了吗？投递失败会重试吗？执行成功才确认吗？
不重：领取是原子的吗？执行是幂等的吗？重复投递会怎样？
不晚：堆积能监控吗？扩容消费者能追上吗？长延迟会不会拖垮短任务？
不错：时区与夏令时怎么处理？错过执行（misfire）怎么办？时钟回拨呢？
```

### 不丢：至少一次 + 消费侧确认

任何投递都按**至少一次**设计：任务只有在业务执行成功后才标 `done`；执行失败或超时则回到可领取状态并增加重试次数，超过上限进死信表并告警。「取出即删除」是最常见的丢任务写法。

### 不重：领取必须原子

```sql
-- PostgreSQL：SKIP LOCKED 让多个 worker 各领各的，互不阻塞
UPDATE delayed_task
SET status = 'claimed', worker = ?, lease_until = now() + interval '30 seconds', retry = retry + 1
WHERE id IN (
  SELECT id FROM delayed_task
  WHERE status IN ('pending','failed') AND due_at <= now()
  ORDER BY due_at
  LIMIT 100
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

Redis ZSET 版本同理，必须用 Lua 把「查得到期项 + 从 ZSET 移除 + 写入处理中列表」合成一步，否则多个消费者会拿到同一个任务：

```lua
local items = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, 100)
if #items > 0 then
  redis.call('ZREM', KEYS[1], unpack(items))
  for _, v in ipairs(items) do redis.call('LPUSH', KEYS[2], v) end
end
return items
```

注意还缺一个**处理中列表的租约与回收**：worker 领走后崩溃，任务会永远卡在 `claimed`。所以要给每个任务加 `lease_until`，由后台扫描把超时未确认的任务重新置回 `pending`（这正是至少一次的代价，必须靠幂等承接）。

### 不晚：堆积是可观测指标，不是事后发现

| 指标                              | 含义                     |
| --------------------------------- | ------------------------ |
| `due_at - now()` 的最老待执行任务 | 调度延迟（lag）          |
| 待执行任务数 / 消费速率           | 预计追平时间             |
| 死信数量与重试分布                | 是否有系统性失败         |
| 任务执行时长 P99                  | 慢任务是否阻塞 worker 池 |

一个经典事故是**长延迟任务把短任务堵住**：同一个队列里既有 7 天后到期的、也有 10 秒后到期的，若按入队顺序消费就会互相拖累。解法是按延迟等级分队列/分 topic，或让时间轮在到期时才把任务投递到执行队列。

### 不错：时区与 misfire

- **统一用 UTC 存储绝对时间戳**，展示层按用户时区渲染；cron 表达式要显式带时区字段，别依赖服务器本地时区（容器默认 UTC，业务却是东八区，是很常见的 8 小时偏移）。
- 夏令时切换日可能出现「不存在的时间」或「重复的一小时」，跨时区业务要么禁用本地时区的 cron，要么用绝对间隔（每 24 小时）而非「每天 02:00」。
- **misfire 策略要预先定**：调度中心停机 20 分钟，恢复后那 20 分钟的任务是补跑一次、全部补跑、还是直接跳过？对账类通常补跑一次，通知类通常跳过，绝不能默认「全部立即补跑」造成雪崩。
- 时钟回拨要监控；用数据库时间或统一时间源，别让各实例自己决定「现在几点」。

## 六、幂等：最后一道防线

至少一次投递意味着重复必然发生，业务侧必须自带幂等：

```sql
-- 关单：状态机 + 唯一键双保险
UPDATE orders SET status = 'closed', version = version + 1
WHERE id = ? AND status = 'pending' AND version = ?;

-- 提醒：去重表
INSERT INTO notify_dedup(task_id, biz_type) VALUES (?, ?)
ON CONFLICT DO NOTHING;
```

检查「影响行数 == 1」再决定后续动作；发消息、扣库存、调第三方接口都要带 `task_id` 或 `Idempotency-Key`。参见「消息队列：选型与可靠性模式」里对三段链路丢失点的拆解。

## 七、一条可用的落地架构

```text
业务写入（同事务）  →  delayed_task 表（真相源、可对账）
                     ↓
          投递器：按 due_at 分片扫表 / 订阅 binlog
                     ↓ 至少一次
        MQ（按延迟等级分 topic）或 Redis 处理中列表
                     ↓
        Worker 池：领取 → 加租约 → 幂等执行 → 确认/重试
                     ↓
        死信表 + 告警 + 人工重放入口
```

关键设计：

- **Outbox 思路**：任务与业务数据在同一次事务写入，避免「订单建了但关单任务没建」。
- **分片键分散热点**：按 `due_at` 或业务 ID 分片，避免所有 worker 抢同一批行。
- **隔离**：不同业务、不同优先级的任务用独立 worker 池，防止一个慢任务拖垮全站调度。
- **可回放**：死信任务保留原始 payload 与失败原因，支持单条重放而不用重跑整批。

## 八、实践清单

- 任务持久化，执行成功后才确认；领取用 `SKIP LOCKED` 或 Lua 原子化。
- 每个任务有 `lease_until`，超时未确认自动回收；回收必然带来重复，业务侧必须幂等。
- 长短期任务分队列/分等级，避免互相阻塞；lag 与预计追平时间要有告警。
- UTC 存储 + 显式时区，预先定义 misfire 策略，禁止「停机后全量立即补跑」。
- 关单、扣减、通知类逻辑用状态机或唯一键兜底，不依赖「调度只会触发一次」。
- 提供死信查询与单条重放入口；调度中心自身也要 HA 并纳入监控。
- 压测包含「堆积 100 万条后恢复」和「调度中心宕机 30 分钟」两个场景。

## 九、面试速答

**Q：为什么不能用 Redis key 过期回调做延迟任务？**
过期事件不保证及时触发、不保证送达，且 Redis 重启后没有补偿机制；它是缓存清理辅助，不是可靠的任务队列。可靠方案需要持久化任务、原子领取、执行确认与失败重试。

**Q：多个 worker 扫同一张任务表怎么避免重复执行？**
用 `SELECT ... FOR UPDATE SKIP LOCKED` 或先原子 `UPDATE ... SET status='claimed'` 再 `RETURNING`，让领取本身互斥；同时加租约超时回收，并用状态机/唯一键保证重复领取时业务仍幂等。

**Q：调度中心宕机半小时，恢复后怎么处理？**
先定 misfire 策略：对账类补跑一次并带幂等键，通知类通常跳过。全部立即补跑会造成瞬时洪峰，应按原时间窗限速回放；同时用业务对账而非调度记录判断哪些结果缺失。

**Q：延迟消息已经「至少一次」了，为什么还要幂等？**
至少一次意味着重复投递是设计前提，网络超时、worker 崩溃、租约回收都会产生同一任务被执行两次。调度层只能保证「不丢」，正确性必须由业务侧的状态机或去重表保证。

## 十、一句话收尾

把调度做好，靠的不是选一个更快的队列，而是把「不丢、不重、不晚、不错」四件事分别落到持久化、原子领取、lag 监控和业务幂等上——**其中只有最后一件在业务代码里，也最容易被忘掉**。
