> 自增主键和 `sync.Mutex` 在单机里几乎是白送的，一旦拆成多实例、多分片，这两个「隐式保证」就同时失效了。这两件事经常被放在一起讲，不是因为技术方案相似，而是因为它们的失败模式很像：**都以为自己拿到了一个全局唯一且不会冲突的东西，实际上只是在局部有效**。

## 一、ID 生成到底要满足什么

| 需求         | 为什么重要                         | 反例                     |
| ------------ | ---------------------------------- | ------------------------ |
| 全局唯一     | 跨库跨表合并、去重、幂等键的基础   | 各库自增导致主键碰撞     |
| 趋势递增     | B+ 树顺序写，减少页分裂与随机 I/O  | UUID v4 让索引局部性极差 |
| 高可用低延迟 | ID 生成在几乎所有写路径上          | 每次发号都同步查 DB      |
| 不泄露信息   | 连续 ID 可被遍历爬数据、推算业务量 | 对外直接用订单自增主键   |
| 时间可解释   | 排障时能反推大致生成时间           | 纯随机串无法定位问题区间 |
| 无中心瓶颈   | 扩容后发号能力要跟着扩             | 单点 DB 成为全站写瓶颈   |

一个常见的架构错误是**把「内部主键」和「对外暴露的 ID」当成一个东西**。内部用趋势递增的 64 位整数方便索引与分片，对外用单独的不透明 ID（随机高熵串或带校验位的编码），两者在网关层映射。这样既保住写入性能，又不给遍历接口留口子。

## 二、发号方案演进

| 方案       | 做法                         | 优点                       | 问题                               |
| ---------- | ---------------------------- | -------------------------- | ---------------------------------- |
| DB 自增    | 单表 `AUTO_INCREMENT`        | 简单、严格递增             | 单点、无法分库、暴露业务量         |
| UUID v4    | 122 bit 随机                 | 本地生成、无协调           | 无序、索引分裂、128 bit 存储浪费   |
| UUID v7    | 时间前缀 + 随机              | 时间有序、无中心           | 仍有随机尾部，页级局部性一般       |
| DB 号段    | 一次取 `[start, start+step)` | 高吞吐、DB 短暂不可用可撑  | 实例重启浪费一段 ID，ID 不严格连续 |
| Redis INCR | 原子自增                     | 简单、够快                 | 持久化与故障切换可能造成回退或空洞 |
| Snowflake  | 时间戳 + 机器位 + 序列       | 本地生成、趋势递增、64 bit | 时钟回拨、机器位分配、时间上限     |

### Snowflake 的位分配

```text
0 | 0000000000 0000000000 0000000000 0000000000 0 | 0000000000 | 000000000000
↑   ↑ 41 bit 毫秒时间戳（相对自定义 epoch）        ↑ 10 bit     ↑ 12 bit 序列
符号位 固定 0                                      workerId    同毫秒内序号
```

- 41 bit 毫秒约 69 年，所以 epoch 要取「项目上线时间」而不是 Unix 纪元，能显著延长可用年限。
- 10 bit worker 最多 1024 个节点，够用但要**有分配机制**：K8s 下可用 StatefulSet 序号、etcd 租约注册，千万别让实例自己随机挑，碰撞是迟早的事。
- 12 bit 序列每毫秒 4096 个，单节点理论 409 万 QPS；溢出就阻塞等到下一毫秒。

### 时钟回拨是必答题

```go
func (s *Snowflake) Next() (int64, error) {
    s.mu.Lock()
    defer s.mu.Unlock()

    now := time.Now().UnixMilli()
    if now < s.lastMs {
        drift := s.lastMs - now
        if drift <= 5 {              // 小幅回拨：等时钟追上
            time.Sleep(time.Duration(drift+1) * time.Millisecond)
            now = time.Now().UnixMilli()
        }
        if now < s.lastMs {          // 大幅回拨：宁可拒绝，也不能发重复 ID
            return 0, fmt.Errorf("clock rollback: %dms", s.lastMs-now)
        }
    }
    if now == s.lastMs {
        s.seq = (s.seq + 1) & seqMask
        if s.seq == 0 {              // 本毫秒序列用尽，自旋到下一毫秒
            for now <= s.lastMs { now = time.Now().UnixMilli() }
        }
    } else {
        s.seq = 0
    }
    s.lastMs = now
    return (now-s.epoch)<<tsShift | s.worker<<workerShift | s.seq, nil
}
```

关键不是代码多精巧，而是三个决策：**小幅回拨可以等，大幅回拨必须报错并告警，绝不靠「加个随机数」蒙混过去**。NTP 步进调整、虚拟机迁移、容器时钟漂移都会触发它。

### 号段模式为什么生产里很常见

```text
实例 A 从 DB 领取 [1000, 2000) → 内存里逐个发
用到 80% 时异步预取下一段 [2000, 3000)（双 buffer）
DB 挂了 → 手里还有几百个 ID，足够撑到恢复或告警
```

它把「每次写都依赖 DB」变成「每几千次写依赖一次 DB」，同时保留趋势递增。代价是 ID 有明显跳变、实例重启会浪费整段，对「连续无空洞」有幻想的业务要提前说清楚——**数据库本来就不该承诺 ID 连续**，回滚、删除、主从切换都会产生空洞。

## 三、分布式锁的需求清单

| 需求     | 说明                                     |
| -------- | ---------------------------------------- |
| 互斥     | 任意时刻只有一个持有者                   |
| 死锁可解 | 持有者崩溃后有超时自动释放               |
| 不误删   | A 超时后 B 加锁，A 恢复时不能删掉 B 的锁 |
| 容错     | 锁服务单点故障时不能出现两个持有者       |
| 可观测   | 等待时长、持有时长、续约失败要有指标     |

## 四、Redis 锁的演进：每一步补一个洞

```text
SETNX key 1 → EXPIRE key 30     ← 两条命令非原子，中间崩溃 = 永久死锁
SET key val NX EX 30            ← 原子了，但没解决误删与超时
DEL key                         ← A 超时后 B 持锁，A 的 DEL 删的是 B 的锁
```

正确的最小实现：`value` 用高熵随机串标识持有者，释放时用 Lua 原子比较再删。

```lua
-- KEYS[1]=lock key, ARGV[1]=owner token
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
```

Go 侧骨架：

```go
token, _ := randToken(16)
ok, err := rdb.SetNX(ctx, key, token, ttl).Result()
if err != nil || !ok { return ErrLockBusy }
defer func() { _ = releaseScript.Run(ctx, rdb, []string{key}, token).Err() }()

// 业务执行可能超过 ttl → 启动 watchdog 定期续期
stop := make(chan struct{})
go func() {
    ticker := time.NewTicker(ttl / 3)
    defer ticker.Stop()
    for {
        select {
        case <-stop: return
        case <-ticker.C:
            if !extendIfOwner(ctx, rdb, key, token, ttl) {
                log.Warn("lock renewal failed, stop doing work")
                cancelWork()
                return
            }
        }
    }
}()
```

**续期失败必须停止业务，而不是假装还持有锁**。这是最常被漏掉的一环：进程 GC 停顿、网络分区、Redis 慢导致续约超时，此时锁可能已被别人拿走，继续写就是在并发修改共享资源。

## 五、Redis 锁真正的硬伤与 Redlock 争议

单实例 Redis 锁在主从切换时可能丢锁：主库写入 `SET` 后尚未同步到从库就宕机，从库提升后新客户端能再次加锁 → 两个持有者。Redlock 试图用多个独立实例多数派解决，但争议点在于它仍依赖「时钟没跳跃、进程没长时间停顿」这两个假设：

```text
客户端 A 拿到锁 → 发生长 GC pause → 锁已过期，B 拿到锁并开始写
A 恢复后以为自己仍持锁 → 也去写 → 两个持有者同时操作共享资源
```

这不是 Redis 实现有 bug，而是**「带租约的互斥锁」在没有 fencing 机制时，无法防御持有者自己暂停**。所以结论通常是：

| 场景                                               | 建议                                                        |
| -------------------------------------------------- | ----------------------------------------------------------- |
| 允许极小概率重复、只做效率优化（如避免重复算缓存） | 单实例 Redis 锁足够，简单且便宜                             |
| 涉及资金、库存、状态机正确性                       | 不要只靠 Redis 锁，用 DB 约束 / 乐观锁 / fencing token 兜底 |
| 需要严格互斥且有运维能力                           | etcd / ZooKeeper 的租约 + 顺序节点                          |

## 六、Fencing Token：把正确性放到资源侧

```text
锁服务每次成功加锁返回单调递增的 token：33 → 34 → 35
客户端写共享资源时必须带上 token
资源侧记住见过最大的 token，拒绝任何更小的写入
```

这样即使 A 停顿后带着 token=33 回来，B 已经用 34 写过，资源侧会直接拒绝 A。**正确性不再依赖「锁没失效」，而依赖「资源端能识别过期持有者」**。代价是存储层必须支持这个校验（CAS 版本号、`UPDATE ... WHERE version = ?`、带版本的状态机）。

工程上更常见的等价做法是**根本不用分布式锁**：

```sql
-- 幂等：唯一键兜底
INSERT INTO task_dedup(biz_id, ...) VALUES (?, ...) ON CONFLICT DO NOTHING;

-- 乐观锁：版本号兜底
UPDATE account SET balance = balance - ?, version = version + 1
WHERE id = ? AND version = ?;
```

或者把并发操作交给单分区消息队列串行化，用「顺序」替代「互斥」。**能靠唯一约束和状态机解决的事，别引入锁服务**。

## 七、选型速查

| 需求                | 首选                              | 备选                     |
| ------------------- | --------------------------------- | ------------------------ |
| 高性能趋势递增 ID   | Snowflake（含时钟回拨处理）       | DB 双 buffer 号段        |
| 不方便维护 workerId | DB 号段                           | Redis INCR（注意持久化） |
| 对外暴露的 ID       | 独立高熵不透明串                  | 带校验位编码             |
| 效率型互斥          | 单实例 Redis 锁 + Lua 释放 + 续期 | 本地锁 + 幂等            |
| 正确性型互斥        | 唯一键 / 乐观锁 / fencing token   | etcd 租约锁              |

## 八、实践清单

- Snowflake 必须处理时钟回拨并告警，workerId 由平台统一分配且有租约回收。
- 号段模式配双 buffer 预取，DB 不可用时的剩余量与降级策略要有监控。
- 内部 ID 与对外 ID 分离，对外接口不暴露连续自增主键。
- Redis 锁一律 `SET NX EX` + 随机 token + Lua 释放，业务超时要续期且续期失败即停写。
- 涉及资金、库存、状态流转的逻辑，用唯一键、乐观锁或 fencing token 在资源侧兜底。
- 锁的等待时长、持有时长、续约失败率、误删尝试都要有指标；加锁失败要区分「被占用」与「锁服务故障」。

## 九、面试速答

**Q：UUID 为什么不适合做数据库主键？**
v4 完全随机，插入 B+ 树时落点分散，导致频繁页分裂、缓存命中率下降和写放大；且 128 bit 比 64 bit 整数更占空间，二级索引也会带着它。需要本地生成时可用时间有序的 UUID v7，或直接用 Snowflake。

**Q：Snowflake 时钟回拨怎么办？**
小幅回拨（几毫秒）自旋等待时钟追上；大幅回拨直接拒绝发号并告警，绝不能用随机位掩饰。根因通常是 NTP 步进、虚拟机迁移或容器时钟漂移，运维上应改用平滑校时并监控回拨次数。

**Q：Redis 分布式锁释放为什么要 Lua？**
`GET` 判断加 `DEL` 分两步不是原子操作：A 判断通过后被挂起、锁过期、B 加锁，A 恢复后 `DEL` 删掉的是 B 的锁。用 Lua 让「比较 owner token 并删除」在 Redis 内一次完成。

**Q：Redlock 为什么有争议？**
它仍假设时钟不跳跃、进程不会长时间停顿。GC pause 或网络分区让持有者以为锁还在，而锁已过期被他人获取，两个持有者会同时写共享资源。正确性场景应使用 fencing token 或数据库约束，把校验放到资源侧。

## 十、一句话收尾

ID 和锁的共同教训是：**分布式系统里任何「唯一」都要有明确的分配边界，任何「互斥」都要在资源侧有兜底验证**；只依赖一个中间件返回的成功，是不够的。
