> 加缓存是性能优化里最便宜的一步，也是引入不一致、脏读和雪崩最便宜的一步。难点从来不是 `GET/SET` 两个调用，而是「谁负责回填」「更新时先动谁」「缓存挂了系统还能不能活」「热 key 把某个分片打爆怎么办」。这篇按读写模式 → 一致性 → 三大经典问题 → 热点治理 → 可观测性串一遍。

## 一、缓存放哪一层

| 层级       | 例子                               | 命中收益         | 一致性难度               |
| ---------- | ---------------------------------- | ---------------- | ------------------------ |
| 客户端     | 浏览器 Cache-Control、App 本地缓存 | 零网络请求       | 极高（版本由客户端持有） |
| CDN / 边缘 | 静态资源、SSR 页面片段             | 就近、抗大流量   | 高（刷新/预热）          |
| 网关       | Nginx / API Gateway 响应缓存       | 挡在应用之前     | 中                       |
| 进程内     | Go `sync.Map` + LRU、Caffeine      | 纳秒级、无网络   | 高（多实例各自为政）     |
| 分布式     | Redis / Memcached                  | 共享视图、容量大 | 中                       |
| 数据库内   | Buffer Pool、查询结果缓存          | 免应用改造       | 由 DB 自己保证           |

多级缓存的经典组合是 **本地 L1 + Redis L2 + DB**：L1 挡热点、L2 保证共享视图、DB 兜底。层级越多，失效广播越复杂，所以通常只给「读极多、变更极少」的数据（配置、字典、商品基础信息）加 L1，并配一个很短的 TTL 作为不一致的上界。

## 二、三种读写模式

### Cache-Aside（最常用）

```text
读：cache GET → miss → 查 DB → SET cache（带 TTL）→ 返回
写：更新 DB → 删除 cache
```

应用自己承担全部逻辑，缓存与 DB 解耦，缓存整体挂掉时退化成「直接查 DB」——**这是它最大的优点**。

### Read-Through / Write-Through

缓存组件自己负责在 miss 时加载、在写时同步落库。业务代码干净，但缓存层变成关键路径，且需要实现加载器，跨语言/多服务时不好统一。

### Write-Behind（Write-Back）

先写缓存，异步批量刷 DB。写延迟极低，但缓存宕机就会**丢已确认的写入**，只适合可丢的计数、埋点、浏览记录，绝不能用于订单和余额。

| 模式               | 读一致性     | 写延迟 | 缓存故障影响        |
| ------------------ | ------------ | ------ | ------------------- |
| Cache-Aside        | 依赖失效策略 | 正常   | 退化到 DB，可能击穿 |
| Read/Write-Through | 较好         | 正常   | 写入链路中断        |
| Write-Behind       | 好           | 极低   | 可能丢数据          |

## 三、一致性：把「窗口」讲清楚

先说结论：**在「DB + 缓存」这套组合里，除非引入分布式事务或把读也串行化，否则只能做到最终一致**。工程上要做的是把不一致窗口压到可接受、并给出兜底。

### 为什么推荐「先更新 DB，再删缓存」

| 顺序                  | 可能出现的问题                                                    |
| --------------------- | ----------------------------------------------------------------- |
| 先删缓存，再更新 DB   | 删完之后、DB 更新前，另一个读请求把**旧值**回填进缓存，长时间脏读 |
| 先更新 DB，再删缓存   | 存在极小窗口：读请求在更新前读到旧值，且回填发生在删缓存之后      |
| 先更新缓存，再更新 DB | DB 失败时缓存里是根本不存在的值，最危险                           |

第二种的窗口需要「读命中 miss + 回查慢于写事务 + 回填晚于删除」同时成立，概率低，且 TTL 会兜底。所以它是默认选择。

```go
// 写路径：事务提交后再删缓存，不要在事务内部删
func UpdateUser(ctx context.Context, u User) error {
    if err := repo.Update(ctx, u); err != nil { // 事务在此提交
        return err
    }
    if err := cache.Del(ctx, userKey(u.ID)); err != nil {
        // 删除失败不能让业务失败，但要告警 + 投递补偿消息重试
        log.Warn("cache del failed, publish invalidate", "key", u.ID, "err", err)
        invalidationQueue.Publish(ctx, userKey(u.ID))
    }
    return nil
}
```

### 让不一致可控的四个手段

1. **删除而非更新缓存**：避免并发写导致「后算的值先写入」，也避免复杂计算结果被覆盖。
2. **失效补偿**：删除失败进消息队列重试，或对 binlog / WAL 做订阅（Canal、Debezium）由独立消费者统一发失效，天然绕开应用漏删。
3. **TTL 作为上界**：所有 key 必须有 TTL，且加随机抖动。它是所有一致性 bug 的最后一道防线。
4. **关键数据绕开缓存**：余额、库存扣减、订单状态读主库或走版本号校验（`CAS` / `version` 字段）。别指望缓存解决强一致问题。

还有个常被忽略的点：**本地 L1 的一致性更差**。要么 TTL 极短（1–5 秒），要么走 pub/sub 广播失效；广播丢失时靠 TTL 收敛。

## 四、穿透、击穿、雪崩

| 问题 | 定义                                  | 后果                  | 主要解法                                             |
| ---- | ------------------------------------- | --------------------- | ---------------------------------------------------- |
| 穿透 | 查询**根本不存在**的数据              | 每次都落到 DB         | 空值缓存、布隆过滤器、参数校验                       |
| 击穿 | 单个**热 key 过期**瞬间大量并发回源   | DB 瞬时被同一行打爆   | `singleflight`、互斥重建、逻辑过期不物理删除         |
| 雪崩 | 大量 key **同时失效**或缓存整体不可用 | DB 全量承压、服务雪崩 | TTL 随机抖动、预热、熔断限流、多级缓存、Redis 高可用 |

```go
// 空值缓存：防止不存在的 id 被反复查询
if errors.Is(err, sql.ErrNoRows) {
    _ = cache.Set(ctx, key, emptyPlaceholder, 60*time.Second+randJitter())
    return nil, ErrNotFound
}
```

**逻辑过期**是处理热点 key 更稳的做法：缓存里存 `expireAt` 字段，物理上永不删除。发现逻辑过期时，只放一个请求异步重建，其余请求先返回旧值。代价是短暂读到旧数据，适合首页、榜单这类可容忍秒级滞后的场景。

```go
// 单飞：同一个 key 的并发回源合并成一次
v, err, _ := group.Do(key, func() (any, error) {
    return loadFromDB(ctx, id)
})
```

`singleflight` 要设超时并注意：如果共享结果里包含可被修改的指针，调用方各自改动会互相污染，应返回副本。

## 五、热点 key 与大 key

热点往往不是设计出来的，是突发事件造出来的（热搜、明星直播、秒杀商品）。

**发现**：Redis `hotkeys`（LFU 开启时）、客户端侧按 key 做 TopN 计数、`--bigkeys` / `MEMORY USAGE` 找大 key、监控单分片 QPS 与 CPU 偏斜。

**治理**：

| 手段     | 说明                                                |
| -------- | --------------------------------------------------- |
| 本地 L1  | 把热点挡在进程内，Redis 分片压力降一个数量级        |
| key 拆分 | `product:{id}:{shard}` 把读分散到多个分片，写需广播 |
| 只读副本 | Redis 主从读写分离，注意复制延迟带来的脏读          |
| 提前预热 | 活动开始前把预期热数据载入并设置错峰 TTL            |
| 限流兜底 | 热点超限直接返回兜底值，保护 DB 而不是硬扛          |

**大 key** 是另一类问题：一个 list/hash 几百 MB，`DEL` 会阻塞事件循环，网络传输打满带宽，迁移时造成分片倾斜。解法是拆分成多个小 key、用 `UNLINK` 异步删除、控制集合元素上限、遍历改用 `SCAN` 而非 `HGETALL`。

## 六、多级缓存骨架

```go
type Cache[T any] struct {
    local *lru.Cache[string, entry[T]] // L1，短 TTL
    redis redis.Client                  // L2
    sf    singleflight.Group
    load  func(ctx context.Context, key string) (T, error)
}

func (c *Cache[T]) Get(ctx context.Context, key string) (T, error) {
    if e, ok := c.local.Get(key); ok && time.Now().Before(e.expireAt) {
        return e.val, nil
    }
    if raw, err := c.redis.Get(ctx, key).Bytes(); err == nil {
        v, err := decode[T](raw)
        if err == nil {
            c.local.Add(key, entry[T]{v, time.Now().Add(time.Second)}) // L1 TTL 很短
            return v, nil
        }
    }
    // 合并回源，避免击穿
    boxed, err, _ := c.sf.Do(key, func() (any, error) {
        v, err := c.load(ctx, key)
        if err != nil { return nil, err }
        ttl := baseTTL + time.Duration(rand.Intn(300)) * time.Second
        _ = c.redis.Set(ctx, key, encode(v), ttl).Err()
        return v, nil
    })
    if err != nil { var zero T; return zero, err }
    return boxed.(T), nil
}
```

几个刻意的设计：L1 只给 1 秒级 TTL；L2 TTL 加随机抖动；回源统一走 singleflight；缓存读写错误**一律不当作业务错误**，只记日志与指标。最后一条决定了「Redis 挂了，站点是变慢还是 500」。

## 七、容量与淘汰

内存估算不要只看 value：

```text
总内存 ≈ key 数 × (key 长度 + value 长度 + 约 100~200B 元数据)
        × 副本数 × 1.2~1.5（碎片、复制缓冲、客户端缓冲）
```

`maxmemory-policy` 的选择：`allkeys-lru` 适合纯缓存；`volatile-lru` 只对设了 TTL 的 key 淘汰，混合存储时容易 OOM；`noeviction` 在写满后直接报错，只适合不允许丢数据的场景。无论哪种，都要给 `maxmemory` 留 20–30% 余量，并监控 `used_memory` 与 `mem_fragmentation_ratio`。

## 八、可观测性：别只盯命中率

| 指标                    | 为什么重要                          |
| ----------------------- | ----------------------------------- |
| 按业务拆分的命中率      | 全局 95% 可能掩盖某个新接口 0% 命中 |
| 回源 QPS / DB QPS 比值  | 缓存失效时最先飙升的先行指标        |
| 穿透率（空结果占比）    | 识别恶意遍历或 id 生成 bug          |
| 缓存 P99 延迟与超时率   | 慢 Redis 比挂掉的 Redis 更难查      |
| 失效消息积压 / 广播延迟 | 衡量不一致窗口的真实长度            |
| 单分片 CPU / key 分布   | 热点与倾斜                          |
| 脏读告警                | 抽样比对缓存值与 DB 值（对账）      |

## 九、实践清单

- 每个 key 都有 TTL，且带随机抖动；没有 TTL 的 key 必须有另一个明确的失效路径。
- 写路径统一为「提交事务 → 删缓存 → 失败走补偿消息」。
- 缓存客户端设置连接超时、读写超时、最大连接数与熔断，避免缓存变慢拖死调用方。
- 关键数据（资金、库存、状态机）不依赖缓存做正确性判断。
- 压测里包含「Redis 全挂」和「热点 key 过期」两个场景，验证降级是否真的生效。
- 上线新缓存前先做影子读：只写不读一段时间，比对命中率与数据一致性再切流量。

## 十、面试速答

**Q：为什么是删缓存而不是更新缓存？**
更新缓存在并发写下会乱序覆盖，而且复杂计算结果重复算一遍不划算；删除让下次读按需重建，天然串行在最新 DB 值之上。

**Q：先删缓存还是先更新 DB？**
先更新 DB 再删缓存。先删会让读请求在 DB 更新前把旧值回填，且没有 TTL 之外的纠正机制；后删的脏读窗口更小且概率更低。订阅 binlog 做失效可以进一步收敛。

**Q：缓存雪崩怎么防？**
四层：TTL 加随机值避免同时过期、热点预热与逻辑过期、本地 L1 + 限流熔断保护 DB、Redis 本身做高可用与多副本。核心思想是**任何时刻 DB 承受的回源量都要有上界**。

## 十一、一句话收尾

缓存的本质是用「短暂的不一致」换「巨大的吞吐」，所有设计都要回答两件事：不一致窗口有多长、缓存失效时系统靠什么活下来。
