> 把「一致性」「共识」「分布式事务」分开讨论，是理解这类问题的第一步。本文以业务系统常见的「写数据库 + 发消息 + 调外部服务」链路为背景：先划清概念边界，再对比方案，最后落到幂等与对账这两个真正决定正确性的环节。

## 一、三个容易被混为一谈的问题

| 问题       | 关注点                             | 典型手段                     |
| ---------- | ---------------------------------- | ---------------------------- |
| 数据一致性 | 多副本或多份数据对外看起来是否一致 | 复制协议、读写策略、冲突解决 |
| 共识       | 多个节点如何就一个值达成一致       | Paxos、Raft、Zab、Quorum     |
| 分布式事务 | 跨多个资源的一次业务操作如何生效   | 2PC、TCC、Saga、Outbox       |

一个系统常常同时用到三者：用 Raft 保证元数据一致，用 Outbox 保证「写库 + 发消息」最终一致。把它们压缩成一句「用了分布式事务所以强一致」，基本就是错误的起点。

## 二、一致性模型与 CAP

| 模型       | 含义                                   | 常见载体           |
| ---------- | -------------------------------------- | ------------------ |
| 线性一致性 | 操作看起来像在某一瞬间原子生效         | 单主写入、共识组   |
| 顺序一致性 | 各节点看到的操作顺序一致，但不保证实时 | 多数复制日志       |
| 因果一致性 | 有因果关系的操作保持顺序               | 会话保证、向量时钟 |
| 最终一致性 | 停止写入后，副本最终收敛               | 异步复制、消息投递 |

CAP 说的是**网络分区发生时**，只能在强一致（C）和可用性（A）之间取舍，不是「三者只能选两个」。更实用的描述是 PACELC：分区（P）时权衡 A 与 C，平时（E）还要权衡延迟（L）与一致性（C）。很多系统不是整体 CP 或 AP，而是按操作分档：转账走强一致， feeds 走最终一致。

BASE（基本可用、软状态、最终一致）不是对 ACID 的否定，而是承认跨服务事务难以做到原子，于是把目标改为「可收敛 + 可补偿 + 可核对」。

## 三、共识与 Quorum 要点

Raft 一类的算法通过任期、多数派选举和日志复制，保证已提交条目不丢失。工程上更常直接面对的是读写多数派：设副本数 `N`、写成功数 `W`、读成功数 `R`，当 `W + R > N` 时读写集合必然相交，能读到最新写入；同时 `W > N/2` 可避免两个写集合互不重叠。常见的 `N=3, W=2, R=2` 即由此而来。

```text
N = 3, W = 2, R = 2
写入 {A, B} 成功 → 读 {B, C} 必然包含已更新的 B → 可见最新值
```

需要注意两点：

- 多数派只保证「能读到」，不自动解决并发写冲突，仍需版本、CAS 或最后写入胜出（LWW）策略。
- 旧主节点被隔离后仍可能自认为有效，必须用租约、任期或 fencing token 让下游拒绝过期写入，否则会出现双写。

## 四、跨服务事务方案对比

| 方案                | 一致性       | 业务侵入 | 性能与可用性         | 适用场景                       |
| ------------------- | ------------ | -------- | -------------------- | ------------------------------ |
| 2PC / XA            | 强一致       | 低       | 阻塞、协调者单点     | 同机房少量数据库、无法改造代码 |
| 3PC                 | 试图减少阻塞 | 低       | 分区下仍可能不一致   | 理论意义大于实践               |
| TCC                 | 近乎强一致   | 高       | 需实现三个接口       | 支付、账户等核心资金链路       |
| Saga                | 最终一致     | 中       | 高，靠补偿回滚       | 长流程、跨多个服务             |
| 本地消息表 / Outbox | 最终一致     | 中       | 高，与业务同事务落库 | 写库后可靠发消息               |
| 事务消息            | 最终一致     | 中       | 依赖 MQ 回查能力     | 已有支持事务消息的中间件       |

### 1. 2PC 为什么在生产里少用

准备阶段各参与者锁定资源并承诺可提交，协调者再决定是否提交。协调者宕机时参与者可能长时间持锁；网络分区还可能让部分节点提交、另一部分未决。数据库内部可以用它（XA），但跨微服务、跨公网调用几乎不适用。

### 2. TCC 的三个动作

`Try` 预留资源（冻结余额而非扣款）、`Confirm` 真正扣减、`Cancel` 释放预留。三个接口都必须幂等，且要处理「Try 未收到响应」「Confirm 超时后重试」「Cancel 与 Confirm 乱序」等情况，通常用事务状态表 + 状态机推进。

### 3. Saga 与补偿

把长事务拆成一串本地事务，每步配一个补偿动作。失败时按相反顺序补偿。补偿不是回滚：外部世界已经发生的效果（短信已发、钱已转出）无法撤销，只能做业务上的反向操作，因此要设计「不可补偿步骤尽量靠后」。

```text
创建订单 → 扣库存 → 支付 → 发货
              ↑失败时反向：解冻结库存 → 取消订单
```

## 五、幂等是所有方案的共同地基

只要存在重试，消息就可能重复；只要存在超时，调用方就不知道对方是否已执行。最终一致方案依赖「重复执行不产生额外效果」：

| 手段     | 做法                                    | 注意点                       |
| -------- | --------------------------------------- | ---------------------------- |
| 幂等键   | 请求携带唯一 ID，服务端记录处理结果     | 键需由调用方稳定生成并持久化 |
| 唯一索引 | `UNIQUE(biz_type, biz_id)` 挡住重复落库 | 用插入冲突判定「已处理」     |
| 状态机   | 只允特定状态迁移，重复事件直接返回成功  | 迁移要有版本号或乐观锁       |
| 去重表   | 消费前先记 `msg_id`，与业务在同一事务   | 与业务写入必须同库同事务     |

```sql
CREATE TABLE consumed_msg (
  msg_id     VARCHAR(64) NOT NULL,
  biz_type   VARCHAR(32) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (msg_id, biz_type)
);
```

消费逻辑应写成「一个本地事务里：插入去重记录 → 更新业务状态」，而不是先查再写；先查再写在并发下会漏判。

## 六、一条完整链路：下单后发消息

```text
[本地事务]
  写 order 表  ─┐
  写 outbox 表 ─┴→ 提交
        ↓ 独立投递进程（轮询 / CDC）
     消息队列 → 消费者（幂等） → 下游服务
        ↓ 定时对账
   补偿长时间未投递或状态不一致的记录
```

关键设计：

1. 业务数据与消息在**同一个数据库事务**中落盘，杜绝「库写成功但消息没发」。
2. 投递进程至少一次发送，因此消费端必须幂等；投递成功标记也放在 outbox 行上。
3. 消息里只放业务 ID 与必要快照，不要让下游依赖消息内容作为唯一事实来源。
4. 对账任务扫描超时未确认的记录并告警/重投，这是最终一致的兜底，不是可选优化。

## 七、常见误区

- **「用了 MQ 就保证一致」**：MQ 只保证投递能力，业务状态是否收敛取决于幂等、顺序与补偿。
- **「重试次数越多越可靠」**：下游已过载时重试会放大流量，必须有退避、抖动、重试预算和熔断。
- **「分布式锁能替代事务」**：锁只解决互斥，不解决崩溃后的状态恢复；持锁时间超过租约还会失效。
- **「依赖本地时钟排序」**：跨节点时钟不可信，涉及顺序与过期判断应服务端单调解值或版本号。
- **「补偿一定能成功」**：补偿本身也会失败，需要可重试、可人工介入、可观测。

## 八、实践清单

1. 先问「能否避免跨服务事务」：把强相关的数据放在同一个库和同一个事务里，是最有效的简化。
2. 明确每个接口的一致性档位：强一致、读己之写、最终一致，并在文档里写清楚。
3. 所有写接口设计幂等键，所有消息消费设计去重表。
4. 每个异步链路配一张状态表和一个对账任务，能回答「现在有多少条没收敛」。
5. 超时、重试、幂等三者必须一起设计，缺一个就会出现重复或悬挂状态。
6. 用故障演练验证：消息延迟、重复投递、消费失败、下游超时、进程在中途崩溃。

## 九、面试速答

**问：CAP 怎么理解？** 分区发生时，强一致要求拒绝无法与多数派通信的请求，可用性则要求继续响应，二者不可兼得；不分区时还有延迟与一致性的权衡，所以更准确的说法是 PACELC。

**问：如何保证「写库并发送消息」不丢？** 用本地消息表或 Outbox，业务数据和消息在同一事务写入，再由独立进程投递，消费端幂等，最后用对账兜底。

**问：Saga 和 TCC 怎么选？** 资金类、步骤少且要求接近强一致用 TCC；流程长、涉及外部系统、允许最终一致用 Saga。两者都要幂等与状态机，Saga 额外需要设计补偿。
