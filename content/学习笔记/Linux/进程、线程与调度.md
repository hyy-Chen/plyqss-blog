> Go 里 `go func()` 一行就能起协程，K8s 里 `replicas: 3` 一行就能起三个 Pod，中间隔着好几层抽象。真遇到「容器里 CPU 没跑满但 P99 抖」「进程退不干净」「线程数暴涨」这类问题，得回到内核视角：它眼里既没有协程也没有容器，只有一个个可调度的 `task_struct`。

## 一、Linux 不区分进程和线程

内核用同一个结构体 `task_struct` 描述调度实体，所谓「线程」只是**与其他任务共享了更多资源的任务**：

| 资源                  | `fork()` 新进程  | `pthread_create()` 新线程 |
| --------------------- | ---------------- | ------------------------- |
| 地址空间              | 复制（写时复制） | 共享                      |
| 页表、文件描述符表    | 复制             | 共享 fd 表                |
| 信号处理器、挂载点    | 复制             | 共享                      |
| 线程 ID / 栈 / 寄存器 | 独立             | 独立                      |

两者底层都是 `clone()`，区别只在传入的 flags（`CLONE_VM`、`CLONE_FILES`、`CLONE_SIGHAND` 等）。`clone` 也是 namespace 的入口，容器隔离正是从这里长出来的（见「容器底层」那篇）。

```text
进程 = 资源容器（地址空间、fd、信号处理）+ 至少一个执行流
线程 = 共享同一份资源的执行流
协程 = 用户态执行流，内核完全看不见
```

协程的特点：切换不进内核、不需要系统调用、栈可以很小（Go 初始几 KB），所以能撑几十万个。但一旦某个协程执行了**阻塞式系统调用**（典型是文件 I/O 或 cgo 调用），承载它的内核线程就被阻塞，需要运行时把其他协程挪走。Go 的 netpoller 只解决了网络 I/O 这一大类，磁盘文件读写仍可能占住线程。

## 二、fork / exec / COW

```text
fork()  → 复制 task_struct 与页表，父子共享物理页并标记为只读（COW）
        → 任一方写入 → 触发缺页异常 → 内核复制该页 → 各自持有
exec()  → 丢弃旧地址空间，装载新程序映像
```

所以 `fork` 并不立即复制内存，代价主要在页表与描述符表。**但大进程 fork 依然贵**：页表项越多复制越慢，且 fork 后子进程立刻 exec 的场景（如 shell 起命令）会做无用功，这才有了 `posix_spawn` / `vfork`。

一个典型误解：认为 `fork` 后父子内存完全独立、子进程可以慢慢用。实际上父子任何一方持续写，都会不断触发 COW 缺页，在内存紧张时还可能触发回收与 swap，表现为「fork 之后的延迟尖刺」。

## 三、调度器在做什么

Linux 的默认调度类长期是 CFS（完全公平调度器），核心是给每个任务记一个 `vruntime`（虚拟运行时间），每次挑红黑树里 `vruntime` 最小的任务运行：

```text
vruntime += 实际运行时间 × (nice 对应的权重倒数)
低 nice（优先级高）→ 权重高 → vruntime 涨得慢 → 更易被选中
```

新内核（6.6 起）逐步切换到 EEVDF，但对外行为与排查思路一致：**调度器保证的是权重比例的公平，不是「实时」**。需要低延迟保障要靠 `SCHED_FIFO`/`SCHED_RR` 实时调度类或 CPU 亲和性隔离，普通服务别乱设。

| 概念       | 含义                                    | 排查入口                            |
| ---------- | --------------------------------------- | ----------------------------------- |
| nice 值    | -20 ~ 19，影响权重                      | `top` 的 NI 列、`renice`            |
| 运行队列   | 每个 CPU 一个队列，负载均衡会迁移任务   | `vmstat 1` 的 `r` 列                |
| 上下文切换 | 自愿（等 I/O/锁）/ 非自愿（时间片用完） | `/proc/PID/status` 的两个 ctxt 字段 |
| CPU 亲和   | 绑定核可减少缓存失效与迁移              | `taskset`、`sched_setaffinity`      |
| 调度延迟   | 任务就绪到真正上 CPU 的时间             | `perf sched`、`runqlat`             |

**`r` 列持续大于 CPU 核数**说明排队；**非自愿切换暴涨**通常意味着 CPU 上任务太多或时间片被反复抢占，此时加线程只会更糟。

## 四、容器里最容易被忽略的 CPU throttling

cgroup v2 用 `cpu.max` 表达配额：

```text
cpu.max = "50000 100000"   → 每 100ms 周期最多用 50ms CPU（约 0.5 核）
```

一旦某周期内用完配额，**该 cgroup 内所有线程被整体冻结到下一个周期**，即使宿主机 CPU 空闲。表现非常反直觉：

```text
监控：容器 CPU 使用率 ~50%，宿主机也很闲
现象：接口 P99 每隔一段时间出现 50~100ms 的规律性尖刺
```

看这个文件就能确认：

```bash
cat /sys/fs/cgroup/cpu.stat
# nr_periods / nr_throttled / throttled_usec  ← throttled 增长即为元凶
```

K8s 把 `resources.limits.cpu` 映射成 `cpu.max`，`requests.cpu` 映射成权重（`cpu.weight`）并用于调度。对延迟敏感的服务，只设 request 不设 limit、或把 limit 放宽，往往比「多给几个核」更有效；这需要和容量规划一起权衡，不能一刀切。

Go 程序还有一层：默认 `GOMAXPROCS` 按**宿主机**可见 CPU 数设置（新版本已支持读取 cgroup 配额），如果运行时起了远多于配额的 P，会加剧排队与 throttling。容器里建议显式设置 `GOMAXPROCS` 或使用 `automaxprocs` 类库。

## 五、用户态、内核态与系统调用开销

```text
用户态函数 → glibc 封装 → syscall 指令陷入内核 → 内核处理 → 返回用户态
```

一次系统调用本身是几百纳秒到微秒级，看起来不多，但高频小 I/O 会把它放大：`read` 1 字节一百万次 = 一百万次陷入 + 拷贝。所以才有批量读写、缓冲、`sendfile`、`io_uring` 这些优化。

`strace -c -p <pid>` 能直接给出系统调用分布，配合 `pidstat -u` 的 `sy` 占比判断「CPU 是不是烧在内核里」：

```bash
strace -c -p <pid> -f        # 各系统调用次数与耗时
pidstat -u 1                 # us / sy 拆分
```

`sy` 高的常见原因：大量小包网络读写、频繁 `stat`/`open`、锁竞争导致的 `futex`、过度 `mmap`/`munmap`。

## 六、进程生命周期里的坑

| 现象         | 原因                               | 处理                                  |
| ------------ | ---------------------------------- | ------------------------------------- |
| 僵尸进程     | 子进程退出，父进程没 `wait` 回收   | 父进程 reap；容器 PID 1 必须承担      |
| 孤儿进程     | 父进程先退出，子进程被 PID 1 收养  | 取决于 PID 1 是否 reap                |
| 进程杀不掉   | D 状态（不可中断睡眠）等内核 I/O   | 查存储/网络文件系统，别盲目 `kill -9` |
| 优雅退出失效 | 没处理 SIGTERM 或 PID 1 不转发信号 | `signal.NotifyContext` + init 进程    |
| 线程数暴涨   | 每个请求起线程且无上限             | 用协程/池，设 `pids.max`              |

容器里的 **PID 1 问题**尤其常见：普通应用作为 PID 1 时不转发信号也不 reap 子进程，于是 `kubectl delete` 后要等 30 秒被 SIGKILL，容器里还堆一片僵尸。解法是用 `tini`/`dumb-init`（`docker run --init`），或在 Go 程序里自己处理信号与 `wait4(-1, ...)`。

```go
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
defer stop()
if err := srv.Shutdown(ctx); err != nil { /* 记录并走超时兜底 */ }
```

注意 `Shutdown` 也需要超时上限，否则一个长连接能无限期拖住退出；K8s 的 `terminationGracePeriodSeconds` 到期后就是硬杀。

## 七、实践清单

- 排查 CPU 先拆 `us`/`sy`/`wa`，再看运行队列、上下文切换与 `cpu.stat` 的 throttling，别只看使用率。
- 容器里显式设置 `GOMAXPROCS`，延迟敏感服务谨慎设 CPU limit。
- 高频 I/O 走批量与缓冲，`sy` 高用 `strace -c` 找系统调用，而不是猜。
- 服务实现 SIGTERM 优雅退出并设超时；容器 PID 1 负责信号转发与僵尸回收。
- 用 `pids.max` 限制线程/进程数，避免失控创建打满宿主机。
- 大进程避免频繁 fork；确需派生子进程用 `posix_spawn` 并做好 COW 代价评估。
- 压测包含「CPU 配额打满」和「滚动发布时 SIGTERM」两个场景，验证 P99 与在途请求。

## 八、面试速答

**Q：进程和线程在 Linux 里有什么区别？**
内核用同一个 `task_struct` 描述，都由 `clone()` 创建，区别只在共享哪些资源。进程拥有独立地址空间和 fd 表；线程共享地址空间、fd、信号处理，只有栈、寄存器和线程 ID 独立。

**Q：容器 CPU 使用率不高，为什么 P99 还是周期性抖动？**
大概率是 cgroup `cpu.max` 的 throttling：一个周期内用完配额后整个 cgroup 被冻结到下个周期，宿主机可能仍然空闲。查 `/sys/fs/cgroup/cpu.stat` 的 `nr_throttled` 与 `throttled_usec`，并复核 K8s 的 CPU limit 与 `GOMAXPROCS`。

**Q：协程一定比线程快吗？**
切换成本更低、内存更省，适合大量 I/O 并发；但协程阻塞在同步系统调用上会拖住内核线程，CPU 密集型任务也享受不到多核并行（除非运行时正确调度到多个 M）。它不是线程的全面替代。

**Q：容器里为什么会有僵尸进程堆积？**
PID 1 没承担 `wait` 回收职责。改用 init 进程或让应用自己 reap，并确保退出时正确转发 SIGTERM。

## 九、一句话收尾

内核只认识 `task_struct`、时间片和 cgroup 配额；**协程与容器都是上层抽象，抽象失效时，症状最终都会落回调度、系统调用和信号这三件事上**。
