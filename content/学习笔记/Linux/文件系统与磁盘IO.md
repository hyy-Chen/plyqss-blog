> `write()` 返回成功，只代表数据进了内核，不代表到了磁盘。这个差别在断电、容器被杀、主从切换时会变成真实的数据丢失。这篇从 VFS 走到块层，讲清 page cache、回写、`fsync`、Direct I/O 和 `io_uring`，最后给出安全写文件与持久化排查的标准动作。

## 一、VFS：一切皆文件的那层抽象

```text
fd → file（打开实例：偏移量、状态标志）
        → dentry（目录项：名字到 inode 的映射与缓存）
              → inode（文件元数据与数据块位置）
                    → superblock（文件系统整体信息）
```

| 对象   | 存什么                                         | 常见现象                               |
| ------ | ---------------------------------------------- | -------------------------------------- |
| inode  | 权限、大小、时间戳、数据块指针，**不含文件名** | `df -i` 满 = inode 用尽                |
| dentry | 路径分量 → inode 的缓存                        | 目录项缓存命中影响路径解析开销         |
| file   | 每次 open 的上下文与当前偏移                   | 多进程共享同一打开实例时偏移会互相影响 |

硬链接是「多个目录项指向同一个 inode」，软链接是「一个存着路径字符串的特殊文件」。删除文件只是解除目录项并减少引用计数，**只要有进程还持有 fd，数据块就不会释放**——这解释了「日志删了但磁盘没腾出来」（用 `lsof +L1` 找）。

## 二、write 之后数据在哪

```text
write() → 用户缓冲区 → 内核 page cache（页被标记为 Dirty）→ 返回成功
                              ↓ 异步
        回写线程按脏页比例/时间/显式 fsync 刷到块层 → 磁盘
```

这层缓存是性能的关键：重复读写同一文件不必每次碰磁盘，写也可以合并与排序。代价是**持久性边界模糊**：

| 调用                 | 保证                                            |
| -------------------- | ----------------------------------------------- |
| `write`              | 数据进入 page cache，掉电可能丢                 |
| `fsync(fd)`          | 该文件的数据 + 必要元数据落盘                   |
| `fdatasync(fd)`      | 数据落盘，只保证影响读取的元数据（略便宜）      |
| `sync()`             | 全局刷脏页，范围大、耗时不可控                  |
| `O_DIRECT`           | 绕过 page cache，直接与块层交互（对齐要求严格） |
| `O_SYNC` / `O_DSYNC` | 每次写自带同步语义                              |

数据库、WAL、配置写盘必须显式 `fsync`。很多人以为「文件 close 了就安全了」，`close` 只释放 fd，不保证刷盘。

## 三、安全写文件：四步一个都不能少

```text
1. 写临时文件 tmp
2. fsync(tmp)                 ← 保证新数据落盘
3. rename(tmp, target)        ← 同一文件系统内原子替换
4. fsync(目录 fd)             ← 保证目录项落盘
```

漏掉第 4 步，断电后可能出现「新文件内容在，但目录仍指向旧文件」或目录项丢失；漏掉第 2 步，rename 后可能指向一个还没写完的 inode。`rename` 的价值是**读者永远看到完整的旧文件或完整的新文件**，不会读到半截。

日志类追加写则是另一套：依赖顺序写 + 定期 `fsync`（或 group commit 合并多次提交的刷盘成本），崩溃后按记录边界截断未确认的尾部。这也是 MySQL WAL、Kafka 段文件、etcd WAL 的共同思路。

## 四、ext4、journal 与延迟分配

ext4 用日志保证元数据一致性，常见三种模式：

| 模式              | 行为                         | 取舍                            |
| ----------------- | ---------------------------- | ------------------------------- |
| `journal`         | 数据 + 元数据都先写日志      | 最安全，写放大最大              |
| `ordered`（默认） | 数据先落盘，再提交元数据日志 | 平衡                            |
| `writeback`       | 只记元数据，数据顺序不保证   | 最快，崩溃后可能读到旧/垃圾数据 |

还有**延迟分配**：内核先只记虚拟的块范围，真正回写时才决定物理位置，从而把零散写合并成连续区间。副作用是「刚写完的文件突然断电，可能得到一个 0 长度文件」——因为数据和元数据都还没落盘。这也是为什么关键文件必须 `fsync`。

## 五、块层与 I/O 调度

```text
page cache / O_DIRECT → bio 结构 → 请求队列 → I/O 调度器 → 设备驱动 → 硬件
```

调度器负责合并相邻请求、排序以减少寻道、控制公平性：

| 调度器        | 适用                                          |
| ------------- | --------------------------------------------- |
| `mq-deadline` | 通用、带读优先与过期时间，避免写饿死读        |
| `kyber`       | 按目标延迟做反馈控制                          |
| `bfq`         | 桌面/交互式，强调公平                         |
| `none`        | NVMe 多队列 SSD，硬件并行度高，交给设备自己排 |

`iostat -x` 的 `await` 是**排队 + 服务时间**，比 `%util` 更能反映应用感受到的延迟；`aqu-sz` 大配合 `await` 升高才是真排队。NVMe 上 `%util` 100% 未必有问题，所以别只盯一个数字。

内核 5.x 起默认 blk-mq（多队列），按 CPU 建队列，减少锁竞争；这和网卡多队列/RSS 是同一个「多核扩展性」思路。

## 六、io_uring：异步 I/O 终于好用

```text
用户态与内核共享两个 mmap 环形队列：
  SQ (Submission Queue)：应用填好 SQE（opcode、fd、buffer、偏移）
  CQ (Completion Queue)：内核写回 CQE（结果、错误码）

提交：填 SQE → 更新尾指针 → io_uring_enter 一次可提交一批
完成：从 CQ 取结果，可配合 eventfd/epoll 等待
```

相比 `epoll`：

|          | epoll                       | io_uring                              |
| -------- | --------------------------- | ------------------------------------- |
| 能力     | 只通知「fd 就绪」           | 可让内核完成整个读写并通知结果        |
| 系统调用 | 每次就绪后仍需 `read/write` | 批量提交 + 批量收割，调用次数大幅减少 |
| 拷贝     | 仍需用户/内核态数据拷贝     | 可配合注册缓冲区、固定文件减少开销    |
| 适用     | 网络长连接                  | 文件/存储密集型，也可用于网络         |

`IORING_SETUP_SQPOLL` 还能让内核线程轮询 SQ，进一步省掉提交时的系统调用，代价是常占一个 CPU。生产落地要注意四点：**内核版本门槛**（特性逐版本增加）、**完成事件乱序**（要自己按 user_data 关联）、**取消与超时**（关闭 fd 或进程退出时的在途请求）、**安全与可观测**（传统 `strace`/pprof 看不到环内操作，需要专门指标）。

Go 标准库目前仍以 netpoller + 同步文件 I/O 为主，使用 io_uring 通常需要第三方库或 cgo；引入前先确认瓶颈真的是系统调用与拷贝，而不是磁盘本身。

## 七、常见持久化事故

| 现象                       | 原因                                             |
| -------------------------- | ------------------------------------------------ |
| 断电后配置丢失             | 写完没有 `fsync`，或用了编辑器式「先清空再写」   |
| 文件变成 0 字节            | 原地覆盖 + 延迟分配，崩溃时元数据未提交          |
| 数据目录出现半截文件       | 没用 `rename` 原子替换                           |
| `fsync` 很慢拖垮吞吐       | 每次写都全量刷盘；需 group commit 或批量         |
| 磁盘没满却写不进去         | inode 耗尽、配额限制、只读挂载、被删文件仍被占用 |
| 数据库开了 `O_DIRECT` 更慢 | 未对齐、失去 page cache 预读、随机小写放大       |

## 八、排查命令

```bash
iostat -x 1                 # await、aqu-sz、读写量
iotop -o                    # 谁在写
cat /proc/meminfo | grep -E 'Dirty|Writeback'   # 待回写脏页
df -h && df -i              # 空间与 inode
lsof +L1                    # 已删除但仍被持有的文件
cat /sys/block/<dev>/queue/scheduler            # 当前 I/O 调度器
blktrace / bpftrace          # 深入块层延迟分解
```

`Dirty` 持续增长而磁盘写量很低，通常是回写出问题（设备卡住、挂载异常）；`Dirty` 周期性冲高再回落并伴随 `await` 尖刺，往往是批量刷盘或 checkpoint 抢占，需要与业务流量错峰。

## 九、实践清单

- 关键写入显式 `fsync`；更新已有文件用「临时文件 + fsync + rename + fsync 目录」。
- 日志/WAL 用顺序追加 + 提交点 `fsync`，必要时 group commit 合并刷盘成本。
- 数据库使用 `O_DIRECT` 前验证对齐、预读收益与随机写代价，别盲目照抄配置。
- 监控 `Dirty`/`Writeback`、`await`、`aqu-sz`、inode 使用率，而不只是磁盘容量。
- 容器里给数据卷单独挂载并明确配额与挂载选项，避免写满根文件系统拖垮整个 Pod。
- 引入 io_uring 前确认内核版本、在途请求取消、完成乱序与可观测方案。
- 断电/强杀演练纳入测试：验证崩溃重启后文件要么完整、要么可安全回退。

## 十、面试速答

**Q：`write()` 成功是不是数据已经落盘？**
不是。默认只写到 page cache 并标记为脏页，由内核异步回写；断电或进程被杀可能丢。需要 `fsync(fd)`（或 `fdatasync`）并在更新目录项后 `fsync` 目录。

**Q：为什么推荐「写临时文件再 rename」？**
同一文件系统内的 `rename` 是原子操作，读者只会看到完整旧文件或完整新文件，不会读到半截；原地覆盖在崩溃时可能留下 0 字节或半写文件。

**Q：epoll 和 io_uring 的区别是什么？**
epoll 只通知 fd 就绪，应用仍需发起 `read/write` 完成数据搬运；io_uring 通过共享提交/完成环，可让内核完成整个 I/O 并批量收割结果，显著减少系统调用与拷贝，但要求较新内核且需处理乱序、取消与可观测性。

**Q：`%util` 100% 一定是磁盘瓶颈吗？**
不一定，尤其 NVMe 支持多队列并行。应结合 `await`（排队+服务时间）、`aqu-sz` 和应用延迟判断；`await` 抬升才是用户真正感受到的拥塞。

## 十一、一句话收尾

从 `write` 到磁盘之间隔着 page cache、回写、日志和块层调度；**性能来自这些缓冲，事故也来自这些缓冲**——明确「哪一步之后数据才算安全」，比背参数更重要。
