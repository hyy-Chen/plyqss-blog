> 「高并发」不是某个函数用得对，而是把「等数据」和「搬数据」这两段成本分开看清楚。本文从一次 `read` 出发，串起五种 I/O 模型、epoll、Reactor 模式与零拷贝，最后落到线上排查命令。

## 一、一次网络读到底在等什么

以 `recv` 读一个 socket 为例，数据要经历两个阶段：

```text
① 等待数据就绪：网卡 → DMA 到内核缓冲区 → 协议栈处理 → 数据进入 socket 接收缓冲区
② 拷贝数据：把接收缓冲区的内容从内核态复制到用户态内存
```

阻塞发生在阶段 ①；阶段 ② 虽然不「等网络」，但仍然是一次实实在在的内存拷贝和系统调用开销。各种 I/O 模型的差异，本质就是**这两段里谁在等、要不要反复问、要不要自己搬**。

## 二、五种 I/O 模型

| 模型         | 阶段 ①                         | 阶段 ②   | 特点                               |
| ------------ | ------------------------------ | -------- | ---------------------------------- |
| 阻塞 I/O     | 调用方线程挂起                 | 同步拷贝 | 简单，一个连接占一个线程           |
| 非阻塞 I/O   | 立即返回 EAGAIN，需轮询        | 同步拷贝 | 单线程可管多连接，但空转耗 CPU     |
| I/O 多路复用 | `select/poll/epoll` 阻塞等就绪 | 同步拷贝 | 一次调用等一批 fd，主流方案        |
| 信号驱动 I/O | 内核就绪时发 SIGIO             | 同步拷贝 | 信号队列与处理复杂，少用           |
| 异步 I/O     | 内核完成包括拷贝后通知         | 内核完成 | `io_uring`；与「非阻塞」不是一回事 |

最容易混淆的是「非阻塞」和「异步」：非阻塞只是**没数据时立刻返回**，数据就绪后仍要应用自己发起 `read` 并等待拷贝完成；异步 I/O 是内核把活干完再通知你，调用一开始就返回了。

还有一个常见误解：I/O 多路复用本身并不比阻塞 I/O「更快」——单次调用甚至更慢。它的价值是让**一个线程同时照看成千上万个连接**，避免线程数与连接数线性绑定。

## 三、select、poll、epoll

| 维度       | select                  | poll               | epoll                      |
| ---------- | ----------------------- | ------------------ | -------------------------- |
| fd 集合    | `fd_set` 位图，有上限   | 数组，无硬上限     | 内核维护红黑树 + 就绪链表  |
| 每次调用   | 需重复传入并拷贝全部 fd | 同样重复传入       | fd 只注册一次              |
| 就绪后查找 | 遍历全部 fd `O(N)`      | 遍历全部 fd `O(N)` | 直接取就绪列表 `O(就绪数)` |
| 触发模式   | 水平触发                | 水平触发           | 水平(LT) / 边缘(ET)        |
| 适合       | 少量连接、跨平台        | 中等连接           | 大量连接、长连接           |

`epoll_wait` 返回的是「已经就绪的 fd」而不是「全部 fd」，这是 C10K 场景差距的来源：10 万个连接里只有 100 个活跃时，select 每次仍要遍历 10 万个，epoll 只处理 100 个。

### LT 与 ET

- **水平触发（LT）**：只要缓冲区里还有数据，`epoll_wait` 就会持续通知。安全，忘了读完下次还会提醒。
- **边缘触发（ET）**：只在状态**从未就绪变为就绪**时通知一次。必须配合非阻塞 fd，并在一次通知里循环读到 `EAGAIN`，否则剩余数据可能再也不会被通知。

ET 减少了重复事件，但代码更容易写错；除非有明确性能需求，LT 更稳妥。

### 惊群

多个进程/线程同时阻塞在同一个监听 socket 的 `accept` 上，新连接到来时全被唤醒但只有一个成功，其余白跑一趟。常见解法：`SO_REUSEPORT` 让每个 worker 有独立监听 socket 由内核分发，或用互斥/主 Reactor 统一 accept 后分发给子 Reactor。

## 四、Reactor 与 Proactor

```text
Reactor（同步 I/O 多路复用）
  epoll_wait → 就绪事件 → 分派给 handler → handler 自己 read/write → 业务处理

Proactor（异步 I/O）
  提交异步操作 → 内核完成读写 → 回调通知 → 业务处理
```

典型 Reactor 变体：

| 变体                | 职责划分                                      | 适用                |
| ------------------- | --------------------------------------------- | ------------------- |
| 单 Reactor 单线程   | 连接、读写、业务全在一个线程                  | 教学、极低负载      |
| 单 Reactor + 线程池 | Reactor 负责 I/O，业务丢线程池                | 常见折中            |
| 主从 Reactor        | 主 Reactor 只 accept，子 Reactor 各管一批连接 | Nginx、Netty 高并发 |

### Go 的 netpoller

Go 把这套机制藏在了运行时里：socket 设为非阻塞，注册到 netpoller（Linux 上是 epoll）；goroutine 读写时若数据未就绪，运行时把它挂起并让出线程；netpoller 发现就绪后唤醒对应 goroutine。

```text
goroutine 写同步风格代码  →  runtime 挂起/唤醒  →  epoll 等待就绪
                          （开发者不必写回调）
```

所以「Go 用同步写法实现异步 I/O」，既保留了可读性，又不会因为每个连接占一个 OS 线程而耗尽资源。代价是：如果业务在 goroutine 里做长时间 CPU 密集计算或调用阻塞式 CGO，仍会拖累调度，需要另行处理。

## 五、零拷贝与发送路径

普通的「读文件 → 写 socket」有多次拷贝与上下文切换：

```text
磁盘 → 内核页缓存 → 用户缓冲区 → socket 内核缓冲区 → 网卡
       (DMA)        (read 拷贝)     (write 拷贝)        (DMA)
```

| 技术           | 省掉了什么                           | 适用                             |
| -------------- | ------------------------------------ | -------------------------------- |
| `sendfile`     | 用户态与 socket 缓冲区间的一次拷贝   | 静态文件、下载、代理转发         |
| `splice`       | 在两个 fd 间用管道搬运，不经过用户态 | 高性能转发                       |
| `mmap`         | 把内核页缓存映射到用户地址空间       | 大文件随机读，注意缺页与映射管理 |
| `MSG_ZEROCOPY` | 减少用户缓冲区到内核的拷贝           | 大包发送，小包反而更慢           |

注意「零拷贝」通常指**省掉 CPU 参与的数据拷贝**，DMA 搬运仍然存在；而且并非所有场景都更快，小报文下系统调用与缓冲区管理的固定成本可能盖过收益。启用 TLS 后还要加密，很多零拷贝路径不再适用。

## 六、文件描述符与资源上限

高并发首先会撞上资源限制，而不是算法：

| 限制             | 表现                     | 检查与处理                               |
| ---------------- | ------------------------ | ---------------------------------------- |
| `ulimit -n` 过小 | `too many open files`    | 提高进程级 nofile，确认 systemd 配置生效 |
| 端口耗尽         | 出向连接偶发失败         | 连接池复用、扩大端口范围                 |
| `TIME_WAIT` 堆积 | 主动关闭方端口被占用     | 优先连接复用，别盲目改内核参数           |
| epoll fd 本身    | 每个监听实例也占 fd      | `SO_REUSEPORT` 多实例时留意总量          |
| 接收/发送缓冲区  | 高带宽长肥管道吞吐上不去 | 按 BDP 调整 buffer 与窗口                |

`TIME_WAIT` 是 TCP 可靠关闭的一部分，用来吸收延迟报文、避免旧连接数据污染新连接。把它「优化掉」往往只是把问题推迟，正确方向是让服务端少主动关闭（连接复用、长连接、让客户端先关）。

## 七、线上排查命令

```bash
ss -s                              # 连接总览：各状态数量
ss -tanp state time-wait | head    # 查看 TIME_WAIT 分布
ss -ti dst 10.0.0.1               # 单连接的 RTT、拥塞窗口、重传
lsof -p <pid> | wc -l              # 进程打开的 fd 数
cat /proc/<pid>/limits             # 进程实际生效的资源限制
sar -n DEV,ETCP 1                  # 网卡吞吐、重传、连接建立速率
strace -p <pid> -e trace=epoll_wait,read,write -T   # 系统调用耗时
tcpdump -i eth0 host 10.0.0.1 -w /tmp/cap.pcap      # 抓包留存证据
```

排查顺序建议：先看连接状态分布与错误率 → 再看是否卡在 fd/端口/缓冲 → 用 `strace`/profile 区分是内核等待还是应用处理慢 → 最后才抓包确认网络行为。`strace` 和抓包都有明显性能开销，生产上要限定进程、限定时间、限定过滤条件。

## 八、常见误区

| 误区                   | 纠正                                                        |
| ---------------------- | ----------------------------------------------------------- |
| epoll 一定比 select 快 | 连接少且几乎全活跃时差距很小，优势在大量空闲长连接          |
| ET 一定比 LT 快        | ET 减少事件数但要求一次读净，写错会造成连接「假死」         |
| 非阻塞就是异步         | 非阻塞仍需应用自己 read，异步是内核完成后通知               |
| 线程越多并发越高       | 上下文切换与内存开销会让吞吐先升后降，连接多≠需要同样多线程 |
| 零拷贝永远更快         | 小数据、加密链路下收益有限，需实测                          |
| `TIME_WAIT` 是故障     | 是正常的协议状态，堆积才说明连接模式需要调整                |

## 九、实践清单

1. 明确服务的连接模型：短连接还是长连接、谁主动关闭、峰值连接数是多少。
2. 上线前核对 fd 上限、端口范围、连接池大小与超时，压测到预期峰值的 1.5 倍。
3. 所有网络调用设超时与取消，避免 goroutine/线程在已无用的连接上永久等待。
4. 大文件传输再考虑 `sendfile`/`mmap`，并用真实数据量做基准。
5. 监控里保留连接状态分布、重传率、fd 使用率，故障时才不用临时抓瞎。

## 十、面试速答

**问：select 和 epoll 的核心区别？** select 每次调用都要把全量 fd 集合拷进内核并线性扫描，且有 fd 数量上限；epoll 把 fd 注册到内核，就绪时直接返回就绪列表，复杂度与活跃连接数相关。

**问：LT 和 ET 有什么区别？** LT 在缓冲区仍有数据时持续通知，安全性高；ET 只在状态变化时通知一次，必须配非阻塞 fd 并循环读到 `EAGAIN`，否则会漏数据。

**问：Go 为什么能用同步写法支撑高并发？** runtime 把非阻塞 fd 注册到 netpoller，I/O 未就绪时挂起 goroutine 而非阻塞 OS 线程，就绪后再唤醒；开发者看到的是同步代码，底层是事件驱动。
