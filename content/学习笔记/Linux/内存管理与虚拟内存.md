> 「`free` 显示内存快没了」「容器 limit 4G、Go 堆才 1G 却被 OOMKill」「malloc 了 1G 但 RSS 几乎没涨」——这三个问题的答案都在同一套机制里：虚拟地址、物理页、缺页异常和页缓存。这篇把进程视角和内核视角对上，再落到容器与 Go 服务的常见事故。

## 一、每个进程看到的都是「假」地址

```text
进程访问 virtual address
  → MMU 查页表（TLB 命中则直接得到物理页）
  → 页表项存在且有效 → 访问物理页
  → 不存在 → 缺页异常 → 内核分配/调入物理页 → 建立映射 → 返回用户态继续执行
```

x86-64 常用 4 级（新硬件 5 级）页表，标准页 4KB，透明大页（THP）可到 2MB。TLB 是页表缓存，进程切换时需要刷新（带 PCID 可部分避免），所以**大量进程频繁切换的隐性成本之一是 TLB 失效**。

关键点：**虚拟地址空间的大小和真实占用物理内存没有直接关系**。`malloc(1GB)` 通常只是向内核申请一段虚拟地址（或 `mmap` 一段匿名映射），只有真正写入时才通过缺页异常一页一页拿到物理页。这解释了为什么 VSZ 可以很大而 RSS 很小。

## 二、缺页的两种，成本差一个数量级

| 类型        | 含义                         | 典型场景                                 | 代价   |
| ----------- | ---------------------------- | ---------------------------------------- | ------ |
| minor fault | 物理页已在内存，只需建映射   | 首次写 malloc 的页、页缓存命中、COW 复制 | 微秒级 |
| major fault | 物理页不在内存，需要从磁盘读 | 首次读还没缓存的文件、被换出的匿名页     | 毫秒级 |

```bash
ps -o pid,min_flt,maj_flt,cmd -p <pid>     # 累计缺页次数
perf stat -e page-faults,major-faults -- <cmd>
```

服务启动后 P99 明显偏高、随后回落，很多时候是 **major fault**：二进制、共享库、配置文件第一次被访问都要从磁盘调入。预热（提前读一遍热点数据、让 page cache 热起来）能显著缩短冷启动的长尾。

## 三、COW：fork 之后到底复制了什么

`fork` 时父子共享同一批物理页，内核把页表项标成只读；任一方写入触发缺页，内核才复制那一页。所以：

- `fork` 本身快，但**页表复制**仍与进程地址空间大小相关；
- 父进程在 fork 后继续大量写，会持续产生 COW 缺页，形成延迟尖刺；
- Redis 做 RDB 时 fork 子进程，若期间写流量大，内存占用可能接近翻倍（COW 复制了被修改的页），这是容量评估里最容易漏的一项。

## 四、内存都去哪了

| 类别                | 说明                                    | 能否回收                     |
| ------------------- | --------------------------------------- | ---------------------------- |
| 匿名页              | 堆、栈、`mmap` 匿名映射                 | 只能换出到 swap              |
| 文件页 / page cache | 文件内容、`mmap` 文件映射               | 干净页可直接丢弃，脏页需回写 |
| 内核内存            | slab、页表、socket buffer、dentry/inode | 部分可回收                   |
| HugePage            | 预留的大页                              | 一般不可换出                 |

**`free` 里 used 很大不等于内存不够**：page cache 是内核拿来加速文件读的缓存，内存紧张时可直接回收，判断要看 `available` 和 `vmstat` 的 `si/so`。

```bash
free -m                          # 关注 available，不是 free
cat /proc/<pid>/smaps_rollup      # RSS / PSS / 匿名页 / 文件页拆分
vmstat 1                         # si/so 非 0 才是真换页
cat /proc/meminfo | grep -E 'Dirty|Writeback|Slab|PageTables'
```

## 五、回收、swap 与直接回收的延迟尖刺

内核维护 active/inactive LRU 链表，由 `kswapd` 在后台异步回收；当分配速度超过回收速度，分配路径会**同步执行回收（direct reclaim）**，此时申请内存的线程被卡住：

```text
分配内存 → 空闲页低于水位 → 唤醒 kswapd（异步）
        → 仍然不够 → 调用线程自己扫描、回写、换出（同步，延迟飙升）
```

`vm.swappiness` 控制换出匿名页相对丢弃文件页的倾向，不是「内存用到多少才开始 swap」的开关。数据库类服务通常调低它，并尽量避免任何换页；对延迟敏感的服务，宁可早点 OOMKill 触发重启/切流，也不要在 swap 上缓慢爬行。

## 六、OOM Killer：整机与容器是两个层面

| 层面       | 触发条件               | 表现                                          |
| ---------- | ---------------------- | --------------------------------------------- |
| 整机 OOM   | 全局内存不足且回收无果 | `dmesg -T` 有 `Out of memory: Killed process` |
| cgroup OOM | 容器超过 `memory.max`  | 容器内进程被杀，宿主机内存可能很充足          |

内核给每个进程算 `oom_score`，可用 `oom_score_adj`（-1000 ~ 1000）调整；`-1000` 表示禁止被整机 OOM killer 选中。容器场景下更常见的是 cgroup OOM，看这两个文件：

```bash
cat /sys/fs/cgroup/memory.events       # oom / oom_kill 计数
cat /sys/fs/cgroup/memory.current      # 当前用量
cat /sys/fs/cgroup/memory.max          # 上限
cat /sys/fs/cgroup/memory.stat         # anon / file / slab / sock 明细
```

**关键区分**：cgroup 计入的不只是应用堆，还有 page cache、socket buffer、线程栈、mmap、glibc 缓存等。于是出现经典现象「Go 堆 1G、limit 4G 却 OOM」——文件缓存或网络缓冲区把剩余额度吃掉了。`memory.stat` 里的 `file`、`sock`、`slab` 能直接定位。

## 七、Go 服务为什么 RSS 远大于堆

```text
RSS ≈ Go 堆(inuse + 空闲未归还) + 栈 + runtime 元数据
     + cgo/mmap 分配 + page cache + socket buffer + 共享库
```

常见原因：

| 原因             | 说明                                                  |
| ---------------- | ----------------------------------------------------- |
| 堆归还滞后       | GC 后内存标记为空闲但未必立刻 `MADV_DONTNEED` 还给 OS |
| 大对象与 mmap    | 大块 `[]byte`、`mmap` 文件、内存数据库                |
| cgo / 第三方库   | 不受 Go GC 管理，pprof 看不到                         |
| page cache       | 读文件、写日志产生的文件页计入 cgroup                 |
| 线程栈与连接缓冲 | 大量连接时不可忽视                                    |

排查顺序：先看 `/proc/PID/smaps_rollup` 与 cgroup `memory.stat` 拆分 → 再看 Go pprof 的 `inuse_space` / `alloc_space` → 两者差额巨大时转向 cgo、mmap、page cache。`GOMEMLIMIT` 能约束 Go 堆增长，但**必须低于容器 limit 并留出 20~30% 给非堆内存**，否则 GC 拼命压堆仍逃不过 cgroup OOM。

## 八、排查路径：内存持续上涨

```text
1. 确认是进程还是容器整体：memory.current 曲线 + 各进程 RSS
2. 拆分 smaps_rollup / memory.stat：匿名页涨还是文件页涨
3. 匿名页涨 → 应用堆/泄漏：采 heap pprof，对比 inuse_space 趋势
4. 文件页涨 → page cache：正常可回收，看是否因 limit 太小导致误杀
5. si/so 非 0 → 真的在换页，延迟抖动优先处理
6. 查 dmesg -T 与 memory.events，确认是否被 OOMKill 而非主动退出
7. 修后验证：RSS 趋稳、P99、GC 频率、oom_kill 计数归零
```

一个常见误判是把 page cache 增长当内存泄漏而急着重启。重启只是清空了缓存，很快会涨回去；正确做法是看 `available`、回收压力和 `memory.events` 是否真的触发 OOM。

## 九、实践清单

- 容器内存按 cgroup 看（`memory.current/max/stat/events`），不用宿主机 `free` 下结论。
- 区分匿名页与文件页增长；page cache 是可回收缓存，不是泄漏。
- Go 服务设置 `GOMEMLIMIT` 并留足非堆余量，同时监控 GC 频率与 `inuse_space`。
- 延迟敏感服务避免 swap；监控 `si/so` 与 major fault，冷启动做预热。
- 评估 `fork` 场景（备份、RDB）的 COW 内存放大，给足余量。
- 大页（THP / HugePages）要先实测：数据库可能受益，随机小对象服务可能因碎片与回收变慢。
- OOM 后保留 `dmesg -T`、`memory.events`、进程内存拆分与当时流量，别只重启了事。

## 十、面试速答

**Q：malloc 了 1GB，为什么 RSS 没涨？**
`malloc` 主要分配虚拟地址空间，物理页在首次写入时通过缺页异常才分配。VSZ 反映虚拟空间，RSS 反映实际常驻物理页，两者不必接近。

**Q：minor fault 和 major fault 的区别？**
minor 是物理页已在内存（如页缓存命中、COW 复制），只需建立映射；major 需要从磁盘调入，代价高几个数量级。冷启动长尾、swap 换入都体现为 major fault 增多。

**Q：容器内存没超限，为什么进程被 OOMKill？**
要区分整机 OOM 与 cgroup OOM。容器看 `memory.events` 的 `oom_kill`：即使应用堆不大，page cache、socket buffer、线程栈、cgo 分配都计入 cgroup 额度，`memory.stat` 可定位具体类别。

**Q：为什么 `free` 看起来内存快用完了却没告警？**
大量内存被 page cache 占用，属于可回收文件页。应看 `available` 与 `si/so`；只有持续换页、direct reclaim 或 OOM 才说明真的紧张。

## 十一、一句话收尾

内存问题之所以难查，是因为同一个「用了多少内存」在**虚拟地址、物理页、cgroup 计费、语言运行时堆**四个层面各有一个答案；先把口径对齐，再谈泄漏与调优。
