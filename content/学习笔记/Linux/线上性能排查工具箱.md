> 「操作系统与线上排障」那篇给的是速答框架，这一篇给**命令与判读逻辑**：某个数字异常代表什么、下一步该看哪里、什么情况下别急着下结论。排障最贵的不是不会敲命令，而是看到 CPU 高就重启、把现场冲掉之后再猜。

## 一、先建立顺序，再翻工具箱

```text
1. 确认影响面：哪些接口/用户/区域、什么时候开始、是否和发布相关
2. 保留现场：指标快照、pprof、线程栈、dmesg、抓包、日志上下文
3. 分层排除：CPU → 内存 → 磁盘 I/O → 网络/连接 → 下游依赖 → 应用自身
4. 形成假设并有数据支撑，改一处、验一次
5. 止损优先于根因：先回滚/限流/切流，事后再慢慢查
```

两个常用框架：**USE**（Utilization / Saturation / Errors，针对资源）和 **RED**（Rate / Errors / Duration，针对服务）。前者回答「机器哪块资源满了」，后者回答「哪个接口坏了、多慢」。

**先别重启**。重启会清掉连接状态、page cache、堆内存现场和进程内的计数，很多偶发问题重启后再也复现不了。至少先存下 `top`、`ss`、`dmesg`、应用 profile 和一份带时间窗的日志。

## 二、CPU：分清是谁在烧

```bash
top -H -p <pid>            # 线程级 CPU
pidstat -u 1               # 每个进程的 us / sy 拆分
vmstat 1                   # r 运行队列、cs 上下文切换、wa iowait
mpstat -P ALL 1            # 是否单核打满（单线程热点/中断不均衡）
perf top -p <pid>          # 内核/用户态热点函数
```

| 现象                | 通常含义                                      | 下一步                           |
| ------------------- | --------------------------------------------- | -------------------------------- |
| `us` 高             | 应用在算：序列化、正则、加解密、死循环        | 采 CPU pprof / perf，找热点函数  |
| `sy` 高             | 系统调用频繁：小包读写、大量连接、频繁 `stat` | `strace -c` 统计调用分布         |
| `wa` 高             | CPU 在等 I/O，不是 CPU 不够                   | 转去查磁盘（`iostat`）           |
| `si` 高             | 软中断，多在网络包处理                        | 看网卡队列、RPS/RSS、包量        |
| `r` 持续 > CPU 核数 | 运行队列积压                                  | 结合 `cs` 判断是否调度开销过大   |
| `cs` 暴涨           | 线程过多或锁竞争                              | 看线程数与 Go 的 `runtime/trace` |

**`wa` 高却去扩容 CPU 是经典误判**：真正瓶颈在磁盘或下游，扩 CPU 只会让空闲更多。同理，Go 服务 CPU 高要区分业务计算与 GC——`GODEBUG=gctrace=1` 或 pprof 的 `runtime.gcBgMarkWorker` 占比能直接给出答案。

## 三、内存：RSS、cache 与 OOM

```bash
free -m                    # 注意 available 而不是 free
vmstat 1                   # si/so 是否发生 swap
sar -r 1                   # 内存与 page cache 趋势
cat /proc/<pid>/smaps_rollup   # RSS / PSS / 共享内存拆分
dmesg -T | grep -i oom     # 是否被 OOM killer 干掉
```

| 概念       | 说明                                                    |
| ---------- | ------------------------------------------------------- |
| VSZ        | 虚拟地址空间，含未实际分配的映射，不能当占用            |
| RSS        | 常驻物理内存，含共享库，多进程相加会重复计              |
| PSS        | 按共享比例摊分，评估容器/多进程更准                     |
| Page cache | 内核缓存文件数据，可回收；`free` 看起来少不等于内存紧张 |
| Swap 使用  | `si/so` 持续非零说明真的在换页，延迟会剧烈抖动          |

Go 服务要区分**堆内存增长**与**运行时外内存**：`pprof` 的 `inuse_space` 看堆，若 RSS 远大于堆，可能是 `mmap`、cgo、大块 `[]byte` 未释放、或 glibc/内核页表开销。容器里还要对齐 cgroup 限制：`/sys/fs/cgroup/memory.max` 与 `memory.current`，宿主机 `free` 完全不能代表容器可用内存。

OOM 排查顺序：`dmesg -T` 确认是不是 OOM killer → 看当时谁占内存 → 区分「真泄漏」与「突发大请求/无界缓存」→ 检查 limit 是否合理。

## 四、磁盘 I/O：利用率不等于健康

```bash
iostat -x 1                # %util、await、r/s、w/s、aqu-sz
iotop -o                   # 哪个进程在写
df -h && df -i             # 空间与 inode 都可能耗尽
sar -d 1                   # 历史趋势
```

| 指标              | 判读                                                       |
| ----------------- | ---------------------------------------------------------- |
| `%util` 接近 100% | 设备饱和，但 SSD/NVMe 有并行度，单看它不准                 |
| `await` 明显升高  | 真正影响延迟的指标，含排队 + 服务时间                      |
| `aqu-sz` 大       | 请求队列堆积，配合 `await` 看                              |
| 写量突增          | 日志级别误开 debug、刷盘策略变更、LSM Compaction、备份任务 |
| `df -i` 满        | 小文件过多，空间还有但建不了新文件                         |

常见现场：磁盘「看起来没满」但服务报 `no space left on device`，多半是 inode 耗尽或某个被删除但仍被进程持有的大文件（`lsof +L1` 可查）。数据库场景还要区分业务写入与后台 Compaction/checkpoint 争抢 I/O。

## 五、网络与连接

```bash
ss -s                      # 连接总数与各状态汇总
ss -tanp state close-wait  # 谁没关连接
ss -ti dst <ip>            # 单条连接的 rtt、cwnd、重传
sar -n DEV 1               # 网卡 pps / 带宽
nstat -az | grep -i retrans # 重传计数
cat /proc/net/sockstat     # 内核 socket 内存与 orphan
tcpdump -i any -nn host <ip> -w /tmp/cap.pcap
```

| 现象                | 常见原因                                           |
| ------------------- | -------------------------------------------------- |
| `CLOSE_WAIT` 堆积   | 应用没关连接：HTTP body 未读未关、DB rows 未 Close |
| 大量 `TIME_WAIT`    | 主动关闭方正常表现；优先连接复用，别急着改内核参数 |
| SYN 重传 / 建连超时 | 握手队列满、防火墙丢包、后端不监听                 |
| 重传率上升          | 链路丢包或拥塞，先看物理/网络设备再怪应用          |
| `orphan` 高         | 应用已关闭但内核仍在等待，或存在大量未读数据       |

`ss -ti` 里的 `retrans`、`cwnd`、`rtt` 能区分「网络慢」和「对端不读」：cwnd 收缩加重传多为链路问题，而 `Recv-Q` 持续不降通常是对端应用处理不过来。

## 六、文件描述符与内核资源

```bash
ulimit -n                       # 进程限制
ls /proc/<pid>/fd | wc -l       # 当前占用
cat /proc/sys/fs/file-nr        # 系统级已分配/上限
lsof -p <pid> | awk '{print $5}' | sort | uniq -c | sort -rn | head
ps -eo pid,stat,wchan,cmd | awk '$2 ~ /D/'   # 不可中断睡眠
```

`too many open files` 的根因通常不是限制太低，而是**泄漏**：HTTP response body 没关、数据库 rows 没关、文件句柄放在缓存里没释放。`D` 状态进程多且 `wa` 高，指向存储或网络文件系统卡住，此时 `kill -9` 也杀不掉，别在业务高峰期硬来。

## 七、完整路径示例：接口 P99 抖动

```text
1. 看 RED：QPS 是否变化、错误率、P99 从何时开始 → 是否与发布/定时任务重合
2. 看资源 USE：CPU(us/sy/wa)、内存(si/so)、磁盘(await)、连接(ss -s)
3. wa 高 → iostat 确认是否 Compaction 或日志刷盘抢占
4. sy 高 + cs 高 → 查线程数、连接数、strace -c 看系统调用分布
5. 都正常 → 看下游：DB 慢查询、Redis 延迟、第三方 RT，别只盯本机
6. 应用侧采 pprof / trace，确认是 GC、锁竞争还是业务热点
7. 抓一段包确认是否有重传、握手排队、连接池等待
8. 改一处 → 对比 QPS、P99、错误率与资源曲线，确认假设成立
```

第 5 步最容易被跳过：本机一切正常时，瓶颈通常在下游。监控面板只有本机指标，会让团队在错误的机器上折腾很久。

## 八、常见误判表

| 误判                    | 正确理解                                   |
| ----------------------- | ------------------------------------------ |
| load 高 = CPU 不够      | load 含 D 状态任务，I/O 卡住也会很高       |
| `free` 少 = 内存不足    | page cache 可回收，要看 available 与 si/so |
| `%util` 100% = 磁盘坏了 | NVMe 有并行度，结合 `await` 和应用延迟判断 |
| CPU 高就扩容            | 先分清 us/sy/wa/GC，可能是死循环或锁竞争   |
| `TIME_WAIT` 多要改内核  | 多数是短连接设计问题，优先连接池与长连接   |
| 重启能解决就没事了      | 现场被冲掉，问题大概率会复发               |

## 九、实践清单

- 止损前先留现场：指标快照、pprof、线程栈、`dmesg -T`、抓包、带时间窗的日志。
- 每台机器有 USE 面板、每个服务有 RED 面板，时间轴对齐到同一时区。
- 容器按 cgroup 看内存与 CPU 配额，不用宿主机 `free`/`top` 下结论。
- 日志级别、慢查询、连接池指标要能按发布版本切分，方便关联变更。
- 常用命令固化成 runbook 脚本，避免故障时现想参数、误敲命令。
- 修复后验证三个指标：QPS、P99、错误率，以及对应的资源曲线，而不是看某个瞬时值下降。
- 定期演练：注入 CPU、I/O、网络延迟，确认监控和告警真的能发现问题。

## 十、面试速答

**Q：线上 CPU 100% 怎么排查？**
先留现场再动手：用 `top -H`/`pidstat` 确认是进程还是线程、是 `us` 还是 `sy`；`us` 高采应用 pprof 找热点，`sy` 高用 `strace -c` 看系统调用，`wa` 高转去查磁盘。同时关联发布与流量变化，止损优先（回滚/限流），修复后对比 QPS 与 P99。

**Q：load average 很高但 CPU 使用率不高？**
load 统计的是运行队列加不可中断睡眠任务，大量进程卡在磁盘 I/O、网络文件系统或锁上会推高 load。用 `vmstat` 看 `r`/`b` 列、`ps` 查 D 状态进程、`iostat` 看 `await`，不要按 CPU 饱和处理。

**Q：`CLOSE_WAIT` 堆积说明什么？**
对端已发 FIN，本端应用没有执行 close，通常是 HTTP response body 未读未关、数据库 rows/文件句柄泄漏。查 `lsof -p` 的句柄类型与代码里的资源释放路径，而不是调 TCP 参数。

## 十一、一句话收尾

命令只是采集器，价值在于**把「现象」翻译成某一层的「证据」**：先确定是哪类资源饱和，再验证假设，最后用 QPS、P99、错误率确认改动有效。别让一次重启把答案也一起清掉。
