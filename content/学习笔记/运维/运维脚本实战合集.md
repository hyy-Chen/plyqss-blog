> 前四篇讲命令、管道、脚本规范和系统托管，这篇把规则落到五个可以直接改用的脚本上：备份归档、健康检查自愈、磁盘水位保护、灰度发布与回滚、日志统计报表。每个脚本都带严格模式、日志、锁或幂等、超时、`DRY_RUN` 预演与明确退出码——**复杂脚本的复杂度应该花在这些护栏上，而不是花在嵌套判断里**。

## 一、共同约定

| 约定                                              | 原因                               |
| ------------------------------------------------- | ---------------------------------- |
| `set -Eeuo pipefail` + 固定 `PATH`                | cron / systemd 环境下行为可预期    |
| 日志走 stderr，带 UTC 时间戳与级别                | 不污染 stdout 数据，便于采集       |
| `DRY_RUN=1` 时只打印不执行                        | 上线前必做的预演                   |
| 删除类操作固定白名单路径                          | 变量拼错也不会删到别处             |
| 关键步骤 `if ! cmd; then ...` 显式判错            | 不迷信 `set -e`                    |
| 退出码：0 成功 / 2 参数 / 3 前置校验 / 4 执行失败 | 调度系统与告警能区分原因           |
| 上线前 `bash -n` + `shellcheck` + 预演            | 静态检查能抓出大部分引号与数组问题 |

以下脚本统一用 `run` 包装「写」动作：

```text
DRY_RUN=1 ./backup.sh order-api 14     # 先看会做什么
./backup.sh order-api 14               # 确认无误后再执行
```

## 二、备份归档与保留策略

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

app="${1:-order-api}"
keep_days="${2:-14}"
src="/data/${app}"
dest="/backup/${app}"
dry_run="${DRY_RUN:-0}"
ts="$(date -u +%Y%m%dT%H%M%SZ)"

log(){ printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}" >&2; }
run(){
  if [[ "$dry_run" == "1" ]]; then printf '[dry-run] '; fi
  printf '%q ' "$@"; printf '\n'
  [[ "$dry_run" == "1" ]] || "$@"
}

[[ -d "$src" ]] || { log ERROR "source missing: $src"; exit 3; }
run install -d -m 0750 "$dest"

archive="${dest}/${app}-${ts}.tar.gz"
if [[ "$dry_run" == "1" ]]; then
  log INFO "would archive $src -> $archive"
else
  tar czf "$archive" -C "$(dirname "$src")" "$(basename "$src")"
  sha256sum "$archive" > "${archive}.sha256"
  sha256sum -c "${archive}.sha256" > /dev/null
  log INFO "archive verified: $archive"
fi

run find "$dest" -maxdepth 1 -type f -name "${app}-*.tar.gz*" -mtime "+${keep_days}" -print -delete
log INFO "backup finished app=$app retention=${keep_days}d"
```

**关键点**：打包后立刻算并校验 `sha256`，把「备份文件其实写坏了」挡在保留策略之前；`-mtime +N` 只清理本 app 命名空间的归档；远端同步可以再加一步 `rsync -a "${dest}/" backup-host:/backup/${app}/`。真正重要的是**定期做恢复演练**，没验证过恢复的备份不算备份。

## 三、健康检查与自动拉起

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

unit="${1:-order-api}"
url="${2:-http://127.0.0.1:8080/health}"
threshold=3
state_dir="/var/lib/${unit}-health"
state="${state_dir}/failures"
lock="/var/lock/${unit}-health.lock"

log(){ printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}" >&2; }

exec 9>"$lock"
if ! flock -n 9; then log WARN "another probe is running, skip"; exit 0; fi
install -d -m 0750 "$state_dir"

failures=0
if [[ -f "$state" ]]; then failures="$(cat "$state")"; fi
[[ "$failures" =~ ^[0-9]+$ ]] || failures=0

if timeout 5s curl -fsS -o /dev/null "$url"; then
  printf '0\n' > "$state"
  log INFO "healthy unit=$unit"
  exit 0
fi

failures=$((failures + 1))
printf '%s\n' "$failures" > "$state"
log WARN "probe failed $failures/$threshold url=$url"
if ((failures < threshold)); then exit 0; fi

if ! timeout 30s systemctl restart "$unit"; then
  log ERROR "restart failed unit=$unit"
  exit 4
fi
printf '0\n' > "$state"
log WARN "restarted unit=$unit after $failures consecutive failures"
```

**关键点**：连续失败阈值避免单次网络抖动就重启；`flock -n` 防止上一轮没结束又拉起一轮；`timeout` 保证探针和重启都不会挂死；state 文件持久化失败计数，重启成功后清零。**自愈脚本必须限次**——否则服务本身有配置错误时，它会变成一台无限重启的机器，需要配合 systemd 的 `StartLimitBurst`。

## 四、磁盘水位保护与日志清理

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

mount_point="${1:-/data}"
threshold="${2:-85}"
clean_dir="/data/app/logs"
dry_run="${DRY_RUN:-0}"

log(){ printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}" >&2; }

case "$clean_dir" in
  /data/app/logs) ;;
  *) log ERROR "refuse to clean unexpected path: $clean_dir"; exit 3 ;;
esac
[[ -d "$clean_dir" ]] || { log ERROR "clean dir missing"; exit 3; }

usage="$(df -P "$mount_point" | awk 'NR==2 {gsub(/%/,"",$5); print $5}')"
[[ "$usage" =~ ^[0-9]+$ ]] || { log ERROR "cannot read usage for $mount_point"; exit 3; }
log INFO "usage=${usage}% threshold=${threshold}%"
if ((usage < threshold)); then exit 0; fi

before="$(du -sh "$clean_dir" | awk '{print $1}')"
if [[ "$dry_run" == "1" ]]; then
  find "$clean_dir" -maxdepth 1 -type f -name '*.log' -mtime +7 -print
else
  find "$clean_dir" -maxdepth 1 -type f -name '*.log' -mtime +7 -print -delete
fi
after="$(du -sh "$clean_dir" | awk '{print $1}')"
log INFO "cleaned $clean_dir from $before to $after"
```

**关键点**：先把可清理路径写成 `case` 白名单，再校验目录存在与水位是合法数字，最后才允许 `find -delete`；`-maxdepth 1` 限制范围，`-name '*.log'` 限制类型。清理前后记录 `du` 便于复盘。生产上更稳的做法是让应用日志走 logrotate，脚本只做兜底。

## 五、灰度发布与失败回滚

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

release="${1:?usage: deploy.sh RELEASE_ID}"
hosts_file="${2:-/etc/ops/hosts.txt}"
artifact="/data/releases/${release}.tar.gz"
link="/data/app/current"
batch=2
dry_run="${DRY_RUN:-0}"

log(){ printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}" >&2; }
run(){
  if [[ "$dry_run" == "1" ]]; then printf '[dry-run] '; fi
  printf '%q ' "$@"; printf '\n'
  [[ "$dry_run" == "1" ]] || "$@"
}

[[ -f "$artifact" ]] || { log ERROR "artifact missing: $artifact"; exit 3; }
[[ -f "$hosts_file" ]] || { log ERROR "hosts file missing: $hosts_file"; exit 3; }
mapfile -t hosts < "$hosts_file"
if ((${#hosts[@]} == 0)); then log ERROR "empty host list"; exit 3; fi

rollback(){
  local h
  for h in "$@"; do
    log WARN "rollback on $h"
    run ssh "$h" "ln -sfn /data/releases/previous ${link}"
  done
}

for ((i = 0; i < ${#hosts[@]}; i += batch)); do
  batch_hosts=("${hosts[@]:i:batch}")
  for h in "${batch_hosts[@]}"; do
    log INFO "deploy release=$release host=$h"
    run ssh "$h" "mkdir -p /data/releases"
    run rsync -a "$artifact" "$h:/data/releases/"
    run ssh "$h" "ln -sfn /data/releases/${release} ${link}"
    if [[ "$dry_run" == "1" ]]; then continue; fi
    if ! timeout 20s curl -fsS -o /dev/null "http://${h}:8080/health"; then
      log ERROR "health check failed on $h"
      rollback "${batch_hosts[@]}"
      exit 4
    fi
  done
  log INFO "batch ok: ${batch_hosts[*]}"
done
log INFO "deploy finished release=$release hosts=${#hosts[@]}"
```

**关键点**：按批次推进、每批健康检查通过才继续；失败时只回滚当前批次，避免放大影响面；用 `ln -sfn` 原子切换软链实现「部署」与「生效」分离，回滚就是把链接指回上一版本。`mapfile` 读主机列表时记得过滤空行与注释；真实环境还应先摘流、并在切换后验证业务指标而不只是 `/health`。

## 六、日志统计报表

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
export LC_ALL=C
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

log_file="${1:?usage: report.sh ACCESS_LOG}"
out_dir="${2:-/var/reports}"
top_n="${3:-10}"

[[ -r "$log_file" ]] || { echo "unreadable: $log_file" >&2; exit 3; }
[[ "$top_n" =~ ^[0-9]+$ ]] || { echo "invalid top_n" >&2; exit 2; }
install -d -m 0750 "$out_dir"

ts="$(date -u +%Y%m%dT%H%M%SZ)"
out="${out_dir}/report-${ts}.csv"
{
  printf 'metric,key,value\n'
  awk '{total++; if ($9 ~ /^5/) err++}
       END{printf "requests,total,%d\nerrors,5xx,%d\n", total+0, err+0}' "$log_file"
  awk '$9 ~ /^5/ {c[$7]++} END{for (k in c) print c[k], k}' "$log_file" \
    | sort -rn | awk -v n="$top_n" 'NR<=n {printf "top5xx,%s,%s\n", $2, $1}'
  awk '{c[$1]++} END{for (k in c) print c[k], k}' "$log_file" \
    | sort -rn | awk -v n="$top_n" 'NR<=n {printf "topip,%s,%s\n", $2, $1}'
} > "$out"

printf 'report written: %s\n' "$out"
```

**关键点**：用 `awk` 关联数组一次扫描完成聚合，再交给 `sort` 得到稳定顺序；`awk -v n=... 'NR<=n'` 而不是 `head`，避免 `pipefail` 下 `head` 提前关闭管道引发 SIGPIPE 让脚本误判失败；`LC_ALL=C` 固定排序口径；输出带 UTC 时间戳的 CSV 便于归档与对比。

## 七、上线前检查清单

```text
1. bash -n script.sh                   语法
2. shellcheck script.sh               引号、数组、可移植性
3. DRY_RUN=1 ./script.sh ...          完整预演，逐条读输出
4. 确认删除/覆盖范围：白名单、绝对路径、maxdepth、文件后缀
5. 确认锁、超时、重试上限与失败退出码
6. 确认日志不含密钥、令牌、完整请求体
7. 确认回滚路径可用（备份可恢复、软链可回指）
8. 小范围单机执行，观察日志与业务指标
9. 接入 systemd timer / cron，观察至少两个周期
10. 写进 runbook：用途、参数、退出码、谁有权执行
```

## 八、危险操作护栏

| 风险                 | 护栏                                        |
| -------------------- | ------------------------------------------- |
| 变量为空导致删根目录 | `${VAR:?}` + 白名单 `case` + 存在性校验     |
| 并发重入             | `flock -n` + 幂等动作                       |
| 外部命令挂死         | 一律加 `timeout`，重试有上限                |
| 半截文件             | 临时文件 + 校验 + `mv`/`ln -sfn` 原子替换   |
| 误把部分失败当成功   | `set -o pipefail` + 关键步骤显式判返回值    |
| 无限重启 / 无限重试  | 连续失败阈值 + `StartLimitBurst` + 退避上限 |
| 密钥泄露             | 不进命令行、不进日志、配置文件 600 权限     |
| 改完没人知道         | 日志带时间戳，runbook 记录参数与退出码      |

## 九、面试速答

**Q：备份脚本里为什么要算 sha256？**
打包成功不代表内容完整（磁盘满、中断、静默损坏），生成校验文件并在同一次运行里 `sha256sum -c` 能立刻发现坏归档；但校验只证明「文件没坏」，能否恢复还要靠定期恢复演练。

**Q：自愈脚本怎么避免把故障放大？**
连续失败阈值 + 非阻塞锁 + 重启超时 + 重启次数上限（配合 systemd `StartLimitBurst`），并在重启后重新清零状态；否则配置错误会导致无限重启，日志与资源都被打满。

**Q：批量发布脚本失败时为什么只回滚当前批次？**
全量回滚成本高且会波及已验证成功的主机；按批次推进时，失败点之前的批次已通过健康检查，只需把当前批次指回上一版本，同时停止后续批次并告警。

## 十、一句话收尾

复杂脚本的价值不在逻辑多精巧，而在于**每一步都能被预演、被限制、被追溯**：先想清楚「最坏情况下它会做什么」，再决定要不要写那一行 `rm`。
