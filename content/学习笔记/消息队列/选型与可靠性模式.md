> 已有笔记讲过 Kafka 的分区、副本与消费组，本文换个视角：不谈某个产品的内部实现，只谈**一条消息从生产到消费结束，中间会在哪些地方丢、重复、乱序，以及怎么用模式兜住**。最后给一张选型对照表。

## 一、先确认真的需要消息队列

| 目标     | 消息队列能做什么                 | 代价                          |
| -------- | -------------------------------- | ----------------------------- |
| 解耦     | 生产者不感知消费者数量与部署     | 链路变长，排障需要 trace 串联 |
| 削峰     | 把突发流量沉淀成可匀速消费的积压 | 处理延迟上升，需要监控 lag    |
| 异步     | 非关键路径后台化，缩短接口耗时   | 结果不能同步返回，需查询状态  |
| 可靠投递 | 重试、持久化、死信兜底           | 至少一次投递，必须做幂等      |

不需要的场景别硬加：两个服务之间简单同步调用、要求立即拿到结果、或数据量极小且可以本地事务解决时，引入 MQ 只是多一个要运维的有状态系统。

## 二、统一概念

不同产品的名词不同，但模型基本一致：

| 概念     | Kafka                | RabbitMQ           | 含义                 |
| -------- | -------------------- | ------------------ | -------------------- |
| 消息通道 | Topic / Partition    | Exchange / Queue   | 消息的分类与存储单位 |
| 并行单位 | 分区数               | 队列/消费者数      | 决定消费并行度上限   |
| 消费进度 | offset（消费组管理） | ack 后删除         | 决定「处理到哪了」   |
| 顺序保证 | 分区内有序           | 单队列单消费者有序 | 全局有序代价极高     |
| 失败兜底 | 无内置死信，需自建   | DLX 死信交换机     | 反复失败的消息隔离   |

一个关键差异：**Kafka 的消息被消费后不会删除**（按保留期或容量清理），同一条消息可被多个消费组重复读；传统队列 ack 后即删除。这决定了 Kafka 更适合「事件流 + 回放」，RabbitMQ 更适合「任务分发 + 逐条确认」。

## 三、三种投递语义

| 语义     | 含义                         | 典型实现                              |
| -------- | ---------------------------- | ------------------------------------- |
| 至多一次 | 可能丢，绝不重复             | 发送不重试、先提交位点再处理          |
| 至少一次 | 绝不丢（正常情况），可能重复 | 处理成功后再提交位点/ack              |
| 恰好一次 | 效果上不丢不重               | 至少一次 + 消费端幂等，或事务型端到端 |

「恰好一次」很少是 MQ 单独提供的能力。Kafka 的幂等生产者与事务只覆盖「写 Kafka」这一段，一旦消费者把结果写进数据库或调用外部服务，就超出了 MQ 的边界。工程上的标准答案是：

```text
至少一次投递 + 消费端幂等 = 业务效果的恰好一次
```

因此可靠性设计的核心不是选一个「支持 exactly-once」的产品，而是把**幂等做在业务边界上**：唯一索引、去重表、状态机、幂等键，且去重记录的写入必须与业务状态更新在同一个本地事务里。

## 四、三段链路的丢失点

```text
[生产者]            [Broker]              [消费者]
 构造消息  →  网络发送  →  落盘/复制  →  拉取  →  业务处理  →  提交进度
   │            │            │           │          │            │
 本地事务     超时未知     副本未同步   重复拉取   处理崩溃    提交失败
 未提交       重试/丢弃    宕机丢数据   重复投递   状态已改    重复消费
```

| 环节   | 常见丢失原因                             | 对策                                             |
| ------ | ---------------------------------------- | ------------------------------------------------ |
| 生产   | 异步发送未等确认、本地事务回滚但消息已发 | Outbox / 事务消息、确认 `acks=all`、处理发送超时 |
| Broker | 单副本宕机、刷盘策略过松、保留期过短     | 多副本 + 最小同步副本数、合理保留期与监控        |
| 消费   | 先提交位点再处理、处理失败直接跳过       | **处理成功后再提交**、失败进重试/死信            |
| 全链路 | 没有 lag 与对账，丢了几小时才发现        | 端到端 trace、对账任务、积压告警                 |

最容易犯错的是消费顺序：先 ack 后处理，崩溃就永久丢消息；先处理再 ack，崩溃就重复消费。两者只能选后者，再用幂等消化重复。

## 五、重复、顺序与并发

### 1. 幂等落库

```sql
CREATE TABLE consumed_msg (
  msg_id     VARCHAR(64) NOT NULL,
  biz_type   VARCHAR(32) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (msg_id, biz_type)
);
```

```text
BEGIN;
  INSERT INTO consumed_msg ...   -- 冲突即视为已处理，直接返回成功
  UPDATE orders SET status = ... WHERE id = ? AND status = ...;
COMMIT;
```

「先查有没有处理过，再写业务」在并发下会漏判，必须靠唯一约束或状态机的条件更新原子判定。

### 2. 顺序的三个层次

1. **全局有序**：几乎总要牺牲吞吐（单分区单消费者），能不用就不用。
2. **分区内有序**：同一业务键（订单 ID、用户 ID）路由到同一分区，是实践中最常用的方案。
3. **因果关系有序**：用版本号或状态机容忍乱序，例如收到「已发货」时若状态仍是「已创建」，先落事件再等待补单，或直接拒绝并重试。

**顺序与重试天然冲突**：某条消息失败后重试，后面的消息要么全部阻塞（保序但积压），要么继续消费（乱序）。常见做法是把失败消息放进按业务键隔离的重试主题，只阻塞同一个键的后续消息，而不是阻塞整个分区。

## 六、重试、退避与死信

```text
主主题 → 消费失败 → 重试主题（分级延迟：10s / 1m / 10m）→ 仍失败 → 死信主题
                                                              ↓
                                                    告警 + 人工排查 + 回放工具
```

要点：

- **退避 + 抖动**，避免下游恢复瞬间被重试流量再次打垮。
- **设置最大重试次数和总时长**，无限重试会让一条脏消息占住分区。
- **死信消息要保留原始载荷、失败原因、trace ID、重试次数**，并能按业务键回放。
- **区分可重试与不可重试错误**：参数格式错误、权限不足重试一万次也不会成功，应直接进死信；网络超时、5xx、限流才重试。
- 重试主题要有独立监控，`lag` 长期不降说明下游存在系统性问题，而不是偶发抖动。

## 七、积压（lag）排查

`lag = 最新位点 - 当前消费位点`，它表示「还差多少条」，但真正该看的是**按当前消费速率需要多久追平**（lag / 每秒消费条数）。

排查顺序：

1. 判断是**生产突增**还是**消费变慢**：对比生产速率与消费速率曲线。
2. 消费变慢时看下游：数据库慢查询、外部接口超时、锁竞争、GC 暂停、单条消息处理耗时分布。
3. 看并行度是否已到上限：Kafka 的消费者数不能超过分区数；盲目加实例无效，需要先扩分区（注意扩分区会改变 key → 分区映射，影响顺序）。
4. 临时止血：扩容消费者至分区上限、关掉非核心消费逻辑、对可合并的消息做批量处理、必要时降级为抽样处理并事后补跑。
5. 长期方案：按业务拆分主题、提高单条处理效率、批量写库、为热点业务键单独分区。

积压时不要直接把位点跳到最新——那等于确认「这些消息已经处理过」，会造成静默丢数据。要跳过必须有明确的业务授权与可追溯记录。

## 八、事务消息与 Outbox

「写数据库 + 发消息」的可靠做法（与分布式事务笔记呼应）：

| 方案     | 做法                                       | 适用                           |
| -------- | ------------------------------------------ | ------------------------------ |
| Outbox   | 业务数据与消息同事务写本地表，独立进程投递 | 通用、不依赖 MQ 特性           |
| 事务消息 | 半消息 → 本地事务 → 确认/回查              | MQ 原生支持（如 RocketMQ）     |
| CDC      | 订阅 binlog 把变更转成事件                 | 已有数据同步链路、不改业务代码 |

三者都只保证「消息最终会被投递」，消费端幂等和对账仍然不可省。消息体尽量只放**业务 ID 与事件类型**，让消费者回查最新状态，避免消息里的快照过期后造成状态倒退。

## 九、选型对照

| 维度       | Kafka                  | RocketMQ       | RabbitMQ           | Pulsar                |
| ---------- | ---------------------- | -------------- | ------------------ | --------------------- |
| 定位       | 事件流/日志            | 业务消息       | 任务队列/路由      | 云原生分层存储        |
| 吞吐       | 极高                   | 高             | 中                 | 高                    |
| 延迟       | 毫秒～十几毫秒         | 毫秒级         | 微秒～毫秒级       | 毫秒级                |
| 顺序       | 分区内有序             | 队列内有序     | 队列内有序         | 分区内有序            |
| 延迟消息   | 需自行实现             | 原生支持       | 插件/TTL+死信      | 支持                  |
| 事务消息   | 有限（写 Kafka 内）    | 原生支持       | 不原生             | 有限                  |
| 回放       | 天然支持               | 按保留期支持   | 不支持             | 支持                  |
| 运维复杂度 | 中（含 KRaft/ZK 演进） | 中             | 低                 | 较高（含 BookKeeper） |
| 典型场景   | 日志、埋点、流处理     | 订单、交易事件 | 异步任务、复杂路由 | 多租户、存算分离      |

选型先问四个问题：要吞吐还是要低延迟、要不要按业务键严格有序、要不要延迟消息与事务消息、团队能否运维这套有状态集群。多数中等规模业务用 RabbitMQ 或 RocketMQ 反而比 Kafka 省心；只有当数据要被多方反复消费或接流处理时，Kafka 的优势才不可替代。

## 十、Go 消费骨架

```go
func (c *Consumer) handle(ctx context.Context, msg Message) error {
    // 1. 幂等：去重表与业务更新在同一事务
    // 2. 处理成功后才提交位点
    if err := c.svc.Apply(ctx, msg); err != nil {
        return err // 不提交，交给重试/死信
    }
    return c.commit(ctx, msg.Offset)
}
```

要点：`ctx` 贯穿处理与提交，服务关闭时先停止拉取、等待在途消息处理完再退出；单条处理要有超时，避免一条卡死的消息占住整个分区；提交位点失败要能容忍重复消费（幂等再次兜底）。批量拉取时，`commit` 的位点应是**连续已成功的最大位点**，不能因为第 100 条成功就提交到第 100 条而跳过中间失败的第 50 条。

## 十一、实践清单

1. 明确每段链路的投递语义，默认按「至少一次 + 幂等」设计。
2. 消息带全局唯一 ID、事件类型、产生时间、trace ID 和版本号。
3. 消费端去重与业务状态更新同事务，先处理再提交进度。
4. 重试分级退避，死信可查、可告警、可回放，区分可重试错误。
5. 监控 lag 与「预计追平时间」，而不只是条数。
6. 顺序需求按业务键收敛到分区，评估重试与顺序的冲突。
7. 扩容前确认并行度上限（分区数），不要只加消费者实例。

## 十二、面试速答

**问：如何保证消息不丢？** 分三段看：生产端用 Outbox/事务消息并等待确认，Broker 用多副本与合理刷盘、保留策略，消费端处理成功后再提交位点并配重试死信；最后靠对账发现长尾问题。

**问：消息重复怎么处理？** 默认接受至少一次投递，在消费端用唯一索引去重表或状态机做幂等，去重写入与业务更新放同一事务，避免先查后写的并发漏判。

**问：积压怎么处理？** 先区分生产突增还是消费变慢，再看下游瓶颈与并行度上限（分区数）；临时扩容到分区上限并降级非核心逻辑，长期优化单条处理耗时或拆分主题，不要直接跳位点。
