> 本文以 Apache Kafka 3.x 的 KRaft 架构为背景。Kafka 的核心是可分区、可持久化、可复制的追加日志，而不仅是“消息队列”。

## 一、核心模型

Topic 是逻辑主题，Partition 是其有序、只追加的日志分区。每条消息在分区内拥有递增的 offset；Kafka 只承诺分区内有序，不保证跨分区全局有序。Broker 保存分区副本，Controller 负责集群元数据和领导者变更。

```text
Producer → Topic 的某个 Partition → Leader 副本 → Follower 副本
                                              │
Consumer Group ← 按分区分配 Consumer ← 提交消费 offset
```

一个消费组内，一个分区同一时刻仅分配给一个 Consumer；Consumer 数量超过分区数时会有成员空闲。吞吐扩展通常依靠增加分区，但分区数不宜无限增加，因为元数据、文件句柄和故障恢复也会增加。

## 二、日志存储与高吞吐来源

### 1. 分段日志与索引

分区日志按 Log Segment 切分，每个段通常包含 `.log`、offset 索引和时间戳索引文件。消息按批次顺序写入活跃段，达到大小或时间阈值后滚动出新段。通过稀疏索引先定位近似文件位置，再顺序扫描，可避免为每条消息建立昂贵索引。

Kafka 的高吞吐来自顺序 I/O、批量写入、压缩和零拷贝等组合：生产者将多条消息聚合成 Record Batch；Broker 顺序追加；消费者可通过 `sendfile` 类机制将页缓存数据直接发送到网络，减少用户态拷贝。

### 2. 保留与压缩

日志保留以时间或大小为界，到期段被删除。日志压缩（`cleanup.policy=compact`）保留每个 key 的最新值，适合变更日志、配置或状态主题；墓碑消息可用于删除 key。`delete` 与 `compact` 可以组合，但压缩不等于实时去重，也不保证历史记录立即消失。

## 三、生产、复制与可靠性

生产者根据 key 的哈希或分区器选择分区，批量发送到该分区 Leader。`acks` 定义确认强度：

| 设置       | 语义                                       |
| ---------- | ------------------------------------------ |
| `acks=0`   | 不等待确认，可能无感知丢失                 |
| `acks=1`   | Leader 写入即确认，Leader 随即故障可能丢失 |
| `acks=all` | 等待 ISR 中副本确认，可靠性最高            |

ISR（in-sync replicas）是与 Leader 保持足够同步的副本集合。设置 `acks=all` 时，`min.insync.replicas` 决定最少可确认副本数；例如副本数为 3、`min.insync.replicas=2`，可容忍一个同步副本故障而仍安全写入。

启用幂等生产者后，Broker 以 producer ID、epoch 和序列号去重，能够避免网络重试导致的同一分区重复写入。它解决生产端重试重复，不自动使“消费后写数据库”等跨系统流程恰好一次。

## 四、消费组、offset 与事务

Consumer 主动拉取数据，利用 `fetch.min.bytes`、`fetch.max.wait.ms` 等参数在延迟和吞吐间取舍。消费进度 offset 通常提交到内部主题 `__consumer_offsets`，而非保存在消息本体中。

重平衡期间，分区会在消费者间重新分配；未及时提交 offset 或处理时间超过 `max.poll.interval.ms` 都可能造成重复消费。业务应设计幂等处理，例如用业务唯一键去重或使用数据库唯一约束。

Kafka 事务能原子地写入多个分区，并把“消费输入 + 生产输出 + 提交 offset”组成 read-process-write 流程。下游使用 `isolation.level=read_committed` 才会过滤未提交或已中止事务的记录。端到端恰好一次仍取决于外部副作用是否能参与同一原子边界。

## 五、KRaft、故障与扩容

KRaft 使用 Controller quorum 保存元数据，替代早期依赖 ZooKeeper 的模式。Controller 负责选举分区 Leader、处理 Broker 注册和元数据变更；数据副本仍由各 Broker 的复制协议维护。

Broker 故障时，Controller 从 ISR 选择新 Leader；若允许从非 ISR 副本选举（`unclean.leader.election.enable=true`），可优先恢复可用性，却可能丢失已确认以外的数据。生产集群通常保持其为 `false`。

扩容新 Broker 不会自动均匀迁移历史分区，需要执行分区副本重分配。增加分区也不会重新哈希旧消息，若 key 的同分区有序性是业务约束，应在设计时预留容量。

## 六、常见误区与排查

1. 分区是并行度与顺序性的边界；不能通过增加 Consumer 获得超过分区数的并行消费。
2. `acks=all` 需配合合理的副本数和 `min.insync.replicas` 才有意义。
3. Kafka 默认至少一次语义很常见，消费者必须能处理重复。
4. 消息过大降低批处理效率并增加 GC、复制与恢复负担；大对象宜放对象存储，消息保存引用和元数据。

重点观察 consumer lag、UnderReplicatedPartitions、ISR 变化、请求延迟、磁盘使用率与 Controller 事件。排查积压时先区分“生产太快、消费太慢、重平衡频繁、下游阻塞”四类原因。
