> 事件循环解决「一台机器怎么同时管很多连接」，这一篇解决「连接之上怎么可靠地说话」：帧怎么定、请求怎么对上响应、断线怎么恢复、连接怎么复用，以及百万长连接时哪些地方会先撑不住。

## 一、为什么长连接值得做

每次新建短连接都要付出：三次握手 1 个 RTT、TLS 握手 1～2 个 RTT、TCP 慢启动重新探测带宽、服务端 accept 与连接对象分配。对高频小请求，这些固定成本可能远大于业务处理本身。

```text
短连接：握手 + TLS + 慢启动 + 请求 + 关闭   ← 每次重复
长连接：握手 + TLS + 一次慢启动 → 请求 × N → 关闭
```

代价是服务端要长期持有连接状态：fd、读写缓冲、会话信息、心跳定时器。因此长连接不是「越多越好」，而是要在**建连成本**与**常驻资源**之间取平衡；内部 RPC、推送、IM、物联网适合长连接，低频的公开 HTTP 接口用连接池复用即可。

## 二、协议帧设计

TCP 只提供字节流，帧是应用层自己定义的消息边界。一个可用的私有协议头通常包含：

| 字段             | 作用                      | 设计要点                 |
| ---------------- | ------------------------- | ------------------------ |
| magic            | 快速识别非法流量/端口扫描 | 固定 2～4 字节           |
| version          | 协议演进                  | 不支持的版本直接拒绝     |
| type             | 请求/响应/心跳/错误/推送  | 决定后续解析方式         |
| request_id / seq | 关联请求与响应、检测乱序  | 单调递增，连接内唯一     |
| length           | payload 长度              | **先校验上限再分配内存** |
| flags            | 压缩、加密、是否分片      | 位标志，便于扩展         |
| checksum         | 可选完整性校验            | 已有 TLS 时可省略        |

```text
+--------+---------+--------+------+--------+-----------+----------+
| magic  | version | type   | seq  | length |  flags    | payload  |
| 2B     | 1B      | 1B     | 8B   | 4B     | 2B        | N bytes  |
+--------+---------+--------+------+--------+-----------+----------+
                     固定头 = 18B，网络字节序（大端）
```

分帧方式对比：

| 方式     | 优点                     | 缺点                         |
| -------- | ------------------------ | ---------------------------- |
| 长度前缀 | 解析快、易预分配         | 长度字段损坏需重新同步       |
| 分隔符   | 人可读、实现简单         | payload 需转义，二进制不友好 |
| TLV      | 扩展性好、可跳过未知字段 | 头部开销略大                 |

三个硬性约束：

1. **固定头先校验**：magic、version、`length <= MAX_FRAME` 全部通过后再为 payload 分配内存。否则一个伪造的大 length 就能打爆服务端。
2. **统一字节序与整数宽度**：跨语言时最容易出错的地方，协议文档要写明。
3. **支持半帧与多帧**：一次 `read` 可能是半个帧或几十个帧，解析器要能被反复调用并保留中间状态（参见事件循环笔记里的解析状态机）。

## 三、请求与响应如何对上

长连接上请求可以并发（流水线），响应可能乱序返回，因此必须用 `request_id` 关联：

```text
客户端维护 pending map: request_id → {chan, deadline}
发送时写入 map，收到响应按 id 取出并唤醒调用方
定时器扫描超时项，从 map 移除并向上返回超时
```

要点：

- `request_id` 只需**连接内唯一**；重连后可以重新从 1 开始，但要确保旧连接的所有在途请求都已结束，否则可能错配。
- 每个请求必须有独立超时，不能依赖「连接还在」来推断请求还有效。
- 超时后服务端可能仍会处理完并回包，客户端收到未知 id 的响应应直接丢弃；业务是否可重试取决于幂等性。
- 服务端推送（无对应请求）用独立的 type 与通道，不要复用响应路径。
- `pending map` 要有上限，防止调用方无限发请求而不读取响应导致内存增长——这是长连接上的**应用层背压**。

## 四、心跳与保活

| 维度             | 建议                                                     |
| ---------------- | -------------------------------------------------------- |
| 间隔             | 30～60s，且必须小于 NAT/LB 的空闲回收时间                |
| 判定死亡         | 连续 N 次（如 3 次）无响应才断开，容忍偶发丢包           |
| 谁发起           | 通常客户端发，服务端回；双向心跳要避免同时探测造成浪费   |
| 心跳内容         | 极小固定帧，可携带负载/版本等轻量状态，不要塞业务数据    |
| 时钟             | 用单调时钟计算超时，避免系统时间被 NTP 校正后误判        |
| 与 TCP keepalive | 二者不互相替代，前者确认业务进程可用，后者只看内核协议栈 |

一个容易忽略的点：心跳间隔会让**所有客户端在同一时刻一起发包**（心跳风暴）。重连或启动时给间隔加随机抖动，把峰值摊平。

## 五、重连与状态恢复

```text
断开 → 指数退避 + 抖动重连 → 重新握手/认证 → 会话恢复 → 续传/补拉
```

设计要点：

- **退避 + 抖动**：服务端重启后，所有客户端同时重连会瞬间打满 accept queue；`base * 2^n + random(0, jitter)` 是必需的。
- **在途请求**：重连后不能盲目重发所有请求。可安全重试的只有幂等操作，写操作要带幂等键；更稳妥的做法是让业务层用「查询状态」确认上次结果。
- **会话恢复**：用 token 恢复订阅关系、鉴权状态与位点（如消息 offset），避免让客户端重新拉取全量数据。
- **序列号与去重**：跨连接用全局递增 seq 或业务幂等键，防止重连期间重复投递。
- **认证与过期**：长连接建立时鉴权一次不代表永久有效，权限变更、token 过期要有主动踢连接的机制。

## 六、连接复用与多路复用

| 方案                | 并发模型                  | 主要限制                 |
| ------------------- | ------------------------- | ------------------------ |
| HTTP/1.1 keep-alive | 一条连接串行处理请求      | 队头阻塞，常需连接池并行 |
| HTTP/1.1 pipelining | 可连发但响应必须按序返回  | 实践中很少使用           |
| HTTP/2              | 单连接多路复用多个 stream | TCP 层丢包仍会阻塞所有流 |
| gRPC streaming      | 基于 HTTP/2 的双向流      | 需处理流级流控与生命周期 |
| HTTP/3 / QUIC       | 基于 UDP，流级独立可靠性  | 运维与中间设备兼容性     |

连接池参数要和长连接策略一起设计：最小/最大连接数、空闲回收时间、借出超时、健康检查、每连接最大并发请求数（HTTP/2 的 `SETTINGS_MAX_CONCURRENT_STREAMS`）。连接池过小会排队，过大则把服务端的 accept queue 和内存吃满。

**队头阻塞**是选型的关键：HTTP/2 解决了应用层的串行等待，但底层仍是一条 TCP 字节流，一个丢包会让所有 stream 一起等重传；QUIC 把可靠性做到流级，才真正隔离。因此弱网、移动端、跨地域场景 HTTP/3 收益更明显。

## 七、TLS 与握手成本

- 会话复用（`session ticket` / TLS 1.3 PSK）能把重连的握手 RTT 降下来，长连接服务应启用。
- TLS 1.3 的 **0-RTT 存在重放风险**：只有幂等请求（如 GET）才允许携带 early data，写操作必须等握手完成。
- 证书链过长会增加握手字节数和首包延迟；OCSP stapling 可减少客户端额外查询。
- TLS 在负载均衡器终止（卸载）时，内网链路的加密边界、mTLS 身份认证、以及 `X-Forwarded-Proto` 透传要明确。
- 开启 TLS 后很多内核零拷贝路径不再适用，性能测试要在真实加密链路上做。

## 八、百万长连接：先算资源

假设每连接常驻：读缓冲 4KB + 写缓冲 4KB + 协议对象与 TLS 状态约 8KB ≈ 16KB，100 万连接约 **16GB**，还没算内核 socket 缓冲与应用框架开销。真实项目常按 20～50KB/连接估算。

| 瓶颈     | 检查与对策                                                                      |
| -------- | ------------------------------------------------------------------------------- |
| fd 上限  | `ulimit -n`、systemd `LimitNOFILE`，留余量给日志与磁盘文件                      |
| 内存     | 按需分配缓冲（空闲连接不预占大缓冲）、压缩对象、避免每连接一个 goroutine 栈过大 |
| 心跳风暴 | 抖动、分层心跳、只在活跃窗口探测                                                |
| 事件循环 | 单 Reactor 处理不过来就按 CPU 核数分多个，fd 固定归属                           |
| 内核参数 | `somaxconn`、`ip_local_port_range`、`tcp_mem`、conntrack 表容量                 |
| 优雅关闭 | 分批断连，避免同时唤醒百万连接造成 CPU 尖峰与客户端同时重连                     |

压测要注意：客户端自身也受端口与 fd 限制，通常需要多台压测机；还要模拟「大量空闲 + 少量活跃」的真实分布，否则测不出心跳和定时器的问题。

## 九、可观测性

| 指标                      | 为什么需要                             |
| ------------------------- | -------------------------------------- |
| 在线连接数（按版本/地域） | 容量与发布验证                         |
| 建连成功率与握手耗时      | 发现 accept queue、证书、DNS 问题      |
| 心跳超时与重连率          | 判断中间设备回收、网络质量、客户端实现 |
| 帧解析错误数              | 协议不兼容、恶意流量、长度字段损坏     |
| 在途请求数与超时分布      | 应用层背压与下游健康度                 |
| 每连接读写队列长度        | 慢客户端与内存风险                     |
| 分位延迟（P50/P95/P99）   | 区分网络抖动与业务处理变慢             |

给每个连接分配唯一 ID 并贯穿日志与 trace，才能把「某条连接上的某次请求」串起来——长连接排查最难的从来是定位，不是修复。

## 十、实践清单

1. 帧协议固定头先验 magic/version/length 上限，统一字节序，解析状态可重入。
2. 每个在途请求有 `request_id`、独立超时和上限，响应乱序靠 id 关联。
3. 心跳间隔小于中间设备回收时间，加抖动，连续失败才判定死亡。
4. 重连带退避抖动，用幂等键或状态查询处理在途请求，用 token 恢复会话。
5. 连接池大小、每连接并发流、空闲回收一起配置，并监控排队时间。
6. 上线前按 20～50KB/连接估算内存，压测「大量空闲 + 少量活跃」与「服务端重启后集中重连」。

## 十一、面试速答

**问：长连接上如何把响应对应到请求？** 每个请求带连接内唯一的 `request_id`，客户端维护 `id → pending` 映射并设超时；响应按 id 唤醒对应调用方，超时项清理，未知 id 的迟到响应直接丢弃。

**问：心跳为什么不能只靠 TCP keepalive？** 默认 keepalive 空闲 2 小时才探测，且只确认内核协议栈可达，无法判断业务进程是否卡死；应用层心跳还能承载状态并适配中间设备更短的空闲回收时间。

**问：HTTP/2 多路复用还有队头阻塞吗？** 应用层没有，但底层仍是单条 TCP 字节流，一个丢包会让所有 stream 等待重传；QUIC/HTTP/3 把可靠性做到流级才隔离了这个问题。
