> `Linux` 目录下的《I/O 模型与高并发网络编程》讲的是模型与选型，这一篇讲**实现**：一个基于 epoll 的服务端事件循环，从 accept 到读写缓冲、帧解析、背压、定时器再到优雅关闭，逐层拆开。写代码时真正折磨人的从来不是 `epoll_wait` 那一行，而是它周围的边界条件。

## 一、一条连接的服务端生命周期

```text
socket() → bind() → listen() → [监听 fd 可读] → accept4()
        → 设为非阻塞 → 注册到 epoll → EPOLLIN
        → 循环 read 到 EAGAIN → 解析帧 → 业务处理 → 写缓冲
        → EPOLLOUT 可写时循环 write → 空闲/超时/错误 → 关闭
```

每个连接至少需要维护：

| 状态      | 内容                                      |
| --------- | ----------------------------------------- |
| fd 与地址 | 对端 IP/端口、接入时间、TLS 状态（若有）  |
| 读缓冲    | 已收到但尚未构成完整帧的字节              |
| 写队列    | 待发送的数据，可能远大于一次 `write` 的量 |
| 解析状态  | 当前帧读到哪一步、期望长度                |
| 活跃时间  | 最后读写时间，用于空闲超时与心跳          |
| 连接状态  | 建立中、正常、正在关闭、已关闭            |

这些是**每连接常驻内存**。百万连接估算内存时，真正占大头的往往是读写缓冲和对象开销，不是 fd 本身。

## 二、为什么阻塞式「一连接一线程」撑不住

阻塞模型代码最短：`accept` 后起一个线程，`read` 阻塞等待数据。问题在于线程成本与连接数线性绑定：

| 成本       | 量级与后果                           |
| ---------- | ------------------------------------ |
| 栈内存     | 每线程默认数 MB，万级连接就是数十 GB |
| 上下文切换 | 活跃线程多时 CPU 花在调度而非业务    |
| 内核调度   | 大量线程在「等网络」，就绪时集中唤醒 |
| 空闲长连接 | 心跳稀疏但线程常驻，资源利用率极低   |

长连接场景下「连接数 ≫ 同时活跃数」，因此正确做法是用**少量线程管大量 fd**：谁就绪就处理谁，没就绪的只占一点内存。

## 三、epoll 事件循环骨架

```c
int ep = epoll_create1(EPOLL_CLOEXEC);
set_nonblocking(listen_fd);
struct epoll_event ev = { .events = EPOLLIN, .data.fd = listen_fd };
epoll_ctl(ep, EPOLL_CTL_ADD, listen_fd, &ev);

for (;;) {
    int n = epoll_wait(ep, events, MAX_EVENTS, timeout_ms);
    if (n < 0 && errno == EINTR) continue;   // 被信号打断不算错误

    for (int i = 0; i < n; i++) {
        int fd = events[i].data.fd;
        if (fd == listen_fd) {
            while (1) {                       // 一次就绪可能有多个连接
                int c = accept4(listen_fd, NULL, NULL,
                                SOCK_NONBLOCK | SOCK_CLOEXEC);
                if (c < 0) {
                    if (errno == EAGAIN || errno == EWOULDBLOCK) break;
                    if (errno == EINTR) continue;
                    break;
                }
                add_conn(ep, c);              // 注册 EPOLLIN
            }
        } else if (events[i].events & (EPOLLIN | EPOLLHUP | EPOLLERR)) {
            on_readable(ep, fd);
        } else if (events[i].events & EPOLLOUT) {
            on_writable(ep, fd);
        }
    }
    expire_idle_connections(now());          // 每轮处理定时事件
}
```

几个容易写错的点：

- `accept4` 直接带 `SOCK_NONBLOCK | SOCK_CLOEXEC`，避免先 accept 再 `fcntl` 之间的竞态，也避免 fd 泄漏到 `exec` 的子进程。
- `epoll_wait` 的超时不应是无限：定时器（空闲剔除、心跳）需要靠它推进，通常取「最近一个定时任务的时间差」。
- `EINTR` 要重试，`EAGAIN` 是「暂时没数据」而不是错误。
- 监听 fd 用水平触发时，一次 `accept` 只取一个连接会拖慢接入；用循环接到 `EAGAIN` 更稳。

## 四、LT / ET 在实现层的差别

概念不重复，这里只看怎么读才不会漏数据：

```c
// 水平触发：一次读一批即可，没读完下次还会通知
ssize_t n = read(fd, buf, sizeof(buf));
if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) return;
if (n == 0) { close_conn(fd); return; }   // 对端关闭
append_to_readbuf(fd, buf, n);

// 边缘触发：必须循环读到 EAGAIN，否则剩余数据可能永不再通知
for (;;) {
    ssize_t n = read(fd, buf, sizeof(buf));
    if (n > 0) { append_to_readbuf(fd, buf, n); continue; }
    if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) break;
    if (n < 0 && errno == EINTR) continue;
    close_conn(fd);
    break;
}
```

ET 还必须配**非阻塞 fd**：如果 fd 是阻塞的，最后一次 `read` 会卡在等数据上，整个事件循环停摆。多线程场景下 LT 还有一个陷阱——同一 fd 的就绪事件可能唤醒多个线程同时操作一个连接，需要 `EPOLLONESHOT` 或把 fd 固定绑定到一个线程（Reactor 的常见做法）。

## 五、读写缓冲与背压

**读缓冲**：TCP 是字节流，一次 `read` 可能拿到半个帧或几十个帧，必须累积到「够一帧」再交给业务解析。缓冲要有上限，超过就断开或限流，否则对端可以无限发包撑爆内存。

**写缓冲**：业务产生响应时先尝试直接 `write`；若返回 `EAGAIN` 或只写了部分，把剩余数据挂到该连接的写队列，并注册 `EPOLLOUT`。可写事件到来时继续发送，队列清空后立刻**取消 `EPOLLOUT` 注册**——否则 socket 大部分时间可写，事件循环会被无意义的写事件刷满（busy loop）。

**背压**：当写队列超过高水位，就暂停读取该连接（`EPOLL_CTL_DEL` 或修改事件去掉 `EPOLLIN`），等降到低水位再恢复。不设背压时，慢客户端会让服务端内存里堆积大量待发数据；这在推送、文件下载、SSE 场景尤其明显。

```text
读方向：fd → readbuf → 帧解析 → 业务 → 写队列 → write → fd
              ↑ 超过上限断开          ↓ 高水位暂停读、低水位恢复
```

## 六、粘包/半包与帧解析

「粘包」不是 TCP 的 bug，而是把字节流误当消息边界。服务端需要一个明确的帧协议，最常见的是长度前缀：

```text
+--------+--------+--------+---------+
| magic  | ver    | length | payload |
| 2 byte | 1 byte | 4 byte | N byte  |
+--------+--------+--------+---------+
```

解析状态机：

1. 缓冲不足 7 字节 → 返回「等更多数据」。
2. 校验 magic 与版本，`length` 转成整数并检查上限（如 `<= 1MB`），非法直接断开。
3. 缓冲不足 `7 + length` → 返回「等更多数据」，保留已有字节。
4. 取出完整 payload 交给业务，从缓冲中消费掉这一段，循环处理下一帧。

关键约束：**先校验长度再分配内存**，否则一个伪造的 `length = 0xFFFFFFFF` 就能让服务端申请巨量内存。业务处理与解析要解耦，一帧解析失败不应影响后续连接。

## 七、定时器：空闲连接与心跳

事件循环里的定时任务通常有三类：空闲连接超时、心跳发送/超时检测、业务级延迟任务。少量连接用最小堆（`O(log N)` 插入），海量长连接用**时间轮**（近似 `O(1)`），按 tick 推进。

实践要点：

- 空闲超时基于「最后一次成功读写」，不是连接建立时间；活跃连接每次读写更新计时器，频繁更新堆/轮要有低成本实现（如只更新时间戳，由扫描线程惰性淘汰）。
- 心跳间隔要小于中间设备（NAT、负载均衡器）的空闲回收时间，常见 30～60s；连续 N 次无响应才判定死亡，避免单次丢包误杀。
- `epoll_wait` 的 timeout 设为「最近一个定时任务剩余时间」，避免定时器被无限期推迟。
- TCP keepalive 与应用层心跳不是一回事，前者默认 2 小时且只探内核协议栈，后者才能确认对端业务进程还活着。

## 八、accept 惊群与多 Reactor

多个 worker 同时 `epoll_wait` 同一个监听 fd 时，新连接可能把它们全部唤醒。两种主流解法：

| 方案           | 做法                                           | 特点                                     |
| -------------- | ---------------------------------------------- | ---------------------------------------- |
| `SO_REUSEPORT` | 每个 worker 独立 listen，内核做分发            | 简单、分发均匀，连接无法在 worker 间迁移 |
| 主从 Reactor   | 主 Reactor 只 accept，通过队列分发给子 Reactor | 可控、能做连接绑定，多一次交接           |

多线程下还要决定**连接归属**：一个 fd 从注册到关闭都应由同一个线程/Reactor 处理，避免两个线程同时读写同一个连接的缓冲队列而引入锁。这也是 Nginx、Netty 采用「每 Reactor 一个事件循环」的原因。

Go 不需要手写这些：runtime 的 netpoller 就是这层封装，goroutine 在 I/O 未就绪时挂起、就绪后唤醒。但当出现「连接数很高、内存涨得快、写响应卡住」这类问题时，定位思路仍然是上面这套：读写缓冲、写队列、背压、空闲超时。

## 九、优雅关闭

```text
① 停止 accept（从 epoll 摘除监听 fd / 摘除注册中心）
② 停止接收新请求，向存量连接发送「即将关闭」或等待在途请求完成
③ 对写队列做半关闭：shutdown(fd, SHUT_WR)，把剩余数据发完
④ 等待在途业务处理完成，设置总超时，超时则强制 close
⑤ 关闭所有 fd、释放缓冲、关闭 epoll 实例
```

注意 `close()` 与 `shutdown()` 的差别：`close` 只是减少 fd 引用计数，多进程/线程共享同一 socket 时不会立刻断开连接；`shutdown` 直接作用于内核 socket，能明确表达「不再写」或「不再读」。有未发完数据时直接 `close` 还可能导致对端收到 RST 而不是完整响应。

## 十、常见坑

| 坑                                  | 后果                         | 改法                           |
| ----------------------------------- | ---------------------------- | ------------------------------ |
| ET 模式没循环读到 EAGAIN            | 数据滞留在内核缓冲，连接假死 | 循环读，且 fd 必须非阻塞       |
| 一直注册 EPOLLOUT                   | 事件循环空转，CPU 100%       | 仅在写队列非空时注册           |
| 忘记处理 `EPOLLRDHUP` / `read == 0` | 对端已关却继续等             | 及时回收连接                   |
| 未限制单帧最大长度                  | 恶意长度导致 OOM             | 校验上限后再分配               |
| 没有写背压                          | 慢客户端拖垮服务端内存       | 高低水位 + 暂停读              |
| 在事件循环里做慢业务/同步 I/O       | 所有连接一起卡住             | 丢业务线程池，事件循环只做 I/O |
| 单连接跨线程处理                    | 缓冲竞争、锁复杂             | fd 固定绑定一个 Reactor        |
| 忽略 `EINTR`                        | 偶发提前退出                 | 重试系统调用                   |

## 十一、实践清单

1. 事件循环里只做 I/O 与分发，任何可能阻塞的操作都移出去。
2. 每连接状态显式建模：读缓冲、写队列、解析进度、活跃时间、上限。
3. 读写都处理 `EAGAIN`/`EINTR`；ET 必须循环读到 `EAGAIN`。
4. 写队列为空就取消 `EPOLLOUT`，超水位就暂停读。
5. 帧协议先校验长度上限，再分配内存；解析与业务解耦。
6. 定时器驱动空闲剔除与心跳，超时时间由 `epoll_wait` 的 timeout 保证。
7. 压测时同时看连接数、内存、写队列长度与事件循环单次耗时，避免只测 QPS。

## 十二、面试速答

**问：epoll 边缘触发为什么要配非阻塞 fd？** ET 只在状态变化时通知一次，实现上必须循环 `read` 直到 `EAGAIN` 才能取净数据；若 fd 阻塞，最后一次读会卡住整个事件循环。

**问：为什么写事件要及时取消？** socket 绝大多数时间可写，常驻 `EPOLLOUT` 会让 `epoll_wait` 不断返回空事件造成忙等；应只在写队列非空时注册，发完立刻取消。

**问：如何处理慢客户端？** 给每连接写队列设高低水位，超高位暂停读并触发背压，降到低位恢复；必要时限流或主动断开，避免待发数据在服务端无限堆积。
