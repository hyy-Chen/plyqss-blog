> 前面几篇讲了 epoll、TCP 状态机和长连接治理，这一篇往上层走一层：为什么 HTTP/1.1 要开六个连接，HTTP/2 用一条连接多路复用却仍然怕丢包，以及 HTTP/3 为什么干脆把传输层换到 UDP 上。重点放在服务端要改什么、会遇到什么坑，而不是背 RFC 名词。

## 一、HTTP/1.1 的瓶颈

```text
请求 A ── 响应 A ── 请求 B ── 响应 B   （同一连接串行）
```

| 问题           | 表现                                      | 当年的绕行方案                  |
| -------------- | ----------------------------------------- | ------------------------------- |
| 应用层队头阻塞 | 前一个响应没回来，后面的请求只能等        | 浏览器开 6 个并发连接、域名分片 |
| 头部冗余       | 每次都重复发 Cookie、UA、Accept           | 精简 Cookie、合并请求           |
| 连接开销       | 每个连接都要 TCP 握手 + TLS 握手          | 长连接 Keep-Alive、连接池       |
| 管道化失败     | Pipelining 要求响应严格按序，代理兼容性差 | 基本弃用                        |

这些绕行方案又带来新成本：多连接意味着更多 fd、更多 TLS 握手、更多拥塞窗口各自慢启动，服务端连接数随用户数线性放大。HTTP/2 的核心动机就是**把并发收回一条连接**。

## 二、HTTP/2：二进制分帧与多路复用

```text
一条 TCP 连接
  ├── Stream 1: HEADERS + DATA
  ├── Stream 3: HEADERS + DATA
  └── Stream 5: HEADERS + DATA
      帧交错发送，接收端按 Stream ID 重组
```

| 机制               | 作用                                         | 服务端要注意                               |
| ------------------ | -------------------------------------------- | ------------------------------------------ |
| 二进制帧           | 替代文本解析，边界明确                       | 不能再用按行读取的裸 socket 解析           |
| Stream / 多路复用  | 单连接并发请求，客户端流 ID 奇数、服务端偶数 | `SETTINGS_MAX_CONCURRENT_STREAMS` 要限流   |
| HPACK 头部压缩     | 静态表 + 动态表 + Huffman                    | 动态表是**连接级有状态**的，跨流存在依赖   |
| 流控 WINDOW_UPDATE | 连接级 + 流级两层窗口                        | 大响应要按窗口分块发，别一次性灌满         |
| 优先级             | 提示资源调度顺序                             | 实现复杂且效果参差，新版已简化             |
| Server Push        | 服务端主动推资源                             | 命中率差、易浪费带宽，主流浏览器已移除支持 |
| GOAWAY             | 优雅关闭连接                                 | 滚动发布时必须先发 GOAWAY 再断连           |

两个容易被忽略的服务端问题：

1. **连接级流控会互相拖累**：某个流消费慢会占满连接窗口，其他流一起被卡住。服务端要按流公平调度，并对慢消费者做超时或背压。
2. **优雅关闭变复杂**：HTTP/1.1 关掉连接即可，HTTP/2 一条连接承载很多流。正确顺序是发 `GOAWAY`（带上已处理的最大 Stream ID）→ 停止接受新流 → 等待在途流结束 → 关闭连接。否则滚动发布时客户端会看到大量 `REFUSED_STREAM` 并重试。

部署形态：

```text
浏览器  ← h2 over TLS（ALPN 协商 "h2"）← 网关 / CDN
网关    ← 通常降级为 HTTP/1.1 → 内网服务（h2c 明文或内部 mTLS）
```

内网是否要全链路 h2 要看收益：低延迟、低丢包的数据中心里，HTTP/1.1 连接池已经够用，全链路 h2 反而引入连接级队头阻塞与更复杂的调试。**边缘到用户这一段收益最大**。

## 三、HTTP/2 为什么还是怕丢包

TCP 提供的是**单一有序字节流**。一个 TCP 段丢失，内核必须等它重传并送达，才能把后面的字节交给应用层——哪怕后面的字节属于完全无关的 Stream。

```text
Stream 1 的包丢了 → 内核缓冲住 Stream 3、5 的后续数据
→ 所有流一起停顿（TCP 层队头阻塞）
```

HTTP/1.1 用 6 条连接时，一条丢包只影响它自己；HTTP/2 收敛到一条连接后，丢包影响面反而变大。这就是在弱网、高丢包移动网络里 HTTP/2 有时不升反降的原因，也是 HTTP/3 的直接动机。

## 四、QUIC：把传输控制搬到用户态

QUIC 基于 UDP，在应用层重新实现了可靠传输、拥塞控制与加密：

| 特性           | 说明                           | 带来的收益                         |
| -------------- | ------------------------------ | ---------------------------------- |
| 流级可靠性     | 每个流独立序号与重传           | 一个流丢包不阻塞其他流             |
| TLS 1.3 内建   | 握手与密钥交换合并进 QUIC 握手 | 1-RTT 建连，恢复会话可 0-RTT       |
| 连接 ID        | 用 CID 而非四元组标识连接      | Wi-Fi 切蜂窝、NAT 重绑后连接不中断 |
| 用户态实现     | 拥塞控制、丢包恢复可随应用升级 | 无需等内核版本，迭代快             |
| 加密报文头     | 连 packet number 都加密        | 中间设备难以篡改或被动测量         |
| 可插拔拥塞控制 | BBR、Cubic 等可替换            | 按业务与网络特征调优               |

**连接迁移**是最被低估的能力：传统 TCP 连接由「源 IP + 源端口 + 目的 IP + 目的端口」四元组确定，手机切网络后源 IP 变了，连接必然重建；QUIC 用连接 ID，客户端换 IP 后继续用同一个 CID 发包，服务端验证路径后即可继续，长连接、音视频、实时协作类应用收益明显。

代价也很实在：

- UDP 在部分企业网络、防火墙、运营商策略里被限速或阻断，必须有回退路径。
- 加密和可靠传输在用户态做，**CPU 开销高于内核 TCP**，高吞吐场景下要评估。
- 内核旁路意味着传统 `tcpdump`/`ss` 的经验失效，排障工具链要重建。
- 0-RTT 早期数据可重放，只允许幂等请求（与 TLS 1.3 的 0-RTT 是同一个限制）。

## 五、HTTP/3 相对 HTTP/2 改了什么

HTTP/3 不是把 HTTP/2 帧直接塞进 UDP，而是把流模型映射到 QUIC 流上：

| 项       | HTTP/2                  | HTTP/3                                |
| -------- | ----------------------- | ------------------------------------- |
| 传输层   | TCP + TLS               | QUIC（内建 TLS 1.3）                  |
| 头部压缩 | HPACK                   | QPACK（避免压缩上下文的跨流队头阻塞） |
| 流实现   | 自己定义 Stream ID 与帧 | 直接复用 QUIC 流                      |
| 队头阻塞 | 仍受 TCP 层影响         | 基本消除                              |
| 协商方式 | TLS ALPN                | `Alt-Svc` 响应头 + ALPN               |

HPACK 的动态表依赖「前面的 HEADERS 帧先被解码」，在 HTTP/2 里形成压缩上下文层面的队头阻塞；QPACK 用独立的单向流同步表状态，让头部解码不再被其他流卡住。

升级流程通常是：

```text
1. 客户端先用 HTTP/2 访问
2. 服务端返回 Alt-Svc: h3=":443"; ma=86400
3. 客户端缓存该声明，后续尝试 QUIC 建连
4. 失败则回退到 HTTP/2（要有超时，别让用户卡在黑洞里）
```

## 六、服务端落地清单

| 项         | 要点                                                                           |
| ---------- | ------------------------------------------------------------------------------ |
| 协议开启   | Nginx/Envoy/Caddy 开启 HTTP/3，开放 **UDP 443**（只开 TCP 是最常见的配置遗漏） |
| 证书       | QUIC 强制 TLS 1.3，证书链与 SNI 配置要和 h2 一致                               |
| `Alt-Svc`  | 设置合理 `ma`（缓存时长），下线 h3 时要能快速撤回                              |
| 回退       | 客户端探测失败要在秒级切回 h2，监控 h3 握手失败率                              |
| 负载均衡   | 四层要按 Connection ID 保持会话，或支持 CID 可迁移；否则迁移后落到不同后端     |
| 0-RTT      | 只对幂等 GET 开放，写接口一律走 1-RTT，并在服务端做票据一次性校验              |
| 连接复用   | h3 下一个连接承载更多流，连接池策略、超时与 GOAWAY 语义要重新验                |
| 可观测     | 分别统计 h2/h3 的握手耗时、0-RTT 比例、迁移成功率、重传率、回退率              |
| 日志与追踪 | 网关日志显式记录协议版本，否则排障时分不清慢的是哪一代协议                     |

特别注意 **0-RTT**：它带来延迟收益，但把「请求可重放」这个风险引入应用层。支付、下单、状态变更接口必须禁用，或配合一次性票据与幂等键。参见「TLS、证书与 mTLS」里对 TLS 1.3 0-RTT 的分析。

## 七、排查工具

```bash
curl -I --http2 https://example.com/          # 验证 h2
curl -I --http3 https://example.com/          # 需带 HTTP/3 支持的 curl
curl -sv --http3 https://example.com/ 2>&1 | grep -i 'alt-svc\|HTTP/3'
openssl s_client -alpn h2 -connect host:443   # 查看 ALPN 协商结果
```

- `Alt-Svc` 会被浏览器缓存，服务端临时关掉 h3 后客户端仍可能尝试一段时间，排查时要清缓存或用无痕窗口。
- QUIC 报文加密，Wireshark 需要配置 SSLKEYLOGFILE 才能解密；否则只能看到 UDP 包大小与时序。
- 浏览器可用 `chrome://net-export` 导出网络日志，确认实际用的是 h2 还是 h3、是否发生了回退。
- 分协议看指标：如果 h3 的 P99 比 h2 还差，优先查 UDP 被限速、CID 路由不一致和 0-RTT 重放保护开销。

## 八、什么时候收益不明显

| 场景                 | 原因                                                     |
| -------------------- | -------------------------------------------------------- |
| 内网服务间调用       | 丢包率极低，TCP 队头阻塞几乎不出现，却要付用户态加密成本 |
| 单大文件下载         | 本来就一个流，多路复用无收益                             |
| 老客户端 / 企业代理  | UDP 被阻断，实际都回退到 h2                              |
| 已做域名分片的旧站   | 迁移到 h2 收益大，但再上 h3 的边际收益有限               |
| CPU 已饱和的边缘节点 | QUIC 的用户态加解密可能先成为瓶颈                        |

协议升级不是免费加速，**先按真实网络条件测 P50/P99、握手耗时和回退率，再决定开多大范围**。

## 九、实践清单

- 边缘开启 h2/h3，内网按实测决定是否全链路升级，不盲目追新。
- 开 UDP 443；`Alt-Svc` 可配置、可快速撤回；保留秒级回退到 h2 的能力。
- 四层负载均衡按 Connection ID 保持，避免连接迁移后落到错误后端。
- 0-RTT 只放行幂等请求，写接口禁用并做票据一次性校验。
- 网关日志与监控显式带上协议版本，分协议看握手、重传、回退与延迟分位数。
- 滚动发布按 GOAWAY 语义优雅关闭，不让在途流被硬断。
- 压测包含丢包、切换网络、UDP 被限速三类弱网场景，验证回退路径真的能用。

## 十、面试速答

**Q：HTTP/2 多路复用解决了什么，又留下什么问题？**
解决了 HTTP/1.1 的应用层队头阻塞与多连接开销，一条连接上用 Stream 并发。但底层仍是 TCP 单有序字节流，一个段丢失会阻塞所有流，形成 TCP 层队头阻塞，弱网下甚至比多连接 HTTP/1.1 更差。

**Q：HTTP/3 为什么基于 UDP？**
要绕开内核 TCP 的单字节流约束，实现流级独立重传、加密报文头、连接 ID 迁移和可插拔拥塞控制；这些改动无法通过修改 TCP 快速落地，只能在 UDP 之上的用户态协议实现。

**Q：QUIC 的连接迁移是怎么做到的？**
连接由 Connection ID 而非四元组标识，客户端换 IP/端口后继续用同一 CID 发包，服务端通过路径验证确认新地址后继续该连接；前提是负载均衡能按 CID 把包送到同一后端。

**Q：0-RTT 有什么风险，服务端怎么处理？**
早期数据没有服务端新鲜性保证，可被录制重放。只放行幂等请求，写操作强制 1-RTT，并配合一次性票据、重放窗口与业务幂等键。

## 十一、一句话收尾

从 HTTP/1.1 到 HTTP/3，主线是**不断把「队头阻塞」和「连接重建成本」从更底层移走**：先合并连接，再换掉承载它的 TCP；代价是服务端的连接治理、优雅关闭、负载均衡与排障方式都要跟着重写一遍。
