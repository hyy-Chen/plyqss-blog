> 服务端的网络问题，多数最终会落在某个 TCP 状态或某个内核队列上：连不上是握手队列，连接数莫名涨是 `CLOSE_WAIT`，延迟抖动是丢包重传，带宽跑不满是窗口不够。这篇按「建连 → 传输 → 断连」把状态机、参数和排查串起来。

## 一、三次握手与两个队列

```text
客户端                          服务端
  SYN ──────────────────────▶  [SYN queue]  SYN_RECV
       ◀──────────────────────  SYN+ACK
  ACK ──────────────────────▶  [accept queue]  ESTABLISHED
                                （应用 accept 后取出）
```

服务端内核维护两个队列：

| 队列         | 含义                        | 相关参数                                                | 溢出表现                                |
| ------------ | --------------------------- | ------------------------------------------------------- | --------------------------------------- |
| SYN queue    | 收到 SYN、等待最后一个 ACK  | `net.ipv4.tcp_max_syn_backlog`、`tcp_syncookies`        | SYN 被丢弃，客户端重传 SYN、建连慢      |
| accept queue | 已完成握手、等待应用 accept | `min(somaxconn, listen(backlog))`、`net.core.somaxconn` | 内核丢弃 ACK 或 SYN，表现为偶发连接超时 |

常见误区：把应用里的 `listen(fd, 128)` 调大就以为够了，实际**上限取 `somaxconn` 与 backlog 的较小值**。突发连接（服务重启后客户端集中重连、秒杀）时 accept queue 溢出会导致客户端「握手成功但首个请求超时」，很难从应用日志看出来。

观察方式：

```bash
ss -lnt                      # Recv-Q 是当前 accept queue 深度，Send-Q 是上限
netstat -s | grep -i listen  # 队列溢出累计计数
nstat -az TcpExtListenOverflows
```

SYN flood 时开启 `tcp_syncookies=1` 可以不占用 SYN queue 完成握手，但不能被当成常规优化：它绕过了部分选项协商，正常情况下应保持队列容量与接入速率匹配。

## 二、四次挥手与关键状态

```text
主动关闭方：FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
被动关闭方：CLOSE_WAIT → LAST_ACK → CLOSED
```

| 状态         | 谁会处在这个状态 | 常见原因                         |
| ------------ | ---------------- | -------------------------------- |
| `TIME_WAIT`  | 主动关闭的一方   | 正常协议行为，持续 2×MSL         |
| `CLOSE_WAIT` | 被动关闭的一方   | **应用没有调用 close**，代码 bug |
| `FIN_WAIT_2` | 主动关闭方       | 对端迟迟不发 FIN，可能卡在业务   |
| `LAST_ACK`   | 被动关闭方       | 已发 FIN 等最后一个 ACK          |

`TIME_WAIT` 的作用是吸收网络中延迟的报文、并让旧连接的重复报文不会污染同一四元组的新连接。它主要消耗的是**主动关闭方的端口与少量内存**。堆积时的正确方向是减少主动关闭：让服务端保持长连接、复用连接池、由客户端先关；而不是粗暴改内核参数把它「消灭」。

`CLOSE_WAIT` 才是真正的故障信号。它表示对端已经发了 FIN，内核在等应用关闭 fd，而应用没关——常见于读取到 `EOF`（`read` 返回 0 / `io.EOF`）后没有 `Close()`、异常分支漏关连接、或连接池回收逻辑有误。

```bash
ss -tanp state close-wait | head      # 看数量和归属进程
lsof -p <pid> | wc -l                 # 配合看 fd 是否持续增长
```

## 三、连接保活

| 机制             | 默认行为                       | 适用                     |
| ---------------- | ------------------------------ | ------------------------ |
| TCP keepalive    | 默认 2 小时空闲后才探测        | 只探内核协议栈，粒度太粗 |
| 应用层心跳       | 30～60s 一次，可带业务状态     | 长连接服务必备           |
| 中间设备空闲回收 | NAT/LB 常 5～15 分钟无流量即断 | 心跳间隔必须小于它       |

TCP keepalive 相关参数（Linux）：

```text
net.ipv4.tcp_keepalive_time    = 7200   # 空闲多久开始探测
net.ipv4.tcp_keepalive_intvl   = 75     # 探测间隔
net.ipv4.tcp_keepalive_probes  = 9      # 失败几次判定死亡
```

应用若要用它，应在 socket 上单独设置（`SO_KEEPALIVE` + `TCP_KEEPIDLE` 等），**不要为了一个服务改全局 sysctl**。更常见的是应用层心跳：连续 N 次无响应才判定连接死亡，避免单次丢包误杀；同时心跳包要轻量且可区分「进程活着」与「业务可用」。

## 四、拥塞控制与丢包

TCP 通过拥塞窗口 `cwnd` 与接收窗口 `rwnd` 共同限制在途数据量：`min(cwnd, rwnd)`。

```text
慢启动：cwnd 从初始值指数增长，直到 ssthresh
拥塞避免：线性增长，探测可用带宽
快速重传/恢复：收到 3 个重复 ACK 即重传，不必等 RTO 超时
RTO 超时：代价最大，cwnd 直接回落，吞吐骤降
```

| 算法       | 特点                                     | 适用                         |
| ---------- | ---------------------------------------- | ---------------------------- |
| Reno/CUBIC | 以丢包作为拥塞信号，Linux 默认多为 CUBIC | 常规机房、低丢包网络         |
| BBR        | 基于带宽与 RTT 建模，不看丢包            | 高丢包、长肥管道、跨地域传输 |

关键结论：**丢包对吞吐的影响远大于对正确性的影响**。一个 1% 丢包的跨地域链路，可能让单连接吞吐掉到带宽的几十分之一，因为窗口反复被削减。排查「带宽明明够但传得慢」时，先看重传率而不是先调应用线程数。

```bash
ss -ti dst 10.0.0.1      # rtt、cwnd、retrans、pacing_rate
sar -n ETCP 1             # 重传、主动/被动连接速率
nstat -az | grep -i retrans
```

## 五、窗口、缓冲与 BDP

高带宽高延迟链路需要足够大的在途窗口才能填满管道：

\[
BDP = 带宽 \times RTT
\]

例如 1 Gbps 链路、RTT 40ms：

\[
BDP = \frac{1000\,\text{Mbit/s} \times 0.04\,\text{s}}{8} \approx 5\,\text{MB}
\]

如果接收窗口只有 128KB，无论怎么加压都只能跑到很低的吞吐。相关参数：

| 参数                             | 作用                                  |
| -------------------------------- | ------------------------------------- |
| `net.ipv4.tcp_rmem` / `tcp_wmem` | 每 socket 读/写缓冲的 min/default/max |
| `net.ipv4.tcp_window_scaling`    | 窗口扩大选项，突破 64KB 上限          |
| `net.ipv4.tcp_moderate_rcvbuf`   | 自动调优接收缓冲                      |
| `net.core.rmem_max` / `wmem_max` | 应用显式设置缓冲时的上限              |

现代内核的自动调优通常够用，应用层不要盲目 `SetReadBuffer` 一个巨大值——缓冲过大会造成**缓冲区膨胀（bufferbloat）**，延迟升高且丢包时恢复更慢。真正需要调的是长肥管道、大文件传输、跨地域复制这类明确场景。

## 六、延迟相关的几个开关

| 项                      | 说明                                                       |
| ----------------------- | ---------------------------------------------------------- |
| Nagle 算法              | 合并小包减少网络开销，但会增加小请求的延迟                 |
| 延迟确认（Delayed ACK） | 最多等约 40ms 捎带 ACK，与 Nagle 叠加可能造成明显卡顿      |
| `TCP_NODELAY`           | 禁用 Nagle，小包立即发送；RPC、游戏、实时推送通常开启      |
| `TCP_QUICKACK`          | 立即确认，属于每次调用生效的临时行为，不是一次设置永久有效 |
| TLS 握手                | 每次新建连接增加 1～2 个 RTT（TLS 1.3 更少），长连接可摊薄 |

对延迟最敏感的小请求 RPC，最有效的优化通常不是调内核，而是**连接复用 + 开启 `TCP_NODELAY` + 减少握手次数**。

## 七、线上问题定位套路

| 现象               | 优先看什么                                                            |
| ------------------ | --------------------------------------------------------------------- |
| 偶发建连超时       | accept queue 溢出、`syncookies` 是否触发、SYN 重传、LB 健康检查       |
| 连接数持续上涨     | `CLOSE_WAIT` 数量、fd 泄漏、连接池配置、心跳是否失效                  |
| 端口耗尽           | 谁在主动关闭、短连接是否过多、`ip_local_port_range`、`TIME_WAIT` 分布 |
| 吞吐上不去         | 重传率、RTT 与 `cwnd`、窗口是否小于 BDP、磁盘或应用是否才是瓶颈       |
| P99 偶发尖刺       | 丢包重传、GC/调度暂停、连接池排队、慢查询                             |
| 服务重启后大量超时 | 客户端集中重连造成 accept queue 溢出、注册中心摘除是否及时            |

排查顺序建议：**先分层定位**（DNS/建连/TLS/首字节/整体响应），再看状态分布与计数，最后才抓包。`tcpdump` 和 `strace` 在生产上有开销，要限定进程、限定时间、加过滤条件。

```bash
ss -s                                  # 各状态连接总览
ss -tanp state time-wait | wc -l
ss -ti                                # 逐连接 RTT、cwnd、重传
sar -n DEV,ETCP 1                      # 网卡吞吐与 TCP 错误计数
netstat -s | grep -Ei 'retrans|listen|overflow'
tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0' -c 200
```

## 八、常见误区

- **「`TIME_WAIT` 太多要清掉」**：它是正常状态，堆积分明是连接模式问题。优先长连接与连接池复用。
- **「调大所有缓冲就能提速」**：缓存过大增加延迟与内存，可能适得其反。
- **「内核参数是万能开关」**：多数性能问题出在应用（连接管理、序列化、慢查询），调 sysctl 前先有证据。
- **「`tcp_tw_reuse` 一开就好」**：不同内核版本语义已变，且对服务端收到的连接不生效，别照抄旧博客。
- **「CLOSE_WAIT 是内核问题」**：几乎总是应用没关 fd。

## 九、实践清单

1. 建连参数按接入峰值配置：`somaxconn` 与 `listen(backlog)` 一起调，并监控 accept queue 溢出。
2. 长连接服务必须有应用层心跳，间隔小于中间设备空闲回收时间。
3. 监控 `CLOSE_WAIT`、`TIME_WAIT`、重传率、建连耗时与 RTT，而不是只看 QPS。
4. 优先连接复用与 `TCP_NODELAY`，谨慎改全局 sysctl；改动前记录基线、改动后对比。
5. 跨地域高延迟链路按 BDP 核算窗口，并检查是否启用了窗口扩大。
6. 压测覆盖「服务重启 + 客户端集中重连」场景，这是最容易暴露队列问题的时刻。

## 十、面试速答

**问：大量 `CLOSE_WAIT` 说明什么？** 对端已发 FIN，本端内核在等应用关闭 socket，但应用没调用 `close`；通常是读到 `EOF` 后没关连接或异常分支漏关，属于应用 bug 而非内核参数问题。

**问：`TIME_WAIT` 需要优化吗？** 它是主动关闭方的正常状态，用来吸收延迟报文。堆积时应减少主动关闭（连接复用、让客户端先关），而不是强行缩短或清除。

**问：带宽足够但传输很慢怎么排查？** 先看重传率与 RTT，再用 `ss -ti` 看 `cwnd` 和接收窗口是否小于 BDP；丢包会让拥塞窗口反复回落，跨地域链路尤其明显。
