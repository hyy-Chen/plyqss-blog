> 本文以 Redis 7.x 为背景。Redis 是内存数据结构服务器：高性能来自内存与事件循环，但持久化、复制和内存治理决定了它是否可靠。

## 一、整体架构

Redis 的主线程负责网络 I/O、命令解析和绝大部分命令执行；命令本身通常在内存中完成，避免了磁盘 I/O。Redis 6.0 起可将部分网络 I/O 交给 I/O 线程，但命令执行仍以单线程为主，因此慢命令仍会阻塞其他请求。

```text
客户端 → TCP 连接 → 事件循环 → 命令查表与执行 → 内存数据结构
                                      ├── 复制输出缓冲区
                                      ├── AOF 缓冲区
                                      └── 响应写回客户端
```

单线程不等于只能处理一个连接：事件循环借助 I/O 多路复用（Linux 常用 `epoll`）同时管理大量非阻塞连接。瓶颈常见于大 key、`KEYS *`、超大聚合、复杂 Lua 脚本和阻塞性模块调用。

## 二、对象系统与底层数据结构

Redis 的键和值以 `redisObject` 表示，对象带有类型、编码、LRU/LFU 信息和引用计数。用户看到的五种基本类型，会按数据规模和内容选择内部编码。

| 逻辑类型 | 常见底层编码            | 典型用途                 |
| -------- | ----------------------- | ------------------------ |
| String   | `int`、`embstr`、`raw`  | 缓存、计数器、序列化对象 |
| List     | `quicklist`             | 队列、时间线             |
| Hash     | `listpack`、`hashtable` | 小对象字段集合           |
| Set      | `intset`、`hashtable`   | 去重、标签、关系         |
| ZSet     | `listpack`、跳表 + 字典 | 排行榜、按分值范围检索   |

### 1. SDS 与字典

字符串使用 SDS（Simple Dynamic String），记录长度与剩余空间，能在 `O(1)` 时间取长度，支持二进制安全，并通过预分配减少追加时的重分配。Redis 的全局键空间和 Hash 等使用哈希表：渐进式 rehash 将旧桶迁移分散到后续操作中，避免一次扩容长时间阻塞。

### 2. 跳表、压缩列表与 listpack

有序集合在元素较多时使用“字典 + 跳表”：字典按成员快速定位分数，跳表按分值有序遍历。跳表的插入、删除、查找平均为 `O(log N)`，范围查询自然高效。

小型聚合对象常用紧凑的 `listpack` 减少指针与分配开销；超过阈值后会转换为哈希表或跳表。这意味着同一条命令在不同数据规模下的内存与时间成本可能不同。

## 三、读写路径与过期淘汰

读命令通常经历“解析 → 查找 DB 字典 → 惰性删除过期键 → 编码对应操作 → 响应”。写命令会修改内存、传播给副本，并按配置写入 AOF。

过期键采用惰性删除和定期删除结合：访问键时发现过期就删除；后台周期性随机抽样带过期时间的键并清理。过期不是内存上限策略；内存达到 `maxmemory` 后，才触发淘汰策略。

| 策略示例                      | 行为                                    |
| ----------------------------- | --------------------------------------- |
| `noeviction`                  | 拒绝会增加内存的写入                    |
| `allkeys-lru` / `allkeys-lfu` | 从全部键中按近似 LRU/LFU 淘汰           |
| `volatile-ttl`                | 从设置过期时间的键中优先淘汰 TTL 更短者 |
| `allkeys-random`              | 随机淘汰，成本低但命中率不可控          |

缓存必须设计失效策略：缓存穿透可用参数校验、空值缓存或布隆过滤器；击穿可用互斥重建或逻辑过期；雪崩可通过 TTL 加随机抖动、限流和多级缓存缓解。

## 四、持久化：RDB 与 AOF

### 1. RDB 快照

RDB 在某一时刻将数据集写成紧凑二进制快照。`BGSAVE` 通过 `fork` 创建子进程写盘，主进程继续处理请求；写时复制（COW）使被修改的内存页额外复制，因此高写入量和大内存实例可能产生明显内存压力。

RDB 恢复快、文件紧凑，适合备份与全量同步；但两次快照之间的修改可能在宕机后丢失。

### 2. AOF 追加日志

AOF 将写命令追加到日志，重启时重放恢复数据。`appendfsync always` 持久性最好但慢；`everysec` 是常见折中；`no` 交给操作系统，丢失窗口更大。AOF 重写会生成等价的最小命令集，避免日志无限增长；重写同样由子进程完成，主进程用重写缓冲区补齐期间写入。

生产常同时启用 RDB 与 AOF：AOF 降低数据丢失窗口，RDB 用于备份和快速全量传输。持久化不是跨机容灾，仍需备份和副本。

## 五、复制、Sentinel 与 Cluster

### 1. 主从复制

副本初次同步时，主库创建 RDB 并发送给副本；后续通过复制积压缓冲区按偏移量进行部分重同步。复制默认异步：主库返回成功不代表副本已落盘。`WAIT` 可等待指定数量副本确认，降低丢数据风险但不能替代共识协议。

### 2. Sentinel

Sentinel 监控主从节点，在主库客观下线后选举新主并通知客户端。它解决单主高可用，不自动把数据切分到多节点；应用需要能发现新的主地址。

### 3. Redis Cluster

Cluster 将键空间分为 16,384 个槽位，槽位按 `CRC16(key) mod 16384` 路由。节点各自负责一段槽位并维护副本；故障转移由集群节点投票完成。多键操作必须落到同一槽，可借助哈希标签：`{order:42}:items` 与 `{order:42}:total`。

## 六、常见误区与排查

1. Redis 是单线程执行命令，不表示所有操作都恒定极快；大 key 和 `O(N)` 命令会阻塞事件循环。
2. 过期时间不保证键到点立刻消失；业务不能依赖“过期瞬间”的精确语义。
3. 复制异步，主从切换可能丢失最近写入；关键数据应有数据库或消息日志等权威来源。
4. 不要用 `KEYS *`、无界 `SMEMBERS` 或无界 `LRANGE` 处理生产大库；使用 `SCAN` 分批遍历。

排查可从 `SLOWLOG GET`、`INFO memory`、`INFO replication`、`LATENCY DOCTOR`、`MEMORY USAGE key` 入手，结合命令耗时、内存碎片率、复制延迟和热 key 分析。
