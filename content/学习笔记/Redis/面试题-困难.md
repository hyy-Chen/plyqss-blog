## 1. Redis 的 AOF 重写为何不会丢失重写期间的写入？

**回答：** 子进程生成精简 AOF 时，主进程继续处理写命令并写入 AOF 重写缓冲区；子进程完成后，主进程追加缓冲区内容，再原子替换旧文件。

**补充：** 重写利用 fork，主进程修改内存页会触发 COW；大实例高写入时要预留内存并避开高峰。重写不是简单复制旧 AOF，而是根据当前数据集生成恢复所需命令。

## 2. RDB fork 会带来哪些生产风险？

**回答：** fork 本身会暂停主线程一小段时间；随后若主进程持续修改数据，COW 会复制被修改页，可能造成内存峰值和延迟抖动。

**补充：** 风险随实例内存、写入率和系统内存余量增大。应观察 `latest_fork_usec`、持久化耗时和内存，必要时拆分实例或调整持久化窗口。

## 3. 如何正确实现 Redis 分布式锁？

**回答：** 加锁使用带随机唯一 token 和 TTL 的 `SET key token NX PX timeout`；释放时通过 Lua 比较 token 后删除。

**补充：** TTL 必须覆盖临界区最坏耗时，业务执行超时要停止继续写；锁失效后原持有者不能再认为自己拥有锁。复杂一致性场景需要 fencing token 或由数据库约束兜底，不能迷信锁。

## 4. Redlock 是否能保证强一致分布式锁？

**回答：** 不能把 Redlock 当作通用强一致方案。它试图在多个独立 Redis 主节点获得多数锁，但网络分区、时钟和暂停会使语义复杂。

**补充：** 对资金、唯一资源等强正确性业务，使用具备共识语义的协调系统或 fencing token；很多普通业务以单 Redis 锁加数据库唯一约束和幂等处理更实际。

## 5. Redis Cluster 在网络分区时怎样保证可用性？

**回答：** 节点通过 gossip 传播状态；主节点故障后其副本经投票提升。少数派通常会停止对外服务以避免脑裂扩散。

**补充：** 异步复制使故障切换仍可能丢失最近写入。`min-replicas-to-write` 等配置可在副本不足时拒绝写入，以可用性换取更小丢失窗口。

## 6. 为什么 Redis Cluster 不适合随意做跨槽事务？

**回答：** 数据按槽分布，跨槽多键操作需要跨节点协调，会破坏低延迟和简单路由模型；大多数多键命令要求同槽。

**补充：** 可用哈希标签让相关小范围 key 同槽，或重新建模为单 key/单分片操作。不要为少数跨槽需求把全部 key 放到一个标签中。

## 7. 如何设计秒杀库存，避免超卖和缓存击穿？

**回答：** Redis 可用 Lua 原子扣减预库存并生成资格；最终订单写入必须有数据库条件更新、唯一约束和幂等校验兜底。

**补充：** Redis 预扣成功不代表订单最终成功，需要异步下单、失败补偿和超时回补。热点流量还要限流、排队、削峰；不能只依赖 `DECR`。

## 8. `WAIT` 命令能提供什么保证？

**回答：** `WAIT n timeout` 等待指定数量副本确认已收到当前连接之前的写入，可降低主库故障时写入丢失概率。

**补充：** 它不保证副本已 fsync，更不提供共识提交或线性一致读。超时返回较少确认数时，调用方必须根据业务决定是否继续。

## 9. 如何排查 Redis 延迟突然升高？

**回答：** 先区分命令执行慢、网络慢、CPU 饱和、持久化 fork/COW、swap 或客户端连接池排队；查看 `SLOWLOG`、`LATENCY DOCTOR`、`INFO` 与系统指标。

**补充：** 重点查大 key、慢 Lua、`KEYS`/大范围聚合、AOF fsync、RDB fork、网卡和虚拟化抖动。不要只看平均延迟，要看 p99 与事件时间线。

## 10. 如何防止缓存雪崩后的数据库被打垮？

**回答：** TTL 加随机抖动，热点键预热；发生故障时使用限流、熔断、请求合并、降级和本地缓存。

**补充：** 缓存恢复也要限速，避免所有请求同时回源。数据库应设置连接、并发和超时保护；缓存集群不可用时必须有明确的业务降级而不是无限重试。

## 11. Redis 复制与持久化能否当备份？

**回答：** 不能完全替代备份。复制会传播误删，持久化文件也可能随故障或逻辑错误受影响。

**补充：** 应把 RDB/AOF 文件或快照定期导出到独立存储，并演练恢复。恢复目标要区分 RPO（可接受丢失）和 RTO（恢复时间）。

## 12. Go 服务使用 Redis 时如何设计超时与重试？

**回答：** 为每次调用设置 context 截止时间和客户端读写超时；仅对幂等操作做有限、带退避的重试。

**补充：** 网络超时后服务端可能已执行命令，非幂等写入重试会重复生效。应使用请求 ID、Lua 原子校验或业务幂等键，并监控连接池等待与超时比例。
