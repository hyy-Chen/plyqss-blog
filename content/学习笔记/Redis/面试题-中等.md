## 1. Redis 的单线程模型如何处理高并发连接？

**回答：** 通过非阻塞网络和 I/O 多路复用同时监听多个 socket，事件就绪后主线程依次执行命令。

**补充：** 单线程串行保证命令原子性，但也意味着任何慢命令都会放大尾延迟。应监控 slowlog、延迟事件与命令复杂度。

## 2. Redis 为什么使用跳表实现 ZSet？

**回答：** 跳表实现简单，平均 `O(log N)` 的查找、插入和删除，并天然支持按分数范围遍历。

**补充：** ZSet 通常结合字典实现：字典按 member 快速查 score，跳表按 score 排序。小集合可使用紧凑编码降低内存开销。

## 3. Redis 的哈希表如何扩容？

**回答：** Redis 使用渐进式 rehash，将旧表桶的迁移分散到后续读写操作，避免一次扩容长时间阻塞。

**补充：** rehash 期间维护两张表，查找会同时检查；定时任务也会协助迁移。大规模 key 创建仍会造成内存和 CPU 峰值，应平滑预热。

## 4. Redis 事务有什么语义？

**回答：** `MULTI`/`EXEC` 将命令按顺序串行执行，执行期间不会插入其他客户端命令；它不提供关系数据库式回滚。

**补充：** 命令入队错误会导致事务无法执行，但运行时错误不会回滚前面成功命令。需要复杂原子读改写时，Lua 脚本或单命令原子操作更常用。

## 5. Lua 脚本的优缺点？

**回答：** Lua 脚本在 Redis 内原子执行，可减少网络往返并实现多步原子逻辑。

**补充：** 脚本执行时阻塞其他命令，必须短小、无阻塞和可预测；脚本不应执行大循环或访问未声明的 key。超时脚本会触发严重延迟。

## 6. Redis 的内存淘汰策略如何选？

**回答：** 缓存场景常选 `allkeys-lru` 或 `allkeys-lfu`；无法接受淘汰则用 `noeviction` 并在应用层处理写失败。

**补充：** LRU/LFU 是近似策略，不是精确全局排序。只对部分键设置 TTL 时，`volatile-*` 只会在这些键中淘汰，可能不符合预期。

## 7. Redis 主从复制的全量和部分同步？

**回答：** 首次或无法续传时主库生成 RDB 做全量同步；副本断线重连且复制积压缓冲区仍包含缺失数据时，可按 offset 部分同步。

**补充：** 复制默认异步，主库确认写成功不代表副本已收到。积压缓冲区太小或断线太久会退化为全量同步，冲击主库和网络。

## 8. Sentinel 的作用与局限？

**回答：** Sentinel 监控主从、判定主观/客观下线、选举新主并通知客户端。

**补充：** Sentinel 解决单主高可用，不负责数据分片；故障切换可能丢失异步复制的最近写入，客户端必须具备地址刷新和重试能力。

## 9. Redis Cluster 如何路由？

**回答：** Cluster 将键空间分成 16,384 槽，槽号由 `CRC16(key) mod 16384` 决定，节点负责不同槽位。

**补充：** 多键命令要求 key 在同一槽。哈希标签如 `{user:1}:profile` 与 `{user:1}:cart` 可强制使用相同槽，但过度使用会制造热点。

## 10. 缓存与数据库双写如何保证一致性？

**回答：** 常用 Cache Aside：先更新数据库，再删除缓存；读缓存未命中时读库并回填。

**补充：** 删除缓存失败会产生脏读，应配合重试、消息/订阅 binlog、短 TTL 或延迟双删等方案。不存在万能强一致双写，需按业务容忍度选最终一致策略。

## 11. 什么是热 key，如何治理？

**回答：** 热 key 是被极高频访问的单个 key，会使单 Redis 节点、单槽或网卡成为瓶颈。

**补充：** 可做本地缓存、多副本拆分读取、请求合并和限流；写热点不能简单复制，必须设计单写源和一致性。先用监控确认热点而非盲目扩容。

## 12. 如何理解 Redis 的原子性？

**回答：** 单条命令和 Lua 脚本在执行期相对其他命令是原子的，但不意味着跨客户端流程、持久化和复制也原子。

**补充：** `GET` 后在客户端计算再 `SET` 不是原子操作，应使用 `INCR`、`HINCRBY`、CAS/Lua 等。原子性不等于持久性和分布式一致性。
