> Elasticsearch 基于 Lucene 构建，是近实时的分布式搜索与分析引擎。它适合全文检索、多维聚合和日志分析，不应被当作事务型关系数据库的直接替代品。

## 一、索引、分片与集群

一个 Elasticsearch index 是逻辑命名空间，拆为多个 primary shard；每个 primary 可有 replica shard。分片是 Lucene index 的实例，也是扩展容量与吞吐的基本单元。主分片数量创建后不能直接修改，副本数可动态调整。

```text
请求 → Coordinating Node → 路由到相关 Primary / Replica Shard
                            └→ 每个分片执行 Lucene 查询 → 汇总结果
```

Cluster State 由 Master-eligible 节点管理，记录索引元数据、节点和分片分配。协调节点接收请求并散发到各分片；它不必保存所有数据，但大查询的聚合与结果归并会消耗其 CPU 和内存。

## 二、Lucene 倒排索引与数据结构

全文字段经 analyzer 处理：字符过滤、分词器和 token filter 将文本转为 term。倒排索引保存 `term → posting list（包含该 term 的文档列表）`，因此按词查文档很快。posting list 通常还可包含词频、位置和偏移，以支持相关性评分、短语查询与高亮。

```text
"distributed search"
  → [distributed, search]
  → distributed: [doc_1, doc_8]
  → search:      [doc_1, doc_4, doc_8]
```

`text` 字段用于分词全文检索，`keyword` 保存未分词完整值，适合精确过滤、聚合和排序。映射应在写入前明确：错误地把标识符映射为 `text`，会导致聚合、精确匹配语义和内存成本都出现问题。

## 三、段、写入与近实时性

Lucene 段（segment）不可变。文档写入先进入内存缓冲和 translog；refresh 将内存内容生成新段并打开搜索器，使新文档可被搜索，因此默认表现为近实时而非立即可见。flush 将数据安全落盘并推进 translog，后台 merge 会合并多个小段、清理已删除文档。

```text
Index API → 内存缓冲 + translog → refresh → 可搜索的新 segment
                                      │
                                      └→ 后台 merge 合并 segment
```

更新与删除本质上是“写新版本 + 标记旧文档删除”，实际回收在段合并时发生。高频更新会带来大量段、合并 I/O 和磁盘放大；批量写入使用 Bulk API，并在导入期间合理调大 refresh interval，通常更高效。

## 四、查询、评分与聚合

查询先在每个目标分片执行，再由协调节点合并。`term` 查询不分析输入，适合 `keyword`、ID 等精确字段；`match` 会按字段 analyzer 处理输入，适合 `text`。BM25 是默认相关性评分模型之一，分数主要用于同一次查询结果的相对排序。

聚合常依赖 doc values——按列存储在磁盘上的数据结构，适合 `keyword`、数值、日期字段的排序和聚合。对 `text` 启用 fielddata 会在堆内存中构建字段数据，成本高；通常应使用 `text` 的 `keyword` 子字段。

深分页代价高，因为各分片都需生成更多候选结果。用户翻页用 `search_after` 配合稳定排序；批量遍历用 PIT（Point in Time）或 Scroll（适合旧式批处理）来保持视图一致。

## 五、写入一致性、复制与恢复

写请求先到主分片，再复制到副本；成功响应受 `wait_for_active_shards` 等条件影响。副本可承担查询并在主分片故障时提升为新主。translog 和 segment 文件参与故障恢复；快照（Snapshot）将数据备份到共享仓库，是跨集群恢复与灾备的标准手段。

Elasticsearch 不提供关系型多行事务。应用若需跨索引一致性，应通过事件日志、幂等写入、版本号（optimistic concurrency control）和补偿机制设计，而不是假设多文档更新天然原子。

## 六、分片设计与常见误区

1. 分片不是越多越好。每个分片有堆内存、文件句柄和查询协调成本；大量小分片会降低稳定性。
2. 映射动态扩张会造成 mapping explosion；对动态字段数量设置限制，并将任意属性放入受控结构。
3. 避免对高基数 `text` 使用 fielddata；为聚合新建 `keyword` 子字段。
4. 不要用频繁 `refresh=true` 追求实时性，它会生成小段、拖慢写入；按业务容忍度设置 refresh interval。
5. `match` 与 `term` 的差别取决于字段映射和分析器，查询前先检查 mapping 与实际 token。

排查使用 `_search` 的 `profile`、`_explain`、`_nodes/stats`、`_cat/shards` 和慢查询日志。重点观察 JVM 堆、GC、线程池拒绝、段数量、合并压力、分片大小偏斜和查询的聚合内存占用。
