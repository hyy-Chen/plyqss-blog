> 很多安全方案看起来「过度设计」，是因为没看见它要填的坑。内网白名单、Basic Auth、Session、API Key、JWT、OAuth2、mTLS，每一代都不是拍脑袋换花样，而是上一代赖以成立的某个假设被现实打破了。这篇按时间线把「老一辈怎么做 → 哪里不合理 → 为什么必须改」讲清楚。

## 一、先把三个词分开

| 概念                | 回答的问题             | 典型产物                                 |
| ------------------- | ---------------------- | ---------------------------------------- |
| 认证 Authentication | **你是谁**             | 口令、证书、生物特征、OIDC ID Token      |
| 授权 Authorization  | **你能做什么**         | 角色、权限、scope、策略引擎结果          |
| 审计 Accounting     | **你做过什么**         | 不可篡改日志、谁在何时用哪个凭证改了什么 |
| 会话管理            | **这个身份还能用多久** | Session、Token、刷新与撤销               |

老系统最典型的毛病不是「密码存得不够复杂」，而是**把认证当成了授权**：登录成功就一路放行，接口里靠 `if user.isAdmin` 散落判断，出了事查不到是谁操作的。鉴权方案演进，很大程度上是在把这三件事拆开、标准化、集中化。

一次合格的鉴权，至少要能回答四问：

```text
1. 凭证是谁签发的？（信任根）
2. 凭证属于谁？（主体标识）
3. 凭证允许做什么、有效期多长？（边界）
4. 凭证现在还有效吗？（撤销/状态）
```

后面每一代方案，都可以拿这四问去体检。

## 二、第 0 代：网络边界就是身份

**老一辈操作**：服务部署在内网，防火墙配 IP 白名单，数据库只对应用网段开放，运维说「内网是安全的，不用再加认证」。调用方靠来源 IP 判断，接口不校验身份。

**当时的合理性**：机器少、拓扑固定、人也在同一个办公室，边界确实清晰且可控。加认证要自己造轮子，成本相对高。

**隐含假设被打破**：

| 假设             | 现实                                                  |
| ---------------- | ----------------------------------------------------- |
| 内网里都是自己人 | 一台被攻陷的机器就是内网跳板，横向移动无阻力          |
| IP 能标识主体    | NAT、容器漂移、弹性伸缩、云函数让 IP 频繁变化且可复用 |
| 边界只有一道     | VPN、合作伙伴专线、第三方 SaaS、移动端把边界切碎      |
| 攻击来自外部     | 大量数据泄露源于内部账号与误配置                      |

**为什么改**：边界一旦被穿透，内部就是「平坦」的，没有任何第二道防线。于是有了零信任的第一原则——**从不因为网络位置授予信任，每次访问都要验证主体与权限**。这不是说防火墙没用，而是它降级成一层纵深防御，不再充当身份系统。

## 三、第 1 代：Basic / Digest Auth——每次都把口令递过去

**老一辈操作**：HTTP Basic 把 `base64(username:password)` 放进 `Authorization` 头；稍微讲究一点的用 Digest，传口令相关的哈希和挑战值。

```text
Authorization: Basic dXNlcjpwYXNz  ← 只是编码，不是加密
```

**当时的合理性**：RFC 现成、浏览器原生支持、服务端无状态、三行代码就能保护一个内部管理页。

**不合理之处**：

- Base64 是编码，明文等价物，**必须依赖 TLS**；一旦某个环节降级或日志打印了 header，口令直接泄露。
- **每个请求都携带长期凭证**，泄露半径等于整个账号的全部权限，且无法只撤销「某次会话」。
- 口令是**共享秘密**：服务端要能验证就得持有可比对的东西，一旦数据库被拖，攻击者可离线爆破或直接重放。
- 无法表达权限边界、过期时间、审计主体；浏览器还会缓存，登出都做不干净。
- Digest 虽不传明文，但要求服务端存明文或等价哈希，反而更糟，最终也没普及。

**为什么改**：核心矛盾是「长期口令被高频使用」。改进方向是把**一次性登录**和**后续请求凭证**分开——认证一次，发一个短期、可撤销、边界受限的凭证。这就是 Session 的由来。顺带，口令存储也从明文 / MD5 换成 bcrypt、scrypt、Argon2 这类慢哈希。

## 四、第 2 代：表单登录 + 服务端 Session + Cookie

**老一辈操作**：登录成功后在 Redis/内存里建一条 `session_id → user` 记录，把随机 `session_id` 写进 Cookie，之后浏览器自动带上。

```text
POST /login  → Set-Cookie: sid=<随机高熵值>; HttpOnly; Secure; SameSite=Lax
GET  /api    → Cookie: sid=... → 服务端查 session 表 → 得到身份
```

**它解决了什么**：口令只在登录时出现一次；`sid` 是随机不透明串，本身不含信息；服务端删掉记录就能立刻撤销；权限变更下一次请求即生效。这些优点到今天依然成立。

**规模化后暴露的问题**：

| 问题          | 说明                                                          |
| ------------- | ------------------------------------------------------------- |
| 有状态        | 每台应用都要能读到同一份 session，强依赖共享存储              |
| 跨域/多端困难 | Cookie 受同源策略约束，多个域名、移动 App、第三方调用都不顺手 |
| 粘性会话      | 早期用本地内存 + 负载均衡粘滞，节点一挂用户集体掉线           |
| CSRF          | 浏览器自动携带 Cookie，恶意站点可借用户身份发起请求           |
| 状态同步成本  | 跨区域部署时，session 存储的延迟与容灾成为链路瓶颈            |

**为什么改**：不是 Session 不安全，而是**「服务端必须在线查状态」这个约束**和分布式、多端、微服务化相冲突。于是出现两条分叉：

- **把状态挪到客户端**：自包含令牌（JWT），验签即可，不需要查库。
- **把状态集中成独立服务**：统一认证中心 / IdP，业务侧只做校验，即后来的 SSO 与 OIDC。

值得强调的是，很多团队「迁到 JWT」只是因为听说无状态更快，结果把撤销、权限变更、登出全做丢了。**Session 至今仍是浏览器第一方场景里很稳的选择**，这点会在《会话、Cookie 与令牌》里展开。

## 五、第 3 代：固定 API Key / AK-SK——机器对机器

**老一辈操作**：给调用方分配一个长期字符串，`X-Api-Key: abc123`，或者 `appkey` + `appsecret` 做签名，写进配置文件、代码常量、CI 变量，常年不换。

**当时的合理性**：调用方是脚本或服务，没有浏览器、没有登录交互，需要一个能离线验证的机器身份。

**不合理之处**：

- **永不过期**：一旦泄露（日志、Git 仓库、截图、离职员工电脑），可能几年都有效，且没人知道。
- **权限颗粒粗**：一个 key 往往能调全部接口，无法按最小权限收敛。
- **无主体语义**：key 属于「某个系统」，出事时追不到是哪个实例、哪个人、哪次发布在用。
- **只认证不防篡改**：只带 key 不签名时，中间人可以改参数；签名写得随意（拼字符串 MD5）又容易被绕过。
- **密钥分发是手工流程**：轮换意味着协调所有调用方同时改，于是干脆不轮换。

**为什么改**：需要让机器凭证也具备「短期、可自动轮换、可审计、可绑定请求内容」的属性。这就是两条现代路线：云上用 IAM 角色 / 工作负载身份（STS 临时凭证、OIDC 联邦），服务间用 mTLS 证书或 SPIFFE 身份；开放平台则用带时间戳与 nonce 的规范化签名（见《请求签名与防重放》）。

## 六、第 4 代：自研 Token 与长寿命 JWT

**老一辈操作**：自己拼一个 `userId + 时间戳 + MD5(secret)` 当 token；或者改用 JWT 但设 30 天过期，把用户手机号、角色、甚至余额塞进 payload，服务端只验签名。

**它解决了什么**：跨域、多端、无共享存储，网关层验签就能拿到身份，横向扩展确实轻松。

**不合理之处（也是 JWT 被误用最多的地方）**：

| 反模式                 | 后果                                                            |
| ---------------------- | --------------------------------------------------------------- |
| 超长有效期             | 等于把长期凭证又请了回来，泄露半径回到第 1 代                   |
| 无撤销路径             | 改密码、禁用账号、员工离职后旧 token 依然能用                   |
| payload 放敏感数据     | JWT 只是签名不是加密，Base64 一解全看见，还会进日志和浏览器缓存 |
| 只验签名不验 claim     | 不校验 `iss`/`aud`/`exp`/`nbf`，等于接受任意自己签的令牌        |
| 信任 header 里的 `alg` | `alg: none`、RS256→HS256 混淆等历史漏洞                         |
| 把 JWT 当 session 用   | 权限变更后 token 里的旧角色仍生效，越权窗口长达整个 TTL         |

**为什么改**：业界逐渐收敛到「**短期访问令牌 + 可轮换刷新令牌 + 明确的撤销机制**」，并把签发这件事交给专业的 IdP（OIDC），而不是每个业务自己造签名格式。JWT 没被淘汰，但被限定在「短时、自包含、可验证」的合适位置上。

## 七、第 5 代：现在的样子

```text
用户/客户端
  → IdP 认证（口令 / MFA / Passkey / 企业联邦）
  → 拿到短期 Access Token（分钟级）+ 轮换式 Refresh Token
  → 访问资源服务器：验签 + 校验 iss/aud/scope/exp + 查撤销状态
  → 网关/策略引擎做授权，业务代码只消费已确认的身份
  → 全链路记录审计（主体、凭证指纹、决策结果）
```

关键变化有五个：

1. **认证集中化**：一个 IdP 统一管口令策略、MFA、风控、锁定与审计，业务不再各自存口令。
2. **凭证短期化**：泄露窗口从「永久」压到分钟级，配合刷新令牌轮换与重放检测。
3. **身份与授权分离**：token 声明 `scope`/角色，具体能不能做由策略引擎（RBAC/ABAC/ReBAC）判定，且能集中改。
4. **凭证绑定**：Bearer Token 拿到就能用，DPoP / mTLS 绑定让令牌只能由持有对应私钥的一方使用，被盗也难以重放。
5. **机器身份一等公民**：工作负载身份、短期证书、自动轮换，替代塞在配置里的静态密钥。

OAuth2 与 OIDC 的分工常被混淆，一句话记：**OAuth2 是授权框架（第三方凭什么能替我访问资源），OIDC 是在它上面加的一层身份（你是谁）**。用 OAuth2 的 access token 去当「登录凭证」是经典误用。

## 八、把演进动力归纳成五条

| 驱动力       | 具体表现                        | 直接催生的改进             |
| ------------ | ------------------------------- | -------------------------- |
| 规模         | 单体 → 分布式 → 多区域          | 无状态校验、集中式 IdP     |
| 边界消失     | 内网、VPN、云、移动端、合作伙伴 | 零信任、mTLS、逐次验证     |
| 泄露半径     | 长期凭证一旦泄露影响无上限      | 短期令牌、自动轮换、绑定   |
| 合规与可追责 | 等保、审计、数据访问留痕        | 统一审计、最小权限、可撤销 |
| 体验         | 多系统重复登录、多端            | SSO、OIDC、Passkey         |

**贯穿始终的一条原理**：凭证的有效期与权限范围，应该和它承担的风险成反比。老做法的问题几乎都能归结为「用一个长期、宽权限、无审计的凭证，去覆盖越来越大的系统」。

## 九、老系统改造的务实顺序

不要一上来「全面上零信任」。按收益/成本排序：

1. **先止血**：全站 TLS；口令改慢哈希；清掉代码与 Git 里的静态密钥；日志与错误响应脱敏。
2. **补撤销**：给现有 token 加短 TTL、`jti` 黑名单或 `token_version` 版本号，让禁用账号立即生效。
3. **收权限**：把散落的 `isAdmin` 判断收敛到统一鉴权中间件与策略表，补齐审计日志。
4. **换签发**：接入 OIDC / IdP，统一 MFA 与登录风控，业务侧只做校验。
5. **缩凭证**：访问令牌分钟级、刷新令牌轮换、密钥自动轮换与双密钥灰度。
6. **强绑定**：对高敏接口上 DPoP / mTLS，服务间上工作负载身份。

每一步都能独立上线、独立回滚，比「推倒重来」现实得多。

## 十、实践清单

- 任何位置（URL、日志、错误体、埋点、Referer）都不出现凭证；`Authorization` 头单独脱敏。
- 认证、授权、审计三件事分开实现，禁止「登录成功即全放行」。
- 每个凭证都能回答四问：谁签发、属于谁、边界与有效期、当前是否仍有效。
- 凭证有明确撤销路径；权限变更在下一次请求生效，而不是等 token 过期。
- 机器凭证与人类凭证走不同的签发与轮换机制，前者必须自动化。
- 高危操作做逐步认证（step-up authentication，重新验证口令或 MFA），而不是只依赖「已登录」这个状态。
- 鉴权逻辑在网关/中间件统一执行，业务代码拿到的是**已验证的身份对象**，不是原始 header。

## 十一、面试速答

**Q：为什么不能只用 IP 白名单做鉴权？**
IP 标识的是网络位置而不是主体，且会被 NAT、容器漂移、地址复用削弱；一旦内网有单点失陷，整张内网没有任何第二道防线。零信任要求每次访问独立验证主体和权限，白名单只能当附加的纵深防御。

**Q：Basic Auth 到底差在哪？**
每个请求都携带长期口令，泄露半径等于账号全部权限，服务端还得持有可比对凭证，且无法表达过期、权限边界与撤销。根因是「长期凭证被高频使用」，Session 和新式令牌都是把「一次认证」与「后续凭证」拆开。

**Q：JWT 为什么不能完全替代 Session？**
JWT 无状态带来扩展便利，但撤销、登出、权限即时变更、敏感信息泄露都变难。生产常见做法是短期 access token + 服务端可撤销的 refresh token，或用不透明引用令牌配合 introspection，在「无状态」和「可控制」之间取平衡。

**Q：为什么说 HTTPS 不等于做了鉴权？**
TLS 只证明「你在和持有该证书私钥的服务器通信」，并保护链路机密性与完整性；它既不告诉服务端「请求者是谁」，也不限制「能做什么」。用户级身份、权限、审计仍然需要应用层的认证授权体系。

## 十二、一句话收尾

鉴权机制的演进，本质是**不断缩小「一次凭证泄露能造成多大损失」**：从把信任押在网络位置，到押在长期口令，再到押在短期、受限、可撤销、可审计、绑定主体的凭证上。理解这条线，就不会觉得 MFA、OIDC、mTLS 是「为了复杂而复杂」。
