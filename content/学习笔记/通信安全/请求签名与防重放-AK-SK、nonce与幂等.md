> 开放平台、Webhook、服务间调用里有一类需求 TLS 满足不了：需要一个**可独立验证、可存档举证**的证据，证明「这条请求确实由某个主体签发，且内容没被改过」。老一辈的做法是拼个字符串 MD5 再加个 `appkey`，看着签了名，其实处处是洞。这篇从旧方案的漏洞一路推到规范化签名、防重放和令牌绑定。

## 一、为什么 TLS 不够

TLS 保护的是**连接**，一旦请求经过网关、消息队列、重试队列、第三方回调或落库审计，连接在中间就断了：

| 场景                | 需要什么                       | TLS 为什么不够                   |
| ------------------- | ------------------------------ | -------------------------------- |
| 开放平台 API        | 识别调用方、限制权限、按量计费 | 需要应用级主体与可验证签名       |
| Webhook 回调        | 接收方确认「确实来自支付平台」 | 回调是反向连接，且可能经代理转发 |
| 异步消息 / 离线对账 | 事后能验证消息未被篡改         | 连接早已结束，只剩报文           |
| 跨域多跳调用        | 中间节点不可完全信任           | TLS 逐跳终止，端到端证据缺失     |
| 审计与抗抵赖        | 谁签发的、签的是哪份内容       | 传输层日志不携带业务身份证据     |

签名提供的是**报文级**保证：身份认证（谁签的）、完整性（改没改）、以及配合 nonce/时间戳后的新鲜性（是不是重放的）。注意它默认**不提供机密性**，敏感数据仍要 TLS 或额外加密。

## 二、老一辈的签名，以及每一处不合理

典型实现大概长这样：

```text
GET /pay?amount=100&appkey=ak_123&sign=MD5(amount + appsecret)
```

或者更随意：把所有参数按前台传来的顺序拼接，加个常量 `secret` 做个哈希。

| 老做法                 | 不合理之处                                                   | 攻击方式                       |
| ---------------------- | ------------------------------------------------------------ | ------------------------------ |
| 只带 `appkey` 不签名   | 主体可伪造                                                   | 改掉 appkey 即冒充他人         |
| 用 MD5/SHA1 拼接       | 无密钥参与的哈希只是校验和；有密钥的裸哈希存在长度扩展等隐患 | 篡改参数后重算                 |
| 参数顺序依赖请求原样   | 前后端/网关解析顺序不一致，签名随机失败；攻击者可加重复参数  | 参数 pollution 绕过校验        |
| 只签部分字段           | method、host、path、body 没进签名                            | 换成退款接口或改 host 仍能通过 |
| secret 放 URL / 前端   | 进入历史、Referer、日志、浏览器缓存                          | 直接捡密钥                     |
| 时间戳不校验           | 报文永久有效                                                 | 无限次重放                     |
| nonce 常量或不存在     | 即使有时间戳，窗口内可重放                                   | 重复扣款                       |
| 一个 secret 全接口通用 | 权限颗粒粗，泄露即全量失陷                                   | 越权调用                       |
| 无密钥轮换             | 泄露后只能全量停机改配置                                     | 长期潜伏                       |

最隐蔽的一类是**「签了名但没签全」**：只签 body 不签 path 和 method，攻击者把同一份合法报文从查询接口重放到转账接口；只签 query 不签 body，金额字段就能随便改。签名方案的安全性取决于**待签串覆盖了哪些语义**，而不是哈希算法有多新。

## 三、规范化待签串（Canonical Request）

现代方案（AWS SigV4、各家开放平台）的共同套路是先构造一个双方都能**确定性重建**的字符串：

```text
HTTP_METHOD + "\n" +
CanonicalURI + "\n" +          // 路径规范化，URI 编码规则固定
CanonicalQueryString + "\n" +  // 参数按 key 排序，重复参数显式处理
CanonicalHeaders + "\n" +      // 只签约定 header（host、x-date、content-type 等）
SignedHeaders + "\n" +
Hex(SHA256(body))              // 空 body 也要有确定的哈希值
```

然后再构造「待签字符串」并算 MAC：

```text
StringToSign =
  ALGORITHM + "\n" +
  ISO8601_TIMESTAMP + "\n" +
  credential_scope + "\n" +     // 日期 / 区域 / 服务 / 版本
  Hex(SHA256(CanonicalRequest))

signature = Hex(HMAC-SHA256(derived_key, StringToSign))
derived_key = HMAC 链式派生(secret, date, region, service)  // 逐级派生，限制密钥作用域
```

为什么要这么啰嗦：

- **排序与显式编码**消除「同一请求有多种字节表示」的歧义，避免代理改写参数顺序导致验签失败或被绕过。
- **签 host / path / method / body 哈希**把语义锁死，报文不能被搬去别处使用。
- **派生密钥按日期与服务作用域**限制单密钥影响面，也让轮换可灰度。
- **HMAC 而非裸哈希**保证只有持密钥者能生成，且不受长度扩展影响。

请求侧带的信息应该是：

```http
Authorization: <ALG> Credential=<AK>/<scope>, SignedHeaders=host;x-date;content-type, Signature=<hex>
X-Date: 20261112T091500Z
X-Nonce: 9f2c7a1e-...
```

**secret 永远不出现在请求里**，只作为本地计算输入。

## 四、防重放：时间戳 + nonce + 一次性存储

签名保证「没被改」，但不保证「只被用一次」。防重放要三件套：

| 要素       | 作用                         | 参数建议                 |
| ---------- | ---------------------------- | ------------------------ |
| 时间戳     | 限定有效期，让旧报文自然失效 | 窗口 ±5 分钟，超窗直接拒 |
| nonce      | 窗口内唯一标识一次请求       | 高熵随机，至少 128 bit   |
| 服务端去重 | 记住窗口内用过的 (AK, nonce) | Redis `SET NX EX=窗口×2` |

```go
// 原子去重：窗口内第二次使用同一个 nonce 直接拒绝
ok, err := rdb.SetNX(ctx, fmt.Sprintf("nonce:%s:%s", ak, nonce), 1, 10*time.Minute).Result()
if err != nil || !ok {
    return ErrReplayed
}
```

几个实现细节：

1. **先校验时间戳再查 nonce**，否则过期报文也占存储；同时拒绝未来时间超过偏差的请求，防客户端时钟错误或故意拖延。
2. **去重 TTL 要大于时间窗口**，否则攻击者等到 TTL 过期、但报文仍在窗口内时可以重放。
3. **校验顺序**：解析 → 时间窗 → nonce 去重 → 查 AK 对应密钥 → 重建待签串 → 常量时间比较签名。把便宜的检查放前面，抗刷。
4. **比较必须用 `subtle.ConstantTimeCompare`**，普通 `==` 的早退特性会泄露逐字节信息（时序侧信道）。
5. **失败信息要统一**，别回「nonce 重复」还是「签名错误」区分太细，减少探测面。

## 五、重放 ≠ 幂等

这两个概念经常混用，但保护的不是同一件事：

|      | 防重放                        | 幂等                               |
| ---- | ----------------------------- | ---------------------------------- |
| 针对 | 攻击者/网络复制同一份合法报文 | 客户端重试、超时后的重复发起       |
| 主体 | 报文级（同一签名与 nonce）    | 业务级（同一 `Idempotency-Key`）   |
| 结果 | 第二次请求被拒绝              | 第二次请求返回首次结果，不重复执行 |
| 存储 | 短窗口内 nonce                | 较长周期的业务键 → 结果/状态       |

**两者都要做**。只做重放防护，客户端超时重试会因为 nonce 相同被拒（体验差）；只做幂等，攻击者拿着截获的合法报文在有效期外仍能构造新的 nonce 重新发起。生产常见组合是：网关层做签名 + 防重放，业务层做幂等键与状态机。

## 六、AK/SK 的生命周期与分级

```text
AK（Access Key ID）    可公开，用于索引密钥与审计主体
SK（Secret Access Key） 只在签发时可见一次，服务端存加盐哈希或由 KMS 托管
scope                  绑定环境 / 服务 / 接口组，限制单一密钥的权限面
```

| 机制       | 做法                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| 最小权限   | 按 AK 绑定接口白名单、IP 段、配额与租户范围                                 |
| 双密钥灰度 | 同时有效 `primary`/`secondary`，先发新密钥、观察流量、再停用旧的            |
| 自动轮换   | 短期凭证（STS/OIDC 联邦）优先；静态 SK 设强制过期与到期告警                 |
| 泄露处置   | 立即吊销 AK、查该 AK 的调用日志、按 scope 评估影响面、回滚已签发凭证        |
| 审计       | 记录 AK、nonce、签名算法版本、来源 IP、决策结果，绝不记录 SK 或完整签名原文 |

Webhook 场景要额外注意：接收方验签用的公钥/密钥应支持**多版本并存**，否则提供方轮换密钥时会造成批量验签失败；同时要校验时间戳，避免攻击者拿几个月前的合法回调重复触发发货。

## 七、Bearer Token 的弱点与令牌绑定

AK/SK 签名是「每请求签一次」，而 Bearer Token 是「签一次、用很多次」——**谁拿到 token 谁就能用**，这是它最大的结构性弱点（日志泄露、XSS、代理缓存、恶意依赖都可能让 token 外流）。

现代改进方向是**把令牌和持有者的私钥绑定**：

| 方案             | 绑定方式                                                     | 效果                                           |
| ---------------- | ------------------------------------------------------------ | ---------------------------------------------- |
| mTLS-bound token | token 内嵌客户端证书指纹 `cnf`                               | 必须同时持有证书私钥才能使用                   |
| DPoP             | 每个请求用客户端私钥签一份 proof（含 method/URL/ nonce/jti） | 令牌被盗也无法单独重放，且请求被绑定到具体 URL |
| 短期令牌 + 轮换  | 缩小时间窗口                                                 | 降低泄露收益，不改变结构弱点                   |

DPoP 的 proof 本质上就是把本文的「规范化签名」思路套在 OAuth 令牌上：签 method 与目标 URI、带服务端下发的 nonce 与时间戳，服务器同时校验令牌签名和 proof 签名。它解决的正是老一辈「一个字符串走天下」的问题。

## 八、实践清单

- 待签串覆盖 method、host、规范化 path、排序后的 query、约定 header、body 哈希；任何影响语义的字段都要签。
- 用 HMAC-SHA256（或更强的 Ed25519 签名），禁用 MD5/SHA1 与「secret 直接拼字符串」。
- 时间戳窗口 ±5 分钟 + 高熵 nonce + Redis 原子去重，去重 TTL 大于窗口。
- 签名比较用常量时间函数，失败信息统一，日志脱敏 AK/SK/签名。
- 支持双密钥灰度与算法版本字段，为轮换留出窗口。
- 网关做签名与防重放，业务做幂等；两者不要互相替代。
- 高敏接口考虑 DPoP / mTLS 绑定，别让长期 Bearer Token 成为唯一凭证。
- 用「篡改 path / 重放旧报文 / 加重复参数 / 改 body / 换 host」五组用例做回归测试。

## 九、面试速答

**Q：已经有 HTTPS，为什么还要对请求签名？**
TLS 保护逐跳连接，不提供跨网关、异步投递和事后审计可验证的报文级证据。签名能证明是哪个主体签发、内容未被篡改，并在配合 nonce/时间戳后防止重放。

**Q：签名方案最容易出错的地方是什么？**
不是哈希算法，而是待签串覆盖不全和规范化不确定：只签 body 不签 path/method 会被搬到别的接口，参数顺序或编码不统一会被绕过或误拒。其次是忽略时间戳与 nonce，导致合法报文可无限重放。

**Q：防重放和幂等有什么区别？**
防重放针对同一份报文被复制，目标是拒绝第二次；幂等针对业务上重复发起同一操作，目标是返回首次结果且不重复执行。前者在网关短窗口完成，后者在业务层用 `Idempotency-Key` 与状态机实现，二者需同时具备。

**Q：Bearer Token 泄露为什么难防，怎么改进？**
令牌本身即凭证，任何拿到它的人都能用，服务端无法区分合法持有者。改进是缩短有效期、刷新轮换，以及用 DPoP / mTLS 把令牌绑定到客户端私钥，使「只有令牌」不足以发起请求。

## 十、一句话收尾

签名方案的强度不取决于用了多新的哈希，而取决于三件事：**签了哪些语义、待签串是否唯一确定、旧报文还能不能再用一次**。老一辈的 MD5 拼接，恰好在这三处全都没答好。
