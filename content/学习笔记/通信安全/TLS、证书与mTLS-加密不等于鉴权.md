> 「我们已经全站 HTTPS 了」是最常见的安全错觉。TLS 解决的是**链路**问题：机密性、完整性、以及（通常只有）服务器的身份认证。它不回答「这个请求代表哪个用户」「他能不能删这条订单」。这篇讲清 TLS 到底保证了什么、证书信任是怎么来的、握手为什么一路改到 TLS 1.3，以及服务间为什么还要 mTLS。

## 一、先拆开四件事

| 目标           | 由谁提供                     | 典型误解                                        |
| -------------- | ---------------------------- | ----------------------------------------------- |
| 机密性         | TLS 对称加密                 | 「加密了就不会被篡改」——还需要完整性校验        |
| 完整性         | AEAD / MAC                   | 「有 MAC 就知道是谁发的」——只说明密钥持有者参与 |
| 服务器身份认证 | 证书链 + 域名校验            | 「有证书就是可信站点」——DV 证书只证明域名控制权 |
| 客户端身份认证 | 应用层凭证或 mTLS 客户端证书 | 「HTTPS 已经认证了客户端」——默认没有            |

HTTPS 只在**客户端验证服务端**这一侧做了认证。浏览器不会向服务器出示证书，服务器识别用户仍要靠 Cookie、Token、口令等应用层机制。这就是为什么「上了 HTTPS 还要做鉴权」不是重复建设。

另外两个常被忽略的边界：TLS 只保护传输中的字节，**不保护**服务端解密后的数据、不保护落到日志里的明文、也不防应用层的越权与注入。

## 二、证书校验到底在校验什么

```text
叶子证书 → 中间 CA → 根 CA（预置在操作系统/浏览器信任库）
         ↓
   1. 链可追溯且签名有效
   2. 域名匹配 SAN（不是 CN）
   3. 在有效期内
   4. 未被吊销（CRL / OCSP / OCSP Stapling）
   5. 密钥用法与策略符合（EKU serverAuth 等）
```

常见翻车点：

| 错误                                        | 后果                                    |
| ------------------------------------------- | --------------------------------------- |
| `InsecureSkipVerify: true` / `verify=False` | 关闭全部校验，中间人可随意伪造证书      |
| 只比对 CN 不比对 SAN                        | 现代浏览器早已忽略 CN，配置与校验不一致 |
| 自签证书直接塞进客户端代码                  | 私钥随客户端分发，等于没有秘密          |
| 忽略吊销                                    | 私钥泄露后证书仍被信任，直到过期        |
| 用通配证书跨环境复用                        | 一张证书泄露，生产/测试全受影响         |
| 证书过期无告警                              | 定时故障，且常在半夜触发                |

Go 里正确的做法是把自签 CA 作为 **RootCAs** 加入信任池，而不是关闭校验：

```go
pool := x509.NewCertPool()
pool.AppendCertsFromPEM(caPEM)
client := &http.Client{
    Transport: &http.Transport{
        TLSClientConfig: &tls.Config{
            RootCAs:    pool,
            MinVersion: tls.VersionTLS12,
        },
    },
}
```

## 三、握手演进：每一次改动都对应一次教训

| 阶段                       | 做法                           | 问题                                                       | 改进                                     |
| -------------------------- | ------------------------------ | ---------------------------------------------------------- | ---------------------------------------- |
| TLS 1.0/1.1 + RSA 密钥传输 | 客户端用服务器公钥加密预主密钥 | 服务器私钥一旦泄露，**历史所有流量**可解密；无前向保密     | 改用 ECDHE 临时密钥交换                  |
| TLS 1.2                    | 2-RTT 握手、可选加密套件很多   | 协商慢；RC4/CBC/压缩等导致 BEAST、CRIME、POODLE 等一串漏洞 | 收敛套件、禁用压缩与老旧算法             |
| TLS 1.3                    | 1-RTT、只留 AEAD、加密握手消息 | 0-RTT 早期数据**可重放**                                   | 仅对幂等请求开放 0-RTT，服务端做重放窗口 |

**前向保密（PFS）**是这里最关键的概念：会话密钥由双方临时生成的 ECDHE 参数导出，用完即弃，长期私钥只用于签名认证。这样即使日后私钥泄露，过去录下的流量也解不开——这是「为什么必须淘汰 RSA 密钥传输」的根本原因，不只是性能。

TLS 1.3 的 **0-RTT** 把延迟降到零，但早期数据没有服务端的新鲜性保证，攻击者录下 `POST /transfer` 重放就可能重复执行。生产上要么全局关闭，要么只允许 GET/HEAD 等幂等请求，并在服务端做一次性票据与重放窗口。

## 四、老一辈的传输层操作与不合理之处

| 老做法                     | 当时的理由                      | 为什么现在不行                                        |
| -------------------------- | ------------------------------- | ----------------------------------------------------- |
| 内网 HTTP 明文             | 「内网可信、加 TLS 有性能损耗」 | 边界消失 + 横向移动；现代 CPU 下 TLS 开销很小         |
| 登录页 HTTPS、其余 HTTP    | 省证书与改造成本                | Cookie/Token 在明文请求里完整暴露，等于没保护         |
| 只做单向 TLS，服务间不认证 | 靠 IP 白名单和 VPC 隔离         | 一台失陷实例可冒充任意内部服务                        |
| 把 token 放 URL query      | 简单、方便调试                  | 进入浏览器历史、Referer、代理日志、CDN 日志           |
| 证书固定写死在客户端       | 防中间人                        | 轮换困难、容易把整批客户端锁死，需备份 pin 与应急通道 |
| 自己实现加密协议           | 「够用就行」                    | 几乎必然在 nonce、填充、认证顺序上出错                |

还有一条运维层面的：**证书与私钥的分发方式**。早期靠人工拷贝 PEM 到机器、多年不换，泄露无感知。现在靠 ACME 自动签发、短周期证书（如 90 天甚至更短）、集中密钥管理（KMS/HSM）与自动轮换，把「凭证长期有效」这个老问题在传输层也解决一遍。

## 五、mTLS：让服务之间也互相证明身份

单向 TLS 里服务端不知道「调用方是哪台服务」。mTLS 在握手中追加客户端证书：

```text
ClientHello → ServerHello + 服务端证书 → 客户端校验
           → 服务端发送 CertificateRequest
           → 客户端发送自己的证书 + CertificateVerify（用私钥签名）
           → 双方基于证书里的身份做授权决策
```

**为什么服务间也需要身份**：

1. 零信任下网络位置不授予信任，服务 A 调用服务 B 必须独立验证。
2. 授权策略要能写成「只有 `payment-service` 能调 `ledger/write`」，而不是「10.0.0.0/8 能调」。
3. 审计要能落到具体工作负载身份，而不是一个共享 IP。

**落地形态**：服务网格（Istio、Linkerd）由 sidecar 统一做 mTLS 与证书轮换，业务代码零改动；非网格环境可用 SPIFFE/SPIRE 给每个工作负载签发短生命周期 SVID，身份格式形如：

```text
spiffe://prod.cluster/ns/payments/sa/order-api
```

关键提醒：**mTLS 提供的是工作负载身份，不等于用户身份，也不等于授权**。一个服务代表成千上万个用户发起调用，仍需把终端用户上下文（token 或可信的断言）透传下去，并在被调用方做用户级鉴权。否则「服务有权限」会变成「绕过用户权限」的后门。

## 六、与 TLS 配套但常被漏掉的几件事

- **HSTS**：`Strict-Transport-Security` 让浏览器强制 HTTPS，防首次请求的 SSL Stripping；上 `preload` 前要确认所有子域都已支持。
- **重定向与混合内容**：`http://` 301 到 `https://` 的那一次请求仍是明文，页面里任何 `http://` 子资源都是降级入口。
- **Cookie 属性**：`Secure` 依赖 HTTPS，缺了它会话凭证可能走明文（见《会话、Cookie 与令牌》）。
- **SNI / ECH**：SNI 暴露目标域名；ECH 逐步解决，但部署与中间件兼容性要评估。
- **TLS 终止点**：在负载均衡或 CDN 终止后，回源链路是否加密、内部头（如 `X-Forwarded-*`）是否可被外部伪造，都要明确。
- **头部脱敏**：网关日志、APM、错误上报默认会采集 header，`Authorization` 与 `Cookie` 必须显式过滤。

## 七、证书与密钥的生命周期

```text
生成（安全随机、私钥不出 HSM/KMS）
  → 签发（ACME / 内部 CA，SAN 明确）
  → 分发（自动化，不经聊天工具/工单附件）
  → 部署（支持双证书灰度，避免轮换中断）
  → 监控（到期告警、链完整性、吊销状态）
  → 轮换（短周期、可回滚）
  → 吊销（私钥泄露时立即执行，并确认客户端真的检查）
```

最常见的生产事故不是被攻击，而是**证书过期**和**轮换时新旧 CA 未并行信任**。所以轮换方案一定要包含「新旧信任根并存」的灰度窗口。

## 八、实践清单

- 全链路 TLS（含内网与回源），最低 TLS 1.2，优先 1.3；禁用老旧套件与压缩。
- 客户端一律开启完整证书校验；内部 CA 通过 `RootCAs` 注入，绝不关闭验证。
- 高敏服务禁用 0-RTT；若启用，仅放行幂等请求并做票据一次性校验。
- 服务间用 mTLS / 工作负载身份，并把用户身份透传到下游做二次授权。
- 证书私钥由 KMS/HSM 托管，自动签发与轮换，配置到期告警。
- 凭证不进 URL、不进日志；所有采集组件对 `Authorization`/`Cookie` 做脱敏。
- 定期验证：吊销是否生效、TLS 终止点之后是否仍加密、内部头能否被伪造。

## 九、面试速答

**Q：HTTPS 已经加密了，为什么还要做用户鉴权？**
TLS 只保证链路机密性、完整性和服务器身份，默认不认证客户端，也不表达「这个用户能做什么」。用户身份、权限范围、撤销与审计都属于应用层，需要 Cookie/Token/证书等机制另行提供。

**Q：TLS 1.3 的 0-RTT 有什么风险？**
早期数据基于上次会话的 PSK，攻击者可以录下来重放，服务端无法确认新鲜性。因此只应对幂等请求开放，并配一次性票据与重放窗口；写操作应走完整 1-RTT 握手。

**Q：为什么要前向保密？**
RSA 密钥传输下，服务器私钥泄露就能解密所有历史录制流量。ECDHE 每次握手生成临时密钥、用完即弃，长期私钥只用于签名，历史会话不受影响。

**Q：mTLS 做完是不是内部调用就安全了？**
不是。mTLS 只证明调用方是哪个工作负载，既不代表终端用户身份，也不做接口级授权。仍需透传用户上下文并做用户级鉴权与审计，否则服务身份会变成越权后门。

## 十、一句话收尾

TLS 把「路上有没有人偷看和伪造」解决了，但「谁在说话、他被允许做什么、事后能不能查清」始终是应用层的责任。把这两层混为一谈，是很多「我们已经很安全了」的起点。
