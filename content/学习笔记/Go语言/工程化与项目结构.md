> 会写 Go 语法和能维护一个长期演进的 Go 服务是两件事。本文聚焦后者：目录怎么分、错误怎么传、配置与启动怎么收敛、并发与关闭怎么收尾。

## 一、目录组织

Go 没有官方强制的目录规范，但社区已形成较稳定的约定。关键是**按依赖方向和可见性分层**，而不是按技术名词堆文件夹。

```text
myservice/
├── cmd/
│   └── api/main.go          # 极薄：组装依赖、启动、信号处理
├── internal/
│   ├── order/               # 按业务域划分，而非按层划分
│   │   ├── handler.go       # HTTP/gRPC 适配
│   │   ├── service.go       # 业务编排
│   │   ├── repo.go          # 持久化实现
│   │   └── model.go
│   ├── config/
│   └── platform/            # 数据库、缓存、日志等基础设施客户端
├── api/
│   └── openapi.yaml         # 对外契约
├── migrations/
├── configs/config.yaml
├── go.mod
└── Makefile
```

| 目录       | 作用                           | 约束                         |
| ---------- | ------------------------------ | ---------------------------- |
| `cmd`      | 每个可执行程序一个子目录       | 只做装配，不写业务逻辑       |
| `internal` | 不希望被外部仓库 import 的代码 | Go 编译器强制可见性限制      |
| `pkg`      | 明确打算被外部复用的库         | 放入前先问是否真的要公开 API |
| `api`      | 协议定义与契约                 | 作为代码生成与契约测试的输入 |

两种常见误区：一是照搬 Java 的 `controller/service/dao` 层层目录，改一个需求要跨五个包；二是过早抽象出 `pkg/xxx`，把内部实现固化成公共 API。小项目按业务域分包（如上例 `order/`）通常更顺手。

## 二、依赖方向

```text
handler（协议适配） → service（业务规则） → repository（存储细节）
                            ↑ 接口定义在消费方
```

接口应该定义在**使用它的那一侧**。service 需要一个「订单存储」能力，就在 service 包里声明 `OrderRepository`，由 repo 实现；不要在 repo 包里先定义一堆接口再让上层依赖，那会让底层细节反向渗透到业务层。

判断分层是否健康的标准：把 HTTP 换成 gRPC，service 和 repo 是否需要改？把 MySQL 换成 PostgreSQL，service 是否需要改？如果答案是否定的，依赖方向就是干净的。

## 三、错误处理

### 1. 包装、判定与分类

```go
var ErrNotFound = errors.New("order not found")

func Load(ctx context.Context, id string) (*Order, error) {
    o, err := r.db.Query(ctx, id)
    if errors.Is(err, sql.ErrNoRows) {
        return nil, fmt.Errorf("load order %s: %w", id, ErrNotFound)
    }
    if err != nil {
        return nil, fmt.Errorf("load order %s: %w", id, err)
    }
    return o, nil
}
```

规则：

- 用 `%w` 保留错误链，让上层能 `errors.Is` / `errors.As` 判定，而不是用字符串匹配。
- 每层**只添加本层上下文**（`load order 42: ...`），避免整条链重复同样的信息。
- 包级 sentinel error（`ErrNotFound`、`ErrConflict`）作为稳定的分类边界；跨服务边界再映射成 HTTP 状态码或 gRPC code。
- 业务代码不要 `panic`，把它留给真正无法恢复的编程错误；顶层用 `recover` 兜底并记录堆栈。
- 不要吞错：`if err != nil { return nil }` 会让故障失去线索；也不要同一条错误既记日志又向上抛，日志会重复两遍。

### 2. 错误只在一处转成响应

```go
func writeErr(w http.ResponseWriter, err error) {
    switch {
    case errors.Is(err, order.ErrNotFound):
        http.Error(w, "not found", http.StatusNotFound)
    case errors.Is(err, order.ErrConflict):
        http.Error(w, "conflict", http.StatusConflict)
    default:
        // 对外隐藏细节，对内记录完整错误与 trace_id
        slog.Error("internal error", "err", err)
        http.Error(w, "internal error", http.StatusInternalServerError)
    }
}
```

## 四、context 的使用边界

- 作为函数**第一个参数** `ctx context.Context` 逐层传递，不要塞进结构体字段长期保存。
- 用它承载取消、超时和 deadline，并透传给数据库驱动、HTTP 客户端和消息 SDK；上游取消后下游应立刻停止工作。
- `context.WithValue` 只放请求级元数据（trace ID、租户、认证主体），且用自定义不可导出类型作 key，不要放业务参数。
- 派生了 `cancel()` 就必须调用，通常 `defer cancel()`；在循环里创建 timer/context 尤其容易漏。

```go
ctx, cancel := context.WithTimeout(r.Context(), 800*time.Millisecond)
defer cancel()

row, err := db.QueryContext(ctx, query, id)
```

## 五、配置、启动与优雅关闭

配置遵循「一份定义、多来源覆盖、启动时校验」：结构体内写好默认值，从文件/环境变量读入后立刻校验必填项（端口范围、DSN、密钥长度），**fail-fast** 优于运行到一半才报错。

```go
func main() {
    cfg, err := config.Load()
    if err != nil {
        log.Fatal(err)
    }
    db := platform.NewDB(cfg.DB)
    defer db.Close()

    srv := &http.Server{
        Addr:              cfg.Addr,
        Handler:           newRouter(db),
        ReadHeaderTimeout: 5 * time.Second,
        ReadTimeout:       15 * time.Second,
        WriteTimeout:      30 * time.Second,
        IdleTimeout:       60 * time.Second,
    }

    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            slog.Error("server failed", "err", err)
            stop()
        }
    }()

    <-ctx.Done()
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutdownCtx); err != nil {
        slog.Error("graceful shutdown failed", "err", err)
    }
}
```

几个容易漏的点：

- 一定要设 `ReadHeaderTimeout`，否则慢速攻击可以长期占住连接。
- `Shutdown` 会等待在途请求结束，因此需要一个独立的超时上下文，超时后强制退出。
- 停止顺序：先摘除流量（注销服务发现 / readiness 置 false）→ 等待在途请求 → 再关闭连接池。
- 消息消费者同样要在收到信号后停止拉取、处理完已拉取的消息、提交位点，再退出。

## 六、日志与可观测性

- 使用结构化日志（`slog`），字段而非拼接字符串：`slog.Info("order created", "order_id", id, "trace_id", tid)`。
- 每个请求生成或透传 `trace_id`，写入日志、错误响应和下游调用头，才能串起一条链路。
- 日志分级：ERROR 需要人处理，WARN 表示异常但可自愈，INFO 记录关键状态变化，DEBUG 默认关闭。
- 不打印密码、令牌、完整身份证号与请求体全文；必要字段做脱敏或哈希。
- 用指标而非日志回答「有多少」：QPS、错误率、P99、连接池使用率、队列积压。

## 七、依赖注入与可测试性

用构造函数显式声明依赖，避免全局变量和 `init()` 里偷偷建连接：

```go
type Service struct {
    repo   OrderRepository
    clock  func() time.Time
    pub    Publisher
}

func New(repo OrderRepository, pub Publisher) *Service {
    return &Service{repo: repo, pub: pub, clock: time.Now}
}
```

把「时间」「随机」「ID 生成」这类隐式外部依赖变成可替换的函数字段，测试就不用真的 sleep 或碰运气。接口保持小（一两个方法），mock 成本才低。

## 八、并发与资源

- 并发要有**明确的所有者**：谁启动 goroutine、谁负责关闭、出错时谁通知其他人取消。`errgroup.WithContext` 能同时表达「任一失败即取消其余」和「等待全部退出」。
- 限制并发度，不要对每个请求无上限地起 goroutine；用带缓冲 channel 或 semaphore 控制。
- 连接池参数（最大打开、最大空闲、连接生命周期）要按数据库承受能力设置，而不是默认值一路跑。
- 所有后台 goroutine 都要能响应 `ctx.Done()`；向已无人接收的 channel 发送会永久阻塞。
- 用 `-race` 跑测试；生产构建也可考虑保留竞态检查的测试环境。

## 九、常见反模式清单

| 反模式                                    | 后果                     | 改进                       |
| ----------------------------------------- | ------------------------ | -------------------------- |
| `init()` 里连接数据库                     | 启动顺序隐式、无法测试   | 显式构造函数               |
| 全局 `var db *sql.DB`                     | 难以替换、测试互相污染   | 依赖注入                   |
| `log.Fatal` 写在业务函数里                | 绕过 defer，无法优雅关闭 | 返回 error，仅在 main 退出 |
| 忽略 `ctx`、下游用 `context.Background()` | 上游超时后下游仍在跑     | 全链路透传                 |
| `interface{}` 满天飞                      | 失去类型检查             | 用具体类型或小接口         |
| 每个包一个 `utils`                        | 变成杂物抽屉             | 就近放，按职责命名         |
| 错误只 `log.Println(err)`                 | 无法分类、无法恢复       | 包装并向上返回             |

## 十、面试速答

**问：`%w` 和 `%v` 有什么区别？** `%w` 会把原错误包进错误链，上层可用 `errors.Is` / `errors.As` 判定；`%v` 只格式化成字符串，类型信息丢失。

**问：Go 服务如何优雅关闭？** 监听 SIGTERM，先把 readiness 置为不可用并从注册中心摘除，再调用 `http.Server.Shutdown` 等待在途请求（带独立超时），最后按顺序关闭消息消费者和连接池。

**问：context 可以放在结构体里吗？** 不建议。context 与单次请求/操作的生命周期绑定，放进结构体容易被长期持有并跨请求复用，导致取消信号错乱；应作为第一个参数显式传递。
