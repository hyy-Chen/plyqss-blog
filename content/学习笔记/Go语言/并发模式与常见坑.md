> 已有笔记讲过 GMP、goroutine 泄漏和 pprof，本文专注**怎么把并发写对**：一组可复用的编排骨架，以及线上最容易踩的坑。判断标准只有一个——出错或超时时，所有 goroutine 能不能干净退出、结果会不会错、资源会不会泄漏。

## 一、动手前的三个问题

1. **有没有共享可变状态？** 有就必须确定保护方式（互斥、通道、不可变快照），而不是靠「应该不会同时跑」。
2. **需要结果吗？错误怎么传播？** 只要有一个失败就取消其余，还是要收集全部结果？这决定用 `errgroup` 还是普通 `WaitGroup` + 结果通道。
3. **谁负责取消、谁负责关闭？** 每个 goroutine 都要有明确的退出条件，每个 channel 只由发送方关闭。

把这三个问题答完，多数「并发写乱了」的问题在设计阶段就消失了。

## 二、模式速查

| 需求                       | 模式                        | 关键点                         |
| -------------------------- | --------------------------- | ------------------------------ |
| 多个独立任务，任一失败即止 | `errgroup`                  | 派生的 ctx 自动取消            |
| 控制并发上限               | 带缓冲 channel / `SetLimit` | 信号量在循环内获取，defer 释放 |
| 固定 worker 处理任务流     | worker pool                 | 关闭任务通道让 worker 退出     |
| 分阶段处理流水线           | pipeline / fan-in           | 每个 stage 关闭自己的输出通道  |
| 合并重复请求               | `singleflight`              | 防缓存击穿，注意错误被共享     |
| 汇总多个扇出结果           | fan-out / fan-in            | 收集通道容量与关闭时机         |
| 定时/周期任务              | `Ticker` + ctx              | 退出时 `Stop()`，避免泄漏      |

## 三、errgroup：有错误传播的并发

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8) // 并发上限，避免一次起几千个 goroutine

for _, id := range ids {
    id := id
    g.Go(func() error {
        result, err := client.Fetch(ctx, id) // 用派生 ctx，取消可透传
        if err != nil {
            return fmt.Errorf("fetch %s: %w", id, err)
        }
        mu.Lock()
        results[id] = result
        mu.Unlock()
        return nil
    })
}
if err := g.Wait(); err != nil {
    return nil, err
}
```

要点：`errgroup.WithContext` 在第一个错误返回时取消 `ctx`，其余任务应通过它尽快退出；`g.Wait()` 会等待**所有**已启动的任务结束，不会泄漏。并发度限制要在启动前设好，而不是靠任务自己 sleep。

如果所有任务都成功也要收集结果，可以给结果切片预分配长度并按索引写入（`results[i] = ...`），这样不需要互斥锁——前提是每个 goroutine 只写自己的下标。

## 四、worker pool：可控的并行度

```go
func Run(ctx context.Context, jobs <-chan Job, n int) error {
    g, ctx := errgroup.WithContext(ctx)
    for i := 0; i < n; i++ {
        g.Go(func() error {
            for {
                select {
                case <-ctx.Done():
                    return ctx.Err()
                case job, ok := <-jobs:
                    if !ok {
                        return nil // 任务通道关闭，worker 正常退出
                    }
                    if err := process(ctx, job); err != nil {
                        return err
                    }
                }
            }
        })
    }
    return g.Wait()
}
```

三个易错点：

- **关闭责任**：`jobs` 由生产者关闭，worker 绝不关闭；多个 worker 同时关闭会 panic。
- **取消与关闭并存**：`select` 里两个 case 都可能就绪，通道被关闭时 `ok == false` 会让 worker 退出，这是正常的。
- **返回 `ctx.Err()`**：被取消时不要静默返回 `nil`，否则调用方以为全部处理成功。

生产者侧要记得「发送完就关闭」：

```go
go func() {
    defer close(jobs)
    for _, j := range all {
        select {
        case jobs <- j:
        case <-ctx.Done():
            return
        }
    }
}()
```

发送也必须用 `select` 监听 `ctx.Done()`，否则所有 worker 因错误退出后，生产者会永久阻塞在无人接收的 `jobs <- j` 上。

## 五、pipeline 与 fan-in

流水线把处理拆成若干 stage，每个 stage 从输入通道读、向输出通道写，并在结束时关闭**自己的输出通道**：

```text
source ──close──> stage1 ──close──> stage2 ──close──> sink
```

扇入（多个生产者写同一通道）时，不能直接各自 `close`，否则先关的那个会让其他生产者 panic。用一个 `WaitGroup` 等所有生产者结束，再由**唯一的协调者**关闭：

```go
go func() {
    wg.Wait()
    close(merged)
}()
```

另外要防止「上游停了下游还在等」：每个 stage 的 `for range` 应能因输入关闭而自然结束；若 stage 内部还依赖外部取消，把 `ctx.Done()` 一并纳入 `select`。

## 六、singleflight 与缓存击穿

热点 key 失效瞬间可能有几百个请求同时回源，`golang.org/x/sync/singleflight` 让同一 key 的并发请求共享一次真实调用：

```go
v, err, shared := group.Do("user:42", func() (any, error) {
    return repo.Load(ctx, 42)
})
```

注意：

- `shared == true` 表示结果被多个调用方共用，**其中一个拿到错误，所有调用方都拿到同一个错误**。不要让某个请求携带的取消信号 `ctx` 影响共享调用，通常用独立于单个请求的超时上下文。
- 它只合并「进程内同一时刻」的相同 key，不替代分布式锁，也不解决缓存一致性。
- 不要给高基数的 key 无差别加 singleflight，否则收益很小却增加了等待链路。

## 七、超时、取消与关闭的完整生命周期

```text
入口 ctx（带 deadline）
   ├─ 派生 errgroup ctx ── 任一错误 → cancel 全部
   ├─ 所有 I/O 调用透传 ctx（DB / HTTP / MQ）
   ├─ 发送方负责 close(channel)
   ├─ 接收方用 range 或 ok 判断退出
   └─ Ticker / Timer 退出前 Stop()
```

规则清单：

- `context.WithTimeout` / `WithCancel` 返回的 `cancel` 必须调用，通常紧跟 `defer cancel()`。
- 不要从接收方关闭 channel；不要关闭已关闭的 channel；向已关闭的 channel 发送会 panic。
- `time.After` 在 `select` 里每次循环都会创建新的定时器且不会被提前回收，循环中用 `time.NewTimer` + `Stop`/`Reset`。
- 服务退出顺序：停止接收新任务 → 取消 ctx → 等待在途 goroutine（`g.Wait` / `wg.Wait`）→ 关闭连接池。

## 八、常见坑

| 坑                              | 后果                            | 改法                                                 |
| ------------------------------- | ------------------------------- | ---------------------------------------------------- |
| 循环变量被闭包捕获              | 所有 goroutine 用到最后一个值   | 循环内 `v := v`（Go 1.22+ 已修复，但仍要留意老代码） |
| `wg.Add(1)` 写在 goroutine 内部 | `Wait` 可能提前返回             | 在启动前 `Add`                                       |
| 无缓冲 channel 无人接收         | goroutine 永久阻塞              | 发送用 `select` 带 `ctx.Done()` 或设缓冲             |
| `select {}` 空语句              | 永久阻塞                        | 至少保留 `case <-ctx.Done()`                         |
| 锁内做网络/磁盘 I/O             | 临界区被放大，吞吐骤降          | 只在锁内读写共享状态                                 |
| 复制含 `sync.Mutex` 的结构体    | 锁失效或死锁                    | 传指针，`go vet` 会报 copylocks                      |
| `sync.Map` 当通用 map 用        | 读写混合场景更慢、类型不安全    | 明确「读多写少且 key 稳定」才用                      |
| 遍历 map 假定顺序               | 结果不稳定                      | 需要顺序就取 key 排序                                |
| 依赖 `time.Sleep` 做同步        | 时快时慢，CI 偶发失败           | 用 channel、`WaitGroup` 或时钟注入                   |
| 忽略 goroutine 的错误           | 失败被静默吞掉                  | 用 errgroup 或错误通道统一收集                       |
| 并发写 `map`                    | 直接 panic（无法 recover 兜底） | `sync.RWMutex` / 分片 / `sync.Map`                   |

「加了锁就安全」也常是错觉：先查后写（`if !exists { insert }`）即使每步都加锁，仍可能重复插入，需要用唯一约束或在同一个临界区/事务里完成判定与写入。

## 九、检测手段

```bash
go test -race ./...                     # 数据竞争，CI 常开
go vet ./...                            # copylocks、循环变量等静态问题
```

- goroutine 数量随时间单调增长 → 看 `debug/pprof/goroutine?debug=2` 的堆栈，找阻塞在哪个 channel / I/O。
- 吞吐上不去但 CPU 不满 → 看 block / mutex profile 是否卡在锁或通道。
- 测试偶发失败 → 优先怀疑并发与共享状态，而不是加 `Sleep` 掩盖；用 `-count=20 -race` 放大复现概率。
- 压测时观察 goroutine 数与 fd 数是否随 QPS 线性增长后回落，回落不了就是泄漏。

## 十、实践清单

1. 任何并发结构都先写清：谁启动、谁取消、谁关闭、错误往哪传。
2. 有错误传播用 `errgroup`，无错误传播用 `WaitGroup` + 预分配结果槽位。
3. 并发度必须有上限，不要按输入数量无限制起 goroutine。
4. 所有阻塞操作（发送、接收、I/O、定时器）都能被 `ctx.Done()` 打断。
5. channel 只由发送方关闭，扇入时由唯一协调者关闭。
6. 提交前跑 `go vet` 与 `go test -race`，并发改动额外跑 `-count=20`。

## 十一、面试速答

**问：如何限制 goroutine 数量？** 用带缓冲 channel 作信号量，或 `errgroup.SetLimit(n)`；固定任务流则用固定数量 worker pool。关键是限制在启动侧，并让每个 goroutine 可响应取消。

**问：channel 应该由谁关闭？** 由发送方关闭；有多个发送方时用 `WaitGroup` 等全部结束后由唯一协调者关闭。接收方关闭会让其他发送者 panic。

**问：为什么 `time.After` 在循环里有坑？** 每次循环都会新建定时器，且在触发前不会被回收，高频循环下会累积大量定时器；应改用可复用并可 `Stop`/`Reset` 的 `time.Timer`。
