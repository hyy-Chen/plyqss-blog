> 以 Go 1.22+ 为背景，面向后端开发。前半部分建立语言与运行时基础，后半部分的“回答”可直接用于面试，“补充”用于展开原理和工程实践。

## 一、基础知识

### 1. 值、指针与零值

Go 采用值传递：函数参数会复制；传递指针、slice、map、channel、func 等值时，复制的是可共享底层数据的描述符或引用。变量始终有零值，合理利用零值能减少初始化代码。

```go
var n int          // 0
var s []string     // nil，可 range 和 append
var m map[string]int // nil，可读但不能写
```

### 2. slice、map 与 string

slice 是指向底层数组的三元组：指针、长度、容量；`append` 超过容量可能分配新数组，因此不要假设 append 后仍与原 slice 共享数组。map 是哈希表，非并发安全；string 不可变且按字节存储，`len` 返回字节数。

### 3. 方法、接口与组合

接口由方法集合定义，类型隐式实现接口。接口值包含动态类型和值；`var p *T = nil; var x interface{} = p` 中 `x != nil`。优先依赖小接口、在使用侧定义接口，并用组合而不是继承组织代码。

### 4. goroutine、channel 与 context

goroutine 是由 Go 运行时调度的轻量执行单元。channel 用于通信与同步；关闭 channel 表示不再发送，不是“清空”。`context.Context` 传播取消、超时和请求范围元数据，必须在调用链上传递且及时调用 `cancel`。

### 5. 错误、defer 与测试

错误是显式返回值，应使用 `%w` 包装并用 `errors.Is/As` 判断。`defer` 在函数返回时按后进先出执行，适合关闭资源和回滚。单元测试使用 `testing`，并用 `go test -race` 检测数据竞争。

## 二、面试题

## 1. Go 的值传递如何理解？

**回答：** Go 只有值传递；传指针时复制的是指针值，因此双方能访问同一对象。

**补充：** slice/map/channel 也按值复制，但其内部仍指向共享数据。修改 slice 元素通常影响原数据；对 slice `append` 后是否共享取决于是否扩容。

## 2. slice 和数组有什么区别？

**回答：** 数组长度是类型的一部分，赋值会复制全部元素；slice 是动态视图，包含指针、长度和容量。

**补充：** slice 切分共享底层数组，子 slice 长期持有大数组会造成内存滞留。需要独立副本时用 `append([]T(nil), src...)` 或 `slices.Clone`。

## 3. nil slice 和空 slice 有什么差异？

**回答：** 两者 `len` 都为 0，均可 range 和 append；nil slice 等于 nil，空 slice 不等于 nil。

**补充：** JSON 序列化中 nil 常为 `null`，空 slice 为 `[]`。API 返回值应按协议明确选择，避免无意改变客户端语义。

## 4. map 为什么并发读写会 panic？

**回答：** Go 内建 map 不是并发安全的，同时读写或写写会产生竞态，运行时可能直接报错。

**补充：** 用 `sync.Mutex/RWMutex` 保护，或使用 `sync.Map`（适合读多写少等特定模式）。先用 `go test -race` 验证，不要仅靠“不太可能同时写”。

## 5. `new` 与 `make` 的区别？

**回答：** `new(T)` 分配零值 T 并返回 `*T`；`make` 初始化 slice、map、channel 并返回其本身。

**补充：** `make(map[K]V)` 才可写入；`new(map[K]V)` 得到的是指向 nil map 的指针，通常无意义。是否分配在堆由逃逸分析决定，不由 `new`/`make` 名字决定。

## 6. 接口的 nil 陷阱是什么？

**回答：** 接口只有动态类型和值都为 nil 时才等于 nil；内部装着 nil 指针的接口不为 nil。

**补充：** 返回 `error` 时尤其常见。应在返回前直接判断具体指针是否为 nil，避免返回“带类型的 nil”。

## 7. goroutine 和线程有什么关系？

**回答：** goroutine 是轻量协程，由 Go 调度器多路复用到少量 OS 线程上执行。

**补充：** G-M-P 模型中 G 是 goroutine，M 是线程，P 是执行 Go 代码所需的逻辑处理器。阻塞系统调用、cgo 和 CPU 密集任务都会影响调度与吞吐。

## 8. channel 应该由谁关闭？

**回答：** 通常由发送方关闭，且只有明确知道不会再发送的一方关闭。

**补充：** 向已关闭 channel 发送会 panic；从关闭 channel 接收会立即得到零值和 `ok=false`。不要让多个发送方竞争关闭，可用 `sync.Once` 或独立协调者。

## 9. 无缓冲和有缓冲 channel 的区别？

**回答：** 无缓冲 channel 的发送和接收必须同步配对；有缓冲 channel 在未满时发送不阻塞。

**补充：** buffer 是有限队列，不是性能魔法。过大 buffer 会掩盖消费者变慢并积压内存；容量应由可接受积压、吞吐和背压策略决定。

## 10. 如何避免 goroutine 泄漏？

**回答：** 为阻塞操作提供退出条件，使用 context 取消，确保发送/接收不会永久等待，并在所有分支回收资源。

**补充：** 常见泄漏是下游不再读取导致发送阻塞、忘记关闭结果 channel、HTTP/DB 调用无超时。用 pprof 的 goroutine profile 定位堆积栈。

## 11. `context` 应如何使用？

**回答：** 将 context 作为第一个参数向下传递，用于取消、超时和请求范围数据；派生后应调用 cancel。

**补充：** 不要把 context 存到 struct 长期持有，也不要用它传可选业务参数。超时应由上游设定并与 DB、HTTP 客户端超时协同。

## 12. `defer` 有哪些易错点？

**回答：** defer 在函数返回时 LIFO 执行，参数在 defer 语句执行时求值。

**补充：** 循环内 defer 会延迟到外层函数返回，可能导致资源积压；应抽成小函数或显式关闭。命名返回值会被 defer 修改，需谨慎避免掩盖错误。

## 13. 什么是逃逸分析？

**回答：** 编译器判断变量生命周期是否超出当前栈帧；若可能超出，变量会分配到堆上。

**补充：** 返回局部变量地址是安全的，编译器会让它逃逸。优化前先 profile，使用 `go build -gcflags=-m` 辅助理解，不要为“全栈分配”牺牲可读性。

## 14. Go 的 GC 有什么特点？

**回答：** Go 使用并发标记清扫 GC，尽量降低停顿时间；GC 自动回收不可达堆对象。

**补充：** GC 压力主要与分配速率和存活堆大小有关。减少不必要临时对象、复用大缓冲区并及时断开大对象引用有帮助；`sync.Pool` 应用于短生命周期临时对象，不是通用缓存。

## 15. 如何处理错误并保留上下文？

**回答：** 在边界处用 `%w` 包装错误，在上层用 `errors.Is/As` 判断并映射为合适的业务或 HTTP 错误。

**补充：** 不要用字符串比较错误。日志应只在能处理或补充关键信息的层记录，避免同一错误在多层重复打印；错误信息不要泄露密码、令牌等敏感数据。

## 16. 什么是数据竞争，如何发现？

**回答：** 多个 goroutine 并发访问同一内存，且至少一个是写入、又没有同步机制时，就是数据竞争。

**补充：** 使用 mutex、channel、atomic 或其他同步原语建立 happens-before 关系。测试和集成环境运行 `go test -race ./...`，它不能覆盖未执行到的路径。

## 17. `sync.Mutex`、`RWMutex` 和 atomic 如何选择？

**回答：** 复杂共享状态用 Mutex；读远多于写且临界区短时可考虑 RWMutex；简单计数、标志位用 atomic。

**补充：** RWMutex 不一定更快，写入频繁或读临界区很短时收益有限。atomic 只保证单变量原子操作，多个变量的不变式仍需要锁或其他协议。

## 18. Go HTTP 服务如何优雅关闭？

**回答：** 接收退出信号后停止接收新连接，用带超时的 `Server.Shutdown` 等待在途请求完成，并关闭依赖资源。

**补充：** 处理器、DB 和 RPC 调用必须尊重 request context，才能真正停止。需要先从负载均衡摘流，再 shutdown；超时后再强制关闭以防永久卡住。
