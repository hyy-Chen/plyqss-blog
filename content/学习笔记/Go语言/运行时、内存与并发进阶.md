## 1. 什么是逃逸分析？局部变量为什么能安全返回指针？

**回答：** 逃逸分析是编译器判断变量的生命周期是否可能超过当前栈帧的过程。若可能超过，变量会分配到堆上并由 GC 管理；因此返回局部变量指针是安全的。

**详细解释：** 栈分配快，函数返回可整体回收；堆对象需要 GC 扫描。逃逸由“引用能否被当前函数之外持有”决定，不是由 `new`、取地址或是否写了指针单独决定。编译器会跨函数内联后再分析，结论可能随 Go 版本与优化变化。

```go
package main

type User struct{ Name string }

func newUser() *User {
	u := User{Name: "codex"}
	return &u // u 在函数返回后仍会被引用，因此逃逸到堆
}

func main() { _ = newUser() }
```

用下列命令查看编译器解释：

```bash
go build -gcflags='-m -m' main.go
```

输出中常见 `moved to heap: u`。它是优化诊断，不是 bug 报告；不要为了消除一条 escape 信息牺牲 API 可读性。先用 benchmark 与 pprof 确认分配是瓶颈。

### 常见逃逸触发点

| 场景                    | 为什么可能逃逸                     |
| ----------------------- | ---------------------------------- |
| 返回局部变量地址        | 调用者仍可能持有引用               |
| 赋给 interface          | 动态大小/生命周期可能无法静态确定  |
| 闭包捕获变量            | 闭包可在原函数返回后执行           |
| 发送到 channel          | 接收方可在当前函数返回后使用       |
| `fmt.Printf` 等接口调用 | 参数可能装箱；是否逃逸取决于编译器 |

## 2. GC 会回收什么？又不会回收什么？

**回答：** GC 回收不可从根对象到达的堆内存；它不替你及时释放操作系统资源、网络连接、文件描述符、锁或 goroutine，也不会回收仍被引用的大对象。

**详细解释：** GC 从 goroutine 栈、全局变量、寄存器等根开始标记可达对象。对象“逻辑不用”但仍被 map、全局缓存、闭包、slice 底层数组引用时，依旧可达，不能回收。GC 主要管理 Go 堆；文件描述符和 socket 属于内核资源，必须显式 `Close`。

### 错误示例：依赖 GC 关闭文件

```go
func bad(path string) error {
	f, err := os.Open(path)
	if err != nil { return err }
	_, err = io.ReadAll(f)
	return err // f 何时被 finalizer 关闭不可预测；高并发下会耗尽 FD
}
```

### 修复示例：在拥有资源的函数中关闭

```go
func readFile(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil { return nil, err }
	defer f.Close()
	return io.ReadAll(f)
}
```

同样原则适用于 `http.Response.Body`、`sql.Rows`、`time.Ticker`、网络连接和事务：谁创建/取得资源，谁应在清晰边界关闭或回滚。`runtime.SetFinalizer` 仅能作为诊断或兜底，不能承担业务资源生命周期。

## 3. slice 为什么会造成内存滞留？

**回答：** 子 slice 仍指向原底层数组；即使只保留几个字节，只要子 slice 存活，整块大数组也可达，GC 不能回收。

### 错误示例

```go
func header(data []byte) []byte {
	// data 可能是 100MB；返回的 20 字节仍引用这 100MB 底层数组。
	return data[:20]
}
```

### 修复示例

```go
func copiedHeader(data []byte) []byte {
	result := make([]byte, 20)
	copy(result, data[:20])
	return result
}
```

**详细解释：** 这不是泄漏：内存仍“正确可达”，只是引用关系不符合业务意图。缓存、队列和全局变量尤其容易长期保存小 slice。用 heap profile 查找存活对象，再检查它是否意外引用大数组。

## 4. 什么是 goroutine 泄漏？如何复现与修复？

**回答：** goroutine 因永远阻塞、没有退出信号或后台任务无人回收而不能结束，就是泄漏。它会持续占用栈、定时器、连接和调度资源。

### 错误示例：无人接收导致永久阻塞

```go
func leak() {
	ch := make(chan int)
	go func() { ch <- 1 }() // 没有接收者，goroutine 永久阻塞
}
```

### 修复示例：用 context 约束生命周期

```go
func send(ctx context.Context, ch chan<- int, v int) error {
	select {
	case ch <- v:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

**详细解释：** 另一类常见泄漏是 worker `for range jobs`，但生产者异常返回且永不关闭 `jobs`；或 HTTP/DB 调用无 context 超时。每个启动 goroutine 的位置都应回答：谁取消？谁等待退出？谁关闭 channel？

```go
// 推荐：调用者拥有 cancel，并等待 worker 收尾。
ctx, cancel := context.WithCancel(context.Background())
defer cancel()
var wg sync.WaitGroup
wg.Add(1)
go func() {
	defer wg.Done()
	for {
		select {
		case <-ctx.Done(): return
		case job := <-jobs: _ = job
		}
	}
}()
// shutdown 时 cancel()；随后 wg.Wait()
```

注意：上例的 `jobs` 若可能关闭，应使用 `job, ok := <-jobs` 判断；否则关闭后会不断读到零值并忙循环。

### 更多典型泄漏场景

#### 场景一：worker 等待永远不会关闭的 jobs channel

```go
// 错误：调用方退出后忘记 close(jobs)，worker 永远卡在 range。
func badWorker(jobs <-chan string) {
	go func() {
		for job := range jobs {
			_ = job
		}
	}()
}
```

**修复：** 若 producer 独占发送权，它在完成发送后关闭 channel；若生命周期更复杂，则由 `context` 统一取消，worker 同时监听 channel 和取消信号。

```go
func worker(ctx context.Context, jobs <-chan string) {
	for {
		select {
		case <-ctx.Done():
			return
		case job, ok := <-jobs:
			if !ok { return }
			_ = job
		}
	}
}
```

#### 场景二：只读取首个结果，其他并发任务发送时被阻塞

```go
// 错误：返回第一个结果后，其他 goroutine 会卡在 out <- err。
func firstBad(ctx context.Context, tasks []func() error) error {
	out := make(chan error)
	for _, task := range tasks {
		go func(task func() error) { out <- task() }(task)
	}
	return <-out
}
```

**修复：** 取消其他任务，并让每个发送操作可因取消而退出；还要等待 goroutine 收尾，避免函数返回后留下后台工作。

```go
func first(ctx context.Context, tasks []func(context.Context) error) error {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()
	out := make(chan error, 1)
	var wg sync.WaitGroup
	for _, task := range tasks {
		wg.Add(1)
		go func(task func(context.Context) error) {
			defer wg.Done()
			err := task(ctx)
			select { case out <- err: case <-ctx.Done(): }
		}(task)
	}
	err := <-out
	cancel()
	wg.Wait()
	return err
}
```

#### 场景三：HTTP 请求没有超时或取消信号

```go
// 错误：服务端/网络一直不响应时，调用链可能长期卡住。
resp, err := http.Get(url)
if err == nil { defer resp.Body.Close() }
```

**修复：** 请求绑定 context，并为客户端配置整体超时；即便调用方超时，传输层也能尽快停止等待。

```go
client := &http.Client{Timeout: 3 * time.Second}
req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
if err != nil { return err }
resp, err := client.Do(req)
if err != nil { return err }
defer resp.Body.Close()
```

#### 场景四：select 只等数据，不处理取消

```go
// 错误：如果 result 永远不来，这个 goroutine 永远等下去。
func waitBad(result <-chan string) { go func() { <-result }() }
```

**修复：** 所有可能长期等待的 channel 接收、发送、锁获取或 I/O 都应有可取消路径。

```go
func wait(ctx context.Context, result <-chan string) {
	go func() {
		select {
		case <-result:
		case <-ctx.Done():
		}
	}()
}
```

#### 场景五：重试循环在调用方离开后仍持续运行

```go
// 错误：后台重试没有退出条件。
func retryBad() {
	go func() {
		for {
			_ = tryOnce()
			time.Sleep(time.Second)
		}
	}()
}
```

**修复：** 将重试的拥有者、最大次数和取消路径写清楚；用 Timer 或 ticker 配合 context，而不是无法停止的 `for` 循环。

```go
func retry(ctx context.Context, tryOnce func() error) error {
	for attempt := 0; attempt < 3; attempt++ {
		if err := tryOnce(); err == nil { return nil }
		t := time.NewTimer(time.Second)
		select {
		case <-ctx.Done():
			t.Stop()
			return ctx.Err()
		case <-t.C:
		}
	}
	return errors.New("retry exhausted")
}
```

### 泄漏防线：启动 goroutine 前的四个问题

1. 谁拥有它，谁负责在 shutdown 时 `Wait`？
2. 它在什么条件下退出：channel 关闭、context 取消、次数上限还是超时？
3. 它阻塞在发送、接收、I/O 或锁时，是否能响应退出？
4. 若调用者提前返回，结果是否仍有人接收，资源是否仍会关闭？

## 5. 如何用 pprof 定位 goroutine 泄漏？

**回答：** 对比正常与异常时的 goroutine 数和 goroutine profile，按相同阻塞栈聚类，回到创建该 goroutine 的业务路径检查退出条件。

```go
import _ "net/http/pprof"

go http.ListenAndServe("localhost:6060", nil)
// 浏览器或命令：go tool pprof http://localhost:6060/debug/pprof/goroutine
```

**详细解释：** `runtime.NumGoroutine()` 只能发现趋势，不能定位原因。goroutine profile 中大量相同的 `chan send`、`chan receive`、`select` 或网络等待栈才是线索。线上开启 pprof 必须受访问控制，不能直接暴露公网。

## 6. `time.After`、Ticker 和 Timer 有什么资源陷阱？

**回答：** 不应在高频循环中反复创建 `time.After`；不再使用的 `Ticker` 应调用 `Stop`；可复用 Timer 以降低分配与定时器堆压力。

```go
// 错误：每轮都创建新 timer；高频路径会产生大量短命对象。
for {
	select {
	case <-time.After(time.Second):
		// ...
	}
}

// 修复：复用 ticker，并在退出时停止。
ticker := time.NewTicker(time.Second)
defer ticker.Stop()
for {
	select {
	case <-ctx.Done(): return
	case <-ticker.C: /* ... */
	}
}
```

**详细解释：** Go 新版本改善了某些 timer 的回收行为，但资源生命周期仍应由代码明确管理；尤其是长生命周期服务和高频重试循环，显式 `Stop` 更清晰、安全。

## 7. `sync.Pool` 是否能减少所有内存问题？

**回答：** 不能。`sync.Pool` 用于复用短生命周期临时对象，池中对象可在 GC 时被清空，不能作为可靠缓存或资源所有权机制。

**补充：** 放入 Pool 前必须重置对象，取出后也不能假设状态。Pool 适合 `bytes.Buffer` 等热点临时对象；若对象很大或长期闲置，反而会提高常驻内存。不要把打开的文件、连接、带 goroutine 的对象放入 Pool。

## 8. 数据竞争与死锁如何区分和排查？

**回答：** 数据竞争是未同步的并发读写，结果不确定；死锁是 goroutine 相互等待而无法继续。前者用 race detector，后者看 goroutine 栈和锁顺序。

```go
go test -race ./...
go tool pprof http://localhost:6060/debug/pprof/goroutine
```

**详细解释：** `-race` 是动态检测，仅覆盖测试实际执行的路径。修复竞争需建立明确的 happens-before：mutex 解锁到后续加锁、channel 发送到对应接收、`WaitGroup` 等。避免在持锁时调用未知耗时函数或按不一致顺序获取多把锁。

## 9. Go 服务发生 OOM，面试时如何分析与处理？

**回答：** 先区分是 Go 运行时主动报 `out of memory`，还是容器/内核因超过内存限制执行 OOMKill。然后通过运行时指标和 heap profile 找到存活对象增长来源，修复无界缓存、请求体/批处理过大、slice 引用大数组、goroutine 泄漏等根因；`GOMEMLIMIT` 只能帮助控制 Go 堆，不会替代容量规划和资源释放。

**详细解释：** OOM 不等于 GC “没有工作”。GC 只能回收不可达堆对象：全局 map、缓存、等待中的 goroutine、未消费队列和被小 slice 引用的大数组仍可达，因而持续占用内存。Kubernetes 中还要看 Pod 的 `resources.limits.memory`、进程 RSS 和 page cache：容器限制针对进程整体内存，不只看 Go heap。

### 演示：无界缓存导致堆持续增长

> 请只在隔离环境运行；该示例会持续申请内存。

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

var cache = map[string][]byte{}

func main() {
	for i := 0; ; i++ {
		cache[fmt.Sprintf("key-%d", i)] = make([]byte, 1<<20) // 每轮约 1 MiB
		if i%10 == 0 {
			var m runtime.MemStats
			runtime.ReadMemStats(&m)
			fmt.Printf("heap=%d MiB, objects=%d\n", m.HeapAlloc>>20, m.HeapObjects)
		}
		time.Sleep(10 * time.Millisecond)
	}
}
```

**为什么 GC 无法解决：** `cache` 是全局变量，所有 value 都可从 GC root 到达；即便业务不再需要旧值，GC 也没有资格回收它。

### 修复：给缓存明确容量、TTL 与降级策略

```go
type entry struct {
	value   []byte
	expires time.Time
}

type Cache struct {
	mu    sync.Mutex
	items map[string]entry
	max   int
}

func (c *Cache) Put(key string, value []byte, ttl time.Duration) bool {
	c.mu.Lock()
	defer c.mu.Unlock()
	if len(c.items) >= c.max { return false } // 实际项目可替换为 LRU/LFU 淘汰
	// 复制避免调用方复用或持有超大底层数组。
	c.items[key] = entry{value: append([]byte(nil), value...), expires: time.Now().Add(ttl)}
	return true
}
```

### 排查步骤与命令

1. **确认现象。** Kubernetes 看 `OOMKilled`、退出码 `137` 与容器内存曲线；宿主机看内核日志。Go panic 通常会出现 `runtime: out of memory`。
2. **暴露受保护的 pprof。** 比较正常与异常时 heap：`go tool pprof http://host:6060/debug/pprof/heap`，用 `top`、`list`、`web` 定位分配/存活热点。
3. **看运行时指标。** `runtime.ReadMemStats` 或 `runtime/metrics` 观察 `HeapAlloc`、`HeapInuse`、goroutine 数和 GC 次数；同时对比 RSS，避免只盯堆。
4. **定位增长类型。** 无界 map/队列、读取无限大 body、过大批处理、slice 滞留、goroutine 堆积分别有不同修复方式；先确认对象为何仍可达。

### `GOMEMLIMIT` 与容器限制

`GOMEMLIMIT`（或环境变量 `GOMEMLIMIT`）是 Go 运行时的软内存限制目标，运行时会更积极 GC 以让 Go 管理内存接近该值。它应低于容器 memory limit，为 goroutine 栈、运行时元数据、cgo、mmap 和非 Go 内存预留余量。

它不能处理“持续增长的可达数据”。当业务工作集本身超过限制时，更频繁 GC 只会提高 CPU 消耗，最终仍会 OOM；正确做法是限流、分批、淘汰、扩容或改变数据模型。

### 更多 OOM 场景 demo

#### 场景一：无限制读取 HTTP 请求体

```go
// 错误：攻击者或异常客户端可发送数 GB 请求体。
func badHandler(w http.ResponseWriter, r *http.Request) {
	body, err := io.ReadAll(r.Body)
	if err != nil { http.Error(w, err.Error(), 400); return }
	_ = body
}
```

```go
// 修复：同时限制协议层和读取层；超过上限返回 413。
func handler(w http.ResponseWriter, r *http.Request) {
	const maxBody = 1 << 20 // 1 MiB
	r.Body = http.MaxBytesReader(w, r.Body, maxBody)
	body, err := io.ReadAll(r.Body)
	if err != nil {
		http.Error(w, "request body too large", http.StatusRequestEntityTooLarge)
		return
	}
	_ = body
}
```

**要点：** 不要只相信客户端的 `Content-Length`；流式解析大文件或 JSON 时，也要限制单字段、单批大小和并发请求数。

#### 场景二：生产速度超过消费速度的无界队列

```go
// 错误：队列没有容量上限，慢消费者会让内存持续增长。
var queue [][]byte
func enqueue(v []byte) { queue = append(queue, v) }
```

```go
// 修复：使用有界 channel 建立背压；满时阻塞、超时或拒绝。
func enqueue(ctx context.Context, jobs chan<- []byte, v []byte) error {
	select {
	case jobs <- v:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	default:
		return errors.New("queue full")
	}
}
```

**要点：** 有界队列不等于固定一个随意数字。容量要按可承受的延迟、每个任务内存大小、消费者吞吐和降级策略估算；队列满时的拒绝/重试必须是业务协议的一部分。

#### 场景三：goroutine 堆积并长期持有请求数据

```go
// 错误：每个请求启动后台任务；下游慢时 goroutine 和 payload 同时堆积。
func badSubmit(payload []byte) {
	go func() {
		time.Sleep(time.Hour) // 模拟卡住的下游
		_ = payload
	}()
}
```

```go
// 修复：固定 worker 数 + 有界任务队列；队列满时拒绝或同步降级。
type Job struct{ Payload []byte }

func worker(ctx context.Context, jobs <-chan Job) {
	for {
		select {
		case <-ctx.Done(): return
		case job, ok := <-jobs:
			if !ok { return }
			_ = job // 调用下游时也必须传 ctx 与超时
		}
	}
}
```

**要点：** goroutine 泄漏常同时是 OOM 根因：每个 goroutine 有栈和运行时元数据，还可能持有闭包、请求体、连接和上下文中的大对象。

#### 场景四：读取大文件后只保留小片段

```go
func badPreview(path string) ([]byte, error) {
	b, err := os.ReadFile(path) // 假设文件 500 MiB
	if err != nil { return nil, err }
	return b[:1024], nil // 返回 1 KiB 仍引用完整 500 MiB 数组
}

func preview(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil { return nil, err }
	defer f.Close()
	b := make([]byte, 1024)
	n, err := io.ReadFull(f, b)
	if err != nil && err != io.ErrUnexpectedEOF { return nil, err }
	return b[:n], nil
}
```

**要点：** 这个问题在从消息、对象存储或数据库读取大 payload 后切片缓存时特别常见。最优修复往往是不要全量读取；必须截取时再复制小片段。

## 10. 进阶面试速答清单

1. 堆分配不等于内存泄漏；不可达对象最终会被 GC。
2. 可达但无用对象、未关闭 FD/连接、永不退出 goroutine 是更常见的线上资源问题。
3. `defer` 适合函数级资源边界，循环内要警惕延迟释放。
4. context 取消是协作式的：下游必须监听 `Done()` 或把 context 传给支持它的 API。
5. 优化顺序：指标/pprof → 定位热点 → benchmark 验证；不要只凭逃逸输出做优化。
