> 测试回答「改动有没有破坏行为」，剖析回答「慢在哪里」。两者共同的前提是可复现：固定的输入、可观测的指标、可比较的基线。本文按日常开发的实际顺序整理工具与流程。

## 一、测试层次与命名

| 层次     | 目标                        | 特点                     |
| -------- | --------------------------- | ------------------------ |
| 单元测试 | 单个函数/分支的逻辑         | 快、无外部依赖、数量最多 |
| 集成测试 | 与数据库、缓存、HTTP 的协作 | 慢一些，验证配置与协议   |
| 契约测试 | 接口 schema 与消费者约定    | 防止上下游字段不兼容     |
| 端到端   | 关键业务链路                | 少而精，覆盖核心路径     |

命名用 `TestXxx_Scenario_Expected`，例如 `TestCreateOrder_DuplicateKey_ReturnsExisting`。测试名本身就是失败时最直接的文档。

## 二、表驱动测试

Go 最常见也最有效的写法：把输入、期望和子用例名组织成一张表。

```go
func TestParseStatus(t *testing.T) {
    tests := []struct {
        name    string
        input   string
        want    Status
        wantErr bool
    }{
        {name: "paid", input: "PAID", want: StatusPaid},
        {name: "empty", input: "", wantErr: true},
        {name: "unknown", input: "SHIPPED_2", wantErr: true},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := ParseStatus(tt.input)
            if (err != nil) != tt.wantErr {
                t.Fatalf("ParseStatus(%q) err = %v, wantErr = %v", tt.input, err, tt.wantErr)
            }
            if !tt.wantErr && got != tt.want {
                t.Errorf("got %v, want %v", got, tt.want)
            }
        })
    }
}
```

要点：

- 循环变量在并行子测试里要重新绑定（Go 1.22 起每次迭代已是新变量，但老代码库仍需 `tt := tt`）。
- `t.Fatalf` 用于「继续跑下去没有意义」的失败，`t.Errorf` 用于可继续收集多个错误。
- 断言消息写清输入与实际值，避免只输出 `got != want`。
- 边界用例至少覆盖：空值、零值、最大值、重复输入、错误输入。

## 三、测试辅助能力

| 能力             | 用途                                           |
| ---------------- | ---------------------------------------------- |
| `t.Helper()`     | 让失败定位到调用方，而不是断言函数内部         |
| `t.Cleanup(fn)`  | 注册清理，LIFO 执行，比 `defer` 更贴合子测试   |
| `t.TempDir()`    | 自动创建并清理临时目录                         |
| `t.Parallel()`   | 并行执行无共享状态的子测试                     |
| `t.Setenv(k, v)` | 设置环境变量并自动还原（不可与 Parallel 同用） |
| `TestMain`       | 包级前后置，如启动一次测试容器                 |

`t.Parallel()` 有个常见陷阱：子测试并行时，外层函数已返回，若用例引用了外部会被修改的变量（如共享的 mock 对象），结果会不稳定。并行只适用于彼此完全独立的用例。

## 四、替身、mock 与 httptest

优先用**小接口 + 手写 stub**，引入 mock 生成框架前先问是否真的需要验证调用次数。

```go
type fakeRepo struct {
    orders map[string]*Order
}

func (f *fakeRepo) Get(_ context.Context, id string) (*Order, error) {
    o, ok := f.orders[id]
    if !ok {
        return nil, ErrNotFound
    }
    return o, nil
}
```

测试 HTTP handler 不需要真实端口，`httptest` 足够：

```go
req := httptest.NewRequest(http.MethodPost, "/v1/orders", strings.NewReader(body))
req.Header.Set("Content-Type", "application/json")
rec := httptest.NewRecorder()

handler.ServeHTTP(rec, req)

if rec.Code != http.StatusCreated {
    t.Fatalf("status = %d, body = %s", rec.Code, rec.Body.String())
}
```

过度 mock 的坏处是测试只验证了「按预期顺序调用了 mock」，一旦重构实现就会大片失败，却没有覆盖真实行为。涉及 SQL 语义、事务、唯一约束的逻辑，用真实数据库（测试容器或独立 schema）做集成测试更可靠。

## 五、集成测试的组织

- 用 build tag 隔离：`//go:build integration`，默认 `go test ./...` 不跑慢测试，CI 单独一步加 `-tags=integration`。
- 每个测试用唯一 schema 或事务回滚，保证可并行且不留脏数据；不要用「清空全表」影响其他用例。
- 外部依赖不可用时测试应明确失败，而不是静默跳过；跳过要打印原因。
- 准备数据用 builder/工厂函数，避免几十行结构体字面量淹没测试意图。

## 六、竞态与覆盖率

```bash
go test -race ./...                       # 数据竞争检测
go test -cover ./...                      # 覆盖率概览
go test -coverprofile=cover.out ./...     # 生成明细
go tool cover -func=cover.out             # 按函数查看
go tool cover -html=cover.out             # 浏览器查看未覆盖行
```

`-race` 会让程序变慢数倍，但能发现 `go test` 正常跑时完全看不出的并发问题，CI 里应至少一个 job 常开。覆盖率适合找「完全没测过的分支」，不是目标本身：把 80% 当作硬指标容易催生只调用函数、不校验结果的假测试。

## 七、基准测试

```go
func BenchmarkMarshal(b *testing.B) {
    order := fixtureOrder()
    b.ReportAllocs()
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        sink, _ = json.Marshal(order)
    }
}

var sink []byte
```

注意：

- 把结果赋给包级变量，防止编译器把无副作用的调用优化掉。
- `b.ResetTimer()` 排除准备数据的耗时；`b.ReportAllocs()` 同时看分配次数与字节数。
- 用 `go test -bench=. -benchmem -count=5` 多次采样，再用 `benchstat` 比较改动前后，避免凭单次数字下结论。
- 基准要贴近真实输入规模：小对象上的结论经常无法外推到大对象。

## 八、pprof：定位「CPU / 内存去哪了」

Go 内置多种 profile：

| 类型        | 回答的问题                   |
| ----------- | ---------------------------- |
| `cpu`       | 时间花在哪些函数             |
| `heap`      | 当前/历史分配的对象来自哪里  |
| `goroutine` | 有多少协程、卡在哪           |
| `block`     | 哪些地方阻塞等待锁或 channel |
| `mutex`     | 锁竞争热点                   |

在服务里暴露（注意只监听内网或加鉴权）：

```go
import _ "net/http/pprof"

go func() {
    log.Println(http.ListenAndServe("127.0.0.1:6060", nil))
}()
```

采集与查看：

```bash
go tool pprof -http=:8080 http://127.0.0.1:6060/debug/pprof/profile?seconds=30
go tool pprof -http=:8080 http://127.0.0.1:6060/debug/pprof/heap
curl -s http://127.0.0.1:6060/debug/pprof/goroutine?debug=2 > goroutines.txt
```

常用命令：`top` 看热点、`list 函数名` 看逐行开销、`web` 看调用图、`peek` 看调用关系。heap profile 要区分 `inuse_space`（当前占用）与 `alloc_space`（累计分配）：前者定位内存泄漏，后者定位高频小对象分配带来的 GC 压力。

对命令行程序可直接生成 profile：

```bash
go test -bench=BenchmarkMarshal -cpuprofile=cpu.out -memprofile=mem.out
go tool pprof cpu.out
```

## 九、trace 与排查顺序

`runtime/trace` 记录调度、GC、系统调用与阻塞事件，适合回答「CPU 没跑满但延迟高」这类问题：

```bash
curl -s http://127.0.0.1:6060/debug/pprof/trace?seconds=10 > trace.out
go tool trace trace.out
```

推荐排查顺序，先确定方向再动工具：

1. 看指标：QPS、P50/P99、错误率、CPU、内存、GC 暂停、连接池使用率。
2. 判断是 CPU 密集、内存/GC、锁竞争还是外部 I/O 等待，不要一上来就改代码。
3. 用对应的 profile 定位到具体函数或调用点，形成可验证的假设。
4. 改一处、用基准或压测对比，保留基线数据；没有数据支撑的「优化」通常是噪声。
5. 复测 P99 与资源占用，确认没有把延迟转移到别处。

常见结论对应关系：CPU profile 里 `json.Marshal`/反射占比高 → 减少序列化次数或换编码；heap 里 `alloc_space` 巨大但 `inuse_space` 小 → 高频临时对象，考虑复用/预分配；goroutine 数量随时间单调增长 → 泄漏，检查是否有未取消的 `ctx` 或无人接收的 channel；block profile 集中在某个锁 → 缩小临界区或分片。

## 十、CI 检查清单

1. `go vet ./...` 与格式化检查（`gofmt -l`）作为提交门禁。
2. `go test -race ./...` 至少一个 job；集成测试用独立 job 并加 build tag。
3. 覆盖率产出报告，关注新增代码的未覆盖分支，而非全仓数字。
4. 关键路径的基准测试记录趋势，显著退化时告警。
5. 测试必须可重复：不依赖本地时间、网络、固定端口或执行顺序。

## 十一、面试速答

**问：`-race` 能发现所有并发问题吗？** 不能，它只检测运行时实际发生的数据竞争，未被执行到的路径和业务逻辑层面的竞态（如先查后写）仍需靠设计与测试覆盖。

**问：CPU 不高但接口 P99 很高怎么查？** 先看是否卡在外部 I/O、锁或 GC：查 block/mutex profile、trace 里的阻塞事件、连接池等待时间与 GC 暂停，再决定是否动 CPU 相关优化。

**问：`inuse_space` 和 `alloc_space` 怎么选？** 怀疑内存泄漏看 `inuse_space`（还活着的对象是谁分配的），怀疑 GC 压力看 `alloc_space`（累计分配最多的是哪段代码）。
