> 面向 Go 后端开发：基础部分建立链路视角，面试题使用“回答—补充”结构，可用于简答和追问。

## 一、基础知识

### 1. 从 URL 到响应

浏览器/客户端先解析 URL，进行 DNS 查询得到 IP；通过 TCP 三次握手建立连接；HTTPS 还需 TLS 握手；随后发送 HTTP 请求。服务端处理后返回响应，连接是否复用取决于 HTTP 版本、响应头和连接池状态。

```text
URL → DNS → TCP 握手 → TLS 握手（HTTPS） → HTTP 请求/响应 → 连接复用或关闭
```

### 2. 分层与常见协议

| 层次   | 关注点                   | 常见协议         |
| ------ | ------------------------ | ---------------- |
| 应用层 | 请求语义、认证、序列化   | HTTP、DNS、gRPC  |
| 传输层 | 端口、可靠传输、拥塞控制 | TCP、UDP、QUIC   |
| 网络层 | IP 寻址与路由            | IPv4、IPv6、ICMP |
| 链路层 | 同网段帧传输             | Ethernet、ARP    |

### 3. 后端最重要的网络原则

任何网络调用都应有超时、取消、并发上限和可观测性。网络没有“必然成功”：DNS、连接、TLS、写入、首字节和完整响应都可能分别失败或超时。

## 二、面试题

## 1. TCP 三次握手和四次挥手是什么？

**回答：** 三次握手用于双方确认收发能力并同步初始序号；关闭时 TCP 是全双工，双方各自发送 FIN 并确认，因此常见为四次挥手。

**补充：** 客户端主动关闭后通常进入 `TIME_WAIT`，等待足够时间以处理延迟报文并防止旧连接报文影响新连接。不能通过简单关闭 `TIME_WAIT` 来“优化”，应优先连接复用和合理端口规划。

## 2. TCP 为什么可靠？

**回答：** 通过序号、确认、超时重传、校验和、滑动窗口和拥塞控制，提供有序、可靠的字节流。

**补充：** TCP 只保证字节流，不保留业务消息边界；应用协议必须自行定义长度、分隔符或使用 HTTP/gRPC 等上层协议。可靠不等于恰好一次，连接断开时写入是否被对端处理仍可能未知。

## 3. TCP 粘包/拆包是什么？

**回答：** TCP 是流协议，接收端一次 `Read` 的数据可能是半个消息、一个消息或多个消息，所谓粘包/拆包是应用误把字节流当消息边界。

**补充：** 使用固定长度头、TLV、分隔符加转义，或现成协议解决。不要依赖一次 `Read` 的返回大小。

## 4. HTTP/1.1、HTTP/2、HTTP/3 的区别？

**回答：** HTTP/1.1 用文本协议和持久连接；HTTP/2 在单 TCP 连接上多路复用二进制帧并压缩头部；HTTP/3 基于 QUIC/UDP，减少 TCP 队头阻塞并改进连接迁移。

**补充：** HTTP/2 虽可多路复用，但底层单个 TCP 丢包仍可能阻塞所有流；HTTP/3 将流级可靠性放到 QUIC，丢包通常只影响对应流。

## 5. HTTPS 比 HTTP 多了什么？

**回答：** HTTPS 是 HTTP 运行在 TLS 之上，提供服务器身份认证、传输加密和完整性保护。

**补充：** TLS 握手协商版本、密码套件和会话密钥，并验证证书链与域名。HTTPS 不保护服务端已解密后的数据，也不能替代输入校验、权限控制或日志脱敏。

## 6. DNS 查询为什么会慢或失败？

**回答：** DNS 可能受本地缓存、递归解析器、权威服务器、网络、TTL 和错误配置影响，故障会表现为请求无法建连或首包延迟高。

**补充：** 应设置 DNS 超时和缓存策略，部署中监控解析耗时与失败率。不要无限缓存 IP：服务发现和负载均衡依赖 TTL 变更。

## 7. 什么是连接池，为什么需要？

**回答：** 连接池复用已建立的 TCP/TLS 连接，减少握手成本并限制到下游的并发连接数。

**补充：** 池过小会排队，过大可能压垮下游或耗尽端口/文件描述符。HTTP 客户端必须读完并关闭 `resp.Body`，否则连接不能回收到池中。

```go
resp, err := client.Do(req)
if err != nil { return err }
defer resp.Body.Close()
_, err = io.Copy(io.Discard, resp.Body) // 确保可复用连接
return err
```

## 8. 超时应如何设置？

**回答：** 将总请求预算分配给 DNS、连接、TLS、响应头和读取，并使用 `context` 传递取消；不能只设置一个无限大的客户端超时。

**补充：** Go 中可配 `net.Dialer.Timeout`、`http.Transport` 的握手/响应头超时和 `http.Client.Timeout`。服务端也要设置 `ReadHeaderTimeout`、`ReadTimeout`、`WriteTimeout` 与 `IdleTimeout` 防御慢连接。

## 9. 重试为什么可能放大故障？

**回答：** 下游已过载时，大量客户端立即重试会使流量指数放大，造成重试风暴。

**补充：** 仅重试瞬态错误与幂等操作，设次数上限、指数退避和随机抖动；配合限流、熔断和请求预算。超时后不能确定服务端是否已执行，非幂等写需要业务幂等键。

## 10. 什么是负载均衡？

**回答：** 负载均衡将请求分发到多个实例，以扩展容量和提高可用性；可在 DNS、四层或七层实现。

**补充：** 四层按 IP/端口转发，开销低；七层理解 HTTP 路径、Host、Cookie，可做路由和重试。健康检查、摘流、会话黏性和连接长短都会影响实际均衡效果。

## 11. 如何排查“接口偶发超时”？

**回答：** 按 DNS、建连、TLS、服务端排队、下游调用、响应传输分段记录耗时，结合 trace ID 定位最长阶段。

**补充：** 同时看客户端错误类型、服务端 p99、连接池等待、CPU/GC、网卡重传、负载均衡日志。不要只看总耗时，否则无法区分网络问题与应用慢查询。

## 12. Go HTTP 客户端的基本安全写法？

**回答：** 复用 `http.Client`，请求携带 context，设置超时，关闭响应体，并限制读取大小。

```go
func fetch(ctx context.Context, client *http.Client, url string) ([]byte, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil { return nil, err }
	resp, err := client.Do(req)
	if err != nil { return nil, err }
	defer resp.Body.Close()
	if resp.StatusCode/100 != 2 { return nil, fmt.Errorf("status: %s", resp.Status) }
	return io.ReadAll(io.LimitReader(resp.Body, 1<<20))
}
```

**补充：** 生产代码还应配置 Transport 的连接池、代理和 TLS 策略；不能把 `http.DefaultClient` 的默认行为当作全部场景的最佳配置。
