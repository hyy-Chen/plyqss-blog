> 现有的 MySQL 笔记已经讲清了 B+ 树、锁和 MVCC，本文只补一件事：**拿到一条慢 SQL，如何有章法地把它优化到可验证**。重点在成本模型、设计方法和排查流程，而不是再背一遍概念。

## 一、先建立成本模型

优化前要能回答「这条 SQL 的钱花在哪」。InnoDB 以 16KB 页为单位读写，索引查找的成本大致由三部分组成：

| 成本       | 含义                             | 观察方式                    |
| ---------- | -------------------------------- | --------------------------- |
| 索引树遍历 | 从根到叶子的层数，通常 3～4 层   | `EXPLAIN` 的 `type`、`key`  |
| 回表       | 二级索引拿到主键后回聚簇索引取行 | `Extra` 是否出现覆盖索引    |
| 扫描与排序 | 扫描行数、临时表、filesort       | `rows`、`filtered`、`Extra` |

一条 SQL 慢，常见是三种情形之一：

1. **没走合适的索引** → 全表扫描或扫描行数远超结果集。
2. **走了索引但回表太多** → 二级索引命中几万行，每行都要一次随机主键查找。
3. **过滤发生在很晚的阶段** → 排序、分组、分页先处理了大量数据，再丢掉大部分。

这决定了优化方向：加索引、改成覆盖索引、还是改写 SQL 让过滤提前。三者不能互相替代，看到「有索引」就说「不该慢」是典型误判。

```text
WHERE status = ? ORDER BY created_at DESC LIMIT 20
   ├─ 无索引：全表扫描 + 全量排序
   ├─ 仅 status 索引：取回全部该状态行 → 回表 → 排序
   └─ (status, created_at) 联合索引：按索引顺序取前 20 行 → 只需 20 次回表
```

## 二、索引设计：从查询反推

不要按「表有哪些字段」设计索引，要按「有哪些查询」设计。把线上高频 SQL 按 `WHERE` 条件、`ORDER BY`、`GROUP BY`、`SELECT` 字段列成清单，再合并出候选索引。

### 1. 列顺序的实用规则

联合索引 `(a, b, c)` 能高效命中的是 `a`、`a,b`、`a,b,c` 这类前缀。确定顺序时：

- **等值条件优先，范围条件靠后**：`WHERE a = ? AND b > ? AND c = ?` 适合 `(a, b)` 或 `(a, c, b)`（需按实际区分度权衡），把范围列放中间会让它右边的列无法用于继续定位。
- **兼顾排序**：如果查询带 `ORDER BY created_at DESC`，把该列放在等值列之后，可直接利用索引有序性消除 filesort。
- **区分度高的列靠前**不是绝对规则：还要看该列是否出现在所有查询里。一个区分度极高但很少被用到的列放在最左，反而让索引对多数查询失效。
- **考虑覆盖**：把 `SELECT` 里需要的少量字段加到索引末尾，能消除回表；但每加一列都会增加索引体积和写入成本。

### 2. 索引不是越多越好

| 代价           | 说明                                         |
| -------------- | -------------------------------------------- |
| 写入放大       | 每次 INSERT/UPDATE/DELETE 要维护所有二级索引 |
| 缓冲池占用     | 索引页与数据页争抢 Buffer Pool               |
| 优化器选择困难 | 候选过多会增加计划选择成本，可能选错         |
| DDL 与备份变慢 | 加索引、全量导入、物理备份时间上升           |

上线新索引前先确认是否有**等价的现有索引**：`(a, b)` 已经能满足 `WHERE a = ?`，再建 `(a)` 通常就是冗余。定期用 `performance_schema` 查未被使用的索引。

### 3. 让索引保持有效

以下写法会让优化器无法用索引定位，或大幅降低选择性：

```sql
-- 隐式类型转换：user_id 是 VARCHAR，传入数字会触发全表扫描
WHERE user_id = 12345

-- 对列做函数或运算
WHERE DATE(created_at) = '2026-11-12'
WHERE amount / 100 > 10

-- 前导通配符
WHERE name LIKE '%abc%'

-- OR 连接不同列且缺少各自索引
WHERE a = 1 OR b = 2
```

对应改法：参数类型与列类型一致（在应用层保证）、把函数运算移到常量侧（`created_at >= ? AND created_at < ?`）、需要模糊搜索改用全文索引或搜索引擎、`OR` 拆成 `UNION ALL` 或补全索引。

## 三、EXPLAIN 怎么读

| 字段                    | 重点看什么                                                                               |
| ----------------------- | ---------------------------------------------------------------------------------------- |
| `type`                  | `system/const` > `eq_ref` > `ref` > `range` > `index` > `ALL`；出现 `ALL` 且行数大要警惕 |
| `possible_keys` / `key` | 有候选却没选，常是统计信息过期或成本估算偏差                                             |
| `key_len`               | 判断联合索引**实际用到了几列**，这是验证最左前缀的关键                                   |
| `rows`                  | 预估扫描行数，与 `filtered` 相乘约为进入上一层的行数                                     |
| `filtered`              | 条件过滤后保留的百分比，很低说明索引选得不够精准                                         |
| `Extra`                 | `Using index`（覆盖）、`Using filesort`、`Using temporary`、`Using where`                |

`EXPLAIN` 给的是**估算**，不是实测。MySQL 8.0 的 `EXPLAIN ANALYZE` 会真正执行并返回每个算子的实际行数与耗时，排查估算偏差非常有用；注意它会在生产库上真实跑这条 SQL，大查询要限定条件或在从库执行。

```sql
EXPLAIN ANALYZE
SELECT id, status, created_at
FROM orders
WHERE user_id = 42 AND status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
```

判断标准不是「有没有 Using filesort」，而是**实际扫描行数与结果行数的比值**。20 行结果却扫了 50 万行，就是明确的优化空间。

## 四、慢查询排查流程

```text
① 发现：慢日志 / APM / P99 告警，拿到完整 SQL 与参数
② 归类：是偶发抖动、参数倾斜，还是稳定慢
③ 建基线：固定参数，记录耗时、扫描行数、返回行数、执行计划
④ 提假设：没索引 / 回表 / 排序 / 锁等待 / 资源瓶颈，一次只验证一个
⑤ 小改动：加索引、改写法、调分页，一次只动一处
⑥ 验证：同参数重跑，对比基线与整体影响（不能只看这一条）
⑦ 防回归：慢日志采样、SQL 审核、压测基线进 CI
```

慢日志配置要点：

```sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.5;       -- 秒，按业务 SLO 定
SET GLOBAL log_queries_not_using_indexes = 'OFF'; -- 生产慎开，会刷屏
```

用 `pt-query-digest` 之类的工具按指纹聚合，优先处理「总耗时 = 单次耗时 × 次数」最高的那类，而不是单条最慢的偶发查询。

**别忽略非 SQL 因素**：同样的执行计划突然变慢，可能是锁等待、Buffer Pool 命中率下降、连接排队、磁盘 I/O 饱和或主从延迟。先看 `SHOW ENGINE INNODB STATUS`、锁等待与系统指标，再动 SQL。

## 五、典型案例

### 1. 深分页

```sql
-- 慢：先扫描并丢弃 100000 行
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- 快：用上一页最大 id 做游标
SELECT * FROM orders WHERE id > ? ORDER BY id LIMIT 20;
```

需要按非主键排序时，用「先查主键再回表」的延迟关联，或建立包含排序列的覆盖索引。

### 2. 回表过多

```sql
SELECT * FROM orders WHERE status = 'paid' ORDER BY created_at DESC LIMIT 20;
```

`idx(status, created_at)` 已经能定位 20 个主键，但 `SELECT *` 仍要 20 次回表——这其实可以接受。真正的问题是全表有几十万 `paid` 且没有这个联合索引：变成扫描全部 + 排序。先确认是「回表」还是「扫描」，不要盲目把所有字段塞进索引。

### 3. 排序与临时表

`ORDER BY` 的列与索引顺序不一致、混用 `ASC/DESC`、或 `GROUP BY` 与 `ORDER BY` 列不同，都容易出现 `Using filesort` / `Using temporary`。让排序方向与索引一致（MySQL 8.0 支持降序索引），并减少 `SELECT` 的宽字段以降低排序数据量。

### 4. JOIN 驱动表

小表驱动大表，被驱动表的连接字段必须有索引；`EXPLAIN` 第一行通常是驱动表。JOIN 后 `WHERE` 条件放在哪、是否先子查询收敛，都会影响扫描量。多表 JOIN 超过三四张时，考虑在应用层拆分或用冗余字段换查询简单性。

### 5. 参数倾斜

同一个 SQL 模板，`status = 'paid'` 走索引很快，`status = 'init'` 命中 80% 数据时优化器可能选择全表扫描。这类问题无法靠「一条 SQL 一个计划」解决，要结合业务分布做分区、分状态归档或强制索引（谨慎使用）。

## 六、写入侧成本与在线变更

二级索引越多，写入越慢；随机主键还会造成页分裂。批量导入时按主键顺序写入、临时关闭非必要索引、控制单事务大小，都比逐条 INSERT 高效得多。

在线给大表加索引要注意：

- MySQL 5.6+ 支持 Online DDL，但「不锁表」不等于「无影响」，仍会消耗 I/O 与 CPU，并可能短暂持有元数据锁。
- 大表用 `pt-online-schema-change` / `gh-ost` 这类工具：建影子表 → 加索引 → 增量同步 → 原子改名换表。
- 变更前确认磁盘余量（影子表 + 索引需要额外空间）、主从延迟阈值、长事务是否会阻塞 DDL。
- 先在预发用等量数据演练，记录耗时；`ALTER` 语句不要在业务高峰执行。

## 七、可观测与防回归

| 手段                 | 回答的问题                             |
| -------------------- | -------------------------------------- |
| 慢日志按指纹聚合     | 哪类 SQL 总耗时最高                    |
| `performance_schema` | 索引使用情况、锁等待、临时表           |
| APM 里的 SQL 埋点    | 哪条链路的调用次数放大了慢查询         |
| 压测基线             | 改动前后 P99 与扫描行数对比            |
| SQL 审核（CI）       | 拦截无索引条件、`SELECT *`、破坏性 DDL |

把「扫描行数 / 返回行数」做成指标比只监控耗时更敏感：数据量增长时，这个比值会先于耗时告警暴露问题。

## 八、实践清单

1. 先量化（实际扫描行数、耗时、频率），再动手改。
2. 索引从查询清单反推，等值列在前、范围与排序列在后，优先覆盖高频场景。
3. 用 `key_len` 验证联合索引用到几列，用 `EXPLAIN ANALYZE` 验证估算偏差。
4. 一次只改一处，改动后同时看「这一条」和「整体写入/其他查询」是否被拖累。
5. 优化不只在 SQL：锁、连接池、Buffer Pool、磁盘与数据分布同样常见。
6. 把慢日志聚合与压测基线固化，防止数据量增长后回归。

## 九、面试速答

**问：加了索引还是很慢，怎么排查？** 先看 `EXPLAIN` 的 `key_len` 与 `rows` 确认是否真正命中、命中几列；再看是回表、排序还是锁等待/资源瓶颈；最后用 `EXPLAIN ANALYZE` 对比估算与实际行数，检查统计信息是否过期。

**问：深分页怎么优化？** 用基于上一页最大排序键的游标分页替代 `OFFSET`；非主键排序可用延迟关联先取主键，或建立包含排序列的覆盖索引。

**问：索引是不是越多越好？** 不是。每个二级索引都增加写入放大、占用 Buffer Pool，并可能让优化器选错计划；应定期清理冗余和未使用的索引。
