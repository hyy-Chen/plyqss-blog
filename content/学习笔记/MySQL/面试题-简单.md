> 面向后端工程师，以 MySQL 8.0 和 InnoDB 为默认背景。每题先说结论，再补原理和落地做法。

## 1. MySQL 的执行一条 `SELECT` 的基本流程是什么？

**回答：** 客户端连接到连接器，Server 层依次完成权限校验、SQL 解析、优化器生成执行计划，执行器调用存储引擎接口读取数据并返回结果。MySQL 8.0 已移除查询缓存，不应再把“查询缓存命中”作为常规执行阶段。

**追问：** 优化器基于统计信息估算代价，选择索引、连接顺序和访问方式；计划不一定永远最优，统计信息过旧或数据分布极端时需要用 `EXPLAIN ANALYZE` 验证。

## 2. InnoDB 和 MyISAM 的主要区别？

**回答：** InnoDB 支持事务、行级锁、MVCC、崩溃恢复和外键；MyISAM 主要是表级锁，不支持事务和崩溃恢复。新业务表通常选 InnoDB。

**追问：** MyISAM 的索引叶子节点存行地址；InnoDB 主键是聚簇索引，叶子节点存完整行，二级索引叶子节点存二级键和主键值。

## 3. 什么是主键、唯一索引和普通索引？

**回答：** 主键要求非空且唯一，一张表只有一个；唯一索引约束值唯一（允许多个 `NULL` 的具体表现受 SQL 语义影响）；普通索引仅用于加速查询，不保证唯一。

**落地：** 应使用稳定且较短的主键。InnoDB 二级索引都携带主键值，过长主键会放大所有二级索引。

## 4. 为什么 InnoDB 推荐使用自增或趋势递增主键？

**回答：** 聚簇索引按主键排序。递增主键多在右侧叶子页追加，页分裂和数据移动较少；随机 UUID 会在 B+ 树中间频繁插入，造成页分裂、碎片和写放大。

**追问：** 分布式 ID 若近似递增（如雪花 ID）通常优于随机 UUID；是否采用还应考虑安全暴露、分库分表和业务约束。

## 5. B+ 树索引为什么适合数据库？

**回答：** 非叶子节点仅存键和页指针，单页可容纳大量指针，树高很低；叶子节点按键有序并串成链表，既支持等值查询，也支持范围、排序和前缀匹配。

**对比：** 哈希索引等值查找快，但不天然支持范围和排序；B+ 树更适合通用关系型查询。

## 6. 什么是聚簇索引和回表？

**回答：** InnoDB 的主键索引是聚簇索引，叶子节点保存整行。二级索引只保存二级键与主键；用二级索引查到主键后，再去聚簇索引取其他列就是回表。

**优化：** 让查询列都包含在二级索引中可形成覆盖索引，避免回表；但不要为了覆盖而盲目建很宽的索引。

## 7. `WHERE` 条件中有索引，为什么仍可能不走索引？

**回答：** 优化器按成本选择。若条件选择性很低、预计需要回表大量数据、表很小或全表扫描更便宜，就可能不走索引。对索引列做函数、隐式类型转换、前导模糊匹配也可能无法有效利用索引。

```sql
-- 可能无法使用 created_at 的普通索引
WHERE DATE(created_at) = '2026-10-14';
-- 改为范围条件
WHERE created_at >= '2026-10-14' AND created_at < '2026-10-15';
```

## 8. `CHAR` 和 `VARCHAR` 如何选择？

**回答：** `CHAR(n)` 定长，适合长度固定的数据；`VARCHAR(n)` 变长，适合长度波动较大的字符串，通常更节省空间。不要把所有字段都设为很大的 `VARCHAR`，应以业务最大长度建模。

**追问：** 字符集影响字节数和索引长度。MySQL 8.0 常用 `utf8mb4`，应明确其存储与索引成本。

## 9. `DELETE`、`TRUNCATE`、`DROP` 的区别？

**回答：** `DELETE` 删除行，可带 `WHERE`，属于 DML，InnoDB 中可回滚；`TRUNCATE` 快速清空整表，通常隐式提交并重建表结构相关数据；`DROP` 删除表定义和数据。线上操作前必须确认库表、备份和影响范围。

## 10. 什么是事务的 ACID？

**回答：** 原子性：事务要么全成功要么全失败；一致性：事务前后满足约束和业务不变量；隔离性：并发事务互不产生不符合隔离级别的影响；持久性：已提交的数据在故障后可恢复。

**原理：** InnoDB 主要借助 Undo Log 实现回滚，MVCC/锁实现隔离，Redo Log 实现崩溃恢复；一致性是数据库机制和业务设计共同结果。

## 11. 什么是慢查询，如何初步排查？

**回答：** 执行时间超过 `long_query_time` 的 SQL 可写入慢查询日志。先确认是否真的慢、是否存在锁等待，再用 `EXPLAIN ANALYZE` 看实际扫描行数、访问索引、回表和各算子耗时。

**不要直接做：** 未理解执行计划就强行加索引或使用索引提示。先定位查询模式、数据量、选择性与并发场景。

## 12. Go 服务如何正确使用 MySQL 连接池？

**回答：** `database/sql` 的 `*sql.DB` 是并发安全的连接池，应在应用生命周期内复用，而不是每个请求 `Open`。设置 `SetMaxOpenConns`、`SetMaxIdleConns`、`SetConnMaxLifetime`，并为每次操作使用带超时的 `context`。

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()
row := db.QueryRowContext(ctx, "SELECT id FROM users WHERE email = ?", email)
```

池大小要结合数据库最大连接数、实例数和查询耗时压测确定；连接池耗尽通常是慢 SQL、长事务或连接泄漏的信号。
