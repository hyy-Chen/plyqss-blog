> 面向有生产经验的后端工程师。重点是解释底层机制、权衡边界，以及出现线上问题时的判断路径。

## 1. MySQL 为什么需要 Redo Log 与 Binlog 两阶段提交？

**回答：** Redo Log 属于 InnoDB，用于崩溃恢复；Binlog 属于 Server 层，用于复制和时间点恢复。若两者分别提交，故障可能造成“本地已提交但 Binlog 没记录”或“Binlog 已记录但本地未提交”。

**过程：** InnoDB 写 Redo `prepare` → 写并刷 Binlog → Redo `commit`。恢复时，处于 prepare 的事务依据 Binlog 是否完整决定提交还是回滚，保持两份日志一致。

## 2. `innodb_flush_log_at_trx_commit` 如何影响一致性与性能？

**回答：** 值为 `1` 时每次提交写入并刷 Redo Log，断电丢失窗口最小；`2` 时每次写入文件系统缓存、通常每秒刷盘；`0` 时写入和刷盘均通常按秒进行。后两者降低 I/O 压力，却可能在操作系统或机器故障时丢失最近约一秒事务。

**面试加分：** 还要结合 `sync_binlog` 看 Binlog 的刷盘保证；关键账务类业务通常选择更强持久化并接受吞吐成本。

## 3. RR 隔离级别下，MVCC 如何避免不可重复读，又如何处理幻读？

**回答：** 普通一致性读使用同一 Read View，从版本链读取对本事务可见的历史版本，因此重复读取结果稳定。对 `UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 等当前读，InnoDB 读取最新版本，并可使用记录锁、间隙锁或临键锁阻止范围内新插入，从而控制幻读。

**边界：** 具体加锁行为取决于索引、查询条件与隔离级别；不要笼统说“RR 完全没有幻读”。

## 4. 如何系统分析死锁日志？

**回答：** 从 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 提取两个事务：各自持有什么锁、等待什么锁、执行了哪条 SQL、使用什么索引。再画出等待环，判断是访问顺序冲突、索引缺失扩大锁范围，还是批量事务过长。

**修复优先级：** 统一资源访问顺序 → 缩短事务和批次 → 补齐索引 → 让调用方对 `1213` 幂等重试。仅提高超时不能消除真正死锁。

## 5. 为什么“给更新条件加索引”能显著降低锁冲突？

**回答：** InnoDB 的锁跟随索引访问路径。精准索引能快速定位记录并只锁较小范围；没有可用索引时，执行器可能扫描大量聚簇索引记录，期间为满足隔离语义而锁定更多记录或间隙，从而增加冲突与死锁概率。

**验证：** 用 `EXPLAIN ANALYZE` 看扫描行数，用锁等待监控确认阻塞对象；不要只凭“字段有索引”判断，表达式与类型不匹配也会令索引失效。

## 6. 如何设计高并发扣库存，避免超卖？

**回答：** 可使用单条带条件的原子更新：

```sql
UPDATE sku SET stock = stock - ?
WHERE id = ? AND stock >= ?;
```

受影响行数为 1 才表示扣减成功。它把检查与更新放在一个语句内，减少“先查再改”的竞态。订单创建、支付回调等重试路径还需业务唯一键和幂等表/唯一索引。

**权衡：** 热门单 SKU 会形成行锁热点；可结合库存分段、异步排队或缓存预扣，但必须设计最终一致性和补偿。

## 7. 主从复制延迟如何产生，如何处理？

**回答：** 主库 Binlog 产生速度超过副本接收或应用速度时出现延迟；大事务、DDL、锁冲突、磁盘慢、网络抖动和单线程应用瓶颈都可能导致。延迟时读从库可能读到旧数据。

**策略：** 监控复制延迟和队列；拆分大事务、优化副本硬件和并行复制；对“写后立刻读”的关键路径读主库或使用会话一致性/GTID 等机制，而不是假设读写分离天然一致。

## 8. 分库分表后，分页和全局唯一 ID 怎么做？

**回答：** 全局 ID 可用号段、雪花类 ID 或数据库序列服务，要求唯一、趋势递增与时钟/容灾策略可控。跨分片深分页不能简单 `OFFSET`：先按路由键缩小到单分片；无法路由时各分片取足够候选集，再在应用层归并，代价随分片数和页码增大。

**原则：** 分片键应来自最常见查询路由条件。没有路由键的高频查询是分库分表设计的红旗。

## 9. 如何在线给大表加索引或修改字段？

**回答：** 先评估 MySQL 版本、操作是否支持 `ALGORITHM=INPLACE/INSTANT` 与 `LOCK=NONE`，并在预发以相近数据量验证。即使声明在线 DDL，也可能存在短暂元数据锁；长查询/长事务可导致 DDL 等待并反向阻塞后续请求。

**生产流程：** 观察活跃事务，设置合理锁等待，选择低峰期；超大表使用在线 schema 变更工具时，要评估触发器、复制和回滚方案。

## 10. Buffer Pool 为什么重要，怎样判断内存配置问题？

**回答：** Buffer Pool 缓存数据页与索引页，命中率高可减少磁盘随机 I/O。它通常是专用数据库实例最大的内存消费者，但不能吃满物理内存，还要给连接、排序、临时表、操作系统页缓存和复制预留空间。

**排查：** 观察 `Innodb_buffer_pool_reads` 与读请求比例、脏页压力、I/O 等待和 OOM；命中率高也不能证明没有索引问题，可能只是工作集恰好在内存中。

## 11. 如何从慢 SQL 定位到可验证的优化？

**回答：** 先用慢日志获取真实参数和频率，确认是否为锁等待；再用 `EXPLAIN ANALYZE` 对比估算行数与实际行数，定位全表扫描、低选择性、回表、排序、临时表或 Join 放大。提出假设后建立最小索引/改写 SQL，并在真实数据分布下复测延迟、扫描行数与写入影响。

**禁忌：** 只看 `type` 排名、迷信强制索引，或只在空表测试。

## 12. Go 服务如何保证“写数据库并发送消息”的一致性？

**回答：** 不应直接在本地事务中同时依赖数据库提交和 MQ 发送成功，因为二者不能天然原子提交。常用 Outbox 模式：在同一个数据库事务内写业务数据与待发送事件表；后台可靠地投递事件，消费者按事件唯一 ID 幂等处理。

**关键点：** Outbox 需要状态机、重试、告警与清理；消息至少一次投递是常态，消费端必须可重复执行。Go 中事务回调不应包含网络发送等长耗时操作。
