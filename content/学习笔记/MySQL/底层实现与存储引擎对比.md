> 本文以 MySQL 8.0 的 InnoDB 为主。MyISAM 主要用于理解历史设计与存量系统，不适合作为新业务默认选择。

## 一、整体架构

MySQL 可分为连接层、Server 层和存储引擎层。Server 层负责 SQL 解析、优化、权限校验、执行器与日志协调；存储引擎层负责数据的实际读写、索引组织、事务与缓存策略。

```text
客户端
  │
连接器 → 查询缓存（8.0 已移除）→ 解析器 → 优化器 → 执行器
                                                    │
                                      存储引擎接口（Handler API）
                                          ├── InnoDB
                                          └── MyISAM
```

同一条 SQL 在 Server 层完成语法与执行计划处理；不同存储引擎决定表数据如何落盘、是否支持事务和行级锁等能力。

## 二、InnoDB：以页为单位管理数据

### 1. 表空间、区、页与行

InnoDB 不直接以“行”作为磁盘 I/O 的最小单位，而是按页（`page`）读写。默认页大小是 `16KB`，可在初始化实例时配置为 `4KB`、`8KB`、`16KB`、`32KB` 或 `64KB`；生产中最常见的是 `16KB`。

```text
表空间（tablespace）
└── 段（segment，例如叶子节点段）
    └── 区（extent，默认 64 个页）
        └── 页（page，默认 16KB）
            └── 行记录（record）
```

一个常见数据页包含文件头、页头、用户记录、空闲空间、页目录和文件尾。页目录保存若干记录槽位，便于在页内做折半定位；记录之间还通过单向链表保持主键顺序。它解释了两个现象：

- 一次读取通常会带来相邻多行；访问局部连续的主键范围更友好。
- 行太宽会让单页容纳的记录变少，索引扫描与缓存命中效率可能下降。

### 2. 聚簇索引与二级索引

InnoDB 的主键索引是聚簇索引（clustered index）：B+ 树叶子节点直接存放完整行记录。二级索引的叶子节点保存“二级索引列 + 主键值”，而不是物理地址。

```text
二级索引查找
WHERE email = 'a@example.com'
        │
        ▼
二级索引 B+ 树：email → id
        │
        ▼
聚簇索引 B+ 树：id → 完整行
```

第二步称为回表。若查询所需字段均已在二级索引中，就能使用覆盖索引，避免回表。例如：

```sql
CREATE TABLE user_account (
  id BIGINT PRIMARY KEY,
  email VARCHAR(128) NOT NULL,
  nickname VARCHAR(64) NOT NULL,
  KEY idx_email_nickname (email, nickname)
) ENGINE = InnoDB;

-- 可由 idx_email_nickname 覆盖：email 是查找条件，nickname 是返回列。
SELECT nickname FROM user_account WHERE email = 'a@example.com';
```

### 3. 为什么使用 B+ 树

B+ 树的非叶子节点只保存键和子页指针，因此扇出高、树高低；叶子节点按键值排序且存在链表连接，适合等值查询和范围查询。相较哈希索引，B+ 树能高效支持范围、排序与最左前缀匹配；相较普通二叉树，磁盘访问次数更少。

联合索引遵循最左前缀原则。索引 `(a, b, c)` 可有效支持以 `a` 开头的条件组合，如 `a`、`a,b`、`a,b,c`；直接只按 `b` 查询通常无法按该索引有序定位。优化器也可能选择索引下推、索引跳跃扫描等策略，但不应把这些优化当作建模前提。

## 三、InnoDB 事务、MVCC 与锁

### 1. ACID 如何落地

| 特性                  | 主要实现                               |
| --------------------- | -------------------------------------- |
| 原子性（Atomicity）   | Undo Log：可撤销未提交或失败事务的修改 |
| 一致性（Consistency） | 事务、约束、并发控制与业务逻辑共同保证 |
| 隔离性（Isolation）   | MVCC 与锁机制                          |
| 持久性（Durability）  | Redo Log、WAL 与崩溃恢复               |

### 2. MVCC：读取合适版本，而非总是加锁

每条聚簇索引记录隐含事务 ID（`DB_TRX_ID`）和回滚指针（`DB_ROLL_PTR`）。更新不会立即抹掉旧版本，而是通过 Undo Log 串起版本链。读操作依据 Read View 判断哪个版本对当前事务可见。

在默认的 `REPEATABLE READ` 隔离级别下：

- 普通 `SELECT` 通常是快照读，使用 Read View，不阻塞写入。
- `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 属于当前读，需要读取最新版本并可能加锁。
- 长事务会使旧版本不能及时清理，导致 Undo Log 增长、历史链变长；应避免“开启事务后长时间不提交”。

### 3. 锁与幻读

InnoDB 主要使用行级锁，并在索引记录上加锁；没有合适索引时，扫描和锁定的范围可能扩大。为抑制范围当前读中的幻读，`REPEATABLE READ` 下还可能使用间隙锁（gap lock）或临键锁（next-key lock，记录锁 + 间隙锁）。

```sql
-- 事务 A：范围当前读，可能锁住命中记录及相邻间隙。
SELECT * FROM orders
WHERE order_no BETWEEN 100 AND 200
FOR UPDATE;
```

设计要点：为高频查询和更新条件建立合适索引；缩短事务；按一致顺序访问多行，降低死锁概率。死锁无法完全避免，应用层应能识别并重试 `Deadlock found` 类错误。

## 四、日志与一次提交的路径

### 1. Redo Log：崩溃后重做

Redo Log 是物理/逻辑结合的重做日志，记录对数据页的变更，用于保证已提交事务的持久性。它采用 WAL（Write-Ahead Logging）：数据页刷盘前，相关 Redo 必须先持久化。崩溃恢复时，InnoDB 可用 Redo 重放尚未写回数据页的已提交修改。

`innodb_flush_log_at_trx_commit` 直接影响提交时 Redo 的刷新策略：值为 `1` 时，每次提交都写入并刷盘，持久性最强；值为 `2` 或 `0` 可降低 I/O 压力，但异常断电时可能丢失最近约一秒的事务。

### 2. Undo Log：回滚与旧版本读取

Undo Log 保存修改前的必要信息：事务回滚时据此逆向恢复；MVCC 的一致性读也依赖其构造历史版本。Undo 不等于备份，不能替代逻辑备份或物理备份。

### 3. Binlog：复制与时间点恢复

Binlog 属于 Server 层，记录会改变数据的事件，主要用于主从复制和基于时间点恢复（PITR）。常见格式：

| 格式        | 特点                                         |
| ----------- | -------------------------------------------- |
| `STATEMENT` | 记录 SQL，体积较小，但非确定性语句有复制风险 |
| `ROW`       | 记录行变更，复制更可靠，通常体积更大         |
| `MIXED`     | 根据场景在两者间切换                         |

### 4. 两阶段提交

同时启用 Binlog 和 Redo Log 时，MySQL 通过两阶段提交避免两份日志状态不一致：

```text
执行器修改 InnoDB 数据
        │
        ▼
Redo Log prepare
        │
        ▼
写入 Binlog 并刷盘
        │
        ▼
Redo Log commit
```

恢复时，处于 `prepare` 状态的事务会依据 Binlog 是否完整决定提交或回滚，从而避免“主库已提交但无法复制”或“Binlog 有记录但本地未提交”的不一致。

## 五、InnoDB 与 MyISAM 对比

| 维度         | InnoDB                                 | MyISAM                                 |
| ------------ | -------------------------------------- | -------------------------------------- |
| 事务         | 支持 ACID、提交与回滚                  | 不支持                                 |
| 锁粒度       | 行级锁为主，也有表/意向/间隙锁         | 表级锁                                 |
| 崩溃恢复     | 依靠 Redo Log 自动恢复                 | 恢复能力弱，可能需修复表               |
| 外键         | 支持                                   | 不支持                                 |
| 索引叶子节点 | 主键聚簇索引保存整行；二级索引保存主键 | 索引保存数据行地址，数据与索引分离     |
| MVCC         | 支持                                   | 不支持                                 |
| 全文索引     | 支持（MySQL 5.6+）                     | 支持                                   |
| 典型用途     | OLTP、并发读写、绝大多数业务表         | 只读或低并发历史场景；新项目通常不推荐 |

MyISAM 的数据文件（`.MYD`）与索引文件（`.MYI`）分离，所有索引叶子节点保存行地址。它不维护事务日志和 MVCC，因此实现较简单，但在并发写入、故障恢复和数据完整性方面明显弱于 InnoDB。

## 六、查询与写入的底层视角

### 1. 一次索引查询

```text
SQL → 解析/优化 → 选择索引
    → Buffer Pool 是否命中页？
       ├── 命中：在内存页中定位记录
       └── 未命中：从磁盘读入 16KB 页后定位
    → 若为二级索引且非覆盖查询：按主键回表
    → 返回结果
```

Buffer Pool 是 InnoDB 缓存数据页和索引页的核心内存区域。内存不足或索引设计不佳会造成更多磁盘 I/O；但盲目增大 Buffer Pool 前，也应为操作系统、连接、排序和临时表等预留内存。

### 2. 一次更新并提交

```text
定位聚簇索引记录 → 加锁/检查可见性 → 修改 Buffer Pool 中的数据页
    → 生成 Undo Log（用于回滚与 MVCC）
    → 生成 Redo Log（用于崩溃恢复）
    → 两阶段提交协调 Binlog 与 Redo Log
    → 脏页由后台线程择机刷回表空间
```

提交成功不表示数据页立即落盘；Redo Log 的存在正是为了把“提交延迟”和“数据页刷盘”解耦。

## 七、易混淆点

1. 主键并非越长越好。InnoDB 的二级索引都包含主键值；长主键会放大二级索引体积。常用单调递增的短整型或有序 ID，避免随机 UUID 直接作为聚簇主键造成频繁页分裂。
2. `REPEATABLE READ` 不代表所有读取都来自旧快照。当前读会读取最新已提交版本并加锁。
3. Redo Log、Undo Log、Binlog 不能互相替代：它们分别服务于崩溃恢复、回滚/MVCC、复制/PITR。
4. “使用了索引”不等于高效。选择性低、回表多、扫描范围大或隐式类型转换都可能让执行计划代价升高。
5. 不要把 MyISAM 的表级锁、非聚簇索引模型套用到 InnoDB。

## 八、学习与排查建议

1. 用 `EXPLAIN ANALYZE` 观察实际执行路径、扫描行数与耗时，而不只看 `EXPLAIN` 的估算。
2. 建表时明确主键；再依据高频 `WHERE`、`JOIN`、`ORDER BY` 和返回列设计联合索引与覆盖索引。
3. 在测试环境复现实验：创建二级索引后，对比覆盖查询和回表查询的执行计划。
4. 观察 `SHOW ENGINE INNODB STATUS`、慢查询日志和死锁信息，把日志与本章的锁、MVCC、页和事务概念对应起来。
5. 后续可继续专题学习：`Buffer Pool 与刷脏`、`索引设计与执行计划`、`隔离级别与锁`、`复制与高可用`。
