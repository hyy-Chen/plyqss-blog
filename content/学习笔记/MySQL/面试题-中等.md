> 面向后端工程师，以 MySQL 8.0/InnoDB 为默认背景。回答时应把索引、事务边界和业务一致性联系起来。

## 1. 联合索引为什么遵循最左前缀原则？

**回答：** 联合索引 `(a, b, c)` 的 B+ 树按 `a`、再 `b`、再 `c` 的字典序排列。没有确定前导列 `a`，就无法像单个连续区间那样按 `b` 直接定位。因此它可高效支持 `a`、`a,b`、`a,b,c` 的组合。

**例外：** 优化器可能使用索引跳跃扫描等优化，但不能据此替代合理索引设计。

## 2. 如何设计联合索引的列顺序？

**回答：** 一般先放等值过滤列，再放范围列，最后考虑排序、分组和覆盖列；同时结合选择性、真实 SQL 和写入成本。不要只背“区分度最高在最左”，因为等值条件、范围条件和排序需求会改变最佳顺序。

```sql
-- 常见查询：先按租户和状态过滤，再按时间排序
WHERE tenant_id = ? AND status = ? AND created_at >= ?
ORDER BY created_at DESC
-- 候选索引：(tenant_id, status, created_at)
```

## 3. `EXPLAIN` 中应重点看哪些字段？

**回答：** 关注 `type`（访问方式）、`possible_keys`/`key`（候选与实际索引）、`key_len`（使用索引前缀）、`rows`（估算扫描行数）、`filtered`、`Extra`。`Using filesort` 和 `Using temporary` 值得分析，但并非出现就一定错误。

**更可靠：** `EXPLAIN ANALYZE` 会展示实际执行时间、循环次数和真实行数，可识别估算偏差。

## 4. 什么是覆盖索引、索引下推？

**回答：** 覆盖索引指查询所需列全在索引中，无需回表；索引下推（ICP）指存储引擎在扫描二级索引时先判断可由索引列判断的条件，减少回表次数。

**注意：** 覆盖索引不是“把所有列塞进索引”，宽索引会增加写放大和 Buffer Pool 压力。

## 5. InnoDB 的 MVCC 是什么？

**回答：** 多版本并发控制让普通一致性读从 Undo Log 版本链中找到对当前事务可见的版本，从而读写通常不互相阻塞。聚簇索引记录隐含事务 ID 和回滚指针，Read View 决定可见性。

**边界：** `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，会读最新版本并加锁，不是普通快照读。

## 6. RC 与 RR 隔离级别有什么实际差异？

**回答：** `READ COMMITTED` 每次一致性读通常创建新 Read View，因此同一事务两次查询可能看见别的事务已提交的数据；InnoDB 默认 `REPEATABLE READ` 中，同一事务的普通一致性读通常复用首次读建立的 Read View，避免不可重复读。

**追问：** RR 下当前读仍读取最新已提交版本；针对范围当前读还可能使用临键锁抑制幻读。

## 7. 什么是行锁、间隙锁和临键锁？

**回答：** 记录锁锁定索引记录；间隙锁锁定记录之间的范围，阻止插入；临键锁是记录锁与前间隙锁的组合。InnoDB 的行锁实际加在索引记录上，缺少合适索引时可能扫描并锁住更大范围。

**落地：** 更新条件要命中索引，事务要短；否则“只更新一行”的业务 SQL 也可能引发广泛阻塞。

## 8. 死锁是如何产生的，如何处理？

**回答：** 两个事务循环等待对方持有的锁即为死锁。例如事务 A 先锁行 1 再锁行 2，事务 B 先锁行 2 再锁行 1。InnoDB 会检测死锁并回滚其中一个事务。

**处理：** 固定多行访问顺序、缩短事务、建立正确索引，并在应用层对错误码 `1213` 做有限次数的幂等重试。不要无限重试。

## 9. 长事务有什么危害？

**回答：** 长事务会长期持锁，并使旧版本无法被 purge 清理，Undo Log 和历史链增长；还会延长主从复制延迟或占用连接。常见原因是事务中夹杂远程调用、用户交互、批量循环或忘记提交。

**Go 实践：** 使用 `BeginTx(ctx, ...)`，在函数边界清晰地 `Commit`/`Rollback`，不要跨 HTTP 请求或 RPC 调用持有事务。

## 10. 如何优化深分页？

**回答：** `LIMIT 1000000, 20` 需要跳过大量行，偏移越大越慢。应使用基于上次排序键的 seek/keyset 分页，并配合索引。

```sql
SELECT id, created_at FROM orders
WHERE tenant_id = ? AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

索引可设计为 `(tenant_id, created_at, id)`；排序键必须稳定，避免翻页时漏数据或重复数据。

## 11. 什么是 Redo Log、Undo Log 和 Binlog？

**回答：** Redo Log 用于崩溃恢复，遵循 WAL；Undo Log 保存旧版本，用于回滚和 MVCC；Binlog 属于 Server 层，主要服务复制和时间点恢复。它们职责不同，不能相互替代。

**追问：** 同时启用 Binlog 与 Redo 时，两阶段提交避免“本地事务状态”和“复制日志状态”不一致。

## 12. 如何避免 SQL 注入并处理动态查询？

**回答：** 值参数必须使用预编译占位符；不能把用户输入直接拼接到 SQL。表名、列名、排序方向不能使用普通占位符，应使用后端固定白名单映射。

```go
// 绑定值，而不是字符串拼接
err := db.QueryRowContext(ctx, "SELECT id FROM users WHERE email = ?", email).Scan(&id)
```

预编译主要解决安全和参数编码，不保证每条 SQL 都自动获得最佳执行计划，仍需要索引与计划分析。
