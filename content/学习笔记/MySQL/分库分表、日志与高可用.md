> 这是一条常见面试追问链：单库为何不足 → 如何拆分与路由 → 如何保证写入可靠 → 主从延迟怎么办 → 集群故障如何切换。

## 一、何时考虑分库分表

先优化索引、SQL、归档、读写分离和硬件；分库分表是复杂度很高的最后手段。信号包括：单表/单库容量或索引无法承受、写入与锁竞争长期成为瓶颈、数据与访问可按稳定维度路由。

拆分前必须回答：分片键是什么？高频查询能否携带它？跨分片事务、分页、排序、聚合和唯一约束如何处理？没有路由键的高频查询会在拆分后演变为广播查询。

## 二、垂直与水平拆分

| 方式     | 做法                   | 适用场景                   |
| -------- | ---------------------- | -------------------------- |
| 垂直分库 | 按业务域拆库           | 用户、订单、支付边界清晰   |
| 垂直分表 | 将低频/大字段拆表      | 宽表、大字段、冷热字段分离 |
| 水平分表 | 同类数据按规则分到多表 | 单表数据量或写入压力过大   |
| 水平分库 | 分片同时分散到多库     | 单实例容量/吞吐成为瓶颈    |

常用分片键是 `user_id`、`tenant_id` 或时间。哈希分片较均衡但扩容迁移麻烦；范围分片便于按时间归档，但容易产生热点。按业务查询模式选择，而不是只看数据分布。

## 三、全局 ID 与跨分片问题

全局 ID 需要唯一、生成高可用，并最好趋势递增以减少 InnoDB 页分裂。可选数据库号段、雪花类 ID 或专用 ID 服务；应明确时钟回拨、号段耗尽与故障降级方案。

跨分片 Join、`ORDER BY`、聚合和深分页成本高。优先反范式、冗余必要字段或建立汇总表；无法避免时，由各分片返回候选集后在应用层归并，并限制页码与结果集。分布式事务应谨慎使用，优先 Saga、最终一致性和幂等补偿。

## 四、Redo、Undo 与 Binlog

| 日志     | 所属      | 主要作用               |
| -------- | --------- | ---------------------- |
| Redo Log | InnoDB    | WAL、崩溃恢复、持久性  |
| Undo Log | InnoDB    | 回滚、MVCC 旧版本      |
| Binlog   | Server 层 | 复制、审计、时间点恢复 |

提交路径是：修改 Buffer Pool → 生成 Undo/Redo → Redo `prepare` → 写入并刷 Binlog → Redo `commit` → 脏页后续刷盘。两阶段提交避免 Redo 与 Binlog 在宕机后出现提交状态不一致。

`innodb_flush_log_at_trx_commit=1` 与合理的 `sync_binlog` 提供更强持久化，但增加 fsync 成本。性能参数是可靠性选择，不能脱离业务可接受的数据丢失窗口讨论。

## 五、传统主从复制与 GTID

主库提交后写入 Binlog；副本的 I/O 线程拉取并写 relay log，SQL/协调线程再重放事务。传统复制通常异步，主库返回成功不等于副本已应用，因此读从库可能读到旧值。

GTID 为每个已提交事务分配全局事务标识，便于故障切换、定位副本进度和自动化运维。半同步复制要求至少一个副本确认接收 Binlog 后主库再返回，可缩小数据丢失窗口，但不等于副本已经执行或对查询可见。

复制延迟常来自大事务、DDL、网络、磁盘、锁冲突或副本应用能力不足。处理方式是拆小事务、启用并行复制、优化副本资源；关键“写后读”请求读主库或使用可验证的一致性等待策略。

## 六、Group Replication 与 InnoDB Cluster

Group Replication（MGR）使用组通信与冲突检测维护成员一致性，可部署单主或多主模式。它仍有事务认证、网络和流控成本；多主并不意味着任意热点行都可无限并发写入，冲突会导致认证失败与重试。

InnoDB Cluster 通常由 MySQL Server + Group Replication + MySQL Router + MySQL Shell 组成：MGR 提供高可用复制组，Router 把读写路由到合适节点，Shell 辅助配置和管理。它适合希望获得官方集成高可用能力的场景，但不是替代备份、容量规划和应用幂等的万能方案。

| 方案                 | 一致性/可用性特征          | 典型用途       |
| -------------------- | -------------------------- | -------------- |
| 异步复制             | 延迟低，故障可能丢最后写入 | 常规读扩展     |
| 半同步复制           | 缩小丢失窗口，仍可能读延迟 | 提升主从可靠性 |
| MGR / InnoDB Cluster | 组复制与自动故障转移能力   | 高可用集群     |

## 七、故障切换与读写一致性

切主前需确认候选节点的 GTID/日志进度、隔离旧主以防脑裂、提升新主并更新路由。自动切换缩短恢复时间，却不能免除演练：应用连接重试、事务失败重放、缓存失效和读写路由都应验证。

读写分离下的常见问题是“刚写入立刻读不到”。可按业务级别选择：关键路径固定读主；在同一会话保留一段读主时间；等待副本达到指定 GTID；或接受最终一致并在 UI/业务上处理。不要把“有副本”误解为“天然强一致”。

## 八、后端实践清单

1. 将分片路由封装在数据访问层，禁止业务层随意拼库表名；用压测覆盖热点分片与扩容迁移。
2. 所有写操作设计幂等键；消息与数据库协同时使用 Outbox/补偿，不能依赖跨系统偶然同时成功。
3. 监控主从延迟、GTID 进度、错误日志、磁盘空间、连接数、慢事务与 MGR 成员状态。
4. 定期做物理/逻辑备份和恢复演练。复制不是备份：误删会复制到所有副本。
5. 对 DDL、切主、扩容写出回滚/降级预案，并在低峰演练。
