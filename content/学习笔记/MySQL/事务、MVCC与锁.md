> 以 MySQL 8.0 / InnoDB 为背景。面试应把三者串成一条线：事务定义边界，MVCC 让大部分读写并发，锁处理需要互斥的当前读与写入。

## 一、事务与 ACID

事务是一组要么全部成功、要么全部失败的操作。InnoDB 的实现分工如下：

| 目标   | 核心机制                           |
| ------ | ---------------------------------- |
| 原子性 | Undo Log 记录旧版本，可逆向回滚    |
| 一致性 | 约束、事务隔离与业务不变量共同保证 |
| 隔离性 | MVCC + 锁                          |
| 持久性 | Redo Log 的 WAL 与崩溃恢复         |

事务应只包含必要数据库操作。RPC、用户交互、文件上传和长循环放在事务内，会延长锁持有时间、阻塞连接，并妨碍 Undo 历史版本清理。

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1 AND balance >= 100;
-- 确认受影响行数为 1 后，再执行同一事务内的必要写入
COMMIT;
```

## 二、隔离级别与并发异常

| 隔离级别         | 典型现象         | InnoDB 实践                      |
| ---------------- | ---------------- | -------------------------------- |
| READ UNCOMMITTED | 脏读             | 很少使用                         |
| READ COMMITTED   | 不可重复读       | 每次一致性读通常生成新 Read View |
| REPEATABLE READ  | 普通快照读可重复 | InnoDB 默认                      |
| SERIALIZABLE     | 并发度最低       | 特殊强约束场景                   |

`REPEATABLE READ` 不是“永远读旧数据”。普通 `SELECT` 是快照读；`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，会读取最新可见版本并加锁。

## 三、MVCC：版本链与 Read View

聚簇索引记录包含隐藏的事务 ID（`DB_TRX_ID`）和回滚指针（`DB_ROLL_PTR`）。更新记录时，新版本写入记录，Undo Log 保存旧版本；回滚指针串起版本链。

```text
当前记录（trx_id=120） → Undo: 旧版本（trx_id=118） → Undo: 更早版本
                             ↑
                    Read View 判断哪个版本可见
```

Read View 记录创建瞬间活跃事务的边界。若版本由已提交且在可见范围内的事务生成，则可见；若版本来自尚未提交或“未来”的事务，则沿 Undo 链继续寻找。因而读操作通常不需要阻塞写操作。

长事务会使其开始时仍活跃的视图长期存在，旧 Undo 不能 purge，导致历史链变长和 Undo 空间膨胀。排查时关注活跃事务时长、`History list length` 和业务中未提交事务。

## 四、快照读与当前读

| 类型   | 示例                    | 行为                                    |
| ------ | ----------------------- | --------------------------------------- |
| 快照读 | `SELECT ...`            | 用 Read View 读历史可见版本，通常不加锁 |
| 当前读 | `SELECT ... FOR UPDATE` | 读最新版本并加排他锁                    |
| 当前读 | `UPDATE` / `DELETE`     | 定位最新记录后修改并加锁                |

库存、状态机等“读后必须修改”的业务不能依赖普通快照读。优先使用单条条件更新，减少读改写竞态：

```sql
UPDATE sku SET stock = stock - 1
WHERE id = ? AND stock > 0;
```

## 五、锁：锁在索引上

InnoDB 的行锁实质作用于索引记录。正确索引能缩小搜索与加锁范围；缺少索引时，即使 SQL 最终只修改一行，也可能扫描并锁住大量记录。

| 锁                      | 作用                       |
| ----------------------- | -------------------------- |
| 记录锁（Record Lock）   | 锁定单条索引记录           |
| 间隙锁（Gap Lock）      | 锁记录之间的间隙，阻止插入 |
| 临键锁（Next-Key Lock） | 记录锁 + 前方间隙锁        |
| 意向锁                  | 表级标记，协调行锁与表锁   |

在 RR 隔离级别，范围当前读可能使用间隙锁/临键锁，防止其他事务在范围中插入新记录，从而抑制幻读。等值唯一索引精确命中时通常只需记录锁；具体行为受查询条件、索引和版本影响。

## 六、死锁、锁等待与排查

死锁是循环等待：事务 A 持有资源 1 等资源 2，事务 B 持有资源 2 等资源 1。InnoDB 会检测并回滚代价较小的一方，应用会收到 `1213`。

```text
事务 A：锁订单 1 → 等订单 2
事务 B：锁订单 2 → 等订单 1
```

解决优先级：统一多行/多表访问顺序；缩短事务和批处理；让更新条件命中索引；对可幂等操作有限重试。用 `SHOW ENGINE INNODB STATUS` 的死锁段识别“持锁 SQL—等待 SQL—索引—锁模式”组成的环。

锁等待超时不是死锁。前者通常是某事务持锁过久，应检查长事务和慢 SQL；不能仅通过调大 `innodb_lock_wait_timeout` 掩盖问题。

## 七、Go 后端实践清单

1. 用 `BeginTx(ctx, ...)`，为事务和每个 SQL 传播超时；所有分支确保 `Rollback` 或 `Commit`。
2. 事务中只做数据库操作；提交后再发 RPC/MQ，跨系统可靠通知采用 Outbox 等模式。
3. 对 `1213` 做带退避上限的幂等重试；对余额扣减、订单创建使用业务唯一键或唯一索引。
4. 为 `UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 的过滤条件建索引，并在真实数据上检查执行计划。
5. 监控慢事务、锁等待、死锁次数、Undo 历史链和连接池等待，按“事务边界—索引路径—并发量”排查。

## 八、常见面试误区

- “MVCC 完全不加锁”错误：它优化普通一致性读，写入与当前读仍依赖锁。
- “RR 完全消除幻读”不严谨：应区分快照读与当前读，以及不同访问路径。
- “行锁只锁一行”错误：锁范围由索引扫描路径决定。
- “发生死锁说明数据库坏了”错误：死锁是正常并发结果，系统要能检测、回滚与重试。
