> MySQL 的笔记讲的是 InnoDB 聚簇索引与 undo log 那套 MVCC。PostgreSQL 走了几乎相反的路：堆表 + 元组多版本 + VACUUM 回收，再加上一套可扩展的索引与类型框架，让同一个内核能同时当关系库、文档库、时序库和向量库用。理解这几处差异，很多「为什么 PG 这里会膨胀」「为什么这个查询不走索引」的问题就不用背结论了。

## 一、和 MySQL 最容易混淆的几个差异

| 维度     | PostgreSQL                             | MySQL / InnoDB                  |
| -------- | -------------------------------------- | ------------------------------- |
| 表组织   | 堆表（heap），行与索引平级             | 索引组织表，主键即聚簇索引      |
| 行定位   | `(page, offset)` 的 ctid               | 主键值回聚簇索引                |
| MVCC     | 旧版本与新版本**都留在堆里**           | 旧版本放 undo log，堆里只有最新 |
| 回收     | VACUUM / autovacuum                    | purge 线程回收 undo             |
| 进程模型 | 每连接一个 backend 进程                | 线程模型                        |
| 并发写   | 更新 = 插入新元组 + 标记旧元组         | 原地更新 + undo                 |
| 扩展     | 扩展框架（extension）、自定义类型/索引 | 存储引擎插件为主                |

最实际的影响有两个：

1. **PG 的 UPDATE 很贵**。即使只改一个字段，也会写入一条完整新元组，并且所有索引都可能要新增条目（`HOT` 更新就是为缓解这一点而生）。高频小字段更新容易带来表膨胀和 WAL 放大。
2. **PG 没有「回表到聚簇索引」这个概念**，但有另一种代价：索引里存的是 ctid，堆里元组被 VACUUM 移动后，索引扫描仍要访问堆页面去判断可见性，于是随机 I/O 与 `Heap Fetches` 成为关键指标。`Index Only Scan` 依赖 visibility map 才能真的不碰堆。

## 二、堆表、元组与 VACUUM

每个元组的头部大致带着这些信息：

```text
t_xmin   创建这个版本的事务 ID
t_xmax   删除/更新这个版本的事务 ID（未删除则为 0）
t_cid    同一事务内的命令序号
t_ctid   指向自身或新版本元组的位置
NULL 位图 + 用户数据
```

一条记录可见，取决于 `t_xmin` 已提交且不在当前快照的活跃事务集合里，同时 `t_xmax` 为空或对应的删除尚未提交。判断快照要查 `pg_xact`（提交日志），不需要像 undo 那样回溯版本链。

```sql
-- 观察 ctid 与更新后的物理位置变化
SELECT ctid, xmin, xmax, id FROM orders WHERE id = 42;
UPDATE orders SET status = 'paid' WHERE id = 42;
SELECT ctid, xmin, xmax, id FROM orders WHERE id = 42;
```

### VACUUM 到底在做什么

| 动作                       | 说明                                       |
| -------------------------- | ------------------------------------------ |
| 标记死元组空间可复用       | 不把空间还给 OS，只写进 free space map     |
| 冻结旧事务 ID              | 防止 32 位 txid 回卷导致数据「突然看不见」 |
| 更新 visibility map        | 让 `Index Only Scan` 跳过堆访问            |
| 更新统计信息（`ANALYZE`）  | 供 planner 估算行数                        |
| 清理索引中指向死元组的条目 | 标准 VACUUM 只能回收，不重建               |

`VACUUM FULL` 会重写整张表并持 `ACCESS EXCLUSIVE` 锁，生产上几乎不可用；需要在线重整通常用 `pg_repack`。

长事务是 autovacuum 最大的敌人：只要还有一个老快照活着，它之后产生的死元组就一律无法回收。排查顺序：

```sql
SELECT pid, age(clock_timestamp(), xact_start), state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

SELECT relname, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;
```

复制槽（replication slot）没被消费、逻辑订阅停掉、忘了提交的事务，都会造成同样后果，而且会把 WAL 一起堆住。

## 三、索引家族：按数据形状选，而不是一律 B-tree

| 索引    | 擅长                   | 典型场景                                 |
| ------- | ---------------------- | ---------------------------------------- |
| B-tree  | 等值、范围、排序       | 默认选择，占绝大多数                     |
| Hash    | 纯等值                 | 长字符串等值（PG 里优势有限）            |
| GIN     | 「一个值里含多个元素」 | `jsonb`、`array`、全文检索 `tsvector`    |
| GiST    | 范围/空间/近似查询     | PostGIS 几何、范围重叠、`pg_trgm` 相似度 |
| SP-GiST | 非平衡可分割结构       | 四叉树、前缀树类数据                     |
| BRIN    | 物理有序的大表         | 按时间递增的日志表，索引极小             |

几个很实用的写法：

```sql
-- 部分索引：只索引活跃订单，索引体积可能小一个数量级
CREATE INDEX CONCURRENTLY idx_orders_active
  ON orders (created_at) WHERE status = 'active';

-- 表达式索引：让 lower(email) 查询走索引
CREATE INDEX CONCURRENTLY idx_users_lower_email
  ON users (lower(email));

-- 覆盖索引：INCLUDE 让更多查询变成 Index Only Scan
CREATE INDEX idx_orders_cover
  ON orders (user_id, created_at) INCLUDE (amount, status);

-- jsonb 的 GIN：默认 jsonb_ops 支持存在/包含，jsonb_path_ops 更小更快
CREATE INDEX idx_events_payload ON events USING gin (payload jsonb_path_ops);
```

注意 `CREATE INDEX CONCURRENTLY` 不能在事务块里执行，且失败会留下 `INVALID` 索引，需要手工 DROP 后重来。这是上线脚本里最容易踩的坑。

## 四、看懂执行计划

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS)
SELECT o.id, o.amount FROM orders o
WHERE o.user_id = 1001 AND o.created_at > now() - interval '30 days'
ORDER BY o.created_at DESC LIMIT 20;
```

关注顺序：

1. **估算行数 vs 实际行数**：`rows=120` 但实际 `rows=48000` 基本等于统计信息失效，先 `ANALYZE`，必要时调 `ALTER TABLE ... SET STATISTICS 500`。
2. **Buffers**：`shared hit` / `read` 直接换算出逻辑读与物理读，比单纯看耗时更能定位 I/O 问题。
3. **Scan 类型**：`Seq Scan` 在大表上不是一定错，如果过滤后仍要取大部分行，顺序读反而更快。
4. **Join 策略**：Nested Loop 适合小驱动集 + 内表有索引；Hash Join 适合大集合；Merge Join 适合两边已排序。嵌套循环套上大结果集是经典慢查询。
5. **Sort / Disk**：`Sort Method: external merge Disk: ...` 说明 `work_mem` 不够，可考虑会话级调大或改索引满足排序。
6. **并行度**：`Workers Planned` 与 `Workers Launched` 不一致，通常是资源或并行安全限制。

planner 是代价模型驱动的，几个参数影响很大：`random_page_cost`（SSD 场景常从 4 调到 1.1）、`effective_cache_size`、`work_mem`、`jit`。**先修统计信息和索引，再动代价参数**，反过来容易把整个实例的计划搞坏。

```sql
-- 找最该优化的语句（需要 pg_stat_statements 扩展）
SELECT calls, round(total_exec_time::numeric / 1000, 2) AS total_s,
       round(mean_exec_time::numeric, 2) AS mean_ms, rows, query
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 20;
```

## 五、WAL、复制与高可用

WAL 是 PG 一切可靠性的底座：变更先顺序写 WAL，再异步刷数据页；崩溃时从最近 checkpoint 开始重放。

| 概念                                 | 作用                                             |
| ------------------------------------ | ------------------------------------------------ |
| `wal_level`                          | `replica` / `logical` 决定能做什么复制           |
| `checkpoint_timeout`、`max_wal_size` | 控制检查点频率与恢复时间/写放大权衡              |
| `full_page_writes`                   | 防止检查点后首次修改页面的「半页写」损坏         |
| `synchronous_commit`                 | 在「提交持久性」与「提交延迟」之间取舍           |
| 复制槽                               | 保证主库保留备库所需 WAL，但停掉的备库会撑爆磁盘 |

复制形态的选择：

- **物理流复制**：整实例级、延迟低、备库只读，适合 HA 和读扩展；同步复制（`synchronous_standby_names`）能保证 RPO≈0，但备库故障会阻塞主库写入。
- **逻辑复制**：按表/按发布订阅，可跨大版本、可做数据汇聚与在线迁移，但不复制 DDL、大对象和序列需要额外处理。
- **故障切换**：探测 → fencing 旧主（防脑裂）→ `pg_ctl promote` → 流量切换。没有 fencing 的自动切换，比人工切换更危险。

## 六、多模能力：一个内核当几个用

| 能力              | 用法                                | 适用边界                                              |
| ----------------- | ----------------------------------- | ----------------------------------------------------- |
| `jsonb`           | 二进制 JSON + GIN 索引 + 表达式查询 | 半结构化字段、变更频繁的属性；不适合强约束的核心实体  |
| `array` / `range` | 原生类型与 GiST 索引                | 标签、时间段冲突检测（如会议室预订）                  |
| 全文检索          | `to_tsvector` + `ts_query` + GIN    | 中小规模中文/英文检索；分词需配合 `zhparser` 等       |
| PostGIS           | 几何类型 + GiST                     | 地理位置查询、围栏判断                                |
| `pgvector`        | 向量类型 + HNSW/IVFFlat 索引        | 中等规模向量召回，配合业务库避免引入新组件            |
| 分区表            | 声明式 range/list/hash 分区         | 按时间归档、大表裁剪，配合 `enable_partition_pruning` |
| FDW               | 外部表包装器                        | 跨库联邦查询，注意谓词下推是否生效                    |

一个典型 hybrid 查询（关键词 + 向量 + 时间）能在一条 SQL 里完成，这是 PG 相对「MySQL + ES + 向量库」组合最省事的地方。但也要清醒：**扩展越多，升级、备份、调优和故障面越复杂**；数据量与 QPS 到一定规模后，专用系统仍然更合适。

```sql
-- jsonb 包含查询，走 GIN
SELECT id FROM events
WHERE payload @> '{"source": "mobile", "level": "error"}';

-- 向量近邻，走 HNSW
SELECT id, embedding <=> $1::vector AS distance
FROM docs ORDER BY distance LIMIT 10;
```

## 七、上线与运维陷阱清单

- **DDL 锁**：`ALTER TABLE` 大多持 `ACCESS EXCLUSIVE`；`ADD COLUMN ... DEFAULT` 在新版本对常量默认值是元数据操作，但 volatile 默认值仍会重写全表。先查 `lock_timeout`，避免排队雪崩。
- **长事务 + DDL**：DDL 等锁，等锁期间后续所有查询排在同一次锁后面，几分钟就能把连接池占满。
- **序列与缓存**：`serial`/`identity` 的序列不随事务回滚，且 `cache` 设置会在故障切换后产生空洞，别把「连续」当业务保证。
- **连接池**：PG 是进程模型，每连接成本高于 MySQL 线程。几百个连接就值得上 PgBouncer（transaction pooling 下注意 prepared statement、临时表、会话变量不可用）。
- **autovacuum 调优**：写密集大表要按表级设置 `autovacuum_vacuum_scale_factor`（默认 0.2 意味着 20% 死元组才触发，大表太迟）。
- **备份与恢复演练**：`pg_dump` 是逻辑备份，大库恢复慢；PITR 需要 base backup + 连续 WAL 归档。**没演练过恢复的备份不算备份**。

## 八、面试速答

**Q：PG 的 MVCC 和 MySQL 有什么本质区别？**
旧版本留在堆表内，靠元组头 `xmin/xmax` + 快照判断可见性，靠 VACUUM 回收；MySQL 把旧版本放 undo log，通过回滚段构造一致性读。因此 PG 更新写放大更明显、会有表膨胀和事务 ID 回卷问题，而 MySQL 更怕长事务撑大 undo 和 purge 滞后。

**Q：为什么建了索引还是慢？**
按顺序查：统计信息是否过期（`ANALYZE`）、查询条件是否匹配索引前缀或表达式、选择性是否太低导致 planner 选顺序扫描、是否因 visibility map 未更新而无法 Index Only Scan、join 顺序是否被错误行数估算带偏。用 `EXPLAIN (ANALYZE, BUFFERS)` 看估算/实际行数差异，而不是猜。

**Q：什么时候不该用 PG 的 jsonb？**
当字段需要强类型约束、频繁按该字段做 join/聚合、或有高并发定点更新时。把它拆成正式列，把整张表塞进一个 `jsonb` 字段的做法通常会在半年后变成最难改的地方。

## 九、一句话收尾

PG 的核心取舍是：**用更大的写放大和更重的回收机制，换来极简的读路径、干净的 MVCC 语义，以及一套能长出新数据类型的扩展框架**。知道这个取舍，就能判断什么时候该用它、什么时候该把它当关系库老实用。
