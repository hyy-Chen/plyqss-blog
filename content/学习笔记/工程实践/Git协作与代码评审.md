> Git 用得顺不顺，决定的是团队协作成本，而不是命令背得全不全。本文围绕四件事：分支怎么管、提交怎么写、评审看什么、误操作怎么救。

## 一、分支模型

| 模型        | 做法                                | 适用                     | 代价                   |
| ----------- | ----------------------------------- | ------------------------ | ---------------------- |
| Trunk-based | 主干 + 短生命周期分支（小时～1 天） | 持续集成、频繁发布       | 需要特性开关与完善测试 |
| GitFlow     | main/develop/feature/release/hotfix | 有固定版本节奏的发版软件 | 分支多、合并成本高     |
| Fork 模型   | 贡献者 fork 后提 PR                 | 开源项目                 | 权限与同步更复杂       |

对多数后端服务，推荐**主干开发 + 短分支 + PR**：分支存活越短，冲突越少，集成越早。长分支（活了一周以上）往往意味着改动该拆分，或该用特性开关先把未完成代码合入主干。

`main` 应始终可发布：合入前跑完门禁，禁止直接 push，用保护分支强制执行。

## 二、提交规范

一条提交回答「为什么改」，diff 已经说明了「改了什么」。推荐 Conventional Commits：

```text
<type>(<scope>): <简短描述>

feat(order): 支持幂等键重复提交返回首次结果
fix(cache): 修复空值缓存未设置 TTL 导致穿透
refactor(db): 抽出事务包装函数，无行为变更
docs(notes): 补充分布式事务笔记
```

常见 type：`feat`、`fix`、`refactor`、`perf`、`test`、`docs`、`chore`、`build`、`ci`。破坏性变更用 `feat!:` 并在正文写 `BREAKING CHANGE`。

好提交的特征：

- **原子**：一个提交只做一件事，`fix` 和 `refactor` 不要混在一起，便于 bisect 和 revert。
- **可构建**：每个提交都能通过测试，不要出现「中间提交编译不过」。
- **解释动机**：正文写清背景、取舍与验证方式，尤其是看起来「多此一举」的代码。
- **不夹带**：格式化、换行符全量改动单独提交，否则评审会被噪声淹没。

## 三、rebase 与 merge

| 操作     | 结果                               | 适用                     |
| -------- | ---------------------------------- | ------------------------ |
| `merge`  | 生成合并提交，保留真实分叉历史     | 公共分支合入、保留时间线 |
| `rebase` | 把提交重放到目标分支之上，历史线性 | 整理自己未推送的本地提交 |
| `squash` | 把一串提交压成一个                 | PR 合入时清理琐碎提交    |

**黄金规则：不要对已经推送、且他人可能基于其工作的分支执行 rebase 或改写历史。** rebase 会生成全新的 commit SHA，其他人手里的旧提交会变成「幽灵」，再次合并时产生重复 diff。

自己的分支想同步主干，优先 `git fetch && git rebase origin/main`（本地历史干净），或者在 PR 里用平台的 "Update branch" 按钮做 merge。交互式变基 `git rebase -i HEAD~N` 适合在提 PR 前整理提交，但整理完需要 `git push --force-with-lease`，绝不要用裸 `--force`。

`--force-with-lease` 会检查远端是否已被别人更新，比 `--force` 安全得多。

## 四、PR 的粒度与描述

一个 PR 最好在几百行以内、只解决一个问题。超过这个规模，评审质量会明显下降——不是 reviewer 不认真，而是人的工作记忆有限。大改动拆成「重构（无行为变化）→ 新功能 → 清理」的序列。

描述模板：

```text
## 背景
为什么需要这次改动，关联的问题或事故。

## 方案
关键设计取舍，以及明确没做什么（非目标）。

## 验证
跑了哪些测试、压测结果、手工验证步骤；数据库变更附兼容说明。

## 风险与回滚
可能影响什么、如何观测、怎么回滚、是否需要灰度。
```

有 UI 改动附截图，有性能改动附前后数据，有接口改动附请求/响应示例。这些不是形式主义，而是把 reviewer 需要自己去找的信息提前给到。

## 五、Code Review 看什么

按优先级从高到低：

1. **正确性**：边界条件、空值、并发、错误传播、事务边界、超时与重试、幂等。
2. **安全性**：鉴权与越权、输入校验、注入、敏感信息是否进日志、依赖是否可信。
3. **设计**：依赖方向是否合理、抽象是否必要、是否引入循环依赖、能否向后兼容。
4. **可观测性**：出错时能否定位，关键路径有没有指标、日志、trace ID。
5. **可读性与命名**：变量是否名副其实、函数是否过长、注释是否解释「为什么」。
6. **测试**：是否覆盖关键分支与回归场景，而不是只测了 happy path。

风格问题（缩进、空行）交给格式化工具，不要在评审里反复讨论；把 lint 规则固化进 CI 才是解法。

评审意见要区分**阻塞**与**建议**，例如用 `nit:` 标注非阻塞的小建议。用提问代替命令（「这里并发调用会不会重复扣减？」比「这样写错了」更容易被接受），也便于发现其实是自己理解错了。评审的目标是让代码变好，不是证明谁更懂。

## 六、作者侧的配合

- 提交前自己先完整看一遍 diff，很多低级错误在这一步就能发现。
- 在容易困惑的代码旁主动留评论，减少来回问答。
- 对每条意见给出明确回应（已改 / 解释原因 / 另开任务），不要静默改完就结束。
- 评审通过后由作者合入，方便顺手处理合入后的 CI 状态。

## 七、误操作恢复

| 情况                    | 处理                                                                    |
| ----------------------- | ----------------------------------------------------------------------- |
| 提交信息写错（未推送）  | `git commit --amend`                                                    |
| 想撤销提交但保留改动    | `git reset --soft HEAD~1`                                               |
| 想彻底丢弃本地改动      | `git restore <file>`；整分支用 `git reset --hard`（**不可恢复，慎用**） |
| 已推送的提交要撤销      | `git revert <sha>`，生成一个反向提交，不改写历史                        |
| rebase/reset 后想找回来 | `git reflog` 找到原 SHA，再 `git reset --hard <sha>`                    |
| 临时切换任务            | `git stash push -m "wip"`，回来 `git stash pop`                         |
| 想只应用某个提交的改动  | `git cherry-pick <sha>`                                                 |

`reset` 移动分支指针、`revert` 新增提交，二者区别决定了能否安全用于公共分支：`revert` 安全，`reset --hard` 会改写历史。`reflog` 记录本地 HEAD 的每次移动，是误操作后的第一救命手段，但它只在本地有效且会过期。

定位回归用 `git bisect`：给定一好一坏两个提交，二分查找引入问题的那次改动，前提是每个提交都能构建、提交足够原子——这也是前面强调原子提交的原因。

## 八、实用命令速查

| 命令                              | 用途                        |
| --------------------------------- | --------------------------- |
| `git log --oneline --graph --all` | 看分支拓扑                  |
| `git diff --check`                | 检查空白错误                |
| `git add -p`                      | 按块暂存，拆分原子提交      |
| `git blame -L 20,40 file`         | 查某段代码的来源提交        |
| `git log -S 'keyword' -- file`    | 搜索引入/删除某字符串的提交 |
| `git reflog`                      | 查看本地 HEAD 变更历史      |
| `git remote prune origin`         | 清理已删除的远端分支引用    |

## 九、实践清单

1. 主干保持可发布，分支活不过一两天，长改动用特性开关拆小。
2. 提交信息写动机，一个提交一件事，每个提交都能过测试。
3. 只对自己未推送的分支 rebase；需要强推时一律 `--force-with-lease`。
4. PR 描述写清背景、方案、验证、风险与回滚。
5. 评审优先看正确性与安全性，风格交给工具。
6. 公共分支上用 `revert` 而不是 `reset --hard`；误操作先查 `reflog`。

## 十、面试速答

**问：rebase 和 merge 的区别？** merge 生成合并提交并保留分叉历史，rebase 把提交重放到目标分支之上形成线性历史；rebase 会改写 commit SHA，因此不能用于他人已基于其工作的公共分支。

**问：`git reset` 和 `git revert` 怎么选？** `reset` 移动分支指针、可能丢弃提交，适合本地未推送的整理；`revert` 新增一个反向提交、不改写历史，适合已推送到公共分支的撤销。

**问：为什么强调原子提交？** 便于评审、便于 `revert` 单个改动、便于 `git bisect` 精确定位回归，也避免一个提交里混入无关改动导致回滚时误伤。
