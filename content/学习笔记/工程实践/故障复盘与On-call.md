> 发布流程解决的是「别把问题带上线」，On-call 和复盘解决的是「问题还是上来了以后怎么办」。很多团队的复盘会开成追责会，最后产出「加强监控」「提高意识」这类无法验证的行动项，于是同一个坑半年后原样再踩一次。这篇讲流程、模板和判断标准。

## 一、先把概念对齐

| 概念           | 含义                                     |
| -------------- | ---------------------------------------- |
| Incident       | 对用户体验或业务指标造成可观测影响的事件 |
| On-call        | 在值班窗口内负责响应告警、协调止损的人   |
| Severity       | 按影响面与紧迫度定的故障等级             |
| MTTD / MTTR    | 平均发现时间 / 平均恢复时间              |
| MTBF           | 平均故障间隔，衡量稳定性趋势             |
| SLO / 错误预算 | 可用性目标与「允许多少不可用」的额度     |
| Runbook        | 针对某类告警的标准处置步骤               |

一个关键观念：**MTTR 比 MTBF 更可控**。分布式系统里彻底消灭故障不现实，把发现、定位、止损的时间压下来，往往比「永不出事」的口号更有价值。

## 二、故障分级要先定好

| 级别 | 典型判据                                 | 响应时限     | 通知范围                  |
| ---- | ---------------------------------------- | ------------ | ------------------------- |
| P0   | 核心链路全站不可用、资金或数据正确性受损 | 立即         | 全员 + 管理层，指定指挥官 |
| P1   | 主要功能严重降级、大面积用户受影响       | 15 分钟内    | 相关团队 + 值班经理       |
| P2   | 局部功能异常、有可用绕行方案             | 工作时间处理 | 责任团队                  |
| P3   | 轻微体验问题、无业务影响                 | 排期         | 工单跟踪                  |

分级的意义不是填表，而是**决定谁有权做什么**：P0 下可以跳过常规评审直接回滚、可以直接切流、可以调用跨团队资源。事先没约定，故障现场就会变成「等领导拍板」的十几分钟。

分级要能被自动判断：用 SLO 燃烧率（error budget burn rate）而不是「CPU 超过 80%」来触发高优告警。资源指标适合做诊断，不适合直接当故障等级。

## 三、响应流程：止损永远排在根因前面

```text
发现（告警/客诉） → 确认影响面 → 定级 → 指定指挥官
   → 止损（回滚 / 切流 / 限流 / 降级 / 关特性开关）
   → 恢复验证 → 根因定位 → 复盘与行动项
```

| 角色      | 职责                                         |
| --------- | -------------------------------------------- |
| 指挥官 IC | 做决策、分派任务、控制节奏，不亲自动手改代码 |
| 操作者    | 执行具体止损与排查动作，实时同步结果         |
| 沟通者    | 对内对外同步进展，收集影响面信息             |
| 记录者    | 记录时间线与决策依据，供复盘使用             |

三条现场纪律：

1. **单一指挥官**：多人同时下令回滚、改配置、重启，比故障本身更危险。
2. **止损优先**：先恢复服务，再查为什么。允许「原因不明但已回滚」，复盘时再补根因。
3. **固定同步节奏**：每 10~15 分钟同步一次「当前影响 / 已做 / 下一步」，避免所有人反复来问。

常见止损手段按代价从低到高：关特性开关 → 限流/降级 → 切流量到健康集群 → 回滚上一版本 → 数据修复。**先用可逆的、影响面小的**。

## 四、时间线模板

复盘的第一份材料是事实，不是观点：

| 时间 (UTC+8) | 事件                         | 来源            |
| ------------ | ---------------------------- | --------------- |
| 14:02        | 发布 v2.3.1，灰度 10%        | 发布系统        |
| 14:07        | 订单接口 5xx 从 0.1% 升至 6% | 监控            |
| 14:09        | 告警触发，值班响应           | Alertmanager    |
| 14:15        | 定级 P1，指定 IC             | 值班记录        |
| 14:21        | 关闭新特性开关，错误率回落   | 操作记录        |
| 14:35        | 确认业务指标恢复，解除状态   | 监控 + 业务核对 |

时间线要标注**监控时间、发现时间、开始止损时间、恢复时间**，这四个点之间的距离就是 MTTD 与 MTTR 的来源。很多复盘最有价值的结论就藏在这里：故障 14:07 就发生，14:09 才告警，但值班 14:15 才真正介入——改进项应该是告警触达或值班响应，而不是「加强代码评审」。

## 五、根因分析：找贡献因素，不找一个人

| 方法         | 适用                                         |
| ------------ | -------------------------------------------- |
| 5 Whys       | 线性因果链清晰的问题，注意别停在「某人疏忽」 |
| 故障树       | 多条件组合的复杂故障                         |
| 时间线对齐   | 多系统、多团队参与的事故                     |
| 瑞士奶酪模型 | 解释「每层都有防护，为什么还是穿透了」       |

「根因是某同事写错了配置」不是根因，是现象。继续问：为什么配置能直接改生产？为什么没有校验？为什么灰度没拦住？为什么监控没发现？**每层缺失的防护都是一个可改进项**。

好的根因描述应包含：触发条件、传播路径、为什么现有防护失效、影响范围为何这么大。并明确区分触发因素（trigger）、根本原因（root cause）与放大因素（contributing factors）。

## 六、复盘文档模板

```text
1. 摘要：一句话说清发生了什么、影响多久、多少用户
2. 影响：业务指标、错误率、资损、客诉量，量化且可核对
3. 时间线：如上表，只写事实
4. 根因与贡献因素：分层分析
5. 做对了什么：哪些机制缩短了 MTTR（要保留并推广）
6. 做错了什么：哪些决策延长了故障或扩大了影响
7. 行动项：owner + 截止日期 + 验收方式 + 优先级
8. 附录：告警、日志、截图、变更记录链接
```

**不追责（blameless）不是不问责**，而是承认人在当时信息下做了合理判断；如果系统允许一个人随手造成全站故障，那是系统设计问题。这个前提不说清楚，大家就会隐去关键信息，复盘就失去价值。

## 七、行动项的质量判断

| 差的行动项          | 为什么无效         | 改写                                                |
| ------------------- | ------------------ | --------------------------------------------------- |
| 加强监控            | 无可验收标准       | 为核心接口补 5xx 燃烧率告警，阈值 X，7 天内验证触发 |
| 提高意识 / 加强评审 | 无法验证、无法回滚 | 配置变更走 schema 校验 + 灰度，禁止直连生产         |
| 以后仔细点          | 归因到人           | 发布前自动 diff 配置，差异超 N 项阻断               |
| 补充文档            | 没人会读           | 把处置步骤写进 runbook，并在下次演练中执行          |

好的行动项满足三条：**有明确 owner 和截止时间、有可验证的验收条件、能降低同类故障的发生概率或 MTTR**。数量控制在 3~7 项，排优先级，并跟踪到关闭；上一轮没关完的行动项要在下次复盘开头列出来。

另一个常被忽略的判据：**改进应作用在系统性防护上，而不是增加流程摩擦**。每加一道人工审批，都要问它能不能被自动化或由工具保证。

## 八、On-call 的健康度

| 指标                 | 关注点                                   |
| -------------------- | ---------------------------------------- |
| 每班次告警数         | 过多说明噪声大，真正告警会被淹没         |
| 非工作时间被叫醒次数 | 直接影响团队可持续性                     |
| 告警可操作性         | 每条高优告警应对应一个明确动作或 runbook |
| 重复告警占比         | 同一根因反复触发，说明没闭环             |
| 演练通过率           | runbook 是否真的能被执行                 |

告警降噪的实操：按 SLO 燃烧率分级、同类告警聚合、抑制依赖链上的连带告警、给每条告警绑定 runbook 链接和负责人。「磁盘使用率 81%」这种既不需要立即行动、又没有明确阈值的告警，应当降为工单而不是半夜叫人。

演练（GameDay / 混沌注入）的价值在于验证「监控能不能发现、值班知不知道怎么处置、止损手段是否真的有效」。没演练过的回滚脚本和没演练过的备份一样，不能算数。

## 九、和发布流程的闭环

- **发布前**：新特性必须有开关、有回滚路径、有对应的监控面板与告警。
- **发布中**：灰度观察窗口按 SLO 设定，而不是「看两分钟没报错就全量」。
- **发布后**：把「变更时间」标注到所有监控面板上，让复盘时能一眼看出关联。
- **复盘后**：把高频根因反灌到 CI 门禁，例如配置 schema 校验、依赖版本检查、必填监控项。

复盘的输入来自可观测性，输出回到发布门禁与架构设计——**不闭环的复盘只是写一篇事故作文**。参见「CI/CD 与发布策略」里关于不可变制品、特性开关与回滚的讨论。

## 十、实践清单

- 故障等级、响应时限、IC 权限、通知路径事先写好并演练。
- 每条高优告警绑定 runbook 与 owner，按 SLO 燃烧率而非资源阈值触发。
- 现场先止损再定位，单一指挥官，固定节奏同步，设记录者。
- 时间线只写事实，量化影响面，标明发现/止损/恢复四个时间点。
- 根因分析找齐触发、传播、防护失效与放大因素，不追责但必须跟踪行动项到关闭。
- 行动项 3~7 条，带 owner、截止与验收方式，下一轮复盘先回顾上轮未关闭项。
- 定期演练回滚、切流、备份恢复，把演练结果反灌到发布门禁。

## 十一、面试速答

**Q：故障发生时先查根因还是先恢复？**
先止损恢复。允许在根因不明时回滚、关开关或切流，把用户影响降到最低，事后再用保留的现场信息做根因分析。反过来会让故障时间被无限拉长。

**Q：什么是 blameless postmortem，是不是不追责？**
是把分析对象从「谁做错了」转向「系统为什么允许这个错误造成全站影响」。人在当时的信息下通常做了合理判断；若单人操作能击穿所有防护，改进点应在校验、灰度、监控和权限上。它不等于对恶意或违规行为不处理。

**Q：怎么判断复盘写得合格？**
看三点：影响是否量化可核对、时间线是否只有事实、行动项是否有 owner/截止/验收且能降低复发概率或 MTTR。「加强监控」「提高意识」这类无法验证的条目说明复盘没做完。

## 十二、一句话收尾

事故复盘的产品不是一份文档，而是**下一次同类故障要么不再发生、要么能被更快发现和止住**；衡量它的唯一标准是行动项有没有真正闭环。
