> 发布出事的常见原因不是代码写错，而是「构建产物与环境绑定」「数据库变更不兼容」「没有可快速执行的回滚」。本文按一条变更从提交到全量的路径，整理每个阶段的约束。

## 一、流水线的阶段

```text
提交 → 静态检查 → 构建 → 单测/集成测试 → 安全与依赖扫描
     → 产出不可变制品 → 预发验证 → 灰度发布 → 观测 → 全量
```

| 阶段     | 目标                              | 失败时的处理           |
| -------- | --------------------------------- | ---------------------- |
| 静态检查 | 格式、vet、lint、生成代码是否过期 | 立即阻断，成本最低     |
| 测试     | 单元 + 竞态 + 集成 + 契约         | 阻断，禁止「先合再修」 |
| 构建     | 产出唯一制品                      | 阻断                   |
| 扫描     | 依赖漏洞、密钥泄漏                | 按严重级别设门禁       |
| 部署     | 按策略放量                        | 自动/手动中止并回滚    |

关键原则是**越早发现越便宜**：能在提交阶段发现的问题，不要留到预发；能在预发发现的问题，不要留到生产。同时流水线要快，超过十分钟的反馈会让开发者绕过它。

## 二、构建产物不可变

同一个制品从预发一路用到生产，不在每个环境重新构建：

```text
commit a1b2c3 → 镜像 registry/app:a1b2c3（唯一）
                    ├── 预发部署（配置 A）
                    ├── 灰度部署（配置 A）
                    └── 生产全量（配置 A）
```

- 镜像 tag 用 commit SHA 或构建号，禁止用 `latest`；`latest` 会让「当前跑的是哪版」无法回答。
- 配置（DB 地址、密钥、开关）通过环境变量或配置中心注入，不打进镜像；不同环境只换配置不换制品。
- 依赖锁定（`go.sum`、锁文件、基础镜像 digest），保证一个月后重建得到相同结果。
- 制品带元数据：commit、构建时间、构建者、版本号，服务端暴露 `/version` 便于核对。

## 三、质量门禁

建议的最小集合：

1. `gofmt -l` / `go vet ./...` / lint；生成代码（proto、OpenAPI、mock）检查是否与源文件一致。
2. `go test -race ./...`；集成测试用独立 job 和 build tag，避免拖慢每次提交。
3. 契约测试：API schema 变更是否破坏已有消费者。
4. 依赖与镜像漏洞扫描、密钥泄漏扫描（不要把 `.env` 提交进仓库）。
5. 覆盖率只对**新增代码**设下限，避免历史包袱卡住所有改动。

门禁要可解释：失败时给出具体文件、具体规则和修复建议，而不是一个泛红的「build failed」。

## 四、数据库变更是发布的最大约束

应用可以多版本并存（滚动发布时新旧实例同时在跑），数据库 schema 通常只有一份。因此变更必须**向后兼容至少一个新旧共存周期**，用 `expand → migrate → contract` 三步走：

| 阶段     | 动作                                 | 应用版本     |
| -------- | ------------------------------------ | ------------ |
| Expand   | 加新列/新表，不删旧列，允许 NULL     | 旧版仍可写   |
| Migrate  | 双写新旧字段、回填历史数据、校验一致 | 新旧版本共存 |
| Contract | 确认无旧版在读，切到新字段，删旧列   | 仅新版       |

具体规则：

- 禁止在一个发布里同时「改代码」和「删列/改列名/改字段类型」。
- 新增字段给默认值或允许 NULL；对 NOT NULL 加列要先回填。
- 大表 DDL 用在线改表工具或分批脚本，避免长时间持锁；先在预发用等量数据演练。
- 双写期间必须有对账，能回答「新旧字段不一致的有多少条」。
- 每个 schema 变更都要有反向脚本或明确的「不可回滚」说明。

## 五、发布策略对比

| 策略       | 做法                           | 优点                 | 代价与风险                 |
| ---------- | ------------------------------ | -------------------- | -------------------------- |
| 滚动       | 逐批替换实例                   | 省资源、K8s 默认     | 新旧版本长期共存，需兼容   |
| 蓝绿       | 两套环境整体切换流量           | 切换/回滚快          | 双倍资源，数据库仍共用     |
| 金丝雀     | 先放 1%～5% 流量观察           | 影响面小、可数据驱动 | 需要流量控制与指标对比     |
| 影子流量   | 复制请求到新版本但不返回给用户 | 可用真实流量验证     | 要处理写操作副作用与去重   |
| 按用户灰度 | 按租户/白名单定向放量          | 精确验证重点客户     | 需维护分组规则，注意公平性 |

无论哪种策略，都要先摘流量再停实例：K8s 里 `preStop` 加短暂等待、readiness 先置 false，让负载均衡器有时间更新端点，否则滚动期间会出现连接被拒。

## 六、特性开关：解耦「部署」与「发布」

代码可以先部署到生产但保持关闭，通过开关决定何时对谁生效。这让发布变成一次配置变更，而不是一次重新构建。

```text
部署（deploy）：新代码进入生产环境，开关 off
发布（release）：开关逐步打开，功能对用户可见
```

注意事项：

- 开关要能按百分比、租户、用户分档，且变更可审计、可秒级回滚。
- 开关状态必须可观测：监控里能看到「当前哪些开关是开的」。
- 设定生命周期，功能稳定后清理分支和开关，否则代码里会长期堆满 `if flag` 的死路径。
- 开关不要用来掩盖未经测试的代码，它只是发布节奏工具。

## 七、回滚

回滚方案应在**发布前**写好，而不是出事后临时想：

1. 明确触发条件：错误率、P99、核心业务指标（下单成功率）超过阈值即中止放量。
2. 明确回滚单位：镜像回退、开关关闭、配置回退，三者速度不同，优先用最快的那个。
3. 明确数据兼容性：新版已写入的数据旧版能否读取？这决定了「代码能不能直接回退」。
4. 有状态服务（消费者位点、缓存格式、队列消息）要单独确认，不能只看无状态实例。
5. 定期演练回滚，验证脚本、权限和镜像是否真的可用；没演练过的回滚等于没有。

数据库是最难回滚的部分，所以宁可让 schema 变更向前兼容、用「再发一个修复版本」来纠正，也尽量避免回滚 DDL。

## 八、发布期间的观测

放量后对比新旧版本的同一组指标，而不是只看大盘：

| 指标     | 关注点                       |
| -------- | ---------------------------- |
| 错误率   | 5xx、业务失败码、超时        |
| 延迟     | P50 / P95 / P99，分接口看    |
| 资源     | CPU、内存、GC 暂停、连接池   |
| 业务     | 下单量、支付成功率、消息积压 |
| 版本对比 | 灰度组 vs 对照组，同口径比较 |

把「错误预算」和自动中止接进流水线：灰度窗口内指标恶化就自动停止放量并回滚，不依赖人盯着面板。发布结束后记录版本、时间与结论，故障复盘时才有时间线可查。

## 九、一份最小流水线示例

```yaml
stages: [check, build, deploy]

check:
  script:
    - gofmt -l . | tee /tmp/fmt && test ! -s /tmp/fmt
    - go vet ./...
    - go test -race ./...

build:
  script:
    - docker build -t registry/app:$CI_COMMIT_SHA .
    - docker push registry/app:$CI_COMMIT_SHA
  only: [main]

deploy-canary:
  script:
    - ./deploy.sh $CI_COMMIT_SHA 5 # 先放 5%
    - ./verify-slo.sh --window 10m # 指标不达标则退出
    - ./deploy.sh $CI_COMMIT_SHA 100
```

`verify-slo.sh` 必须有非零退出码来阻断后续步骤；只打印告警不会拦住一条正在出问题的发布。

## 十、实践清单

1. 一次构建、唯一 tag、到处部署，配置外置。
2. 任何 schema 变更都先问「新旧版本同时跑会不会出错」。
3. 发布前写清回滚步骤与触发阈值，并定期演练。
4. 金丝雀放量必须有明确的对照指标和自动中止。
5. 发布中与发布后都能查到「当前版本、开关状态、放量比例」。
6. 特性开关设过期时间，避免长期堆积条件分支。

## 十一、面试速答

**问：蓝绿和金丝雀怎么选？** 蓝绿适合需要整体快速切换、资源充足的场景；金丝雀适合想用小流量验证真实效果、风险更可控的场景，但要求有流量控制和指标对比能力。

**问：为什么滚动发布要求数据库向后兼容？** 发布期间新旧版本实例同时在线且共用同一套 schema，新版本写入的数据结构必须能被旧版本读取，否则回滚和共存都会出错。

**问：部署和发布有什么区别？** 部署是把代码放到生产环境，发布是让用户真正用到该功能；特性开关让两者解耦，可以先部署再按节奏放量。
